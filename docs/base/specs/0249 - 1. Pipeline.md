## COMPILER-007 — Semantic MIR Optimization

Đây là phase nối trực tiếp từ COMPILER-006. Mục tiêu không phải “thêm thật nhiều optimization”, mà là xây một **optimization pipeline có khả năng xóa gần như toàn bộ chi phí của abstraction Axiom** trước khi xuống ABI/LIR.

Nguyên tắc trung tâm:

> **Optimization không được chứng minh lại semantics; nó chỉ được phép biến đổi một MIR đã được verifier chứng minh thành MIR tương đương về observable behavior.**

---

# 1. Pipeline

Tôi chốt pipeline ban đầu:

```text
Verified MIR
    │
    ├── Canonicalization
    ├── CFG Simplification
    ├── Constant Propagation
    ├── SCCP
    ├── Copy Propagation
    ├── Dead Code Elimination
    ├── Dead Store Elimination
    ├── Aggregate / Scalar Optimization
    ├── Memory / Alias Optimization
    ├── Escape Analysis
    ├── Allocation Optimization
    ├── Inline / Devirtualize
    ├── Loop Optimization
    ├── Tail Call Optimization
    ├── Drop Optimization
    ├── Panic Path Optimization
    └── Final MIR Cleanup
            │
            ▼
       ABI Lowering
```

Không nên chạy tất cả pass một lần. Optimization cần **iterative fixed-point pipeline**.

---

# 2. Optimization levels

Axiom nên có:

```text
-O0
-O1
-O2
-O3
-Os
-Oz
```

nhưng:

> Optimization level không được thay đổi semantics.

`-O0` vẫn phải:

- kiểm tra ownership;
- kiểm tra capability;
- kiểm tra overflow semantics;
- giữ atomic ordering;
- giữ Drop;
- giữ volatile;
- giữ panic behavior.

Chỉ khác mức độ tối ưu.

---

# 3. Optimization phải deterministic

Cùng:

```text
source
compiler version
target
flags
dependencies
```

→ cùng MIR optimized.

Không được phụ thuộc:

```text
hash-map iteration order
thread scheduling
machine timing
random seed
```

trừ khi explicitly configured.

---

# 4. Observable behavior

Optimizer phải phân biệt:

```text
Observable
Non-observable
```

Observable gồm:

- memory access tới externally observable memory;
- volatile;
- atomic;
- syscall/FFI;
- I/O;
- externally visible function call;
- synchronization;
- panic/trap;
- program termination;
- externally observable address;
- required ABI behavior.

Không được xóa chỉ vì “result không dùng”.

---

# 5. Pure computation

Ví dụ:

```axiom
let x = 10 + 20;
let y = x * 2;
print(y);
```

MIR:

```text
%1 = ADD 10, 20
%2 = MUL %1, 2
CALL print(%2)
```

→

```text
CALL print(60)
```

---

# 6. Constant propagation

Compiler duy trì:

```text
ConstantState {
    Unknown
    Constant(value)
    Overdefined
}
```

Ví dụ:

```axiom
let x = 10;
let y = x + 5;
```

→

```text
y = 15
```

---

# 7. SCCP

Sparse Conditional Constant Propagation dùng cả:

```text
value lattice
+
CFG reachability
```

Ví dụ:

```axiom
if false {
    expensive();
} else {
    cheap();
}
```

Compiler chứng minh:

```text
then block unreachable
```

và loại bỏ.

---

# 8. Không biến checked semantics thành UB

Ví dụ Axiom:

```text
ADD { overflow: Checked }
```

Optimizer không được biến:

```text
x + 1
```

thành unchecked machine `ADD` rồi giả định overflow không xảy ra.

Chỉ được bỏ check nếu chứng minh:

```text
x != MAX
```

hoặc tương đương.

---

# 9. Wrapping arithmetic

```text
ADD { overflow: Wrapping }
```

có thể map trực tiếp machine add nếu target semantics phù hợp.

Đây là lý do MIR phải giữ overflow mode.

---

# 10. Saturating arithmetic

```text
ADD { overflow: Saturating }
```

có thể:

- target instruction;
- branchless sequence;
- branch sequence;

tùy target.

Đây là optimization, không phải semantic change.

---

# 11. Copy propagation

```axiom
let a = b;
use(a);
```

Nếu `a` chỉ là semantic copy:

```text
use(b);
```

Nhưng với owning Move:

```axiom
let a = move b;
use(a);
```

optimizer có thể rename value:

```text
use(b)
```

**chỉ sau khi ownership verification đã chứng minh `b` không còn được sử dụng theo semantic rules.**

---

# 12. Ownership abstraction có thể biến mất

Source:

```axiom
let b = move a;
consume(b);
```

MIR:

```text
MOVE a
DROP/...
CALL consume
```

Sau optimization có thể:

```text
CALL consume(a)
```

nếu không có observable distinction.

Đây là **Move elimination**.

---

# 13. Drop elimination

Ví dụ:

```axiom
struct Temp {
    value: i32
}
```

nếu `Temp` không có Drop:

```text
DROP temp
```

không có side effect.

→ xóa.

Nhưng:

```axiom
struct File {
    ...
}
```

có Drop observable:

```text
DROP file
```

không được xóa.

---

# 14. Empty Drop

Nếu compiler chứng minh:

```text
Drop::drop(T)
```

không có observable effect:

```text
DROP T
```

→ eliminate.

Điều này rất hữu ích cho zero-cost generic abstractions.

---

# 15. Nhưng Drop không được suy đoán

Không được:

> “Destructor có vẻ đơn giản nên xóa.”

Phải có compiler fact:

```text
DropEffect = None
```

hoặc body đã được optimize và chứng minh dead.

---

# 16. Dead code elimination

Các instruction không ảnh hưởng observable behavior có thể xóa.

Ví dụ:

```text
x = expensive_pure_calculation()
return 42
```

→ calculation bị loại.

Nhưng:

```text
x = read_file()
return 42
```

không được xóa nếu read có observable effect/error/panic semantics.

---

# 17. Calls có effect facts

Function summary:

```text
FunctionFacts {
    pure
    may_panic
    may_allocate
    may_io
    may_block
    reads_memory
    writes_memory
    may_trap
}
```

Những facts này **internal**, không phải user-facing effect system.

# 18. Pure call

Nếu:

```text
foo()
```

được compiler chứng minh:

```text
Pure
NoPanic
NoMemoryWrite
```

và return unused:

```text
foo();
```

→ có thể xóa.

# 19. Unknown external function

FFI:

```text
extern "C" fn foo();
```

mặc định:

```text
Unknown side effects
```

Không được tự ý DCE.

Nếu programmer/compiler có explicit contract:

```text
@pure
```

sau này có thể cung cấp.

Nhưng chưa cần đưa `@pure` vào Core v1.

# 20. Escape Analysis

Compiler xác định object:


# 21. NoEscape

```axiom
fn foo() {
    let x = Box::new(Data);
    use(x);
}
```

Nếu `x` không escape:

```text
Box dynamic storage
```

có thể được:

- stack promoted;
- scalarized;
- eliminated.

---

# 22. Allocation elimination

Ví dụ:

```axiom
let p = Box::new(Point { x: 1, y: 2 });
return p.x + p.y;
```

Nếu address không observable:

```text
ALLOC
STORE x=1
STORE y=2
LOAD x
LOAD y
DEALLOC
```

→

```text
return 3
```

Toàn bộ allocation biến mất.

Đây là mục tiêu quan trọng của:

> `Box<T>` có dynamic-storage semantics nhưng không bắt buộc physical heap allocation.

---

# 23. Scalar Replacement of Aggregates

```axiom
struct Point {
    x: i32,
    y: i32,
}
```

Source:

```axiom
let p = Point(10, 20);
return p.x + p.y;
```

MIR aggregate:

```text
p.x = 10
p.y = 20
```

SROA:

```text
%px = 10
%py = 20
return %px + %py
```

Không cần materialize `Point`.

---

# 24. Nested aggregate

```text
A {
    b: B {
        c: i32
    }
}
```

Compiler có thể scalarize:

```text
a.b.c
```

thành:

```text
%c
```

nếu không có observable address/layout requirement.

---

# 25. Address escape

Ngược lại:

```axiom
unsafe {
    pass_address(&raw x);
}
```

nếu address trở nên observable:

```text
StorageIdentity = Observable
```

thì compiler phải materialize storage.

Đây chính là invariant:

> **Observable address constrains storage optimization.**

---

# 26. Alias analysis

Axiom có lợi thế lớn ở đây.

Compiler đã có:

```text
Capability facts
Region facts
Provenance
```

Ví dụ:

```axiom
fn add(
    a: mut_view<f32>,
    b: view<f32>
)
```

nếu verifier chứng minh:

```text
a.region DISJOINT b.region
```

backend có thể nhận:

```text
NoAlias(a,b)
```

---

# 27. Alias facts không được bịa

Nếu:

```text
region(a) = UNKNOWN
region(b) = UNKNOWN
```

optimizer không được giả định:

```text
a != b
```

Axiom safe semantics:

> unknown overlap = potentially overlapping.

---

# 28. Load forwarding

```text
STORE x, 10
%a = LOAD x
```

nếu không có intervening write/observable alias:

```text
%a = 10
```

---

# 29. Store elimination

```text
STORE x, 10
STORE x, 20
```

Store đầu có thể bỏ nếu:

```text
x
```

không bị observable giữa hai stores.

Nếu `x` volatile → không được.

Nếu atomic → không được coi như ordinary store.

# 30. Memory dependence

Compiler xây:

```text
MemorySSA
```

**sau** khi Verified MIR đã có alias facts.

MemorySSA không phải semantic authority.

Nó chỉ là optimizer analysis.

- generic dispatch.

# 33. Generic functions

Ví dụ:

```axiom
fn max<T: Ordered>(a: T, b: T) -> T
```

`max<i32>` sau monomorphization:

```text
max_i32
```

Optimizer có thể inline.

Không còn trait lookup runtime.

---

# 34. Devirtualization

Nếu source:

```axiom
dyn Trait
```

nhưng compiler biết concrete type:

```text
Dynamic object → known concrete type
```

có thể:

```text
CALL_INDIRECT
```

→

```text
CALL_DIRECT
```

→ inline.

Nhưng không được giả định concrete type nếu dynamic semantics cho phép nhiều implementation.

---

# 35. Static dispatch vẫn là default

Do đó phần lớn code Axiom:

```text
generic
trait
extension
method
```

cuối cùng:

```text
direct call
```

Không có vtable overhead.

---

# 36. Closure devirtualization

```axiom
let f = |x| x + 1;
f(10);
```

Compiler biết closure concrete.

→ direct call.

Sau inlining:

```text
return 11;
```

---

# 37. Tail-call optimization

Source:

```axiom
fn f(x) {
    return g(x);
}
```

Nếu ABI cho phép:

```text
CALL g
RET
```

→

```text
JUMP g
```

Không cần stack growth.

---

# 38. Guaranteed tail call

Không cần source keyword trong v1.

Compiler chỉ biến thành tail call nếu:

```text
ABI-compatible
return convention-compatible
stack arguments compatible
cleanup complete
```

Nếu không → ordinary call.

# 39. Loop canonicalization

Compiler nhận diện:

```text
while

loop + branch
```

thành canonical loop CFG.

Ví dụ:

```text
header
  ↓
body
  ↓
latch
  ↓
header
```

Điều này đơn giản hóa:

- LICM;
- induction variables;
- bounds check;
- vectorization.

---

# 40. Loop invariant code motion

```axiom
while i < n {
    x = expensive_constant();
    use(x);
    i += 1;
}
```

Nếu `expensive_constant()` không observable:

```text
preheader:
    x = expensive_constant()

loop:
    use(x)
```

---

# 41. Bounds-check elimination

Axiom arrays/views có bounds semantics.

Ví dụ:

```axiom
for i in 0..n {
    use(a[i]);
}
```

Compiler có thể chứng minh:

```text
0 <= i < n
```

→ eliminate repeated bounds checks.

Đây là một optimization quan trọng để đạt hiệu năng C/C++ mà vẫn giữ safe semantics.

---

# 42. Bounds check không được biến thành UB

Nếu không chứng minh được:

```text
i < len
```

thì check phải còn.

Không được:

```text
“C/C++ thường làm vậy”
```

để bỏ check.

# 47. Axiom alias model + vectorization

Ví dụ:

```axiom
fn add(
    a: view<f32>,

    out: mut_view<f32>
```

# 48. Allocation sinking

Ví dụ object chỉ được sử dụng trong một branch:

```text
if condition {
    allocate X
    use X
}
```

Compiler có thể move allocation vào branch.

Hoặc nếu branch unreachable → xóa.

---

# 49. Allocation hoisting

Ngược lại, nếu allocation invariant loop và stable:

```text
while (...) {
    use(buffer)
}
```

có thể hoist ra ngoài loop.

Chỉ khi semantics của allocation timing không observable.

---

# 50. Resource lifetime shortening

Compiler có thể thấy:

```axiom
let file = open();
use(file);
do_other_work();
return;
```

Nếu `file` không cần sống tới cuối scope:

```text
DROP file
```

được hoist lên ngay sau last use.

Điều này giảm:

- resource lifetime;
- memory pressure;
- lock hold time;
- live ranges.

Nhưng phải giữ observable Drop ordering semantics.

---

# 51. Drop scheduling optimization

Không được tùy ý reorder destructor.

Ví dụ:

```text
a
b
```

mặc định:

```text
drop b
drop a
```

Compiler có thể shorten `b` lifetime nếu:

- không vi phạm dependency;
- không thay đổi observable Drop order đối với live resources;
- không phá capability validity.

---

# 52. Panic path optimization


```text

```

Machine/backend sau đó đặt panic path vào cold block.

# 70. Invariant quan trọng

**Không để ABI details lọt ngược vào semantic optimizer.**

Ví dụ optimizer không được quyết định:

> “x86 trả struct 16 byte bằng RAX/RDX.”

Đó là ABI layer.

MIR optimizer chỉ biết:

```text
return Point
```

# 73. Một điểm rất quan trọng cho mục tiêu “nhanh bằng hoặc hơn C/C++”

Axiom không thể đảm bảo mọi chương trình luôn nhanh hơn C/C++. Nhưng kiến trúc hiện tại cho Axiom một số lợi thế compiler-visible:

```text
C/C++ pointer aliasing thường khó chứng minh
             ↓
Axiom capability/region facts
             ↓
NoAlias facts khi thực sự được chứng minh
             ↓
better load/store optimization
             ↓
better vectorization
```

và:

```text
ownership
   ↓
escape analysis
   ↓
allocation elimination
   ↓
scalarization
   ↓
zero runtime ownership overhead
```

cộng thêm:

```text
generic static dispatch
closure specialization
async state minimization
bounds elimination
```

Đây mới là hướng thực tế để đạt mục tiêu hiệu năng của Axiom, thay vì cố làm ngôn ngữ “thấp cấp” hơn C.
