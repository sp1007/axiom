Tiếp tục. Tôi nghĩ phần **Object Model & Data Layout** nên được chốt theo một nguyên tắc rất mạnh:

> **Axiom có type semantics ổn định, nhưng representation mặc định không ổn định và compiler được toàn quyền tối ưu representation khi không observable.**

Điều này cực kỳ quan trọng nếu mục tiêu là hiệu năng ngang hoặc hơn C/C++.

# 1. `struct` là semantic data, không phải memory layout

Ví dụ:

```axiom
struct Person {
    age: u8
    active: bool
    id: u64
}
```

Về mặt source:

```text
Person
├── age
├── active
└── id
```

Nhưng compiler **không bắt buộc** lưu:

```text
offset 0 → age
offset 1 → active
offset 2 → padding
offset 8 → id
```

Nó có thể reorder:

```text
id
age
active
padding
```

để giảm padding.

Hoặc thậm chí scalarize:

```text
id → RAX
age → RCX
active → RDX
```

Không có object nào tồn tại trong RAM.

Đây nên là default.

---

# 2. Semantic field order ≠ physical field order

Nếu source:

```axiom
struct S {
    a: A
    b: B
    c: C
}
```

thì:

```text
a,b,c
```

là thứ tự semantic khi truy cập bằng tên.

Nhưng physical:

```text
b,c,a
```

có thể hoàn toàn hợp lệ.

Compiler chỉ phải bảo đảm:

```axiom
x.a
```

luôn lấy đúng `a`.

---

# 3. Khi nào layout trở thành observable?

Có 4 trường hợp chính:

```text
FFI
raw pointer/address
serialization contract
explicit repr/layout attribute
```

Ví dụ:

```axiom
@repr(C)
struct Header {
    magic: u32
    size: u32
}
```

lúc này layout phải tương thích C.

Hoặc:

```axiom
@repr(transparent)
struct UserId(u64)
```

thì representation phải tương thích với `u64` ở ABI contract tương ứng.

---

# 4. `repr(C)` không chỉ là "field order"

Nó phải định nghĩa:

```text
size
alignment
field offsets
padding
aggregate ABI classification
```

theo C ABI target.

Ví dụ:

```text
Axiom
   │
   ▼
@repr(C)
   │
   ▼
Target C layout rules
   │
   ├── x86_64 SysV
   ├── Windows
   ├── ARM64
   └── ...
```

Không nên nói:

> `repr(C)` luôn có một layout duy nhất.

C ABI cũng phụ thuộc target.

---

# 5. `repr(transparent)` cực kỳ quan trọng

Ví dụ:

```axiom
struct UserId(u64)
```

semantic type khác:

```text
UserId != u64
```

Nhưng:

```axiom
@repr(transparent)
struct UserId(u64)
```

cho phép:

```text
UserId
  ↕ ABI-compatible
u64
```

mà không cần runtime wrapper.

Đây là cách Axiom có **strong type safety + zero-cost newtype**.

---

# 6. Không có `@size(N)` trong Core

Tôi vẫn giữ quyết định này.

Không nên cho:

```axiom
@size(64)
struct Foo { ... }
```

một cách tùy tiện.

Vì compiler phải chèn:

```text
padding
dummy fields
alignment hacks
```

hoặc từ chối.

Nếu programmer cần fixed-size binary representation:

```text
PackedBytes
SerializedFoo
repr(C)
```

nên dùng abstraction phù hợp.

---

# 7. Alignment là semantic contract khi cần

Có thể có:

```axiom
@align(64)
struct CacheLine {
    ...
}
```

Ý nghĩa:

```text
address % 64 == 0
```

được đảm bảo cho storage phù hợp.

Nhưng:

```text
@align(64)
```

không có nghĩa compiler phải đặt object trên stack nếu nó không cần tồn tại.

Nếu value bị scalarize thì alignment có thể không còn observable.

Nếu address được lấy:

```text
address(x)
```

thì contract phải được thực hiện.

---

# 8. Padding không có semantic value

Ví dụ:

```text
struct {
    u8
    u64
}
```

có padding.

Padding bytes:

```text
NONSEMANTIC
```

Không được mặc định coi:

```text
padding == 0
```

hoặc:

```text
padding has deterministic value
```

trừ khi representation contract nói rõ.

Điều này giúp compiler không phải zero-fill memory vô ích.

---

# 9. Đây có ảnh hưởng đến `memcmp` không?

Có.

Không nên cho:

```axiom
a == b
```

hạ thành:

```text
memcmp(&a, &b, sizeof(a))
```

một cách tổng quát.

Vì:

```text
semantic fields
```

có thể giống nhau nhưng:

```text
padding bytes
```

khác nhau.

Equality phải dựa trên **semantic value**.

Compiler chỉ được tối ưu thành bitwise comparison khi chứng minh representation cho phép.

---

# 10. Hash cũng tương tự

Không nên mặc định:

```text
hash(struct)
=
hash(raw memory)
```

vì:

- padding;
- niche;
- NaN;
- representation variants;

có thể làm raw bytes khác nhau nhưng semantic value giống nhau.

Hash phải là semantic operation.

---

# 11. Float là ví dụ rất rõ

`f32` có:

```text
+0
-0
NaN
Infinity
```

Một số semantic equality rules không giống raw bit equality.

Do đó:

```text
bit representation
```

và:

```text
semantic equality
```

phải tách.

---

# 12. Enum: compiler được quyền niche optimization

Ví dụ:

```axiom
enum Option<T> {
    None,
    Some(T)
}
```

Không nhất thiết phải:

```text
tag + payload
```

Nếu `T` có invalid representation:

```text
Option<Box<T>>
```

có thể encode:

```text
null → None
non-null → Some
```

mà không thêm tag.

Nhưng source semantics vẫn:

```text
Some
None
```

Compiler được tự do.

---

# 13. Enum layout không được programmer phụ thuộc nếu không có repr

Ví dụ:

```axiom
enum Color {
    Red,
    Green,
    Blue
}
```

Không nên mặc định cam kết:

```text
Red = 0
Green = 1
Blue = 2
```

Nếu cần ABI/C enum:

```axiom
@repr(C)
enum Color {
    ...
}
```

hoặc representation contract rõ ràng.

---

# 14. Nhưng `repr(C)` enum cần cẩn thận

C enum không hoàn toàn giống tagged union tổng quát.

Axiom nên phân biệt:

```text
C enum
```

với:

```text
Axiom algebraic enum
```

Đặc biệt enum có payload:

```axiom
enum Result<T,E> {
    Ok(T),
    Err(E)
}
```

không nên cố giả vờ là C enum.

FFI cần representation rõ:

```text
C-compatible tagged representation
```

nếu muốn truyền qua ABI.

---

# 15. Union

Tôi vẫn giữ:

> **Union được phép, nhưng là overlapping storage chứ không phải magic type-punning.**

Ví dụ:

```axiom
union Bits {
    i32: i32
    f32: f32
}
```

Representation:

```text
┌───────────────┐
│ shared bytes  │
└───────────────┘
```

Không có tag mặc định.

---

# 16. Safe union phải rất hạn chế

Không nên:

```axiom
union Evil {
    file: File
    socket: Socket
}
```

rồi để compiler không biết active member là gì.

Vì Drop sẽ trở thành vấn đề.

Do đó v0.1:

> Union chứa arbitrary `Drop` resources không được phép.

Union an toàn nhất cho:

```text
Copy/POD-like
trivial representation
```

Các union phức tạp hơn:

```text
unsafe
```

và programmer phải quản lý active member.

---

# 17. Không có unrestricted `transmute`

Tôi nghĩ đây là quyết định rất quan trọng.

Không có:

```axiom
transmute<A,B>(x)
```

tùy tiện.

Thay vào đó:

```text
value conversion
bit_cast
ptr_cast
addr_cast
reinterpret_bytes
```

mỗi loại có semantics riêng.

---

# 18. `bit_cast`

Ví dụ:

```axiom
let bits: u32 = bit_cast<float_bits)
```

Điều kiện:

```text
sizeof(A) == sizeof(B)
```

và compiler phải xác định việc đọc representation hợp lệ.

Không được dùng `bit_cast` để tạo:

```text
invalid enum
invalid bool
invalid pointer
```

một cách safe.

---

# 19. Raw bytes → T phải khó hơn

Đây là lỗi thiết kế phổ biến của systems language.

Không nên:

```axiom
let x: Foo = bytes.as<Foo>()
```

vì bytes arbitrary có thể không phải representation hợp lệ của Foo.

Nên có:

```text
decode
```

hoặc unsafe:

```text
reinterpret_bytes<Foo>()
```

với programmer chịu invariant.

---

# 20. `bool` không nên có C-style representation freedom trong safe semantic layer

Semantic:

```text
bool = true | false
```

Không có:

```text
42 == true
```

và không được coi mọi non-zero byte là valid bool trong safe code.

FFI `repr(C)` có thể có target-specific C-compatible representation.

# 21. SIMD

Tôi vẫn giữ:

```axiom
Vector<T,N>
```

là semantic vector.

Không viết:

```text
__m256
__m512
NEON register
```

trong Core.

Ví dụ:

```axiom
let a: Vector<f32, 8>
```

Compiler có thể:

```text
AVX
AVX2
AVX-512
NEON
SVE
scalar
```

tùy target.

---

# 22. `Vector<f32, 8>` không đảm bảo một register

Có thể:

```text
1 × 256-bit register
```

hoặc:

```text
2 × 128-bit registers
```

hoặc:

```text
8 scalar registers
```

Semantics vẫn giống nhau.

Điều này cực kỳ tốt cho cross-platform.

---

# 23. Nhưng alignment của SIMD phải có thể kiểm soát

Ví dụ vector API có thể yêu cầu:

```text
load_aligned
load_unaligned
```

hoặc compiler biết alignment từ type/storage.

Không nên bắt mọi SIMD data phải 32/64-byte aligned.

---

# 24. AoS vs SoA

Đây là một vấn đề lớn cho game/AI/scientific computing.

Ví dụ:

```axiom
struct Particle {
    position: Vec3
    velocity: Vec3
    mass: f32
}
```

AoS:

```text
P0: pos vel mass
P1: pos vel mass
P2: pos vel mass
```

SoA:

```text
positions[]
velocities[]
masses[]
```

Tôi **không** muốn compiler tự động thay đổi:

```text
AoS → SoA
```

một cách tổng quát trong v0.1.

Vì layout/alias/address semantics có thể khiến transformation không an toàn.

---

# 25. Nhưng nên hỗ trợ SoA ở library level

Ví dụ:

```text
ArrayOf<T>
StructOfArrays<T>
```

hoặc codegen/data-oriented library.

Như vậy:

```text
semantic abstraction
```

vẫn zero-cost.

Compiler có thể inline/vectorize.

---

# 26. False sharing cũng không nên là Core semantic

Có thể hỗ trợ:

```axiom
@cache_align(64)
```

hoặc:

```text
CachePadded<T>
```

nhưng không cần một memory type mới.

Ví dụ:

```axiom
struct Counters {
    a: CachePadded<Atomic<u64>>
    b: CachePadded<Atomic<u64>>
}
```

là đủ.

---

# 27. ZST — Zero Sized Types

Nên hỗ trợ.

Ví dụ:

```axiom
struct Marker {}
```

có thể:

```text
size = 0
```

Nhưng cần một rule quan trọng:

> **Không được suy ra rằng hai ZST values có địa chỉ khác nhau.**

Compiler có thể không allocate chúng.

Điều này rất tốt cho:

```text
Phantom/marker types
type-level tags
zero-cost abstractions
```

---

# 28. Nhưng `addr_of(ZST)` phải có semantics đặc biệt

Nếu ZST không có storage thực sự:

```axiom
address_of(marker)
```

không nên được coi là một identity address bình thường.

Tôi đề xuất:

> ZST không có stable storage identity mặc định.

Nếu programmer cần unique identity:

```text
explicit allocation/storage
```

phải được sử dụng.

---

# 29. Struct layout có thể được optimizer scalarize

Ví dụ:

```axiom
struct Vec2 {
    x: f32
    y: f32
}

fn length(v: Vec2) -> f32 {
    ...
}
```

Compiler có thể:

```text
v.x → XMM0
v.y → XMM1
```

Không cần memory.

Đây chính là:

> **Abstraction Erasure**

Struct là abstraction source-level, không phải lời hứa rằng RAM phải chứa struct object.

---

# 30. Nhưng FFI phải đóng băng layout

```axiom
@repr(C)
struct Vec2 {
    x: f32
    y: f32
}
```

khi truyền:

```axiom
extern "C" fn process(v: Vec2)
```

ABI lowering phải bảo đảm C ABI classification.

Lúc này optimizer vẫn có thể giữ values trong registers, miễn external ABI nhìn thấy representation đúng.

Ví dụ:

```text

Hoặc:

```

# 32. Layout query phải tồn tại

Compiler/compile-time code cần biết:

```text
size_of<T>()
align_of<T>()
offset_of<T.field>()
```

nhưng chỉ trong compile-time/context thích hợp.

Ví dụ:

```axiom
const SIZE = size_of<MyStruct>()
```

được phép.

Điều này rất hữu ích cho:

- serialization;
- allocator;
- FFI;
- GPU;
- networking;
- low-level structures.

---

# 33. Nhưng `offset_of` không nên tồn tại cho arbitrary optimized value

Nếu:

```text
struct S
```

không có addressable storage contract:

```text
offset_of(S.a)
```

vẫn có thể trả **layout offset** của canonical representation.

Nhưng:

```text
address(s) + offset
```

không được tự động trở thành safe access.

Đây là sự khác nhau giữa:

```text
layout information
```

và:

```text
actual storage
```

# 34. Endianness

`u32` không phải:

```text
[u8;4]
```

Semantic integer độc lập endian.

Chỉ khi chuyển thành bytes:

```axiom
to_le_bytes()
to_be_bytes()
```

mới có endian semantics.

Điều này đặc biệt quan trọng cho:

```text
network
file format
serialization
FFI
```

# 35. Bitfields

Tôi vẫn khuyên:

> Không có C-style bitfield trong Core.

Thay vào đó:

```axiom
flags & MASK
flags >> SHIFT
```

hoặc library:

```axiom
BitField<T, OFFSET, WIDTH>
```

Compiler có thể tối ưu thành instruction tương ứng.

Lý do:

C bitfield layout phụ thuộc compiler/ABI cực kỳ khó portable.

FFI bitfield có thể nằm trong system representation layer sau.

# 36. Packed struct

Có thể:

```axiom
@repr(packed)
struct Header {
    ...
}
```

nhưng đây phải là **unsafe/system-level**.

Vì:

```text
unaligned field access
```

có thể gây:

- performance penalty;
- hardware fault trên một số target;
- compiler phải generate byte accesses.

Safe code không nên vô tình tạo ra vấn đề này.

# 38. Invariants nên freeze

### ALAYOUT-01 — Semantic/Physical Separation
Semantic type identity is independent of physical representation.

### ALAYOUT-02 — Compiler-Controlled Default Layout
Default struct layout is compiler-controlled.

### ALAYOUT-03 — Field Semantic Identity
Field access is based on semantic identity, not physical offset.

### ALAYOUT-04 — Explicit Stable Layout
ABI/layout guarantees require explicit representation contracts.

### ALAYOUT-05 — `repr(C)` Compatibility
`repr(C)` establishes target-specific C-compatible representation.

### ALAYOUT-06 — Transparent Newtype
`repr(transparent)` provides ABI-compatible representation for the designated underlying representation.

### ALAYOUT-07 — Padding Is Nonsemantic
Padding bytes have no semantic value unless explicitly specified.

### ALAYOUT-08 — Semantic Equality
Equality is defined over semantic values, not arbitrary object bytes.

### ALAYOUT-09 — Semantic Hash
Hashing is defined over semantic value, not padding representation.

### ALAYOUT-10 — Enum Layout Freedom
Enum layout is compiler-controlled unless explicitly constrained.

### ALAYOUT-11 — Niche Optimization
Compiler may exploit invalid representations when semantics remain unchanged.

### ALAYOUT-12 — Restricted Union
Union is overlapping storage and does not implicitly own arbitrary resources.

### ALAYOUT-13 — No Implicit Type Punning
Changing interpretation of storage requires explicit conversion/unsafe operation.

### ALAYOUT-14 — Valid Bit Patterns
Only valid representations may form safe values.

### ALAYOUT-15 — No Unrestricted Transmute
Representation conversion is divided into explicit operations with explicit contracts.

### ALAYOUT-16 — SIMD Representation Freedom
Semantic vectors are independent of physical SIMD register width.

### ALAYOUT-17 — ZST Support
Zero-sized types are valid and carry no mandatory storage identity.

### ALAYOUT-18 — Explicit Alignment
Alignment guarantees require explicit type/storage contracts when observable.

### ALAYOUT-19 — Packed Is Unsafe
Packed/unaligned representation is system-level and unsafe where required.

### ALAYOUT-20 — Endian Independence
Numeric semantics are independent of byte ordering.

### ALAYOUT-21 — ABI/Representation Separation
Data layout and calling-convention classification are separate compiler stages.

### ALAYOUT-22 — Abstraction Erasure
Structs, generics, vectors and other abstractions may disappear completely when their semantics permit.

## Một điểm tôi muốn bổ sung cho triết lý Axiom

Đến đây có thể thấy Axiom đang hình thành một nguyên tắc rất mạnh:

> **Không có “object” theo nghĩa runtime bắt buộc.**

Có:

```text
Value
Storage
Identity
Capability
```

chứ không phải:

```text
Object
 ├── header
 ├── vtable
 ├── GC metadata
 ├── RTTI
 └── identity
```

Điều này khiến `struct + function + trait` mà ta chọn trước đó không chỉ là một lựa chọn syntax. Nó thực sự nhất quán với toàn bộ memory/ABI model.

---

### Bước tiếp theo tôi đề xuất

Bây giờ nền tảng memory đã khá hoàn chỉnh. Ta nên chuyển sang **Function ABI + Calling Convention + Parameter Passing + Return Value**.

Đây là nơi quyết định trực tiếp:

- `struct` truyền bằng register hay memory;
- `view<T>` thực chất truyền thế nào;
- `mut_view<T>`;
- large struct return;
- closure;
- generic;
- `dyn Trait`;
- variadic FFI;
- tail call;
- `extern "C"`;
- Windows/Linux/macOS;
- và quan trọng nhất: **làm thế nào để Axiom abstraction không tạo overhead so với C**.
