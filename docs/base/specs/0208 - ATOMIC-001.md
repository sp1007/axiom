Tiếp tục với **ATOMIC-001 — Atomic & Memory Ordering Model**.

Đây là một trong những phần nên thiết kế thật kỹ vì Axiom phải vừa đủ mạnh để tự viết **scheduler, lock-free queue, allocator, channel, runtime, device code**, vừa không bắt lập trình viên bình thường phải vật lộn với memory model.

# ATOMIC-001

## 1. Nguyên tắc

Tách ba khái niệm:

```text
Atomicity
    = operation không bị quan sát ở trạng thái dở dang

Ordering
    = quan hệ quan sát giữa các memory operation

Visibility
    = khi nào một execution domain được phép quan sát kết quả
```

Không nên gom cả ba thành một khái niệm "atomic".

---

# 2. `Atomic<T>`

Axiom có:

```axiom
var counter: Atomic<u64>
```

Các thao tác cơ bản:

```axiom
counter.load(.relaxed)

counter.store(10, .release)

counter.fetch_add(1, .relaxed)

counter.swap(10, .acq_rel)

counter.compare_exchange(...)
```

Atomic không phải `T`.

Nếu:

```text
Atomic<u64>
```

thì không được:

```axiom
let x: u64 = counter
```

và đặc biệt không được tạo:

```text
mut_view<u64>
```

từ atomic.

---

# 3. Có nên giữ 5 memory order?

**Có.**

Tôi không khuyên đơn giản hóa thành chỉ:

```text
relaxed
strong
```

dù như vậy dễ học hơn.

Axiom cần tự viết:

- scheduler
- lock-free channel
- MPMC queue
- reference counting
- work stealing
- allocator
- runtime
- GPU synchronization

nên cần biểu đạt chính xác:

```text
Relaxed
Acquire
Release
AcqRel
SeqCst
```

Nhưng Axiom có thể làm cho chúng **dễ sử dụng hơn C/C++** bằng cách compiler diagnostics tốt hơn và API rõ ràng hơn.

---

# 4. `Relaxed`

```axiom
counter.fetch_add(1, .relaxed)
```

Guarantee:

```text
operation atomic
```

Nhưng không tạo synchronization với memory khác.

Ví dụ counter thống kê:

```axiom
requests.fetch_add(1, .relaxed)
```

rất phù hợp.

Không được suy luận:

```text
requests == 10
```

đồng nghĩa với việc những memory write trước đó đã visible.

---

# 5. `Release`

```axiom
ready.store(true, .release)
```

Release nói:

> Các memory operation trước operation này không được bị quan sát theo cách vi phạm release synchronization khi một acquire tương ứng observes nó.

Mẫu kinh điển:

```axiom
data = 42
ready.store(true, .release)
```

---

# 6. `Acquire`

Thread khác:

```axiom
if ready.load(.acquire) {
    use(data)
}
```

Nếu acquire observes release:

```text
Producer                     Consumer

data = 42
   │
   ▼
ready.store(release)
   │
   │ synchronization
   ▼
                         ready.load(acquire)
                                │
                                ▼
                           read data
```

Đây là pattern nền tảng của Axiom scheduler/channel.

---

# 7. `AcqRel`

Dùng cho operation vừa đọc vừa publish:

```axiom
state.fetch_add(1, .acq_rel)
```

hoặc CAS:

```axiom
compare_exchange(
    expected,
    desired,
    .acq_rel,
    .acquire
)
```

---

# 8. `SeqCst`

Axiom vẫn hỗ trợ:

```axiom
.seq_cst
```

Nhưng đây không nên là default cho performance-sensitive code.

`SeqCst` cung cấp ordering mạnh hơn và tạo một **single global order cho các SeqCst atomic operations** theo memory model.

Compiler vẫn có thể tối ưu nếu không thay đổi observable semantics.

---

# 9. Không có implicit atomic ordering

Không cho:

```axiom
counter.fetch_add(1)
```

nếu API không có default ordering rõ ràng.

Tôi đề xuất **bắt buộc ordering trong low-level Atomic API**:

```axiom
counter.fetch_add(1, .relaxed)
```

Điều này làm code systems rõ ràng.

Nhưng thư viện cấp cao có thể che giấu ordering:

```axiom
queue.push(value)
```

và implementation tự chọn.

Đây chính là:

> Explicit at semantic boundaries, implicit inside abstractions.

---

# 10. Compare Exchange

API nên tránh kiểu C++ quá khó đọc:

```text
compare_exchange_weak(expected, desired,
                      success_order,
                      failure_order)
```

Axiom có thể:

```axiom
let result = atom.compare_exchange(
    expected,
    desired,
    success: .acq_rel,
    failure: .acquire
)
```

Kết quả:

```text
CompareExchangeResult<T>
├── exchanged
└── observed
```

hoặc đơn giản:

```axiom
Ok(old)
Err(actual)
```

nhưng cần phân biệt **CAS failure** với **actual operation error**.

Tôi nghiêng về:

```axiom
CompareResult<T>
```

là một enum chuyên biệt.

---

# 11. Weak CAS

Cần hỗ trợ:

```axiom
compare_exchange_weak()
```

vì lock-free algorithms có thể cần retry loop.

Nhưng programmer thông thường không cần dùng.

Library API:

```text
AtomicStack
AtomicQueue
Arc
Once
```

sẽ sử dụng weak CAS nội bộ.

---

# 12. Strong CAS

```axiom
compare_exchange()
```

là strong.

Semantics:

- success → value changed
- failure → comparison failed

Weak CAS có thể fail spuriously.

---

# 13. Failure ordering

Rule:

```text
CAS success ordering
    >=
CAS failure ordering
```

và failure không được là:

```text
Release
AcqRel
```

Compiler phải reject.

Ví dụ hợp lệ:

```axiom
compare_exchange(
    expected,
    desired,
    success: .acq_rel,
    failure: .acquire
)
```

Không hợp lệ:

```axiom
success: .acquire
failure: .release
```

Compiler diagnostic nên chỉ rõ lý do thay vì bắt programmer nhớ luật.

---

# 14. Atomic type nào?

Core MVP:

```text
Atomic<bool>
Atomic<i8/i16/i32/i64>
Atomic<u8/u16/u32/u64>
Atomic<isize>
Atomic<usize>
Atomic<ptr>
```

Nhưng **không đảm bảo mọi target hỗ trợ lock-free cho mọi kích thước**.

Đây là distinction rất quan trọng:

```text
Atomic<T>
```

≠

```text
LockFreeAtomic<T>
```

---

# 15. `is_lock_free`

Có API:

```axiom
Atomic<u64>.is_lock_free()
```

hoặc compile-time capability:

```text
atomic_is_lock_free<T>()
```

Compiler/backend target quyết định.

Một atomic có thể được implement bằng:

```text
CPU atomic instruction
```

hoặc:

```text
runtime/library fallback
```

nếu platform không có native operation.

---

# 16. Có nên có `LockFree<T>`?

Có thể có abstraction library:

```text
LockFreeAtomic<T>
```

nhưng không nên là Core primitive ban đầu.

Compiler intrinsic có thể expose:

```axiom
@compile_time
const ATOMIC_U64_LOCK_FREE = ...
```

để library chọn implementation.

---

# 17. Pointer atomics

Cần:

```axiom
Atomic<*mut T>
```

nhưng chỉ trong unsafe/system context.

Pointer atomic không tự tạo ownership.

Ví dụ:

```text
Atomic<*mut Node>
```

không có nghĩa:

```text
Atomic<Owned<Node>>
```

Đây là raw machine pointer.

Nếu muốn lock-free ownership structure:

```text
Arc
HazardPointer
Epoch
GenerationHandle
```

là abstraction riêng.

---

# 18. ABA problem

Axiom không cố "giải quyết" ABA trong Atomic.

Ví dụ:

```text
A → B → A
```

CAS có thể thấy:

```text
A == A
```

dù object đã thay đổi.

Đây là responsibility của lock-free abstraction.

Thư viện có thể cung cấp:

```text
TaggedPtr
GenerationHandle
AtomicHandle
```

Compiler không thể tự động loại bỏ ABA.

---

# 19. Atomic wait/notify

Đây là tính năng rất đáng có.

```axiom
atom.wait(expected)
atom.notify_one()
atom.notify_all()
```

Ví dụ:

```axiom
while state.load(.acquire) == WAITING {
    state.wait(WAITING)
}
```

Điều này cho phép xây:

- mutex
- semaphore
- condition variable
- scheduler parking
- channel

mà không cần spin liên tục.

---

# 20. `wait` không phải busy loop

Semantic:

```text
wait()
```

có thể:

```text
spin
↓
park
↓
OS futex
↓
wake
```

Implementation target-specific.

Axiom không quy định syscall nào.

---

# 21. Wait semantics

`wait(expected)` chỉ có nghĩa:

> Chờ cho tới khi atomic value khác `expected` hoặc implementation thực hiện một wake/spurious wake hợp lệ.

Do đó phải reload:

```axiom
while atom.load(.acquire) == expected {
    atom.wait(expected)
}
```

Không được giả định một lần wait là predicate đã đúng.

---

# 22. Notify

```axiom
notify_one()
notify_all()
```

không đảm bảo waiter đã lập tức chạy.

Nó chỉ tạo wake opportunity.

Scheduler quyết định khi nào task/thread chạy.

---

# 23. Fence

Cần:

```axiom
fence(.acquire)
fence(.release)
fence(.acq_rel)
fence(.seq_cst)
```

nhưng nên coi là **advanced unsafe/system-level operation**.

Code application bình thường gần như không cần.

---

# 24. `compiler_fence`

Có hai khái niệm khác nhau:

```text
hardware memory fence
compiler ordering barrier
```

Nếu cần, Axiom nên có:

```axiom
compiler_fence(...)
```

nhưng chỉ trong low-level compiler/runtime APIs.

Không nên dùng `volatile` để thay thế.

---

# 25. Volatile

Đây là phần cần tách cực rõ.

```text
atomic
≠
volatile
```

Atomic:

```text
thread synchronization
```

Volatile:

```text
observable machine/device access
```

Ví dụ memory-mapped I/O:

```axiom
unsafe {
    mmio.write_volatile(addr, value)
}
```

Volatile **không đảm bảo thread synchronization**.

---

# 26. `volatile` không phải atomic

Không cho programmer nghĩ:

```text
volatile write
```

tương đương:

```text
release store
```

Hai semantic hoàn toàn khác.

---

# 27. Device/GPU atomics

GPU đã có execution/storage domains.

Do đó atomic nên mở rộng:

```text
AtomicScope
├── Thread
├── Workgroup
├── Device
└── System
```

Nhưng không đưa GPU-specific scopes vào CPU Core type system.

Có thể:

```axiom
@kernel
fn ...
```

sử dụng:

```axiom
atomic.add(&counter, 1, .relaxed, .device)
```

hoặc abstraction library:

```text
DeviceAtomic<T>
```

Core atomic semantics vẫn là nền tảng.

---

# 28. Atomic alignment

Atomic storage phải đáp ứng alignment của target.

Compiler tự đảm bảo:

```text
Atomic<u64>
```

được align đúng.

Không cho:

```text
@repr(packed)
struct {
    x: Atomic<u64>
}
```

trong safe code.

`packed atomic` phải reject hoặc unsafe với target-specific restrictions.

---

# 29. False sharing

Không phải language semantic.

Nhưng Axiom nên hỗ trợ:

```axiom
@cache_align
```

hoặc:

```axiom
@align(64)
```

đã có `@align`.

Ví dụ:

```axiom
struct Counters {
    @align(64)
    producer: Atomic<u64>

    @align(64)
    consumer: Atomic<u64>
}
```

Đây là optimization/storage contract.

---

# 30. Atomic memory order và compiler optimization

Compiler được phép:

```text
reorder
eliminate
combine
hoist
sink
```

nếu không phá:

```text
happens-before
synchronizes-with
atomic modification order
```

Do đó memory model phải được kiểm tra **trước** optimizer.

Pipeline:

```text
Typed HIR
 ↓
Ownership/Concurrency verification
 ↓
MIR
 ↓
Atomic semantic verification
 ↓
Verified MIR
 ↓
Optimization
```

Optimizer không được tự suy đoán atomic là ordinary memory.

---

# 31. Data race

Axiom safe code phải không có data race.

Ví dụ:

```axiom
var x: i32

thread A:
    x = 1

thread B:
    x = 2
```

Nếu execution concurrent mà không synchronization:

```text
ERROR
```

Không được coi data race là:

```text
undefined behavior silently
```

như C/C++.

Đây là một trong những khác biệt lớn của Axiom.

---

# 32. Unsafe và data race

`unsafe` không nên biến:

```text
x = 1
```

thành magically safe.

Unsafe cho phép programmer thực hiện operation compiler không thể chứng minh.

Nhưng compiler vẫn ghi nhận:

```text
unsafe boundary
```

và sau đó safe capability phải được establish đúng contract.

Đã khớp:

```text
AUNSAFE-56
AUNSAFE-57
```

---

# 33. Memory model không dựa trên "undefined behavior"

Đây là điểm tôi khuyến nghị giữ rất mạnh.

Không:

```text
data race => arbitrary optimizer behavior
```

trong safe Axiom.

Thay vào đó:

```text
safe program
    ↓
race-free invariant
```

Unsafe program:

```text
programmer assumes responsibility
```

nhưng machine behavior vẫn phải được mô tả theo execution/target semantics càng nhiều càng tốt.

---

# 34. `Atomic<T>` và ownership

Atomic không phá ownership.

Ví dụ:

```axiom
var counter = Atomic<u64>.new(0)
```

`counter` vẫn là owned value.

Move:

```axiom
let other = counter
```

là ownership move.

Nhưng:

```text
multiple threads
```

không thể cùng access nếu atomic object không được shared qua một valid mechanism.

Thường:

```text
Arc<Atomic<u64>>
```

hoặc:

```text
SharedAtomic<u64>
```

là library abstraction.

---

# 35. Có cần `Atomic<T>` có `Share`?

Có, với điều kiện target/type phù hợp.

Mục tiêu:

```text
Atomic<T>
```

là synchronization-safe shared state.

Do đó:

```text
Atomic<T>: Share
```

không có nghĩa:

```text
T: Share
```

giống Mutex.

---

# 36. Atomic reference counting

`Arc` có thể implement:

```text
strong_count.fetch_add(1, Relaxed)
strong_count.fetch_sub(1, Release)
fence(Acquire)
```

và CAS tùy implementation.

Điều này chứng minh tại sao **Atomic phải được hoàn thiện trước Arc**.

Arc không cần Core primitive riêng.

---

# 37. Scheduler

Scheduler cũng sử dụng:

```text
task.state
queue indices
wake flag
```

với:

```text
Relaxed
Acquire
Release
AcqRel
```

Do đó:

```text
Atomic model
    ↓
Scheduler
    ↓
Channel
    ↓
Mutex
    ↓
Async runtime
```

không có circular semantic dependency.


Ngắn nhưng rất rõ.

# Bức tranh memory/concurrency hiện tại

Axiom bây giờ có một tầng khá sạch:

```text
                    MEMORY MODEL
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
      Ownership       Capability      Atomic
          │              │              │
          │              │       ┌──────┴──────┐
          │              │       ↓             ↓
          │              │   Ordering       Wait/Notify
          │              │
          └──────┬───────┘
                 ↓
          Synchronization
          ┌──────┼───────┐
          ↓      ↓       ↓
       Mutex   RwLock  Semaphore
          │
          ↓
        Guard
          │
      ┌───┴────┐
      ↓        ↓
    view    mut_view
```

Điểm rất quan trọng là **Atomic không phải một escape hatch khỏi ownership**. Nó chỉ thay đổi protocol truy cập bộ nhớ.

# Tiếp theo: `ARC-001 — Shared Ownership`

Đây là task hợp lý tiếp theo.

Sau Atomic, ta có đủ nền tảng để thiết kế:

```text
Arc<T>
Weak<T>
AtomicShared<T>
reference counting
cycle problem
strong/weak count
destruction ordering
thread-safe shared ownership
```

Đặc biệt cần chốt một quyết định lớn cho Axiom:

> **Có nên đưa `Arc<T>` thành một type chuẩn của `std`, hay tạo một primitive `Shared<T>` trong Core?**

Hướng tôi đang nghiêng tới là:

```text
Core:
    ownership
    Send
    Share
    Atomic

std:
    Arc<T>
    Weak<T>
    Rc<T>
    Shared<T> abstractions
```

Tức **reference counting không trở thành cơ chế quản lý bộ nhớ của ngôn ngữ**; nó chỉ là một chiến lược ownership được thư viện xây dựng trên nền ownership + atomic của Axiom.
