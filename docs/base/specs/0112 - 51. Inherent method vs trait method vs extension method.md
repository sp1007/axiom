Tiếp tục **Consistency Pass #3**. Lần này tập trung vào **trait, method resolution, generic, enum, closure và ownership**. Đây là nhóm dễ tạo ra “luật ngầm” nếu không khóa semantics sớm.

---

# 51. Inherent method vs trait method vs extension method

Ta có:

```axiom
struct Vec2 {
    x: f32
    y: f32
}

impl Vec2 {
    fn length(self: view<Self>) -> f32 {
        ...
    }
}
```

Trait:

```axiom
trait Shape {
    fn area(self: view<Self>) -> f32
}

impl Shape for Vec2 {
    fn area(self: view<Self>) -> f32 {
        ...
    }
}
```

Extension:

```axiom
fn normalize(v: mut_view<Vec2>) {
    ...
}
```

Gọi:

```axiom
v.length()
v.area()
v.normalize()
```

Resolution phải deterministic.

Tôi đề xuất thứ tự cố định:

```text
1. Inherent function
2. Direct trait implementation
3. Explicitly imported extension function
4. Generic extension function
```

Không có “compiler đoán function nào có vẻ phù hợp nhất”.

---

# 52. Method ambiguity

Nếu:

```axiom
trait A {
    fn test(self: view<Self>)
}

trait B {
    fn test(self: view<Self>)
}
```

và:

```axiom
impl A for Foo { ... }
impl B for Foo { ... }
```

thì:

```axiom
foo.test()
```

phải **compile error**.

Không được chọn dựa trên:

- thứ tự import;
- thứ tự declaration;
- độ dài tên;
- generic specificity;
- compiler heuristic.

Muốn chỉ rõ:

```axiom
A.test(foo)
```

hoặc syntax tương đương qualified call mà ta sẽ chuẩn hóa sau.

### Invariant

**AMETHOD-20 — Method Resolution Is Deterministic**

**AMETHOD-21 — Ambiguous Method Resolution Is A Compile Error**

---

# 53. Inherent method thắng trait method

Ví dụ:

```axiom
impl Foo {
    fn size(self: view<Self>) -> usize
}

trait SizedThing {
    fn size(self: view<Self>) -> usize
}

impl SizedThing for Foo { ... }
```

`foo.size()` gọi inherent `Foo.size`.

Điều này hợp lý vì inherent API thuộc trực tiếp type.

Trait vẫn gọi được bằng qualified form.

---

# 54. Extension method không được “chiếm” API

Ví dụ package A định nghĩa:

```axiom
fn serialize(x: view<Foo>)
```

Package B import extension:

```axiom
fn serialize(x: view<Foo>)
```

Nếu Foo không có inherent/trait method phù hợp thì:

```axiom
foo.serialize()
```

→ ambiguity.

Không nên để import sau tự động override import trước.

Điều này cực kỳ quan trọng với package ecosystem.

---

# 55. Generic method resolution

Ví dụ:

```axiom
fn print<T: Display>(x: view<T>)
```

và:

```axiom
fn print(x: view<User>)
```

Gọi:

```axiom
print(user)
```

Có hai ứng viên.

Không nên xây dựng một overload ranking quá phức tạp.

Tôi đề xuất:

> **Exact inherent/explicitly selected APIs được ưu tiên; generic fallback chỉ được dùng khi không có candidate non-generic phù hợp.**

Nếu vẫn còn nhiều candidate tương đương → compile error.

Không có implicit “best template” kiểu C++ overload maze.

---

# 56. Generic specialization

Hiện spec nói:

> compiler có thể specialization nội bộ.

Điều này phải được tách khỏi programmer-visible semantics.

Ví dụ:

```axiom
fn max<T: Ord>(a: T, b: T) -> T
```

Compiler có thể tạo:

```text
max<i32>
max<f64>
max<MyType>
```

hoặc code sharing.

Programmer không được dựa vào:

```text
if T == i32
```

trừ khi có semantic mechanism riêng.

Không có user-defined specialization v0.1.

### Tại sao?

Nếu cho:

```axiom
impl<T> ...
impl<i32> ...
```

sẽ tạo một hệ thống coherence/specialization rất phức tạp.

Axiom không cần nó ở v0.1.

---

# 57. Trait coherence

Giữ rule:

```text
impl Trait for Type
```

chỉ hợp lệ nếu:

```text
Trait thuộc package hiện tại
OR
Type thuộc package hiện tại
```

Ví dụ:

```text
foreign Trait
foreign Type
```

→ forbidden.

Mục đích:

```text
package A
package B
package C
```

không thể tạo ba implementation khác nhau cho cùng:

```text
TraitA for TypeB
```

làm method resolution phụ thuộc dependency graph.

# 58. Associated type

Ví dụ:

```axiom
trait Iterator {
    type Item

    fn next(self: mut_view<Self>) -> Option<Self.Item>
}
```

Implementation:

```axiom
impl Iterator for Counter {
    type Item = i32
    ...
}
```

Ở đây `Self.Item` là compile-time type relation.

Không phải runtime metadata.

Do đó:

```text
Self.Item
```

có thể được resolve trước monomorphization.

### Invariant

**ATRAIT-20 — Associated Types Are Compile-Time Type Relations**

---

# 59. Generic + associated type

Ví dụ:

```axiom
fn collect<I: Iterator>(it: mut_view<I>) -> Vec<I.Item>
```

Compiler cần resolve:

```text
I
↓
Iterator implementation
↓
I.Item
↓
concrete type
```

Sau đó monomorphize.

Không cần runtime type information.

# 60. Copy + Drop

Đây là điểm phải khóa rất chặt.

Không cho type vừa có semantic:

```text
Copy
```

vừa có:

```text
custom Drop
```

Ví dụ:

```axiom
struct FileHandle {
    fd: i32
}

impl Drop for FileHandle { ... }
```

không được:

```axiom
impl Copy for FileHandle
```

Nếu copy:

```text
fd = 10
fd = 10
```

thì hai object cùng nghĩ mình sở hữu resource.

Đó là double-release.

### Rule

**ADROP-15 — A Type With Custom Drop Cannot Be Copy**

Đây là một trong những invariant quan trọng nhất của resource safety.

---

# 61. `Copy` không đồng nghĩa bitwise memcpy

Đối với:

```text
i32
f64
Point
```

thường compiler sẽ copy register/bits.

Nhưng semantic:

```text
Copy = tạo value ownership độc lập
```

không phải:

```text
memcpy(sizeof(T))
```

Điều này cho phép compiler thay đổi representation.

---

# 62. `Option<T>` và niche optimization

Axiom có:

```axiom
Option<T>
```

là ordinary enum.

Nhưng compiler có thể tối ưu.

Ví dụ:

```text
Option<Box<Node>>
```

có thể dùng null pointer representation.

Nhưng programmer không được phụ thuộc vào bit representation.

Semantic vẫn:

```text
Some(x)
None
```

### Invariant

**AENUM-20 — Enum Representation Is Compiler-Controlled Unless Explicitly Represented**

**AENUM-21 — Niche Optimization Is Semantics-Preserving**

---

# 63. `Option<NonNull<T>>`

Có thể có niche.

Nhưng:

```text
None
```

không có nghĩa programmer được dùng:

```text
null
```

trong safe Axiom.

Null chỉ là một possible physical representation.

Đây là distinction rất quan trọng:

```text
logical value ≠ physical encoding
```

---

# 64. Enum layout

Ví dụ:

```axiom
enum Message {
    Quit,
    Text(Text),
    Move { x: i32, y: i32 }
}
```

Compiler có thể layout:

```text
tag + payload
```

hoặc tối ưu niche.

Programmer chỉ được quan tâm đến:

```text
Message.Quit
Message.Text(...)
Message.Move(...)
```

Nếu muốn C-compatible layout:

```axiom
@repr(C)
enum ...
```

thì ABI rules riêng áp dụng.

---

# 65. `match` + ownership

Đây là test quan trọng.

```axiom
match message {
    Message.Text(text) => print(text),
    Message.Move { x, y } => move_to(x, y),
    Message.Quit => quit(),
}
```

Nếu `Text` là non-Copy, pattern:

```text
Message.Text(text)
```

có thể move payload.

Sau match, `message` không còn fully usable nếu payload đã moved.

Compiler phải track ownership theo từng pattern branch.

---

# 66. Match + view

Nếu:

```axiom
fn inspect(m: view<Message>) {
    match m {
        Message.Text(text) => print(text),
        ...
    }
}
```

`text` không được trở thành owning `Text`.

Nó phải là:

```text
view<Text>
```

hoặc read capability phù hợp.

Đây là cùng rule field projection đã thiết lập trước đó.

Không được tạo một semantics đặc biệt riêng cho pattern matching.

### Invariant

**AMATCH-20 — Pattern Binding Preserves Source Capability**

---

# 67. Match + partial move

Ví dụ:

```axiom
var message = Message.Text(big_text)

match message {
    Message.Text(text) => consume(text),
    Message.Quit => ...
}
```

Sau branch Text, payload đã moved.

Nếu compiler cần Drop `message`, nó phải biết trạng thái.

Với enum compiler-derived Drop:

```text
payload moved → do not drop payload
```

Với enum custom Drop, áp dụng restriction tương tự struct:

> custom Drop type không cho phép partial move.

---

# 68. Pattern matching phải không tạo hidden copies

Ví dụ:

```axiom
match large_struct {
    Foo { huge_field } => ...
}
```

Nếu `huge_field` non-Copy, compiler không được âm thầm clone nó chỉ để làm pattern matching.

Pattern semantics phải xác định rõ:

```text
move
view
ignore
bind
```

và optimizer chỉ được eliminate physical movement nếu semantics không đổi.

---

# 69. Closure capture inference

Ví dụ:

```axiom
let x = 10

let f = || println(x)
```

`x` có thể Copy.

Compiler có thể capture by value.

Nếu:

```axiom
let buffer = Buffer(...)

let f = || process(buffer)
```

Nếu closure escape, compiler cần xác định capture.

Có ba semantic possibilities:

```text
READ capture
WRITE capture
MOVE capture
```

Tôi đề xuất:

> Closure capture mode được compiler suy luận từ cách sử dụng; programmer chỉ cần `move` khi muốn ép ownership capture.

Ví dụ:

```axiom
move || process(buffer)
```

=> move.

Không cần syntax:

```text
|&x|
|&mut x|
```

---

# 70. Closure capture không thể phá ownership

Ví dụ:

```axiom
var buffer = Buffer(...)

let f = || {
    modify(buffer)
}

use(buffer)
```

Nếu closure vẫn sống và giữ mutable capability thì `use(buffer)` có thể conflict.

Compiler phải xem closure như một object có captured capability.

Nếu capability còn live:

```text
buffer WRITE capability
```

→ access conflict.

Nếu closure đã dead:

```text
drop(f)
```

→ capability hết.

---

# 71. Closure + `move`

```axiom
var buffer = Buffer(...)

let f = move || {
    process(buffer)
}

use(buffer)
```

Sau tạo closure:

```text
buffer → MOVED
closure.buffer → OWNED
```

Đây là semantics rõ ràng.

---

# 72. Closure + async

```axiom
let task = async {
    process(data)
    await network()
    use(data)
}
```

Closure/future object có thể sở hữu:

```text
data
```

Nếu `data` sống qua await:

```text
Future.data
```

Như phần async trước.

Không cần một ownership system riêng cho async closure.

---

# 73. Async closure + Send

```axiom
spawn(async move {
    process(data)
})
```

Compiler kiểm tra:

```text
Future: Send
```

từ toàn bộ state machine.

Không phải chỉ closure ban đầu.

Ví dụ nếu trước await có:

```text
Rc<T>
```

nhưng object không sống qua await thì nó có thể biến mất trước suspension.

Do đó:

> `Send` của Future phụ thuộc **state thực sự tồn tại tại migration/suspension points**, không nhất thiết mọi local từng xuất hiện trong source.

Đây là optimization + semantic analysis rất quan trọng.

---

# 74. Async migration

Nếu executor có thể chuyển Future:

```text
Thread A
   ↓
await
   ↓
Thread B
```

mọi state còn live qua migration phải thỏa điều kiện cần thiết.

Nhưng nếu executor guaranteed single-thread:

```text
spawn_local(...)
```

thì không cần `Send`.

Điều này đã nhất quán với:

```text
spawn → Send
spawn_local → same execution domain
```

# 75. Public generic API

Ví dụ:

```axiom
pub fn map<T, U>(
    value: T,
    f: fn(T) -> U
) -> U
```

API fingerprint phải bao gồm:

```text
name
generic parameters
constraints
parameter types
return type
effects nếu có
trait requirements
ABI-relevant attributes
```

Không bao gồm:

```text
private local variables
private helper functions
optimizer decisions
machine code
```

Như vậy incremental compilation có thể tránh rebuild consumer khi implementation thay đổi.

# 76. Package version và type identity

Nếu:

```text
package math v1
package math v2
```

cùng có:

```axiom
struct Vec2 { ... }
```

thì:

```text
math.v1.Vec2
```

và:

```text
math.v2.Vec2
```

là **hai type identity khác nhau**.

Không được tự động coi structural similarity là type compatibility.

Muốn chuyển:

```text
Vec2_v1 → Vec2_v2
```

phải có explicit conversion.

# 77. Module cycles

Module graph có thể:

```text
A imports B
B imports A
```

nếu chỉ là declarations/type references có thể resolve.

Nhưng package graph:

```text
Package A → Package B
Package B → Package A
```

vẫn cấm.

Điều này tránh dependency build cycle.

# 78. `comptime` + generic

Ví dụ:

```axiom
comptime fn make_array<T, const N: usize>() -> Array<T, N> {
    ...
}
```

Comptime vẫn dùng:

```text
type checking
generic constraints
ownership
```

Không tạo một "ngôn ngữ comptime thứ hai".

Điều này rất quan trọng.

Compiler chỉ có:

```text
one language
one type system
one MIR semantics
```

nhưng có:

```text
execution domain = compile-time
execution domain = runtime
```

# 79. `@repr(C)` + generic

Đây là một chỗ cần restriction.

Không nên cho:

```axiom
@repr(C)
struct Foo<T> {
    value: T
}
```

và giả định mọi `T` đều C-compatible.

Thay vào đó:

```text
@repr(C)
```

chỉ hợp lệ khi tất cả thành phần có known C-compatible representation.

Compiler phải reject nếu:

```text
T
```

không thỏa ABI constraint.

Ví dụ:

```text
@repr(C)
struct Foo<T: CRepr> { ... }
```

hoặc compiler intrinsic rule tương đương.

Không nhất thiết expose `CRepr` như trait surface; có thể là ABI property nội bộ.

---

# 80. `@repr(C)` + enum

Axiom enum:

```axiom
enum Result<T,E> { ... }
```

không tự động tương đương C union/tagged union.

Nếu cần C ABI:

```text
explicit representation
```

và phải thỏa C ABI restrictions.

Không được:

```text
@repr(C)
enum arbitrary_generic_Axiom_enum
```

rồi hứa layout tương thích C.

# 81. ABI và zero-cost abstraction

Một nguyên tắc cần thêm:

> ABI representation chỉ cố định khi programmer yêu cầu ABI stability/interop.

Ví dụ:

```axiom
@repr(C)
struct Foo ...
```

compiler bị ràng buộc.

Còn:

```axiom
struct Foo ...
```

compiler có thể:

```text
reorder fields
scalarize
pack
split
register-pass
caller-allocate
```

miễn semantic không thay đổi.

### Invariant

**AABI-20 — Representation Is Flexible Until An ABI Contract Freezes It**

# 82. C callback

```axiom
extern "C" fn register_callback(
    callback: extern "C" fn(i32) -> i32
)
```

Một closure:

```axiom
let factor = 10

register_callback(|x| x * factor)
```

**không được implicit convert**.

Vì closure có environment.

C function pointer không có environment.

Nếu muốn:

```text
callback + context pointer
```

phải dùng explicit FFI pattern:

```text
extern "C" fn callback(ctx: *mut void, value: i32)
```

và programmer quản lý context contract.

# 83. Closure ABI

Closure không có stable ABI mặc định.

Compiler có thể biểu diễn:

```text
environment
+
call function
```

nhưng representation không public.

Nếu closure không escape, toàn bộ closure có thể biến mất sau optimization.

Đây là một abstraction-erasure case điển hình.

# 85. Một thay đổi khái niệm tôi muốn đóng băng

Sau ba vòng, tôi nghĩ Axiom nên có **ba loại identity**, không chỉ hai:

### 1. Value Identity

```text
x: Vec2
```

Copy tạo value độc lập.

### 2. Storage Identity

```text
Box<T>
Arena<T>
Pool<T>
```

Đại diện cho một vùng storage có identity.

### 3. Logical Identity

```text
Handle<T>
EntityId
GenerationHandle
```

Identity tồn tại độc lập với physical address.

Sơ đồ:

```text
                 IDENTITY
                    │
       ┌────────────┼────────────┐
       │            │            │
     VALUE        STORAGE      LOGICAL
       │            │            │
     Copy          Box          Handle
     Move          Arena        EntityId
                    │            │
                 address       index/gen
```

Điều này rất quan trọng với mục tiêu của Axiom.

Programmer không nên dùng:

```text
pointer address
```

làm identity trong safe application code.

Raw pointer vẫn tồn tại cho systems programming.

```text
              ↓

              ↓

```

Ví dụ:

```text

 ↓

 ↓
pointer + length / register

 ↓
state machine
 ↓
possibly scalarized

 ↓
monomorphization
 ↓
possibly inlined

closure
 ↓
environment
 ↓
possibly eliminated

Box
 ↓
allocation
 ↓
possibly stack/register

Result
 ↓
branch
 ↓
possibly branchless machine code

trait
 ↓

 ↓
possibly direct/inlined call
```

Đây chính là **Abstraction Erasure** của Axiom.

# 87. Trạng thái hiện tại

Sau 3 vòng, tôi đánh giá architecture đã bắt đầu đạt trạng thái:

```text
                    AXIOM v0.1
                         │
 ┌───────────────────────┼────────────────────────┐
 │                       │                        │
VALUE                  CAPABILITY               RESOURCE
 │                       │                        │
Copy/Move             view/mut_view              Drop
 │                       │                        │
Enum/Struct          Alias/Region               Allocation
 │                       │                        │
Generic               Send/Share                 Storage
 │                       │                        │
Trait                 Atomic                    Handle
 │                       │
Closure               Async
                         │
                    Execution Domain
                         │
                 ┌───────┼────────┐
                 │       │        │
                CPU     GPU      FFI
```

Điểm đặc biệt là **không có một hệ thống riêng biệt cho từng feature**.

Async dùng ownership.

Concurrency dùng capability.

GPU dùng execution domain + capability.

FFI dùng ABI + ownership contract.

Drop dùng ownership.

Generic dùng type system.

Đó là dấu hiệu khá tốt về tính nhất quán của thiết kế.
