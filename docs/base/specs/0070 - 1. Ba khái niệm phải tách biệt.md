Tiếp tục với **Axiom Module + Namespace + Global State Model v0.1**. Phần này tưởng như chỉ là cú pháp, nhưng thực tế nó quyết định rất nhiều thứ: compile-time dependency, incremental build, linker, startup, static initialization và việc Axiom có bị kéo theo một runtime ngầm hay không.

# 1. Ba khái niệm phải tách biệt

Axiom nên có:

```text id="4m6r8n"
Module
    = semantic namespace

Package
    = distribution/dependency boundary

Object
    = compilation/link boundary
```

Ví dụ:

```text id="a9t2vc"
package my_app
│
├── module app
├── module graphics
├── module audio
└── module math
```

Không để package/module/object trở thành một khái niệm nhập nhằng.

---

# 2. Module là namespace, không phải file

Ví dụ:

```axiom id="m7k4vp"
module graphics.renderer
```

có thể nằm trong một hoặc nhiều source files theo build configuration.

Semantic identity là:

```text id="w2n5xk"
graphics.renderer
```

chứ không phải:

```text id="r1d8bz"
C:\project\graphics\renderer.ax
```

Điều này rất hữu ích cho incremental compilation.

---

# 3. Import là semantic dependency

```axiom id="x8q2fd"
import std.io
```

không phải:

```text id="0y8s5f"
#include "std/io.ax"
```

Compiler load **module interface/semantic information**, không paste source text.

---

# 4. Không có textual include

Tôi nghĩ đây nên là invariant:

> **Axiom không có `#include` tương đương C trong language core.**

Header-like information được compiler lấy từ:

```text id="c4n8vz"
module interface
```

hoặc compiled semantic metadata.

---

# 5. Import cụ thể

Ví dụ:

```axiom id="v8h3qs"
import std.io.File
import std.io.read
```

hoặc:

```axiom id="k5r1bd"
import std.io.{File, read}
```

Syntax cụ thể có thể thay đổi, nhưng semantic là:

```text
module → selected symbols
```

---

# 6. Wildcard import

Tôi **không muốn wildcard import mặc định**:

```axiom id="c2d6km"
import std.io.*
```

vì nó làm namespace thay đổi theo version dependency.

Nếu hỗ trợ, nên dành cho:

```text
local/internal convenience
```

và compiler vẫn phải phát hiện ambiguity rõ ràng.

# 7. Namespace qualification

Có thể luôn viết đầy đủ:

```axiom id="a7v4qx"

```

Đây là escape hatch cho ambiguity.

Ví dụ:

```text id="d2x5js"
graphics.Color
```

không được compiler tự đoán.

# 12. `pub` không đồng nghĩa ABI-public

Một function:

```axiom id="e7r3cp"
pub fn foo(x: i64) -> i64
```

có nghĩa:

```text id="v5j8nm"
visible to dependent Axiom code
```

không nhất thiết:

```text id="q3w6ht"
exported linker symbol
```

Muốn export native symbol:

```axiom id="b1k7fz"
@export("foo")
pub extern "C" fn foo(...)
```

hoặc syntax tương đương.

Đây là distinction rất quan trọng.

# 13. Re-export

Module A:

```axiom id="j3s6qm"
pub struct User
```

Module B có thể:

```axiom id="u8c4vp"
pub use A.User
```

Ý nghĩa:

```text id="n6y2br"
B.User
```

là public route tới cùng type identity.

Không tạo type mới.

# 14. Re-export và dependency API

Package có thể tổ chức:

```text id="z9c3hk"

    parser
    lexer
    ast

public/
    api
```

và:

```axiom id="a5f7nx"
pub use internal.parser.Parser
```

External users chỉ thấy:

```text id="e4k8wm"
api.Parser
```

Compiler vẫn biết underlying identity.

---

# 15. Cyclic module dependency

Tôi đề xuất:

```text id="f8m1vq"
module A imports B
module B imports A
```

**được phép ở mức type/interface nếu không tạo initialization cycle**, nhưng cần cẩn thận.

Ví dụ:

```text id="d7w2ks"
A defines struct A { b: B }
B defines struct B { a: A }
```

Nếu value-by-value trực tiếp:

```text id="q5r9nc"
A contains B
B contains A
```

thì layout vô hạn.

Compiler phải reject.

Nhưng:

```text id="h3x6vt"
A contains Box<B>
B contains Box<A>
```

có thể hợp lệ vì indirection phá vòng layout.

# 16. Module dependency và type dependency khác nhau

Compiler nên phân biệt:

```text id="k1q8sj"
Name dependency
Type dependency
Value dependency
Initialization dependency
```

Ví dụ:

```text id="x4n6vp"
A uses type B
```

không nhất thiết có runtime dependency.

Nhưng:

```text id="r7m2cz"
A global initializer calls B.init()
```

tạo runtime initialization dependency.

Đây là distinction cực quan trọng.

# 17. Compile-time interface

```text id="u5v9kx"
    public traits
    public constants
    public generic definitions
```

# 18. Semantic Interface Fingerprint

Ví dụ:

```text id="v3m7pa"

```

```text id="s1n9wd"

```

Dependent module không nhất thiết rebuild.

# 19. Nhưng generic implementation khác

Nếu:

```axiom id="k2r8vf"
pub fn max<T: Ord>(a: T, b: T) -> T
```

thay đổi generic body, dependent code có thể cần re-specialize.

SIF phải bao gồm:

```text id="h7m4qs"
generic semantic definition fingerprint
```

chứ không chỉ function signature.

# 20. Trait interface




# 26. Global variables

Đây là phần quan trọng.

Tôi đề xuất Axiom cho:

```axiom id="y7k3vc"
static COUNTER: Atomic<i64> = Atomic(0);
```

nhưng **không có implicit mutable global**.

Ví dụ:

```axiom id="c4m8zx"
var counter: i64 = 0;
```

ở module scope:

→ **không hợp lệ**.

Muốn global mutable state:

```axiom id="v2n6rq"
static mut COUNTER: i64 = 0;
```

và đây phải là unsafe/system-level.


Nếu:



# 29. `const` và `static`

# 35. Có thể có lazy static



# 36. Static Drop

Đây là một vấn đề khó.

Nếu:

```axiom id="n7c3xm"
static RESOURCE: Resource = ...
```

và `Resource: Drop`:

Khi process kết thúc, có nên gọi Drop?

Tôi đề xuất:

> **Không có guaranteed global destruction trong Core v0.1.**

Lý do:

- OS sẽ reclaim process memory;
- shutdown order phức tạp;
- dependency cycles;
- threads có thể đã dừng;
- FFI shutdown ordering;
- freestanding không có process runtime.

Nếu resource cần cleanup:

```axiom id="c8m2qv"
main()
 ↓
shutdown()
```

phải explicit.

---

# 37. Nhưng OS resource thì sao?

Ví dụ socket/file.

Không nên dựa vào:

```text id="s1v7kc"
static File Drop
```

để flush/close khi process exit.

API nên có:

```axiom id="r9q4mx"
fn shutdown() -> Result<(), Error>
```

và programmer kiểm soát.

OS vẫn reclaim file descriptors/process resources khi process chết, nhưng semantic correctness của application không dựa vào đó.

# 50. Module invariants

### AMOD-01 — Module Is Semantic Namespace
Module không phụ thuộc physical file layout.

### AMOD-02 — Import Is Semantic
Import không phải textual inclusion.

### AMOD-03 — Private by Default
Symbol private mặc định.

### AMOD-04 — Public ≠ Linker Export
Visibility và native symbol export tách biệt.

### AMOD-05 — Stable Identity
Re-export không tạo type identity mới.

### AMOD-06 — No Implicit Module Execution
Import module không chạy initialization code.

### AMOD-07 — Interface Fingerprint
Incremental compilation dựa trên semantic interface.

### AMOD-08 — Dependency Separation
Type dependency và runtime initialization dependency tách biệt.

### AMOD-09 — No Hidden Global Constructors
Core không có implicit static initialization graph.

### AMOD-10 — Global Mutable State Explicit
Mutable global state phải explicit và subject to safety rules.

### AMOD-11 — Static Initialization Compile-Time
Core static initialization mặc định phải compile-time evaluable.

### AMOD-12 — Global Destruction Not Guaranteed
Không dựa vào global Drop để đảm bảo shutdown correctness.

# 51. Điều này tạo ra một startup model rất sạch

Chương trình nhỏ:

```axiom id="e8q2m1"

}
```

có thể compile thành:

```text id="w3k7vp"

    call main

```

Trong khi chương trình lớn:

```text id="n5c8qx"

 ├── init_logging()

 ├── init_network()
 └── run()
```

runtime complexity đến từ **những capability thực sự được sử dụng**, không phải vì ngôn ngữ ép mọi executable mang theo runtime.

Đây chính là **Capability-Driven Runtime** mà ta đã đặt làm nền tảng.

# 52. Một điều rất đáng chú ý

Axiom hiện đang hình thành một nguyên tắc thống nhất ở rất nhiều tầng:

```text id="q9m3vx"
GLOBAL:
    no hidden initialization

MEMORY:
    no hidden allocation

OWNERSHIP:
    no hidden shared ownership

CONCURRENCY:
    no hidden synchronization

ERROR:
    no hidden exception propagation

DISPATCH:
    no hidden dynamic dispatch

RUNTIME:
    no hidden runtime component
```

Nhưng đồng thời:

```text id="z4k8qp"
COMPILER:
    can infer
    can optimize
    can specialize
    can eliminate
    can choose representation
```

Đây có lẽ là một trong những **đặc trưng kiến trúc mạnh nhất của Axiom**:

> **Không bắt programmer trả giá cho abstraction mà compiler có thể chứng minh và xóa bỏ; nhưng cũng không tự ý đưa runtime semantics vào chương trình mà source không yêu cầu.**

---

## Phần tiếp theo nên chốt: `Memory Access + Pointer + Slice + FFI` ở mức machine model

Chúng ta đã có `view<T>`, `mut_view<T>`, raw pointer, region và ownership, nhưng chưa khóa hoàn toàn **pointer semantics**.

Tôi muốn xử lý rất kỹ:

```text
Value
  ↓
view<T>
  ↓
raw pointer
  ↓
address
```

đặc biệt:

- pointer provenance;
- pointer arithmetic;
- pointer → integer và ngược lại;
- null;
- dangling pointer trong `unsafe`;
- alignment;
- volatile;
- memory-mapped I/O;
- `view<T>` từ raw pointer;
- slice representation;
- FFI pointer;
- `restrict`-like optimization;
- alias analysis;
- liệu Axiom có cần một kiểu `addr` riêng hay không.

Đây sẽ là phần quyết định Axiom có thực sự đủ sức viết **OS/kernel, driver, allocator, renderer, game engine, database engine** hay chỉ mạnh ở application-level.
