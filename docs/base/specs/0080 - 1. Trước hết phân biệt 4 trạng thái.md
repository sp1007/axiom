Tiếp tục. Phần này tôi nghĩ nên chốt thành **Axiom Initialization & Destruction Model v0.1**. Nó là mảnh ghép nối `Move / Drop / Result / panic / async / struct` lại với nhau.

Mục tiêu là:

> **Không có object ở trạng thái “nửa sống nửa chết” trong safe code, nhưng programmer cũng không phải viết constructor/destructor/lifetime ceremony.**

---

# 1. Trước hết: phân biệt 4 trạng thái

Một local không nên chỉ có `alive/dead`.

Compiler cần trạng thái:

```text id="x6e8ov"
UNINIT
   │
   ▼
INITIALIZED
   │
   ├── MOVE ──► MOVED
   │
   └── DROP ──► DROPPED
```

Với struct:

```text id="7i8m6p"
Foo {
    a: A
    b: B
    c: C
}
```

có thể có:

```text id="vqjwmx"
Foo
├── a = initialized
├── b = initialized
└── c = uninitialized
```

trong quá trình khởi tạo.

Nhưng trạng thái này chỉ tồn tại **bên trong compiler**.

---

# 2. Programmer không nên được phép sử dụng partial object

Ví dụ:

```axiom id="i7gkcs"
var x: Foo

x.a = create_a()
x.b = create_b()

use(x)
```

Nếu `c` chưa initialized:

```text id="fb0p5r"
ERROR
```

Không được phép coi `x` là một `Foo` hoàn chỉnh.

Nhưng:

```axiom id="tgj8b3"
var x: Foo

x.a = create_a()
x.b = create_b()
x.c = create_c()

use(x)
```

thì:

```text id="jy37c2"
Foo = fully initialized
```

---

# 3. Nhưng Axiom nên cho phép field-by-field initialization

Tôi không muốn bắt buộc:

```axiom id="xq56bb"
Foo.create(a, b, c)
```

mọi lúc.

Ví dụ low-level code rất hay cần:

```axiom id="yk5hja"
var packet: Packet

packet.header = ...
packet.length = ...
packet.payload = ...
```

Compiler theo dõi:

```text id="0ebh80"
packet.header  INIT
packet.length  INIT
packet.payload INIT
```

đến khi:

```text id="0pxnzw"
FULLY_INITIALIZED
```

mới cho phép:

```text id="0h8z3u"
use(packet)
```

# 4. Nếu return giữa chừng thì sao?

Đây là chỗ Drop trở nên quan trọng.

```axiom id="8oqd5g"
fn make() -> Result<Foo, Error> {
    var x: Foo

    x.a = create_a()?
    x.b = create_b()?
    x.c = create_c()?

    return Ok(x)
}
```

Nếu:

```text id="g82tgn"
create_c()
```

fail:

```text id="kvxqjh"
x.a initialized
x.b initialized
x.c uninitialized
```

Compiler phải generate:

```text id="prkzrh"
drop x.b
drop x.a
return Err(...)
```

Không được:

```text id="1zfrf0"
drop x.c
```

vì `c` chưa tồn tại.

---

# 5. Đây chính là Partial Drop

Ví dụ:

```text id="4fqlwb"
Foo
├── a OWNED
├── b OWNED
└── c UNINIT
```

khi scope kết thúc:

```text id="9c9qyp"
DROP b
DROP a
```

Không drop `c`.

Nếu:

```text id="b1r6z8"
Foo
├── a OWNED
├── b MOVED
└── c OWNED
```

thì:

```text id="yplx3m"
DROP c
DROP a
```

`b` không được drop lần nữa.

Đây phải là invariant compiler, không phải programmer responsibility.

# 6. Struct Drop nên được tổng hợp tự động

Giả sử:

```axiom id="lq7tjm"
struct User {
    name: Text
    age: i32
    file: File
}
```

Không cần programmer viết:

```text id="w2gq3c"
~User()
```

Compiler biết:

```text id="z2xk8r"
Drop(User)
    ↓
Drop(file)
Drop(name)
```

theo dependency/initialization order.

`i32` không có Drop nên không làm gì.

# 7. Nhưng cần cho phép custom Drop

Một số resource cần cleanup đặc biệt:

```axiom id="a8s6wt"
struct MutexGuard { ... }
struct File { ... }
struct GpuBuffer { ... }
```

Có thể có:

```axiom id="7s3w6k"
impl Drop for File {
    fn drop(self) {
        ...
    }
}
```

Nhưng tôi đề xuất `Drop` có các giới hạn mạnh:

- không được recoverable-error;
- không được trả `Result`;
- không được move ownership ra ngoài;
- không được gọi `drop(self)` lần thứ hai;
- không được làm object sống lại;
- không được gây undefined behavior trong safe implementation.

# 8. `Drop` không phải `close`

Điểm này nên freeze thật rõ.

```text id="h5t1e8"
Drop
  = guaranteed cleanup

close()
  = explicit fallible operation
```

Ví dụ file:

```axiom id="f9w2cb"
file.write(data)?
file.close()?
```

Nếu programmer quên:

```text id="3w4w9j"
scope exit
    ↓
Drop(file)
```

nhưng nếu `close()` có lỗi:

```text id="4n5s6m"
close() -> Result
```

thì lỗi phải được xử lý trước.

Không được:

```text id="g2ak0d"
Drop() -> Result
```

vì điều này làm cleanup graph trở nên cực kỳ phức tạp.

---

# 9. `?` phải tích hợp trực tiếp với partial Drop

Ví dụ:

```axiom id="0kl9v4"
fn load() -> Result<Data, Error> {
    let a = open_a()?
    let b = open_b()?
    let c = open_c()?

    return build(a, b, c)
}
```

Nếu `open_c()` thất bại:

```text id="g3b7m4"
a = OWNED
b = OWNED
c = UNINIT
```

lowering:

```text id="i9gc5u"
call open_c
  │
  ├── Ok(c)
  │      ↓
  │    continue
  │
  └── Err(e)
         ↓
       drop(b)
         ↓
       drop(a)
         ↓
       return Err(e)
```

Không cần exception runtime.

---

# 10. `return` cũng là cleanup

Ví dụ:

```axiom id="e3p1x9"
fn f() -> i32 {
    let file = open()

    if condition {
        return 10
    }

    return 20
}
```

Semantic:

```text id="d6l0a3"
return 10
   ↓
drop(file)
   ↓
return 10
```

và:

```text id="8gk6f9"
return 20
   ↓
drop(file)
   ↓
return 20
```

Compiler có thể optimize cleanup nếu resource không cần runtime action.

# 11. `break` và `continue` cũng vậy

```axiom id="2u7t7q"
while cond {
    let guard = lock()

    if done {
        break
    }

    if skip {
        continue
    }
}
```

`break`:

```text id="3e4x6s"
drop(guard)
↓
exit loop
```

`continue`:

```text id="9oyk7v"
drop(guard)
↓
next iteration
```

Đây phải là semantic invariant.

---

# 12. `panic` cũng phải cleanup

Nếu panic profile là unwind:

```text id="i5yydm"
panic
 ↓
cleanup
 ↓
unwind
```

Nếu:

```text id="1o9bwl"
--panic=abort
```

thì chương trình terminate và không cần unwind toàn bộ stack.

Nhưng compiler không được biến:

```text id="3yn9fd"
normal return
```

thành abort để bỏ qua Drop.

# 13. Drop order

Tôi đề xuất rule đơn giản:

### Local variables

Reverse successful initialization order.

```axiom id="m2m1zq"
let a = A()
let b = B()
let c = C()
```

→

```text id="h8y6s4"
drop(c)
drop(b)
drop(a)
```

### Struct fields

Reverse field initialization/dependency order.

Đây quan trọng hơn việc đơn giản dùng source declaration order, vì Axiom cho phép field initialization linh hoạt.

Compiler có thể canonicalize thành một **drop dependency order**.

# 14. Partial move

Ví dụ:

```axiom id="l9c2v7"
let user = User {
    name: ...,
    file: ...
}

let file = user.file
```

Nếu `User` không Copy:

```text id="f1t0a8"
user
├── name = OWNED
└── file = MOVED
```

Khi scope kết thúc:

```text id="w8g4o1"
drop(name)
```

Không drop `file`.

Đây là một trong những lý do compiler phải có ownership tree.

# 15. Nhưng tôi không muốn syntax destructuring trở nên nguy hiểm

Ví dụ:

```axiom id="j9l8y3"
let User { name, file } = user
```

Compiler phải biết:

```text id="l6k8h2"
name → moved
file → moved
user → PARTIALLY_MOVED / fully moved
```

Nếu toàn bộ field đã move:

```text id="1zq8cx"
user = MOVED
```

Nếu còn field:

```text id="7kq1yb"
user = PARTIAL
```

# 16. Assignment là nơi dễ có bug nhất

Ví dụ:

```axiom id="0r2x8s"
a = b
```

Nếu `a` đang sở hữu resource:

```text id="q5t4kp"
a = old resource
b = new resource
```

không được đơn giản:

```text id="v4m7hy"
a ← b
```

mà phải semantic:

```text id="0c4f1v"
evaluate RHS
      ↓
move b
      ↓
drop old a
      ↓
store new value into a
```

Tuy nhiên compiler phải xử lý alias/self-assignment.

# 17. Self-assignment

Nếu:

```axiom id="n6y8zz"
x = x
```

với Copy:

```text id="6p4g6x"
allowed
```

nhưng với owning non-Copy:

```text id="4a9u0v"
x = move(x)
```

phải được xử lý rõ.

Tôi đề xuất:

> **Self-move của non-Copy là compile error.**

Không cố tạo semantics kỳ quặc.

# 18. `var` và `let`

```text id="9c8x4q"
var
```

= binding có thể được gán lại.

# 21. Arrays cũng cần partial initialization

Ví dụ low-level:


Nếu khởi tạo từng phần:


# 24. `Drop` + async

Đây là chỗ mô hình này rất mạnh.

```axiom id="p8y3w4"
async fn process() {
    let file = open()

    await read()

    use(file)
}
```

Compiler state machine:

```text id="z5x7vn"
FutureState {
    state,
    file
}
```

Khi future complete:

```text id="7p3j8q"
use(file)
↓
Drop(file)
↓
Future finished
```

Nếu future bị cancellation:

```text id="6k8n2p"
cancel
↓
drop live owned state
```

với cancellation semantics của executor.

Không cần một garbage collector.

# 25. Một vấn đề cần quyết định: cancellation có đảm bảo Drop không?

Tôi đề xuất:

### Safe structured task

```text
cancellation
    ↓
task cleanup
    ↓
Drop live owned resources
```

### Process abort / power loss / OS kill

Không đảm bảo.

Điều này giống bản chất hệ thống:

> Drop là language-level deterministic cleanup, không phải bảo đảm thế giới bên ngoài luôn cho chương trình chạy cleanup.

# 33. Invariant nên freeze

### AINIT-01 — No Use Before Initialization

Safe code cannot observe an uninitialized value.

### AINIT-02 — Partial Initialization Is Compiler-Tracked

The compiler tracks initialized subobjects independently.

### AINIT-03 — Partial Drop

Only successfully initialized owned subobjects are destroyed.

### AINIT-04 — Move Invalidates Ownership

Moved values cannot be used or dropped twice.

### AINIT-05 — Drop Is Deterministic

Owned resources are released at deterministic scope/control-flow boundaries.

### AINIT-06 — Drop Does Not Return Recoverable Errors

Fallible cleanup belongs to explicit operations such as `close()`.

### AINIT-07 — Return Runs Cleanup

All required cleanup occurs before normal return.

### AINIT-08 — Structured Exit Runs Cleanup

`break`, `continue`, and equivalent exits perform required cleanup.

### AINIT-09 — Panic Cleanup

Unwinding executes required cleanup; abort mode does not promise full cleanup after process termination.

### AINIT-10 — No Implicit Default Initialization

Types without a defined valid default value are not automatically initialized.

### AINIT-11 — Valid Representation Required

Initialized values must satisfy the representation validity rules of their type.

### AINIT-12 — Constructor Is Ordinary Code

Constructors are functions/expressions, not a mandatory object-system primitive.

### AINIT-13 — Destructor Is Resource Semantics

`Drop` is deterministic resource cleanup, not object-oriented destruction semantics.

### AINIT-14 — Self-Move Is Invalid

Moving a non-Copy value into itself is rejected.

### AINIT-15 — Initialization and Ownership Are Independent Analyses

The compiler tracks initialization state separately from ownership state.

## 34. Sau phần này, Axiom đã có một memory model khá hoàn chỉnh

Ta hiện có:

```text
                     AXIOM MEMORY
                          │
          ┌───────────────┼────────────────┐
          │               │                │
        VALUE          STORAGE          ACCESS
          │               │                │
     Copy / Move       Identity         READ
                       Relocation        WRITE
                       Stable            MOVE
                          │                │
                          │            Capability
                          │                │
                          └───────┬────────┘
                                  │
                              LIFETIME
                                  │
                    ┌─────────────┴─────────────┐
                    │                           │
              INITIALIZATION               CONCURRENCY
                    │                           │
                Drop/cleanup               Atomic/Mutex
                    │                           │
                    └─────────────┬─────────────┘
                                  │
                              UNSAFE/FFI
```

Điểm đáng chú ý là **không cần GC, không cần borrow syntax, không cần class/destructor hierarchy, không cần implicit reference counting** mà vẫn có thể định nghĩa rất chặt semantics.

### Phần tiếp theo tôi đề xuất đi vào một vấn đề còn lớn hơn: **Object Model & Data Layout**

Không phải class/object theo kiểu OOP, mà là:

- struct layout mặc định;
- field reordering;
- padding;
- alignment;
- zero-sized type;
- enum/niche;
- union;
- bit-level representation;
- `repr(C)`;
- transparent newtype;
- packed data;
- SIMD;
- AoS vs SoA;
- cache locality;
- false sharing;
- ABI.

Phần này sẽ quyết định Axiom có thực sự cho compiler **tự do tối ưu representation như C nhưng vẫn giữ FFI/layout control khi cần** hay không.
