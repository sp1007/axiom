## ERROR-001 — Error, Result, Panic & Failure Model

Ta khóa phần này theo cùng triết lý của Axiom:

> **Recoverable failure là value. Fatal failure là control flow. Resource cleanup vẫn deterministic.**

Không đưa exception runtime kiểu C++ vào Core.

---

# 1. Ba loại failure phải tách biệt

Axiom nên phân biệt rõ:

```text
Recoverable Error
        │
        ▼
   Result<T,E>

Absence
        │
        ▼
   Option<T>

Fatal Program Failure
        │
        ▼
 panic / trap / abort
```

Không dùng một cơ chế duy nhất cho tất cả.

### Ví dụ

```axiom
fn read_file(path: StringView) -> Result<File, IoError>
```

File không tồn tại → `Err`.

```axiom
fn find_user(id: UserId) -> Option<User>
```

Không tìm thấy → `None`.

```axiom
assert(index < len)
```

Invariant chương trình bị phá vỡ → `panic`/`trap`.

---

# 2. `Result<T,E>`

Semantic:

```axiom
enum Result<T, E> {
    Ok(T),
    Err(E),
}
```

Nhưng đây chỉ là cách biểu diễn logic.

Compiler có thể tối ưu representation.

Ví dụ:

```axiom
fn divide(a: i32, b: i32) -> Result<i32, MathError>
```

có thể lower thành:

```text
result register
error flag/register
branch
```

Không bắt buộc heap allocation.

Không bắt buộc runtime.

---

# 3. `Option<T>`

```axiom
enum Option<T> {
    Some(T),
    None,
}
```

Không có `null` trong safe core.

Nhưng compiler được phép dùng **niche optimization**.

Ví dụ:

```axiom
Option<*mut T>
```

hoặc các type có trạng thái không hợp lệ có thể được biểu diễn bằng bit pattern đặc biệt.

Điều này là optimization, không phải programmer-visible representation.

---

# 4. `?` — error propagation

Đây nên là một trong những cú pháp quan trọng nhất của Axiom.

```axiom
fn load_config() -> Result<Config, Error> {
    let text = read_file("config.toml")?
    let cfg = parse_config(text)?
    return Ok(cfg)
}
```

Semantics:

```text
Ok(x)  → unwrap and continue
Err(e) → return Err(e)
```

Compiler lower trực tiếp thành control flow.

Không:

```text
throw
catch
stack unwinding
exception object
```

trong trường hợp thông thường.

---

# 5. `?` không phải magic runtime

Ví dụ:

```axiom
let x = foo()?
bar(x)
```

MIR có thể thành:

```text
r = call foo()

switch r.tag:
    OK  → x = r.value
          goto next

    ERR → return r.error

next:
    call bar(x)
```

Optimizer có thể tiếp tục:

- eliminate temporary
- merge branches
- propagate error
- tail-return
- register allocation

Kết quả thường gần như code C viết thủ công.

---

# 6. Error conversion

Axiom nên cho phép:

```axiom
let x = foo()?
```

khi `foo()` trả:

```text
Result<T, E1>
```

nhưng function hiện tại cần:

```text
Result<U, E2>
```

chỉ khi có conversion hợp lệ:

```text
E1 → E2
```

thông qua trait/library mechanism.

Ví dụ:

```axiom
impl From<ParseError> for ConfigError
```

Compiler thực hiện conversion tại `?`.

Không có implicit conversion tùy tiện.

---

# 7. Không dùng exception để thay thế Result

Không nên có:

```axiom
try {
    foo()
}
catch e {
    ...
}
```

trong Core v1.

Lý do:

- hidden control flow
- khó dự đoán cost
- khó tối ưu
- ABI phức tạp
- khó freestanding
- khó kernel/GPU
- khó AI/compiler reasoning
- dễ biến mọi function thành potentially-throwing

Axiom ưu tiên:

```text
Result = explicit data flow
panic = exceptional control flow
```

---

# 8. Nhưng panic vẫn cần tồn tại

Có những failure không hợp lý để trả `Result`.

Ví dụ:

```axiom
let x = array[999]
```

nếu compiler không chứng minh được bounds.

Hoặc:

```axiom
assert(ptr != null)
```

Trong safe code, đây không phải recoverable business error.

Dùng:

```text
panic
```

---

# 9. Panic không phải exception

Panic là **fatal/unrecoverable control-flow mechanism**, không phải general exception mechanism.

Profile có thể chọn:

```text
abort
unwind
custom
```

### Freestanding

```text
panic → abort/trap
```

### Hosted debug

có thể:

```text
panic → unwind
```

nếu runtime profile bật unwind.

---

# 10. Panic strategy phải là compilation profile

Ví dụ:

```text
--panic=abort
--panic=unwind
```

Nhưng semantics của source code không thay đổi.

`Drop` vẫn phải được xử lý đúng nếu profile là unwind.

---

# 11. Panic unwind

Nếu:

```axiom
fn foo() {
    let a = acquire_a()
    let b = acquire_b()

    panic()
}
```

với unwind profile:

```text
panic
 ↓
drop(b)
 ↓
drop(a)
 ↓
unwind caller
```

Không được bỏ qua resource cleanup.

---

# 12. Panic trong Drop

Không nên cho phép một `Drop` thông thường tạo thêm recoverable failure.

Đặc biệt trong unwind:

```text
panic
 ↓
Drop A
 ↓
Drop A panic
```

sẽ tạo nested failure rất nguy hiểm.

Quy tắc:

> **Drop là non-fallible.**

Nếu cleanup có thể thất bại:

```axiom
file.close() -> Result<(), IoError>
```

phải được gọi explicit.

Ví dụ:

```axiom
let file = open(path)?

file.write(data)?
file.close()?
```

`Drop` sau đó chỉ là fallback resource release.

---

# 13. `drop(x)` explicit

Axiom vẫn hỗ trợ:

```axiom
drop(file)
```

nhưng semantics là:

> kết thúc ownership/resource lifetime semantic của `file`.

Không đảm bảo:

```text
free()
```

ngay lập tức.

Điều này phù hợp với memory model hiện tại.

---

# 14. Allocation failure

Không nên để:

```text
allocation failure → hidden panic
```

là semantic duy nhất.

Standard library API nên có profile/strategy rõ ràng.

Ví dụ:

```axiom
Vec.try_reserve(n) -> Result<(), AllocError>
```

và có thể:

```axiom
Vec.reserve(n)
```

cho API có policy panic-on-failure.

Như vậy programmer chọn semantic phù hợp.

---

# 15. Hai API allocation

Nên có pattern:

```text
try_* → Result
normal → profile/library-defined failure policy
```

Ví dụ:

```axiom
let v = Vec.try_with_capacity(1024)?
```

hoặc:

```axiom
let v = Vec.with_capacity(1024)
```

API thứ hai có thể panic nếu allocation không thể đáp ứng.

---

# 16. Không có hidden exception object

Một điểm quan trọng:

```text
Result<T,E>
```

không cần:

```text
heap allocation
exception object
stack trace object
runtime registry
```

Error có thể là:

```axiom
enum IoError {
    NotFound,
    PermissionDenied,
    ...
}
```

rất nhỏ.

Compiler có thể trả trực tiếp trong register.

---

# 17. Error type nên ưu tiên enum

Ví dụ:

```axiom
enum FileError {
    NotFound,
    PermissionDenied,
    InvalidPath,
    Io(IoError),
}
```

Pattern matching:

```axiom
match open(path) {
    Ok(file) => use(file),
    Err(FileError.NotFound) => create_default(),
    Err(e) => return Err(e),
}
```

Compiler biết exhaustive cases.

---

# 18. Error payload có thể lớn

Không phải error nào cũng nhỏ.

Ví dụ:

```axiom
struct ParseError {
    position: usize,
    message: String,
}
```

Axiom không ép error phải nằm trong register.

ABI/compiler có thể sử dụng:

```text
return slot
caller-provided storage
hidden return pointer
```

tùy target.

---

# 19. Error và ownership

`Result<T,E>` phải tuân thủ ownership bình thường.

Ví dụ:

```axiom
let r = acquire()
```

Nếu:

```text
Ok(resource)
```

resource thuộc `Result`.

Nếu:

```text
Err(error)
```

resource không tồn tại.

Không có hidden ownership transfer.

---

# 20. `Result<T,E>` không được Copy tùy tiện

Nếu `T` hoặc `E` có ownership:

```text
Result<T,E>
```

thường cũng non-Copy.

Compiler áp dụng trait derivation.

Ví dụ:

```axiom
let a = foo()
let b = a
```

là Move nếu `Result` không Copy.

---

# 21. `Option<T>` cũng tương tự

```axiom
Option<Box<T>>
```

không Copy.

```axiom
Option<i32>
```

có thể Copy.

Compiler không cần special-case quá nhiều ở semantic layer.

---

# 22. `panic!` và `assert`

Nên có:

```axiom
panic("message")
assert(condition)
debug_assert(condition)
```

Nhưng `assert` nên là compiler/library intrinsic có thể:

```text
debug profile → giữ
release profile → giữ hoặc loại nếu compiler chứng minh/được cấu hình
```

Không được tùy tiện loại bỏ một assertion có observable semantics nếu profile yêu cầu giữ.

---

# 23. `unreachable`

Có:

```axiom
unreachable()
```

nhưng đây là semantic assertion:

> control flow không được tới đây.

Nếu tới:

```text
panic/trap/UB boundary?
```

Axiom nên **không biến safe `unreachable()` thành UB**.

Khuyến nghị:

```text
safe unreachable → trap/panic
unsafe compiler intrinsic → machine unreachable
```

Như vậy optimizer vẫn có primitive mạnh trong unsafe/compiler-internal code.

---

# 24. Integer overflow

Phần này phải gắn với error model.

Axiom không dùng C-style signed overflow UB.

Các operation rõ ràng:

```axiom
a + b
a.checked_add(b)
a.wrapping_add(b)
a.saturating_add(b)
```

Default `+` nên phụ thuộc profile nhưng semantic phải xác định.

Khuyến nghị mạnh:

```text
Debug/default safety → checked/trap
Release → defined wrapping hoặc compiler-selected defined behavior
```

Tuy nhiên tốt hơn nữa là khóa một semantics duy nhất:

> **Primitive arithmetic có defined semantics ở mọi profile.**

Ví dụ signed overflow:

```text
panic/trap
```

và nếu muốn modulo:

```axiom
wrapping_add
```

Như vậy optimizer không phải suy đoán dựa vào “UB”.

---

# 25. Đây là khác biệt quan trọng với C/C++

Axiom:

```axiom
let x = a + b
```

compiler **không được giả định**:

```text
a+b cannot overflow
```

chỉ để tối ưu.

Nếu programmer muốn optimizer có assumption mạnh hơn:

```axiom
unsafe {
    assume(...)
}
```

hoặc intrinsic compiler-level sau này.

Không đưa `assume` thành công cụ thường ngày.

---

# 26. `Result` và async

`Result` phải hoạt động hoàn toàn tự nhiên với async:

```axiom
async fn load() -> Result<Data, Error> {
    let a = read_a().await?
    let b = read_b().await?
    Ok(combine(a, b))
}
```

Semantics:

```text
await
 ↓
Pending → suspend
Ready(Err) → return Err
Ready(Ok) → continue
```

Không cần exception runtime.

---

# 27. `Result` và thread

```axiom
let handle = Thread.spawn(fn() -> Result<Data, Error> {
    ...
})
```

`join()`:

```axiom
let result = handle.join()?
```

có thể phân biệt:

```text
ThreadError
Result<Data, Error>
```

Ví dụ:

```text
join
 ├── thread execution failure
 └── user function Result
```

Không được nhập nhằng hai tầng lỗi.

---

# 28. Thread panic

Nếu thread panic:

```axiom
let r = handle.join()
```

có thể:

```text
Err(ThreadError::Panicked)
```

nếu panic profile cho phép quan sát panic.

Như vậy panic trong worker không nhất thiết làm process chết ngay.

Nhưng nếu profile là global abort:

```text
panic → process termination
```

đó là profile semantic policy.

---

# 29. FFI errors

C ABI không nên expose trực tiếp:

```text
Result<T,E>
```

trừ khi cả hai bên biết Axiom ABI.

Ví dụ C-compatible:

```axiom
@repr(C)
struct Status {
    code: i32,
}
```

hoặc:

```axiom
extern "C" fn foo(...) -> i32
```

Sau đó wrapper Axiom:

```axiom
fn foo_safe(...) -> Result<T, Error>
```

---

# 30. Syscall/OS layer

Core không biết:

```text
ENOENT
EAGAIN
HRESULT
Win32 error
NSError
```

Standard/platform library chuyển chúng thành error type phù hợp.

Ví dụ:

```text
OS errno
   ↓
platform error
   ↓
Axiom IoError
   ↓
Result<T, IoError>
```

---

# 31. GPU

`@kernel` không nên có panic/unwind.

GPU kernel phải thuộc execution profile hạn chế:

```text
Result
```

có thể được hỗ trợ nếu backend cho phép.

Nhưng:

```text
panic
unwind
filesystem
thread spawn
```

không hợp lệ trong kernel.

Bounds violation trong kernel nên:

```text
debug → trap
release → configured behavior
```

với semantics explicit.

---

# 32. Error propagation và zero-cost abstraction

Mục tiêu compiler:

```axiom
fn foo() -> Result<i32, E> {
    let a = bar()?
    let b = baz(a)?
    Ok(b + 1)
}
```

có thể trở thành:

```text
call bar
branch error
call baz
branch error
add
return
```

Không:

```text
allocate error object
register exception
stack metadata
try/catch frame
```

nếu panic/unwind không liên quan.

---

# 33. `Result` nên được compiler hiểu ở mức tối ưu

Không nhất thiết biến `Result` thành Core primitive type.

Nhưng compiler nên nhận diện algebraic data type + branch patterns để tối ưu:

```text
Result
Option
enum
```

Ví dụ niche optimization, branch folding, payload placement.

Điều này vẫn giữ:

> **One semantic question, one mechanism.**

`Result` chỉ là enum.

---

# 34. Error effects không đưa vào Core

Ta **không nên** làm:

```axiom
fn foo() throws IOError
```

hoặc:

```text
fn foo() !IOError
```

ở type level.

`Result<T,E>` đã thể hiện recoverable failure.

Panic không cần xuất hiện trong function type.

Điều này giữ function type đơn giản.

---

# 35. Nhưng tooling vẫn có thể biết panic

Compiler có thể phân tích:

```text
may_panic
```

như diagnostic/static analysis metadata.

Không biến nó thành type-level effect bắt buộc.

Ví dụ IDE có thể báo:

```text
This function may panic because:
  array indexing at foo.ax:31
```

Đó là analysis/tooling, không phải language type system.

---

# 36. `catch_unwind`?

Không đưa vào Core v1.

Nếu unwind runtime tồn tại, standard library có thể cung cấp mechanism để boundary bắt panic trong những profile phù hợp.

Nhưng đây phải là **advanced runtime facility**, không phải cách xử lý lỗi thông thường.

---

# 37. Failure hierarchy

Axiom có thể khóa hierarchy:

```text
                     FAILURE
                        │
             ┌──────────┴──────────┐
             │                     │
        Recoverable             Fatal
             │                     │
        Result<T,E>          panic / trap
             │                     │
        Option<T>             abort/unwind
```

`Option` thực ra không phải error; nó là **absence**. Nhưng API-level nó nằm cùng nhánh explicit outcome.

---

# 38. Quy tắc API rất quan trọng

Standard library nên tuân:

```text
try_*       → Result
*_or_none   → Option
normal API  → defined failure policy
assert      → programmer invariant
panic       → unrecoverable failure
unsafe      → caller assumes machine-level precondition
```

Ví dụ:

```axiom
Vec.try_reserve()
Vec.reserve()

Map.get() -> Option<&V>
Map.require() -> Result<&V, Error>
```

Tên cụ thể có thể điều chỉnh sau.

---

# 39. Error conversion không được làm mất thông tin

Không implicit:

```text
IoError → String
```

chỉ để thỏa type.

Conversion phải explicit/trait-defined.

Ví dụ:

```axiom
map_error(...)
```

hoặc `From`.

---

# 40. Error messages

`Error` không nên mặc định chứa `String`.

Đây là vấn đề binary size.

Thay vì:

```axiom
struct Error {
    message: String
}
```

có thể dùng:

```axiom
enum Error {
    NotFound,
    PermissionDenied,
    InvalidFormat,
}
```

và formatting nằm ở optional library.

Freestanding binary không cần kéo cả Unicode formatting/runtime chỉ vì error handling.

---

# 41. Embedded/freestanding

Axiom phải cho phép:

```axiom
fn main() -> never {
    ...
}
```

hoặc entry point không có standard error runtime.

Ví dụ embedded:

```text
Result
Option
enum
match
```

vẫn hoạt động bình thường.

`panic` có thể:

```text
trap
```

không cần OS.

---

# 42. Compiler IR

Error handling nên lower qua CFG bình thường.

Ví dụ:

```text
HIR:
    foo()?

MIR:
    %r = call foo
    switch_result %r
        Ok   -> ...
        Err  -> return

```

Không cần exception edge trong MIR cho `Result`.

Panic/unwind là một control-flow mechanism riêng.

---

# 43. Drop + Result

Ví dụ:

```axiom
fn foo() -> Result<Data, Error> {
    let a = acquire()?
    let b = acquire2()?
    return Ok(make_data(a, b))
}
```

Nếu `acquire2()` fail:

```text
a
 ↓
Drop(a)
 ↓
return Err
```

Compiler tự insert Drop.

Đây là một điểm cực kỳ quan trọng:

> **`?` không phá vỡ deterministic destruction.**

---

# 44. `?` trong destructor-sensitive code

Ví dụ:

```axiom
let file = open(path)?
let buffer = allocate()?
process(file, buffer)?
```

Mỗi failure point đều có implicit cleanup.

MIR:

```text
call open
  Err → return

call allocate
  Err → drop(file)
        return

call process
  Err → drop(buffer)
        drop(file)
        return
```

Sau optimization, compiler có thể tối ưu rất mạnh.

# 46. Hai điểm tôi muốn khóa mạnh

### Quyết định 1

**Không có exceptions trong Core.**

Axiom có:

```text
Result
Option
panic
trap
abort
unwind profile
```

nhưng không có C++-style:

```text
throw/catch
```

làm nền tảng ngôn ngữ.

### Quyết định 2

**`?` là control-flow sugar cho Result, không phải exception propagation.**

Đây là yếu tố giúp Axiom vừa ergonomic vừa có khả năng đạt hiệu năng C/C++.

# Bước tiếp theo: TRAIT-001

Sau Error Model, phần cần khóa tiếp theo là **Trait / Generic / Dispatch System**.

Đây là phần đặc biệt quan trọng vì Axiom đã quyết định:

```text
struct + function
        ↓
method syntax
        ↓
trait
        ↓
generic
        ↓
static dispatch
        ↓
dynamic dispatch chỉ khi explicit
```
