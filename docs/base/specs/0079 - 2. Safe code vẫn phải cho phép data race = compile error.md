Tiếp tục với **Memory Ordering + Atomic Model**. Tôi nghĩ đây là một trong những phần Axiom phải thiết kế rất kỹ, vì mục tiêu của bạn là hiệu năng cao nhưng không muốn lập trình viên phải gánh một hệ thống concurrency quá nặng.

## 1. Nguyên tắc lớn: tách 3 vấn đề

Axiom không nên gom tất cả thành “thread safety”.

```text
              CONCURRENCY
                  │
        ┌─────────┼─────────┐
        │         │         │
    Ownership  Visibility  Ordering
        │         │         │
       Send      Atomic    Acquire/
       Share     Sync      Release
```

### Ownership

Ai sở hữu dữ liệu?

### Visibility

Thread A có nhìn thấy thay đổi của thread B không?

### Ordering

Các thao tác trước/sau synchronization được phép quan sát theo thứ tự nào?

Ba thứ này độc lập.

---

# 2. Safe code vẫn phải cho phép data race = compile error

Ví dụ:

```axiom
var x = 0

spawn {
    x += 1
}
```

Nếu `x` được truy cập đồng thời mà không có synchronization:

```text
READ x
WRITE x
```

thì verifier phải từ chối.

Không cần programmer viết:

```text
unsafe
```

chỉ để compiler bỏ qua lỗi.

---

# 3. Nhưng Axiom không nên tự động biến mọi shared variable thành atomic

Ví dụ:

```axiom
var counter = 0
```

không có nghĩa:

```text
Atomic<i64>
```

Nếu programmer muốn lock-free:

```axiom
var counter = Atomic<i64>(0)
```

hoặc abstraction tương đương.

Điều này rất quan trọng đối với performance.

Không có:

```text
implicit atomic
implicit mutex
implicit RC
implicit synchronization
```

trong safe core.

---

# 4. `Send` và `Share` vẫn là hai property riêng

Ta đã chốt:

```text
Send != Share
```

Ví dụ:

```text
T: Send
```

nghĩa:

> ownership của T có thể chuyển sang execution context khác.

Còn:

```text
T: Share
```

nghĩa:

> T có thể được nhiều execution context cùng đọc an toàn.

Không nên suy ra:

```text
Send → Share
```

hoặc:

```text
Share → Send
```

---

# 5. Atomic phải là primitive semantic, nhưng API có thể là library

Compiler cần hiểu:

```text
atomic load
atomic store
atomic RMW
atomic CAS
```

để đảm bảo semantics.

Nhưng source không cần có một ngôn ngữ atomic riêng.

Ví dụ:

```axiom
counter.fetch_add(1, .relaxed)
```

Compiler lowering:

```text
Typed MIR
   ↓
ATOMIC_RMW
   │
   └── op = ADD
       order = Relaxed
```

Sau đó backend quyết định:

```text
lock xadd
```

hoặc instruction tương ứng trên ARM.

---

# 6. Tôi đề xuất 5 memory orders

Axiom v0.1:

```text
Relaxed
Acquire
Release
AcqRel
SeqCst
```

Không cần thêm các biến thể phức tạp.

### Relaxed

Atomicity + modification order, nhưng không tạo synchronization/happens-before.

Dùng cho:

```text
counters
statistics
reference counts ở một số trường hợp
lock-free algorithms
```

---

### Acquire

Một atomic read với Acquire có thể quan sát các thao tác Release tương ứng.

Conceptually:

```text
Thread A                    Thread B

write data
   │
   ▼
store(flag, Release)
                            load(flag, Acquire)
                                  │
                                  ▼
                              read data
```

Nếu synchronization thành công:

```text
write data
    ↓
Release
    ↓
Acquire
    ↓
read data
```

---

### Release

Đảm bảo các thao tác trước đó không bị compiler/CPU reorder vượt qua synchronization boundary theo cách phá semantics.

---

### AcqRel

Cho read-modify-write:

```text
CAS
fetch_add
exchange
```

vừa acquire vừa release.

---

### SeqCst

Sequentially consistent atomic ordering.

Đây nên là:

> semantics mạnh nhất, nhưng không mặc định.

---

# 7. Không có “atomic mặc định”

Ví dụ:

```axiom
var x: Atomic<i64>
```

chỉ xác định atomicity.

Còn:

```axiom
x.load(.relaxed)
x.load(.acquire)
```

mới xác định ordering.

Tôi thích cách này hơn:

```axiom
x.load()
```

tự động chọn memory order.

Vì nếu compiler tự chọn:

```text
Acquire
```

hoặc:

```text
Relaxed
```

thì semantics có thể thay đổi theo optimization.

Axiom phải deterministic.

---

# 8. CAS nên có hai dạng

Ví dụ:

```axiom
compare_exchange(
    expected,
    desired,
    success_order,
    failure_order
)
```

vì memory ordering của success/failure khác nhau.

Nhưng API có thể cung cấp shorthand:

```axiom
compare_exchange_acqrel(...)
```

nếu muốn tiện.

Core semantics vẫn chỉ có:

```text
success_order
failure_order
```

---

# 9. Atomic không đồng nghĩa volatile

Điều này phải freeze cực rõ.

```text
Atomic
    ↓
thread synchronization

Volatile
    ↓
observable memory access
```

MMIO:

```axiom
volatile_store(...)
```

không tự động thread-safe.

Atomic:

```axiom
atomic_store(...)
```

không có nghĩa thiết bị phần cứng sẽ coi nó là MMIO operation hợp lệ.

Invariant:

> **VOLATILE ≠ ATOMIC**

---

# 10. Atomic cũng không tự tạo ownership

Ví dụ:

```axiom
Atomic<*mut Foo>
```

không biến `Foo` thành memory-safe.

Atomic pointer chỉ đảm bảo thao tác trên **pointer value** có atomic semantics.

Nó không chứng minh:

```text
Foo còn sống
Foo không bị use-after-free
Foo không bị concurrent mutation
```

Do đó:

```text
Atomic pointer
```

vẫn là system-level/unsafe territory nếu dùng để quản lý raw memory.

---

# 11. `Arc` cũng không biến dữ liệu thành mutable-safe

Ví dụ:

```axiom
let x = Arc.create(Foo(...))
```

Hai thread có thể cùng sở hữu:

```text
Thread A ─┐
          ├── Arc ── Foo
Thread B ─┘
```

Nếu `Foo` chỉ immutable:

```text
READ + READ = OK
```

Nhưng:

```text
Thread A WRITE
Thread B READ
```

vẫn phải có synchronization.

Vì vậy:

```text
Arc<T>
```

không đồng nghĩa:

```text
Arc<Mutable<T>>
```

an toàn.

---

# 12. Mutex phải giải quyết bằng capability

Ví dụ:

```axiom
let guard = mutex.lock()
guard.value += 1
```

Semantic:

```text
Mutex
  │
  └── lock
       ↓
    exclusive capability
       ↓
    mutable access
```

Khi:

```axiom
guard
```

ra khỏi scope:

```text
Drop(guard)
   ↓
unlock
```

Điều này phù hợp hoàn toàn với ownership model hiện tại.

Không cần:

```text
unlock()
```

bắt buộc bằng tay.

---

# 13. Nhưng Mutex không phải Core primitive về API

Compiler cần hiểu:

```text
LOCK
UNLOCK
```

về effect/concurrency semantics nếu muốn tối ưu và verifier reasoning.

Nhưng:

```text
Mutex<T>
RwLock<T>
Semaphore
ConditionVariable
```

nên nằm ở library/platform.

---

# 14. `RwLock` rất tự nhiên với capability model

```text
read lock
    ↓
READ capability × N
```

và:

```text
write lock
    ↓
WRITE capability × 1
```

Nên:

```text
READ + READ → OK
READ + WRITE → blocked
WRITE + WRITE → blocked
```

về mặt runtime.

Compiler không cần phải biến mọi `RwLock` thành một hệ thống type phức tạp.

---

# 15. Memory ordering và ownership phải bổ sung nhau

Ví dụ channel:

```axiom
channel.send(x)
```

nếu channel transfer ownership:

```text
Thread A
   │
 MOVE x
   │
   ▼
 Channel
   │
   ▼
Thread B
   │
 OWN x
```

Đây vừa là:

```text
ownership transfer
```

vừa có:

```text
synchronization boundary
```

Nhưng programmer không cần tự viết:

```text
atomic store Release
atomic load Acquire
```

Channel implementation đảm nhận.

Đây là một điểm rất hay của Axiom:

> **Low-level atomic primitives tồn tại; high-level synchronization abstractions che giấu chúng khi có thể.**

---

# 16. Thread spawn cũng là synchronization boundary

Ví dụ:

```axiom
let x = Data(...)
spawn(move || process(x))
```

Ownership:

```text
caller
  │
 MOVE
  ▼
task
```

Compiler/runtime phải đảm bảo các semantics cần thiết của task creation.

Không cần programmer tự dựng:

```text
Release
Acquire
fence
```

cho việc truyền ownership bình thường.

---

# 17. Thread join cũng là boundary

```axiom
let handle = spawn(...)
let result = handle.join()
```

Sau `join`:

```text
worker
   │
   ▼
JOIN
   │
   ▼
caller
```

Các effect phù hợp từ thread hoàn thành có thể được quan sát theo semantics của join.

Một lần nữa, programmer không cần trực tiếp điều khiển atomic fence.

---

# 18. Fence không nên xuất hiện thường xuyên

Axiom vẫn nên có:

```text
atomic_fence(order)
```

nhưng thuộc system/low-level API.

Không nên biến:

```text
fence
```

thành một feature thường xuyên trong code application.

---

# 19. Compiler có được reorder atomic không?

Có, nhưng chỉ trong giới hạn memory model.

Ví dụ:

```text
Relaxed
```

cho phép nhiều reorder hơn.

Nhưng compiler **không được** biến:

```text
Acquire
```

thành:

```text
Relaxed
```

chỉ vì thấy “nhanh hơn”.

Tương tự:

```text
Release → Relaxed
```

không hợp lệ nếu làm thay đổi observable synchronization.

---

# 20. Atomic operations phải có side effects

Effect system:

```text
ATOMIC
SYNC
```

Ví dụ:

```text
x.load(Relaxed)
```

có:

```text
ATOMIC
```

nhưng chưa chắc:

```text
SYNC
```

trong nghĩa happens-before.

Còn:

```text
x.load(Acquire)
```

có synchronization semantics.

Điều này giúp optimizer hiểu:

```text
pure expression
```

khác:

```text
atomic expression
```

và không được CSE/DCE tùy tiện.

---

# 21. Compiler có thể optimize atomic khi semantics cho phép

Ví dụ hai phép đọc:

```axiom
let a = x.load(.relaxed)
let b = x.load(.relaxed)
```

Không được mặc định biến thành:

```text
a = b
```

vì atomic value có thể thay đổi giữa hai reads.

Atomic không phải pure expression.

Đây là một điểm optimizer rất dễ sai.

---

# 22. Nhưng non-atomic immutable values có thể tối ưu mạnh

Ví dụ:

```axiom
let x = 10
let y = x + 2
```

thì:

```text
x → 10
y → 12
```

hoàn toàn có thể constant-fold.

Concurrency model chỉ cần bảo vệ những storage/capability thực sự shared.

---

# 23. `volatile` còn mạnh hơn về observability

Ví dụ:

```axiom
volatile_load(mmio)
```

compiler không được:

```text
remove
duplicate
merge
reorder
```

theo cách thay đổi semantics của volatile sequence.

Nhưng volatile ordering giữa các CPU threads không tự động được đảm bảo như atomic synchronization.

# 24. Data race trong unsafe

Safe:

```text
data race → compile error
```

Unsafe:

```axiom
unsafe {
    ...
}
```

cho phép programmer làm những thứ compiler không thể chứng minh.

Nhưng tôi **không** muốn quy tắc:

> `unsafe` = compiler bỏ qua concurrency checking.

Thay vào đó:

```text
unsafe
    ↓
programmer assumes responsibility for unsafe preconditions
```

Compiler vẫn giữ:

```text
type checking
CFG correctness
ABI correctness
representation rules
```

và những invariant mà nó vẫn có thể kiểm chứng.

# 25. Atomic reference counting

Một trường hợp thú vị:

```text
Arc<T>
```

có thể dùng atomic refcount.

Nhưng đó là **library implementation**, không phải language-level RC.

Điều này rất phù hợp với:

> No implicit RC.

Ví dụ chương trình không dùng `Arc`:

```text
binary
```

không phải link atomic reference-counting machinery.

# 28. Memory model tổng thể

Tôi đề xuất Axiom v0.1 chính thức có:

```text
                    MEMORY MODEL
                         │
          ┌──────────────┴──────────────┐
          │                             │
     NON-SHARED                     SHARED
          │                             │
       normal                       atomic
       values                       mutex
       ownership                    rwlock
       views                        channel
          │                             │
          └──────────────┬──────────────┘
                         │
                    SYNCHRONIZATION
                         │
             ┌───────────┼───────────┐
             │           │           │
          Acquire     Release      SeqCst
             │
           AcqRel
             │
          Relaxed
```

Và riêng:

```text
Volatile
```

là một nhánh khác:

```text
                     MEMORY
                       │
             ┌─────────┴─────────┐
             │                   │
         concurrency        external IO
             │                   │
          atomic              volatile
```

# 29. Các invariant nên freeze

Tôi đề xuất thêm:

### AMC-01 — Data-Race Freedom

Safe code cannot contain an unsynchronized conflicting concurrent access.

### AMC-02 — Send/Share Separation

`Send` and `Share` are independent semantic properties.

### AMC-03 — No Implicit Atomicity

Ordinary variables are not automatically atomic.

### AMC-04 — Explicit Ordering

Atomic ordering is explicit and deterministic.

### AMC-05 — Atomicity ≠ Synchronization

An atomic operation does not automatically establish all synchronization guarantees.

### AMC-06 — Acquire/Release Preservation

Compiler and backend must preserve acquire/release semantics.

### AMC-07 — SeqCst Preservation

Sequential consistency cannot be weakened by optimization.

### AMC-08 — Volatile ≠ Atomic

Volatile access does not establish thread synchronization.

### AMC-09 — Atomic ≠ Ownership

Atomic values do not automatically establish object lifetime or memory ownership.

### AMC-10 — Synchronization Abstraction

Mutex/channel/thread APIs may encapsulate atomic and synchronization primitives.

### AMC-11 — No Mandatory Concurrency Runtime

Atomic operations require no runtime; higher-level synchronization links runtime components only when used.

### AMC-12 — Unsafe Does Not Erase Type Semantics

`unsafe` does not disable ordinary type/representation checking.

### AMC-13 — Atomic Operations Are Observable

Atomic operations cannot be removed, duplicated, or reordered in a way that changes permitted memory-model observations.

### AMC-14 — Ownership Transfer Is Synchronizable

Thread/task/channel ownership transfer establishes the necessary synchronization semantics defined by the abstraction.

### AMC-15 — Lock Guards Are RAII Resources

A lock guard is non-Copy and releases the lock deterministically on destruction.

## 30. Một quyết định tôi đặc biệt khuyên giữ

**Đừng thêm một “concurrency type system” lớn hơn nữa.**

Axiom đã có:

```text
Ownership
View
MutView
Send
Share
Effect
Atomic
```

là đủ nền tảng.

Không nên tiếp tục thêm:

```text
ThreadSafe<T>
RaceFree<T>
Sync<'a>
Concurrent<T>
Lockable<T>
AtomicSafe<T>
```

trừ khi sau này thực sự chứng minh cần.

Mục tiêu là:

```text
Source language
      ↓
simple concepts
      ↓
compiler verification
      ↓
strong concurrency guarantees
      ↓
zero-cost native code
```

chứ không phải:

```text
Source language
      ↓
programmer manually constructs proof
      ↓
compiler checks proof
```

---

### Sau phần này, tôi nghĩ còn một nút rất quan trọng cần giải quyết: **Initialization + Partial Initialization + Drop**

Đây là phần tưởng nhỏ nhưng ảnh hưởng trực tiếp đến:

- struct constructor,
- `var`,
- `let`,
- arrays,
- early return,
- panic,
- `Drop`,
- move từng field,
- error `Result`,
- async state machine,
- FFI,
- và thậm chí optimizer.

Nếu thiết kế không kỹ, ownership model hiện tại sẽ có những góc rất khó chịu. Nếu thiết kế tốt, Axiom có thể có **RAII mạnh như C++ nhưng không cần constructor/destructor/class hierarchy và không cần programmer viết lifetime**.
