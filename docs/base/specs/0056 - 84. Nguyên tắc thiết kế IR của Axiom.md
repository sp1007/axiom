Tiếp tục. Bây giờ tôi sẽ đi vào phần **IR schema cụ thể**. Đây là bước nên đóng băng trước khi cho agent code compiler, vì nếu IR chỉ mô tả bằng prose thì agent rất dễ tự diễn giải khác nhau.

# 84. Nguyên tắc thiết kế IR của Axiom

Có 4 yêu cầu:

1. **Compiler xử lý nhanh**
2. **Con người đọc được**
3. **AI agent đọc/biến đổi được**
4. **Có thể serialize để debug, cache và differential testing**

Nhưng không nên dùng JSON làm representation nội bộ.

Kiến trúc:

```text
Source
  ↓
in-memory IR structs
  ↓
fast compiler operations
  ↓
optional serializer
  ↓
AXIR text / binary
```

Tức:

> **Text IR để quan sát; native data structures để compiler chạy.**

---

# 85. ID system

Tất cả entity trong IR dùng typed ID.

```text
ModuleId
FunctionId
BlockId
LocalId
ValueId
TypeId
StructId
EnumId
TraitId
SymbolId
StringId
```

Ví dụ:

```text
FunctionId(12)
BlockId(4)
ValueId(37)
TypeId(8)
```

Không dùng pointer/reference giữa các IR object nếu có thể tránh.

Thay vì:

```text
Function → pointer → Block → pointer → Value
```

dùng:

```text
FunctionId
BlockId
ValueId
```

Lợi ích:

- serialize dễ
- cache dễ
- debug dễ
- clone module dễ
- tránh lifetime phức tạp trong compiler
- AI agent ít phá ownership của compiler implementation

---

# 86. ID không nên là global pointer

Ví dụ:

```text
ValueId = u32
```

nhưng semantic identity là:

```text
(FunctionId, ValueId)
```

hoặc ValueId chỉ unique trong Function.

Như vậy:

```text
fn foo:
    ValueId(0)

fn bar:
    ValueId(0)
```

hoàn toàn hợp lệ.

Điều này giảm kích thước IR.

---

# 87. String interning

Tên identifier không nên copy liên tục.

Compiler có:

```text
StringInterner
```

Ví dụ:

```text
StringId(17) → "add"
StringId(18) → "main"
StringId(19) → "i64"
```

AST có thể dùng StringId.

Sau HIR, phần lớn semantic entity dùng ID.

# 88. MIR Function schema

Một MIR function:

```text
MIRFunction {
    id: FunctionId
    name: SymbolId

    params: [LocalId]
    return_type: TypeId

    locals: [LocalDecl]
    blocks: [BasicBlock]

    entry: BlockId

    attributes: FunctionAttributes
}
```

`LocalDecl`:

```text
LocalDecl {
    id: LocalId
    type: TypeId
    mutable: bool
    name: Option<SymbolId>
    span: Span
}
```

Tên có thể bị loại bỏ ở optimized MIR nhưng giữ trong debug build.

# 89. BasicBlock

```text
BasicBlock {
    id: BlockId
    statements: [Statement]
    terminator: Terminator
}
```

Không dùng:

```text
Option<Terminator>
```

nếu compiler invariant yêu cầu block luôn terminated.

Tức data structure nên làm cho trạng thái invalid khó tồn tại.

# 90. Statement

Genesis:

```text
Statement =
    Assign {
        destination: Place,
        rvalue: Rvalue
    }
```

Sau này có thể:

```text
StorageLive(LocalId)
StorageDead(LocalId)
Drop(Place)
```

Nhưng đừng đưa mọi thứ vào một enum khổng lồ từ đầu.

Có thể chia:

```text
Statement
    ├── Assign
    ├── Storage
    └── Resource
```

nếu implementation language phù hợp.

# 91. Rvalue

Genesis:

```text
Rvalue =
    Use(Operand)

        op: BinaryOp
        lhs: Operand

    }

        operand: Operand

    }

        type: TypeId
```

Sau này:

```text
Index

```

# 92. Operand

```text
Operand =
    Const(ConstantId)
    Copy(Place)
    Move(Place)
```

Genesis có thể chưa cần `Move` ở machine semantics, nhưng **nên có ngay trong schema**.

Ví dụ:

```axiom
let y = x;
```

nếu `x: i64` Copy:

```text
COPY x
```

Nếu:

```axiom
let y = resource;
```

thì:

```text
MOVE resource
```

Compiler verifier phân biệt.

# 93. Place

Đây là một trong những struct quan trọng nhất của toàn bộ Axiom compiler.

```text
Place {
    base: PlaceBase
    projections: [Projection]
}
```

Base:

```text
PlaceBase =
    Local(LocalId)
    Static(SymbolId)
```

Projection:

```text
Projection =
    Field(FieldId)
    Index(ValueId)
    Deref
```

Ví dụ:

```axiom
p.address.city
```

có thể:

```text
Place
base = Local(p)

projections:
    Field(address)
    Field(city)
```

---

# 94. Tại sao Place quan trọng đến vậy?

Nó cho phép verifier phân biệt:

```text
p.name
```

và:

```text
p.age
```

thay vì chỉ thấy:

```text
p
```

Sau này:

```text
MemoryRegion(p.name)
MemoryRegion(p.age)
```

có thể được chứng minh:

```text
DISJOINT
```

Đây chính là nền tảng cho mutable field access mà không cần borrow syntax kiểu Rust.

# 95. Terminator

```text
Terminator =

    Jump {

    Branch {
        condition: Operand

    }

    Call {
        function: Callee
        args: [Operand]
        destination: Option<Place>
        next: BlockId
```

Sau này:

```text
Switch

Suspend
Spawn
```

```text
Direct(FunctionId)
```

# 97. MIR example hoàn chỉnh

Source:

```axiom
fn add(a: i64, b: i64) -> i64 {
    a + b
}
```

MIR dạng text:

```text
function @add(%a: i64, %b: i64) -> i64 {

    %v2 = add.checked copy(%a), copy(%b)
    return %v2
}
```

Một syntax dump như vậy rất hữu ích cho AI agent.

# 98. Nhưng text MIR không phải source of truth


Do đó không nên thiết kế parser MIR phức tạp ngay.



# 106. X86 condition codes

```text

```

```text
CMP

```

```text

    GT
    GE

    ULE

    UGE
```

Backend phải phân biệt signed/unsigned.

```text
i64 x > y
```


# 107. Overflow

Ví dụ:

```text
ADD_CHECKED
```

không thể selector đơn giản thành:

```asm
add rax, rbx
```

rồi bỏ overflow.

Có thể:

```asm
add rax, rbx
jo .overflow
```

Hoặc nếu compiler chứng minh:

```text
overflow impossible
```

thì:

```asm
add rax, rbx
```

không cần branch.

Đây là một optimization rất quan trọng:

```text
semantic check
       ↓
proof
       ↓
machine check elimination
```

# 108. Đây cũng là cách Axiom đạt hiệu năng cao

Không phải bằng cách làm semantics “unsafe”.

Mà bằng:

```text
Strong semantics
       ↓
Compiler proves unnecessary checks
       ↓
Checks disappear
```

Ví dụ bounds:

```axiom
for i in 0..array.len {
    sum += array[i];
}
```

Compiler có thể chứng minh:

```text
0 <= i < len
```

và loại bỏ bounds check trong loop.

Programmer không cần viết:

```text
unsafe
```

chỉ để đạt performance.

# 114. Một nguyên tắc rất đáng thêm

### IR Stability Rule

Mỗi compiler phase chỉ được **thêm hoặc loại bỏ information theo một chiều hợp lý**.

Ví dụ:

```text
AST
↓
HIR
```

thêm semantic resolution.

```text
HIR
↓
MIR
```

thêm explicit control flow + typed operations.

```text
MIR
↓
LIR
```

loại bỏ high-level semantics.

```text
LIR
↓
Machine IR
```

thêm target information.

Không được:

```text
Machine IR
 ↓
frontend semantics
```

hoặc:

```text
LIR
 ↓
ownership verifier
```

# 122. Tổng kết trạng thái architecture hiện tại

Axiom bây giờ đã có một đường khá rõ:

```text
                LANGUAGE
                   │
                   ▼
             AST / HIR
                   │
                   ▼
          ┌────────────────┐
          │ Semantic Kernel│
          │ Type + MIR     │
          │ Verifier       │
          │ Oracle         │
          └───────┬────────┘
                  │
                  ▼
             Verified MIR
                  │
             semantic erase
                  │
                  ▼
                 LIR
                  │
             ABI lowering
                  │
                  ▼
               ABI MIR
                  │
            target lowering
                  │
                  ▼
            Machine IR
                  │
           register allocation
                  │
                  ▼
             machine code
                  │
                  ▼
          Object / Executable
```

Và tôi nghĩ **đây là lúc không nên mở rộng thêm IR nữa**.

Bước kế tiếp hợp lý nhất là lấy một chương trình duy nhất:

```axiom
fn add(a: i64, b: i64) -> i64 {
    a + b
}

fn main() -> i64 {
    add(20, 22)
}
```

rồi đặc tả **từng byte và từng IR transition**:

```text
Source
 → tokens
 → AST
 → HIR
 → Typed HIR
 → MIR
 → Verified MIR
 → LIR
 → ABI MIR
 → x86 Machine IR
 → allocated Machine IR
 → exact x86 bytes
 → exact ELF sections
 → executable
 → exit code 42
```

Đó sẽ là **Axiom Genesis Trace v0.1** — một test xuyên suốt đủ nhỏ để AI agent có thể implement từng bước, nhưng đủ sâu để nếu nó chạy được thì ta biết kiến trúc compiler thực sự đã nối thông từ ngôn ngữ xuống CPU.
