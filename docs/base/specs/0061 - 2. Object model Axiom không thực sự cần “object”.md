Tiếp tục từ baseline hiện tại, tôi nghĩ phần quan trọng tiếp theo của Axiom không phải thêm syntax, mà là **chốt mô hình “computation + memory + abstraction”** sao cho sau này không phải quay lại phá compiler.

Tôi đề xuất đi tiếp theo thứ tự:

1. **Object/Value model**
2. **Expression & evaluation model**
3. **Error/panic model**
4. **Compile-time execution**
5. **Effect system**
6. **Optimization contract**
7. **ABI/FFI boundary**
8. Sau đó mới mở rộng concurrency/async/stdlib.

### 1. Một quyết định tôi muốn Axiom chốt rất rõ

Axiom nên phân biệt ba thứ:

```text
VALUE
  │
  ├── owns data
  │
  ├── view/mut_view → accesses data
  │
  └── raw pointer   → addresses data
```

Tức là:

```text
Value ≠ Address
View  ≠ Pointer
Ownership ≠ Storage
```

Đây là điểm rất quan trọng.

C/C++ thường khiến lập trình viên suy nghĩ:

```text
object → memory address → pointer → lifetime
```

Axiom nên hướng tới:

```text
value → ownership → capability
                  ↓
             compiler decides
             actual storage
```

Chỉ khi lập trình hệ thống mới cần:

```text
value → raw address
```

và lúc đó bước vào `unsafe`.

Điều này giúp tránh việc toàn bộ ngôn ngữ bị “pointer-centric”.

# 2. Object model: Axiom không thực sự cần “object”

Tôi nghiêng mạnh về việc **không dùng Object làm primitive của ngôn ngữ**.

Có:

```text
struct
enum
array
tuple
function
closure
trait
```

nhưng không có khái niệm:

```text
Object
```

theo kiểu Java/C#/C++.

Ví dụ:

```axiom
struct Player {
    hp: i32
    position: Vec3
}
```

Đây chỉ là một value:

```text
Player
 ├── hp
 └── position
```

Không mặc định có:

```text
vtable
typeinfo
object header
reference count
GC metadata
identity
heap allocation
```

Nếu cần identity:

```axiom
Box<Player>
```

Nếu cần shared ownership:

```axiom
Arc<Player>
```

Nếu cần dynamic polymorphism:

```axiom
dyn Drawable
```

Nếu cần địa chỉ:

```axiom
unsafe
```

### Đây là một abstraction boundary rất đẹp:

```text
struct Player
     ↓
pure value
```

Trong khi:

```text
Box<Player>
     ↓
stable dynamic storage
```

và:

```text
dyn Drawable
     ↓
runtime polymorphism
```

Không ép tất cả chúng vào một Object Model.

# 3. Expression model

Một ngôn ngữ hiệu năng cao nhưng dễ dùng cần **evaluation order tuyệt đối rõ ràng**.

Tôi đề xuất:

> Axiom có deterministic evaluation order.

Ví dụ:

```axiom
f(a(), b())
```

phải có thứ tự xác định.

Không được để:

```text
a() trước b()
```

hay

```text
b() trước a()
```

tùy backend/optimizer.

Nhưng compiler vẫn được phép tối ưu nếu observable behavior không thay đổi.

Ví dụ:

```axiom
let x = a() + b()
```

semantic order:

```text
a()
↓
b()
↓
+
```

nhưng nếu:

```axiom
let a = 10
let b = 20
let x = a + b
```

compiler có thể biến thành:

```text
x = 30
```

hoàn toàn.

### Invariant mới

**AEX-01 — Deterministic Evaluation**

Mọi biểu thức có side effect phải có thứ tự đánh giá xác định.

**AEX-02 — Optimization Preservation**

Compiler không được thay đổi observable evaluation order.

**AEX-03 — Pure Reordering**

Các computation được chứng minh không có observable dependency có thể được reorder/eliminate.

# 4. Pure function nên được compiler hiểu

Đây là chỗ Axiom có thể khác C/C++ khá nhiều.

Ta nên có khái niệm effect nội bộ:

```text
PURE
READ
WRITE
ALLOC
IO
ATOMIC
PANIC
UNSAFE
```

Nhưng **không nhất thiết bắt lập trình viên viết annotation**.

Ví dụ:

```axiom
fn square(x: i64) -> i64 {
    x * x
}
```

compiler suy ra:

```text
effect = PURE
```

Trong khi:

```axiom
fn save(file: File, data: view<u8>) -> Result<()> {
    ...
}
```

có thể suy ra:

```text
READ
IO
```

Compiler dùng thông tin này để:

- constant folding
- common subexpression elimination
- dead code elimination
- function reordering
- parallelization khi an toàn
- vectorization
- memoization nội bộ trong một số trường hợp
- kiểm tra concurrency
- tối ưu async

nhưng programmer không phải viết:

```text
pure fn
```

cho mọi function.

Có thể sau này cho phép annotation để **cam kết/ép contract**, nhưng inference nên là mặc định.

# 5. Error model

Tôi nghĩ Axiom nên tránh cả hai cực:

```text
C:
return code khắp nơi
```

và:

```text
C++:
exception machinery rất lớn
```

Core nên có:

```axiom
Result<T, E>
Option<T>
panic(...)
```

Ví dụ:

```axiom
fn read() -> Result<Data, IOError>
```

và:

```axiom
let data = read()?
```

`?` chỉ là syntax sugar cho propagation.

Semantic model:

```text
Ok(value)
     ↓
continue

Err(error)
     ↓
return Err(...)
```

Không cần exception table/runtime nếu chương trình không sử dụng exception-like unwind.

---

# 6. Panic phải là một profile

Axiom không nên cố định một kiểu panic duy nhất.

Có thể compile:

```text
--panic=abort
```

thì:

```text
panic()
 ↓
cleanup cần thiết
 ↓
trap/exit
```

hoặc:

```text
--panic=unwind
```

thì compiler/runtime thêm unwind metadata.

Quan trọng:

> `panic` ≠ `Result`

`Result` là recoverable control flow.

`panic` là abnormal termination/control escape.

Do đó:

```text
Result → business/error flow
panic  → violated assumption / unrecoverable condition
```

# 7. Compile-time execution

Đây là một feature rất đáng để Axiom đầu tư sớm.

Không cần macro system khổng lồ, nhưng compiler nên có:

```axiom
const
comptime
```

Ví dụ:

```axiom
const TABLE = comptime make_table()
```

Compiler chạy function đó trong compile-time interpreter.

Kiến trúc:

```text
Axiom source
     ↓
Typed HIR
     ↓
MIR
     ↓
Semantic Oracle / CT evaluator
     ↓
constant value
     ↓
program
```

Tức là compiler **không cần một ngôn ngữ compile-time thứ hai**.

Đây là lợi thế rất lớn.

C++ có:

```text
template metaprogramming
constexpr
macros
code generation
```

Axiom có thể hướng tới một model đơn giản hơn:

```text
normal Axiom code
       +
compile-time execution
```

---

# 8. Nhưng compile-time không nên cho phép mọi thứ

Nếu:

```axiom
comptime {
    network_download(...)
}
```

thì reproducibility/security trở thành vấn đề.

Vì vậy compile-time execution nên có capability profile:

```text
CT-PURE
CT-ALLOC
CT-READ-FILE
CT-ENV
CT-NETWORK
```

và mặc định:

```text
comptime = deterministic + sandboxed
```

Muốn truy cập filesystem/network phải explicit build capability.

Điều này cực kỳ có giá trị cho:

- reproducible builds
- package security
- AI-generated code
- build caching

# 9. Optimization Contract

Một điều tôi nghĩ Axiom nên ghi thành nguyên tắc chính thức:

> **Compiler được tự do thay đổi representation và execution strategy miễn là observable semantics không thay đổi.**

Ví dụ:

```axiom
let x = Point { x: 1, y: 2 }
```

semantic:

```text
Point value
```

Compiler có thể tạo:

```text
RAX = 1
RDX = 2
```

không cần memory.

Hoặc:

```text
stack[32]
```

hoặc:

```text
heap
```

nếu abstraction yêu cầu.

Programmer không được mặc định suy luận:

```text
struct → stack
```

hay:

```text
Box → heap luôn luôn
```

trừ khi API semantic yêu cầu storage identity.

# 10. Abstraction Erasure nên trở thành nguyên tắc lớn của Axiom

Ta đã có ý tưởng:

**AZC-04 — Abstraction Erasure**

Tôi đề nghị nâng nó thành một trong những nguyên tắc trung tâm.

Ví dụ:

```axiom
fn sum<T>(...)
```

sau compile:

```text
T không còn tồn tại
```

nếu không cần runtime metadata.

Trait:

```axiom
impl Add for Vec3
```

có thể biến thành:

```text
direct call
```

Closure:

```axiom
|x| x * 2
```

có thể biến thành:

```text
inline arithmetic
```

View:

```axiom
view<T>
```

có thể biến thành:

```text
pointer + length
```

hoặc thậm chí:

```text
không tồn tại
```

nếu compiler chứng minh không cần.

Ownership:

```text
Move
Drop
Send
Share
```

có thể biến mất hoàn toàn khỏi binary.

Nhưng:

```text
File Drop
MutexGuard Drop
dyn Trait
stable Box address
atomic
FFI handle
```

thì runtime effect vẫn tồn tại vì chúng **observable**.

Đây chính là điểm giúp Axiom có khả năng đạt:

```text
high-level source
        ↓
very low-level machine code
```

mà không bắt programmer viết low-level code.

# 11. Tôi nghĩ Axiom nên có 4 tầng abstraction chính

Cuối cùng mô hình toàn ngôn ngữ có thể rất rõ:

```text
┌───────────────────────────────┐
│        APPLICATION            │
│ Vec / Map / async / GUI ...   │
├───────────────────────────────┤
│        LANGUAGE MODEL         │
│ struct / trait / generic      │
│ closure / ownership / view    │
├───────────────────────────────┤
│        MEMORY MODEL           │
│ value / region / capability   │
│ storage / allocation          │
├───────────────────────────────┤
│        MACHINE MODEL          │
│ pointer / atomic / ABI / FFI  │
│ register / address / SIMD     │
└───────────────────────────────┘
```

Programmer thường làm việc ở hai tầng trên.

Compiler hiểu cả bốn.

`unsafe` là cửa đi xuống machine model.

Đây có thể trở thành triết lý cốt lõi của Axiom:

> **Không bắt programmer quản lý những thứ compiler có thể chứng minh và tối ưu; nhưng không khóa programmer khỏi machine.**

Tôi cho rằng sau khi chốt phần này, **bước tiếp theo đáng làm nhất là thiết kế “Axiom Effect System v0.1”** — vì nó sẽ nối trực tiếp `ownership + concurrency + async + optimization + compile-time + FFI`, và quyết định khá nhiều kiến trúc compiler sau này.
