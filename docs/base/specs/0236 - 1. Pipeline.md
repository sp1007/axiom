Tiếp tục **MACHINE-IR-005 — Frame Layout, Stack Frame & Prologue/Epilogue**.

Đây là tầng nối giữa register allocation và machine code thực tế. Tôi đề xuất một nguyên tắc rất quan trọng cho Axiom:

> **Không tồn tại “stack frame mặc định”. Function chỉ có stack frame khi ABI, local storage, spill, callee-saved register, outgoing arguments, dynamic allocation hoặc một yêu cầu debug/unwind nào đó thực sự cần.**

---

# 2. Frame Analysis

Trước khi layout, compiler thu thập:

```text
FrameRequirements {
    local_objects
    spill_slots
    incoming_args
    outgoing_args
    sret_storage
    callee_saved_registers
    dynamic_stack_alloc
    alignment_requirement
    red_zone_usage
    stack_probe_requirement
    frame_pointer_requirement
    unwind_requirement
    security_requirement
}
```

Sau đó mới quyết định frame thực sự có tồn tại hay không.

---

# 3. Zero-frame function

Ví dụ:

```text
fn add(a: i64, b: i64) -> i64 {
    a + b
}
```

Sau ABI:

```text
a → RDI
b → RSI
return → RAX
```

Machine code conceptual:

```text
ADD RAX, RSI
RET
```

Không:

```text
PUSH RBP
MOV RBP, RSP
SUB RSP, ...
...
MOV RSP, RBP
POP RBP
```

Đây phải là trường hợp bình thường, không phải optimization đặc biệt.

---

# 4. Leaf function

Function:

```text
fn square(x: i64) -> i64 {
    x * x
}
```

Không gọi function khác.

Có thể:

```text
IMUL RDI, RDI
MOV RAX, RDI
RET
```

Nếu ABI cho phép.

---

# 5. Không phải leaf mới được frame-less

Function có call:

```text
fn foo(x: i64) -> i64 {
    bar(x)
}
```

vẫn có thể:

```text
JMP bar
```

nếu tail-call hợp lệ.

Hoặc:

```text
CALL bar
RET
```

nếu không.

Không được suy luận:

```text
CALL => stack frame
```

một cách cứng nhắc.

# 7. Spill slot

Ví dụ:

```text
v1 → SpillSlot #0
v2 → SpillSlot #1
```

Frame allocator có thể:

```text
slot0: [0..8]
slot1: [8..16]
```

hoặc reuse:

```text
slot0:
    v1 [0..20]
    v2 [21..40]
```

---

# 8. Local variable

Một local:

```text
var x: i64
```

không nhất thiết có stack slot.

Nếu compiler thấy:

```text
x = 10
y = x + 2
```

có thể giữ hoàn toàn trong register.

Vì vậy:

> Source-level local ≠ stack object.

---

# 9. Address-taken local

Nếu:

```text
view(x)
```

hoặc unsafe code lấy address của `x`, storage identity có thể trở thành observable.

Khi đó compiler có thể phải materialize:

```text
x → stack slot
```

trừ khi có storage strategy khác đáp ứng contract.

---

# 10. Escape analysis

Ví dụ:

```text
fn foo() {
    var x = 42
    use(&x)
}
```

Nếu `use` không làm address escape:

```text
x
```

vẫn có thể được scalarized/registerized.

Nếu:

```text
store_global(&x)
```

thì lifetime/storage requirement thay đổi.

Axiom compiler phải phân tích escape thay vì mặc định đưa mọi local lên stack.

---

# 11. Stable address

Nếu programmer yêu cầu abstraction có stable address:

```text
Box<T>
```

hoặc một storage contract tương đương, compiler không được tùy tiện relocate sau khi địa chỉ observable.

Đây liên kết trực tiếp với:

```text
AMEM-21
AMEM-55
AMEM-61
AMEM-70
AMEM-72
```

---

# 12. Stack alignment

Frame layout phải thỏa:

```text
SP % ABI_ALIGNMENT == 0
```

tại các ABI-defined points.

Ví dụ một ABI có yêu cầu 16-byte alignment.

Compiler phải tính:

```text
locals
spills
saved registers
outgoing args
padding
```

đồng thời.

Không được chắp vá alignment ở cuối pass.

---

# 13. Alignment padding

Ví dụ:

```text
slot A: 8 bytes
slot B: 32-byte aligned
```

Frame:

```text
A
padding
B
```

Padding là machine-frame detail, không phải source semantic.

---

# 14. Red zone

Một số ABI cho phép vùng dưới SP mà leaf function có thể dùng mà không điều chỉnh SP.

Ví dụ SysV x86-64 có red zone.

Axiom target description:

```text
RedZone {
    supported
    size
    forbidden_in_contexts
}
```

Nhưng không được sử dụng nếu context không cho phép.

Ví dụ interrupt/signal-sensitive/kernel code có thể cấm.

---

# 15. Red zone không phải Core semantic

Axiom source:

```text
fn foo() { ... }
```

không biết:

```text
red zone
stack frame
SP
```

đây là backend/ABI policy.

---

# 16. Windows shadow space

Windows x64 có ABI requirement khác.

Caller có thể phải reserve:

```text
shadow/home space
```

cho callee.

Axiom không nên hard-code vào calling convention chung.

Thay vào đó:

```text
CallingConvention {
    argument_locations
    return_locations
    stack_alignment
    outgoing_home_area
    callee_saved
    caller_saved
}
```

Windows backend mô tả shadow space.

---

# 17. Outgoing argument area

Nếu function gọi:

```text
foo(a,b,c,d,e,...)
```

một số arguments có thể nằm trên stack.

Frame layout cần biết:

```text
max_outgoing_stack_args
```

của function.

Có thể:

```text
reserve once
reuse for every call
```

thay vì:

```text
allocate/deallocate
```

mỗi call.

---

# 18. Dynamic outgoing arguments

Nếu số argument size thay đổi runtime hoặc ABI yêu cầu dynamic placement:

```text
STACK_ALLOC_DYNAMIC
```

có thể cần.

Khi đó frame layout phức tạp hơn.

---

# 19. Dynamic stack allocation

Ví dụ:

```text
alloca(n)
```

không được coi như local stack slot cố định.

Có:

```text
fixed frame
+
dynamic stack region
```

Ví dụ conceptual:

```text
high address
──────────────
saved state
locals
spills
outgoing args
──────────────
dynamic allocation
──────────────
SP
low address
```

---

# 20. Dynamic stack allocation và alignment

Nếu:

```text
p = stack_alloc(n, 64)
```

compiler phải đảm bảo:

```text
address(p) % 64 == 0
```

và restore SP chính xác khi region kết thúc.

---

# 21. Dynamic allocation không nên làm hỏng mọi local

Đây là lý do nên có:

```text
FrameBase
```

abstract trong LIR/Machine IR trước khi final layout.

Nếu dùng SP-relative cứng quá sớm, dynamic SP adjustment sẽ làm mọi offset phức tạp.

---

# 22. Frame pointer

Axiom không yêu cầu frame pointer mặc định.

Có thể:

```text
SP-relative
```

khi frame static.

Nếu cần:

```text
FP-relative
```

thì backend tạo frame pointer.

---

# 23. Khi nào cần frame pointer?

Ví dụ:

- debug policy
- dynamic stack allocation
- unusual ABI
- unwind requirement
- stack probing strategy
- platform requirement

Nhưng không nên biến thành:

```text
mọi function đều dùng RBP
```

---

# 24. Frame pointer elimination

Ví dụ:

```text
fn add(a,b) -> i64
```

không cần:

```text
RBP
```

Allocator không nên vô tình giữ RBP nếu target policy cho phép sử dụng nó làm GPR.

---

# 25. Callee-saved registers

Nếu allocator dùng:

```text
RBX
```

và ABI quy định callee phải preserve:

```text
RBX
```

Frame analysis ghi:

```text
used_callee_saved = {RBX}
```

Prologue generator mới quyết định cách save.

---

# 26. Save/restore strategy

Không bắt buộc:

```text
PUSH RBX
...
POP RBX
```

Có thể:

```text
STORE [frame+offset], RBX
...
LOAD RBX, [frame+offset]
```

AArch64 có thể dùng:

```text
STP
LDP
```

Backend chọn sequence tối ưu.

---

# 27. Save nhiều register

Nếu:

```text
RBX
R12
R13
R14
```

đều được sử dụng, x86 có thể tạo nhiều push/pop.

AArch64 có thể pair store/load.

Do đó Prologue/Epilogue phải target-specific.

---

# 28. Prologue generation

Conceptually:

```text
Prologue {
    establish_stack
    save_callee_saved
    establish_frame_pointer
    allocate_frame
    stack_probe
    initialize_security_state
}
```

Nhưng từng bước optional.

---

# 29. Epilogue

```text
Epilogue {
    restore_stack
    restore_callee_saved
    destroy_dynamic_frame
    RET
}
```

Phải có nhiều exit path.

Ví dụ:

```text
if error:
    return
```

và:

```text
normal:
    return
```

có thể dùng cùng epilogue.

---

# 30. Shared epilogue

Compiler có thể biến:

```text
return a
return b
return c
```

thành:

```text
...
JMP common_epilogue

common_epilogue:
    restore
    RET
```

giảm code size.

Nhưng nếu hot path cần tránh branch, có thể giữ nhiều epilogue.

---

# 31. Epilogue duplication

Optimization goal `Speed` có thể cho phép:

```text
multiple epilogues
```

để giảm branch.

`Size` có thể ưu tiên:

```text
shared epilogue
```

---

# 32. Tail call

Nếu:

```text
fn foo(x) {
    return bar(x)
}
```

và ABI tương thích:

```text
JMP bar
```

không cần:

```text
CALL
RET
```

Frame của `foo` có thể không cần tồn tại.

---

# 33. Guaranteed tail call

Không nên coi mọi tail-call là guaranteed.

Có hai khái niệm:

```text
TailCallCandidate
GuaranteedTailCall
```

Guaranteed chỉ khi ABI/semantics cho phép chắc chắn.

---

# 34. Tail call và frame

Nếu đã có:

```text
callee-saved register
```

cần restore trước khi tail-jump.

Compiler có thể:

```text
restore
JMP target
```

---

# 35. Stack probes

Một stack allocation rất lớn:

```text
stack_alloc(10 MB)
```

không thể luôn:

```text
SUB SP, 10MB
```

mà bỏ qua OS stack guard mechanism.

Một số target/OS cần stack probing.

Frame analysis:

```text
needs_stack_probe = true
```

Prologue generator tạo probe sequence hoặc helper.

---

# 36. Stack canary

Nếu Axiom security profile bật:

```text
StackProtection
```

frame có:

```text
canary slot
```

Prologue:

```text
load canary
store frame canary
```

Epilogue:

```text
check canary
```

Không nên mặc định đưa vào mọi freestanding binary nếu mục tiêu là minimal runtime/code size.

# 37. Security policy

Nên có:

```text
SecurityProfile {

```

Các policy có thể ảnh hưởng:

- stack canary

- CFI

# 38. Unwind

Đây là phần rất quan trọng với Drop và panic/unwind.

Compiler cần tạo:

```text
UnwindInfo
```

độc lập với source-level exception model.

Ví dụ:

```text
DWARF .eh_frame
Windows .pdata/.xdata
```

---

# 39. Panic=abort

Nếu:

```text
panic = abort
```

không cần full exception unwind machinery.

Một panic path có thể:

```text
CALL axiom_panic
UD2
```

hoặc target equivalent.

---

# 40. Panic=unwind

Nếu:

```text
panic = unwind
```

compiler cần:

```text
cleanup regions
landing pads
unwind metadata
```

Nhưng vẫn không cần C++ exception runtime.

---

# 41. Drop cleanup

Ví dụ:

```text
fn foo() {
    var a = Resource()
    bar()
}
```

Nếu `bar()` panic và unwind:

```text
bar()
↓
cleanup a
↓
unwind
```

Machine-level landing/cleanup structure phải khớp `CleanupGraph` từ MIR.

---

# 42. Frame layout không được quyết định Drop

Ranh giới:

```text
MIR:
    "resource a phải được drop"

Frame:
    "a đang nằm ở đâu?"
```

Không để backend suy luận ownership.

---

# 43. TLS

TLS object không nằm trong ordinary stack frame.

Ví dụ:

```text
thread_local var x
```

Machine IR có:

```text
TLS symbol/reference
```

ABI lowering chọn:

```text
TLS model
```

Target có thể dùng:

- local exec
- initial exec
- general dynamic
- platform-specific

---

# 44. TLS model

Axiom compiler nên hỗ trợ:

```text
TLSModel {
    LocalExec
    InitialExec
    LocalDynamic
    GeneralDynamic
    TargetDefault
}
```

nhưng programmer không cần biết trừ system-level API.

---

# 45. Stack and async

Async Future state machine không nhất thiết nằm stack.

Nếu compiler chứng minh:

```text
future does not escape
```

có thể:

```text
stack/register
```

Nếu:

```text
spawn(future)
```

và task storage yêu cầu stable address:

```text
dynamic/task storage
```

được runtime/scheduler abstraction quyết định.

---

# 46. Fiber

Fiber có stack riêng.

Đây là một trường hợp storage contract rõ ràng:

```text
Fiber
 └── stack
```

Fiber stack lifetime bao phủ execution của Fiber.

Nhưng Machine IR của function chạy trên Fiber vẫn chỉ thấy:

```text
SP
```

không cần biết scheduler.

---

# 47. Stack switching

Fiber context switch có thể thay đổi:

```text
SP
IP
callee-saved registers
```

đây là target-specific system intrinsic.

Không nên đưa Fiber semantics vào generic frame pass.

---

# 48. Interrupt / naked functions

System programming cần:

```text
@interrupt
@naked
```

hoặc tương đương.

Nhưng đây phải là **explicit ABI/system attributes**.

Một `@naked` function:

```text
không được compiler tự động tạo prologue/epilogue
```

và có machine-level restrictions.

---

# 49. `@naked`

Nên giới hạn rất mạnh:

```text
@naked
unsafe fn handler(...)
```

Không cho compiler giả định:

- stack frame
- preserved registers
- ordinary local storage

nếu function tự quản lý.

Đây là system-level escape hatch.

---

# 50. `@interrupt`

Interrupt ABI có thể yêu cầu:

- special return instruction
- register preservation khác
- interrupt frame
- stack switching
- target-specific state

Do đó:

```text
CallingConvention::Interrupt
```

không nên hack vào SysV/Windows ABI.

---

# 51. Frame layout algorithm

Tôi đề xuất:

```text
1. Collect frame objects
2. Determine required alignment
3. Color/reuse spill slots
4. Place fixed ABI objects
5. Place callee-saved saves
6. Place locals/spills
7. Place outgoing area
8. Insert padding
9. Compute total size
10. Determine SP/FP addressing
11. Determine probing requirement
12. Determine prologue/epilogue requirements
```

    ...

# 58. `alloca` và recursion

Dynamic stack allocation trong recursive function phải được restore trước return.

Không được để:

```text

```

---

# 59. Stack frame và GC

Axiom không có GC Core.

Do đó frame layout không phải phục vụ:

```text
GC root scanning
```

đây là một lợi thế đáng kể cho backend.

Nếu một optional runtime sau này có moving GC, đó sẽ là một execution/storage profile riêng, không phải assumption của machine backend.

---

# 60. Runtime-free function

Một function:

```text
fn add(a: i64,b:i64)->i64
```

có thể tạo:

```text
ADD
RET
```

Không:

```text
runtime_init
stack_init
GC barrier
object header
exception object
```

Đây chính là mục tiêu **zero mandatory runtime overhead**.

# 62. Ví dụ hoàn chỉnh

Source:

```text id="xv7l8h"
fn add(a: i64, b: i64) -> i64 {
    a + b
}
```

ABI lowering:

```text id="1y8b8a"
a → RDI
b → RSI
return → RAX
```

Instruction selection:

```text id="fybq1u"
ADD RDI, RSI
```

Register allocation:

```text id="v8s6na"
v_a → RDI
v_b → RSI
result → RAX
```

Frame analysis:

```text id="ij2i7f"
locals = 0
spills = 0
callee_saved = 0
outgoing_args = 0
dynamic_alloc = false
```

→ **no frame**

Final:

```text id="j4u2gd"
ADD RAX, RSI
RET
```

Tùy ABI move/coalescing, có thể cần một move từ argument register sang return register:

```text id="g5a6ry"
MOV RAX, RDI
ADD RAX, RSI
RET
```

Và optimizer có thể loại bỏ move nếu selector/allocator tổ chức destination tốt.

# 64. Một điểm tôi muốn khóa rất rõ

Axiom **không nên có một “runtime stack object” bắt buộc**.

Stack là:

> **một execution/storage mechanism của target và ABI.**

Cũng giống như register:

> register không phải một phần của Axiom value model.

Điều này giữ cho abstraction rất sạch:

```text
Axiom semantic value
        ↓
storage strategy
        ↓
register / stack / static / dynamic / device
```
