Tiếp tục với **CHANNEL-001 — Ownership-Preserving Message Passing**.

Đây là phần rất quan trọng vì channel phải tận dụng được ownership model của Axiom mà **không biến mọi message thành heap allocation + reference counting + mutex**.

# CHANNEL-001

## 1. Nguyên tắc nền tảng

Axiom channel nên được định nghĩa đơn giản:

> **Channel là một ownership-transfer boundary giữa các execution domains.**

Không phải:

```text
queue + mutex + Arc + GC
```

và cũng không phải một object đặc biệt của Core.

Mô hình:

```text
Producer
   │
   │ move T
   ▼
 Channel<T>
   │
   │ move T
   ▼
Consumer
```

Với:

```text
T: Send
```

nếu channel đi qua execution domain khác.

---

# 2. Gửi là Move

Ví dụ:

```axiom
let data = Buffer.alloc(4096)

tx.send(data)?

// data không còn hợp lệ ở đây
```

Compiler chuyển ownership:

```text
Producer owns data
       ↓
      send
       ↓
Channel owns data
       ↓
     recv
       ↓
Consumer owns data
```

Không copy.

Đây là điểm Axiom có thể rất mạnh:

```text
send(T)
```

không có nghĩa:

```text
clone(T)
```

---

# 3. Channel không cần `Arc<T>`

Ví dụ channel:

```text
Channel<Buffer>
```

không cần:

```text
Arc<Buffer>
```

vì:

```text
Channel owns Buffer
```

Chỉ khi **nhiều execution domain cùng cần giữ cùng một object** mới cần:

```text
Arc<T>
```

Channel và shared ownership là hai vấn đề khác nhau.

---

# 4. API cơ bản

Tôi đề xuất:

```axiom
let (tx, rx) = channel<T>()
```

Sender:

```axiom
tx.send(value)?
```

Receiver:

```axiom
let value = rx.recv()?
```

Async:

```axiom
let value = rx.recv().await?
```

Non-blocking:

```axiom
match rx.try_recv() {
    Ok(value) => ...
    Empty => ...
    Closed => ...
}
```

---

# 5. Bounded channel là default primitive

Không nên để channel mặc định là unbounded.

Có:

```axiom
channel<T>(capacity: 1024)
```

Ví dụ:

```text
Producer
   ↓
┌──────────────┐
│  Ring Buffer │
│  0 1 2 3 ... │
└──────────────┘
   ↓
Consumer
```

Bounded channel cho phép:

- predictable memory
- backpressure
- cache locality
- tránh producer chạy vô hạn.

---

# 6. Unbounded channel là library abstraction

Nếu cần:

```axiom
unbounded_channel<T>()
```

thì runtime có thể dùng:

```text
segments
linked blocks
arena
heap
```

Nhưng không nên biến unbounded queue thành Core primitive.

---

# 7. SPSC/MPSC/MPMC

Không nên ép mọi channel vào MPMC.

Axiom nên có các specialization:

```text
SPSC
MPSC
SPMC
MPMC
```

### SPSC

```text
1 producer
1 consumer
```

có thể rất nhanh:

```text
lock-free ring buffer
```

### MPSC

```text
many producers
1 consumer
```

### MPMC

```text
many producers
many consumers
```

phức tạp hơn.

# 8. Type-level channel mode

Tôi không muốn programmer phải viết:

```axiom
Channel<T, MPSC>
```

trong API thông thường.

Có thể inference từ constructor:

```axiom
let (tx, rx) = channel_spsc<T>()
```

hoặc:

```axiom
channel<T>(ChannelMode::...)
```

Nhưng **default API nên đơn giản**.

Compiler/runtime có thể specialize nếu usage pattern chứng minh được.

# 9. Compiler optimization

Ví dụ:

```axiom
let (tx, rx) = channel::<Message>(1)

spawn(fn() {
    tx.send(message)
})

let msg = rx.recv()?
```

Compiler/runtime có thể nhận ra:

```text
single producer
single consumer
```

và chọn:

```text
SPSC ring buffer
```

thay vì MPMC.

Không cần programmer biết implementation.

---

# 10. Zero-copy

Đây là mục tiêu quan trọng.

Không nên:

```text
producer Buffer
   ↓
malloc
   ↓
copy Buffer
   ↓
queue
   ↓
copy
   ↓
consumer
```

Mà:

```text
producer owns Buffer
        │
        │ MOVE
        ▼
   channel slot
        │
        │ MOVE
        ▼
consumer owns Buffer
```

Nếu `Buffer` là:

```text
ptr + len + cap
```

thì chỉ chuyển descriptor.

Dữ liệu 4 MB không bị copy.

---

# 11. Nhưng channel slot vẫn phải chứa value

Ví dụ:

```text
Channel<SmallStruct>
```

thì ring buffer chứa trực tiếp:

```text
slot[0] = T
slot[1] = T
...
```

Không cần pointer.

Đối với:

```text
Channel<LargeStruct>
```

runtime có thể:

- inline slot
- indirect storage
- specialized move

tùy compiler.

Semantic vẫn là:

```text
move T
```

---

# 12. Uninitialized slots

Ring buffer không nên yêu cầu:

```text
T: Default
```

vì Axiom không có implicit zero initialization.

Slot conceptually:

```text
Slot<T>
├── empty
└── value: T
```

hoặc:

```text
MaybeUninit<T>
```

được compiler/runtime quản lý.

Điều này rất hợp với `MaybeUninit` intrinsic đã có.

---

# 13. Channel ownership

Tôi đề xuất:

```text
Channel
├── Sender
└── Receiver
```

`Sender` có thể clone nếu channel cho phép multiple producers:

```axiom
let tx2 = tx.clone()
```

Nhưng `clone()` ở đây clone **capability to send**, không clone messages.

Receiver tương tự chỉ clone nếu semantics cho phép multiple consumers.

---

# 14. `Sender` không phải `Copy`

Sender có resource/state semantics:

```text
Sender<T>
```

nên:

```text
let tx2 = tx
```

là move.

Muốn thêm producer:

```text
let tx2 = tx.clone()
```

Nhưng channel implementation có thể dùng:

```text
atomic producer_count
```

hoặc intrusive sender registration.

---

# 15. Channel close

Channel đóng khi ownership endpoint cuối cùng biến mất.

Ví dụ:

```text
tx
tx2
```

Nếu:

```text
drop(tx)
drop(tx2)
```

thì:

```text
all senders gone
       ↓
receiver wakes
       ↓
recv() → Closed
```

Tương tự receiver:

```text
receiver dropped
       ↓
send() → Closed
```

---

# 16. Drop Sender không drop messages ngay

Ví dụ:

```text
tx dropped
```

không nhất thiết:

```text
queue.clear()
```

Nếu receiver còn:

```text
queued messages
```

thì receiver vẫn phải lấy được chúng.

Semantic:

```text
SENDERS = 0
QUEUE != empty
```

thì:

```text
recv() → messages
```

sau đó:

```text
recv() → Closed
```

Đây là behavior rất quan trọng.

---

# 17. Async recv

```axiom
let value = rx.recv().await?
```

Nếu queue empty:

```text
Receiver task
    ↓
WAITING
    ↓
channel wait list
```

Producer:

```axiom
tx.send(value)
```

sẽ:

```text
enqueue value
    ↓
wake receiver
```

Không polling liên tục.

---

# 18. Async send và backpressure

Bounded channel:

```text
capacity = 1024
```

Nếu đầy:

```axiom
tx.send(value).await?
```

thì:

```text
Producer
    ↓
WAITING_SEND
```

Consumer lấy message:

```text
recv()
 ↓
free slot
 ↓
wake producer
```

Đây là backpressure tự nhiên.

---

# 19. Không tạo Task cho mỗi wake

Đây là optimization quan trọng.

Không:

```text
wake producer
 ↓
spawn new task
```

Chỉ:

```text
WAITING → READY
```

Task đã tồn tại.

---

# 20. Channel wait queue

Một channel có thể có:

```text
Channel<T>
├── ring buffer
├── sender state
├── receiver state
├── waiting senders
└── waiting receivers
```

Nhưng nếu không có waiter:

```text
wait lists = empty
```

không cần allocation.

Nếu có:

```text
WaitNode
```

có thể intrusive vào Task.

Do đó:

```text
Task
 └── WaitLink
```

được reuse giống scheduler queue.

---

# 21. Không allocation trong uncontended path

Mục tiêu:

```text
try_send()
try_recv()
```

trong channel SPSC:

```text
load index
check
store value
store index
```

Không:

```text
malloc
mutex
syscall
```

Đây nên là performance invariant.

---

# 22. Memory ordering

SPSC ring buffer có thể dùng:

```text
producer:
    write data
    release tail

consumer:
    acquire tail
    read data
```

Ngược lại:

```text
consumer:
    release head

producer:
    acquire head
```

Không cần `SeqCst` toàn hệ thống.

Compiler/runtime chọn ordering phù hợp.

---

# 23. MPMC

MPMC phức tạp hơn.

Ta không nên ép implementation cụ thể.

Semantic contract:

```text
send(T)
recv() -> T
```

Implementation có thể:

```text
lock-free
mutex
ticket queue
bounded ring
segmented queue
```

Miễn:

- đúng ownership
- đúng ordering contract
- không data race.

---

# 24. Ordering

Channel phải document ordering.

Default:

> **FIFO per sender.**

Ví dụ:

```text
Sender A:
A1
A2
A3
```

Receiver không được nhận:

```text
A2
A1
A3
```

Nhưng giữa nhiều sender:

```text
A1
B1
A2
B2
```

thứ tự toàn cục phụ thuộc synchronization/race giữa send operations nếu API không thiết lập ordering.

Không nên giả định:

```text
A1 B1 A2 B2
```

là guaranteed.

---

# 25. Ownership + channel

Đây là phần compiler verifier cần hiểu.

```axiom
tx.send(x)
```

sẽ tạo semantic event:

```text
MOVE x → Channel
```

Sau đó:

```text
use(x)
```

compile error.

Khi:

```axiom
let y = rx.recv()?
```

thì:

```text
Channel → ownership(y)
```

Compiler có thể track provenance:

```text
Producer region
      ↓
Channel region
      ↓
Consumer region
```

---

# 26. Views không được gửi

Ví dụ:

```axiom
let v = view(buffer)

tx.send(v)
```

không được phép nếu channel storage có thể outlive `buffer`.

Compiler:

```text
view<T>
```

là capability phụ thuộc owner.

Channel không được biến nó thành owned value.

Do đó mặc định:

```text
view<T>: !Send
```

trừ khi abstraction cụ thể chứng minh lifetime/storage contract.

---

# 27. `mut_view` càng nghiêm ngặt

Không cho:

```axiom
tx.send(mut_view(buffer))
```

vì đây là exclusive mutable capability.

Muốn truyền dữ liệu:

```text
move owning Buffer
```

hoặc:

```text
copy data
```

explicit.

Điều này giúp channel trở thành boundary cực sạch:

```text
ownership transfer
```

thay vì:

```text
alias transfer
```

---

# 28. Shared channel data

Nếu thực sự muốn:

```text
multiple consumers access same object
```

thì:

```axiom
Arc<T>
```

hoặc:

```axiom
Shared<T>
```

là explicit:

```text
tx.send(shared.clone())
```

Channel không tự thêm sharing semantics.

# 29. Channel và error handling

`send`:

```text
Result<(), SendError<T>>
```

Điểm rất hay:

Nếu channel closed:

```text
SendError<T>
```

phải trả lại **ownership của T**.

Ví dụ:

```text
send(x)
 ↓
receiver closed
 ↓
Err(SendError { value: x })
```

Programmer vẫn sở hữu `x`.

Không được làm:

```text
x lost
```

# 30. `recv`

```text
Result<T, RecvError>
```

Các trạng thái:

```text
Message
Closed
```

Không cần `Option<Result<T>>`.

# 31. `try_recv`

```text
TryRecv<T>
├── Value(T)
├── Empty
└── Closed
```

Có thể là enum.

# 32. Select

Sau channel cơ bản, cần:

```axiom
select {
    rx_a.recv() => ...
    rx_b.recv() => ...
    timer.after(1s) => ...
}
```

Nhưng **không nên biến `select` thành runtime magic**.

Compiler có thể lower thành:

```text
Future combinator
```

hoặc library macro/compile-time mechanism trong tương lai.

Vì macro chưa có Core v0.1, MVP có thể cung cấp:

```axiom
select(a, b, c)
```

như library combinator.

# 33. Channel cancellation

Nếu:

```axiom
await rx.recv()
```

bị task cancel:

```text
Task cancellation
 ↓
remove wait registration
 ↓
drop waiter
```

Không được để channel giữ dangling pointer tới Task.

Đây là capability lifetime issue.

---

# 34. Channel wait node ownership

Tôi đề xuất:

```text
Task
└── WaitLink
```

Channel chỉ giữ:

```text
pointer/reference to Task WaitLink
```

nhưng capability phải được compiler/runtime chứng minh:

```text
Task WAITING
```

Task không thể complete trong lúc channel còn giữ waiter.

Khi wake:

```text
Channel
 ↓
remove WaitLink
 ↓
Task READY
```

Sau đó Task có thể được reclaim.

---

# 35. Điều này kết nối rất đẹp với ownership verifier

Ta có:

```text
Task scheduler ownership
        +
Channel wait capability
        +
Task lifetime
```

Rule:

> **A task cannot be reclaimed while an external wait registration retains a live wake capability to it.**

Đây nên là invariant runtime/compiler.

---

# 36. Zero-copy API nâng cao

Sau này có thể:

```axiom
tx.send_with(|slot| {
    slot.write(...)
})
```

để producer ghi trực tiếp vào channel slot.

Conceptually:

```text
reserve slot
 ↓
mut_view<T>
 ↓
write
 ↓
commit
```

Không tạo temporary `T`.

Ví dụ network:

```text
receive packet
 ↓
write directly into channel buffer
```

Đây có thể cực kỳ mạnh.

Nhưng API này nên để **advanced library**, không phải Core.

# 37. Batch operations

High-performance code:

```axiom
tx.send_batch(items)
rx.recv_batch(buffer)
```

có thể giảm synchronization.

Channel semantic vẫn ownership transfer.

Ví dụ:

```text
Vec<T>
 ↓ move

```

hoặc từng element move vào ring.

# 38. Channel memory allocation

Bounded channel:

```text
capacity = N
```

nên có thể allocate toàn bộ storage một lần:

```text
Channel<T>
 └── N × Slot<T>
```

Không allocation per message.

Unbounded channel:

```text
Segment
Segment
Segment
```

có thể allocate theo block.

Không cần GC.

# 39. Cache locality

Channel implementation nên ưu tiên:

```text
producer index
consumer index
```

tách cache line nếu MPMC:

```text
Producer metadata
──────── cache line ────────

Consumer metadata
──────── cache line ────────
```

Tránh false sharing.

Đây là implementation detail, nhưng rất đáng đưa vào benchmark/harness.

# 40. Channel và scheduler

Cuối cùng:

```text
                    Scheduler
                       │
                 READY / WAITING
                       │
              ┌────────┴────────┐
              ↓                 ↓
          Channel A          Channel B
              │                 │
          send/recv          send/recv
              │                 │
              └────── wake ─────┘
```

Channel không tự tạo thread.

Không tự tạo scheduler.

Không tự tạo task.

Nó chỉ:

```text
store ownership
wake waiting computation
```

# 42. Kiến trúc hiện tại

Đến đây concurrency stack của Axiom trở thành:

```text
                   OWNERSHIP
                       │
                 ┌─────┴─────┐
                 ↓           ↓
              Send          Share
                 │           │
                 ↓           ↓
              Channel    Shared<T>
                 │
                 ↓
               Task
                 │
              Future
                 │
                 ↓
             Scheduler
          ┌──────┼──────┐
          ↓      ↓      ↓
       Thread   Fiber  Domain
```

Điểm quan trọng:

**Channel không cần `Arc`, không cần GC, không cần exception, không cần runtime object cho từng message.**

Một message lớn có thể đi:

```text
Producer owns 4 MB Buffer
        │
       MOVE
        ↓
Channel slot
        │
       MOVE
        ↓
Consumer owns 4 MB Buffer
```

và **4 MB dữ liệu không cần copy**.

## Bước tiếp theo: SYNCHRONIZATION-001

Sau channel, mảnh còn thiếu của concurrency core là **Mutex / RwLock / Condition / Semaphore / Barrier / Once**.

Đặc biệt ta cần giải quyết một vấn đề rất quan trọng:

> **Guard của Mutex/RwLock sẽ tương tác thế nào với `view<T>` và `mut_view<T>` để compiler tự hiểu rằng khi guard còn sống thì lock vẫn được giữ, nhưng programmer không phải viết lifetime/borrow annotation?**

Nếu thiết kế tốt phần này, mô hình:

```axiom
lock.lock().write()
```

có thể tạo trực tiếp:

```text
MutexGuard<T>
      ↓
mut_view<T>
```

và compiler tự bảo đảm **không thể unlock quá sớm, không thể dùng view sau khi guard chết, và không thể tạo hai mutable access đồng thời** mà không cần Rust-style lifetime syntax.
