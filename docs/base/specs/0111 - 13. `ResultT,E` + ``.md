Tiếp tục **Consistency Pass v0.1 — nhóm 2**. Tôi sẽ tập trung vào các giao điểm khó nhất: `Result`, `Drop`, `async`, concurrency, unsafe và FFI.

---

# 13. `Result<T,E>` + `?`

Ví dụ:

```axiom
fn load(path: view<Text>) -> Result<Text, AppError> {
    let file = File.open(path)?
    let data = file.read_all()?
    Ok(data)
}
```

`?` phải được hiểu hoàn toàn như control-flow.

Khái niệm MIR:

```text
r0 = CALL File.open(path)

MATCH r0
    Ok(file) =>
        ...
    Err(e) =>
        DROP currently_owned_values
        RETURN Err(convert(e))
```

Điểm quan trọng:

> `?` không phải exception.

Không có:

```text
throw
catch
stack unwinding
exception object
```

trong semantic model của `?`.

---

# 14. `Result` + `Drop`

Đây là test rất quan trọng.

```axiom
fn process() -> Result<Text, Error> {
    let file = File.open("data.txt")?
    let data = file.read_all()?
    transform(data)
}
```

Nếu:

```text
read_all() → Err
```

thì `file` vẫn đang owned.

Compiler phải sinh:

```text
CALL read_all()

if Err:
    DROP file
    RETURN Err(...)
```

Không được:

```text
return Err(...)
```

rồi bỏ qua `file`.

### Quy tắc

**AFERR-43 — `?` Preserves Deterministic Cleanup**

Mọi đường thoát được tạo bởi `?` phải thực hiện cleanup đối với toàn bộ resource đang owned tại điểm thoát.

Điều này khiến:

```text
Result + Drop
```

hoàn toàn tương thích với nhau.

---

# 15. `Result` + partial move

```axiom
struct State {
    file: File
    name: Text
}
```

Nếu:

```axiom
let name = state.name
operation()?
```

thì tại `?`:

```text
state.file = OWNED
state.name = MOVED
```

Nếu operation fail:

```text
DROP state.file
RETURN Err(...)
```

Không drop `name`.

Đây là lý do ownership state phải tồn tại ở MIR chứ không thể chỉ là type-checking đơn giản.

# 16. Async + owned state

Ví dụ:

```axiom
async fn download(url: view<Text>) -> Result<Bytes, Error> {
    let request = make_request(url)
    let response = await request.send()
    response.read_all()
}
```

Sau `.await`, compiler phải xác định biến nào còn sống.

Giả sử:

```text
request
response
```

chỉ `response` còn cần sau await.

State machine không cần giữ `request` nếu nó đã được consume trước suspension.

Conceptually:

```text
Future {
    state: State::WaitingResponse,
    response: Response
}
```

Không phải:

```text
Future {
    EVERYTHING_FROM_FUNCTION
}
```

### Invariant

**AASYNC-20 — Async State Contains Only Semantically Live State**

Compiler được phép loại bỏ mọi local không sống qua suspension point.

# 17. Async + view

Đây là điểm cực kỳ nhạy cảm.

```axiom
async fn process(data: view<Bytes>) {
    await something()
    use(data)
}
```

Có thể `data` trỏ vào memory của caller.

Trong lúc `await`, caller có thể tiếp tục mutation hoặc storage có thể thay đổi.

Vì vậy v0.1 nên giữ rule rất đơn giản:

> **Một `view<T>` không được sống qua `.await`.**

Ví dụ trên:

```text
ERROR
view capability survives suspension
```

Nhưng:

```axiom
async fn process(data: view<Bytes>) {
    use(data)
    await something()
}
```

hợp lệ nếu compiler chứng minh `data` đã last-use trước `.await`.

# 18. Owned data qua `await`

Ngược lại:

```axiom
async fn process(data: Bytes) {
    await something()
    use(data)
}
```

hoàn toàn hợp lệ.

Compiler chuyển ownership của `data` vào future state.

```text
caller
  │
  MOVE
  ▼
Future.data
```

Future chịu trách nhiệm Drop khi:

- hoàn thành;
- bị drop/cancel;
- panic/abort theo profile.

**AASYNC-21 — Owned Values May Live Across Await**

**AASYNC-22 — Suspended Future Owns Its Live State**

# 19. `mut_view` + async

```axiom
async fn process(data: mut_view<Buffer>) {
    await something()
    data.modify()
}
```

Tôi đề xuất **v0.1 cấm**.

Không phải vì compiler không thể làm được.

Mà vì nếu cho phép, chúng ta phải giải quyết đồng thời:

```text
mutable capability
+
suspension
+
executor migration
+
caller access
+
concurrency
+
cancellation
```

Complexity tăng rất mạnh.

Thay vào đó:

```axiom
async fn process(data: Buffer) {
    data.modify()
    await something()
    data.modify()
}
```

hoặc:

```axiom
async fn process(data: view<Buffer>) {
    use(data)
    await something()
}
```

### Quy tắc

**AASYNC-23 — `mut_view` Cannot Survive Await in v0.1**

**AASYNC-24 — `view` Cannot Survive Await in v0.1**

Đây là một constraint rất đáng giá vì nó giữ async model sạch.

# 20. Async Future có phải heap object?

Không.

```axiom
async fn foo() { ... }
```

trả về một future value.

Future có thể nằm:

```text
register
stack
inline
caller storage
heap
arena
```

Compiler quyết định.

Nếu:

```axiom
foo().await
```

và future không escape, compiler có thể scalarize hoàn toàn state machine.

Do đó:

> `async` không đồng nghĩa heap allocation.

# 21. `spawn` + closure capture

Ví dụ:

```axiom
fn run(data: Buffer) {
    spawn(move || {
        process(data)
    })
}
```

`move` ở đây rất quan trọng.

Closure lấy ownership:

```text
run.data
   │
   └── MOVE → closure.data
```

Sau đó:

```text
closure → task → executor
```

Nếu task có thể chạy trên thread khác:

```text
closure must satisfy Send
```

Compiler kiểm tra.

---

# 22. `spawn` + capture reference/view

```axiom
fn run(data: Buffer) {
    spawn(|| {
        use(data)
    })
}
```

Nếu closure capture `data` bằng view/reference ngầm, task có thể outlive `run`.

Vì vậy **không được có implicit escaping view**.

Compiler phải chọn:

```text
capture by value
```

nếu semantics cho phép, hoặc reject.

Với `move` thì rõ ràng:

```axiom
spawn(move || use(data))
```

ownership chuyển vào task.

### Quy tắc

**ACONC-20 — Escaping Closure Cannot Capture Non-Escaping View**

**ACONC-21 — Spawn Requires Ownership-Safe Captures**

# 23. `Send` và `Share`

Ta giữ đúng phân biệt:

```text
Send  = có thể chuyển ownership sang execution domain khác
Share = có thể cùng đọc an toàn
```

Không suy ra:

```text
Send → Share
Share → Send
```

Ví dụ:

```text
Vec<T>
```

có thể `Send` nếu `T: Send`.

Nhưng không nhất thiết `Share`.

Một immutable shared object có thể:

```text
Share
```

nhưng không nhất thiết transferable theo mọi abstraction.

# 24. `spawn` và Send

```axiom
spawn(move || process(data))
```

Compiler kiểm tra:

```text
closure: Send
```

Nếu closure chứa:

```text
Rc<T>
```

thì có thể reject.

Nếu:

```text
Arc<T>
```

và `T` phù hợp:

```text
Send
```

có thể hợp lệ.

Không cần programmer viết:

```text
where T: Send
```

cho closure bình thường.

Compiler tự suy luận.

# 25. `MutexGuard` → `mut_view`

Đây là abstraction rất đẹp.

```axiom
let guard = mutex.lock()?
guard.value += 1
```

Conceptually:

```text
Mutex
  ↓
MutexGuard
  ↓
mut_view<T>
```

Trong thời gian `guard` tồn tại:

```text
WRITE capability
```

Khi:

```text
guard DROP
```

thì lock release.

Không cần một `unlock()` bắt buộc.

---

# 26. Nhưng guard không được Copy

Nếu:

```axiom
let g2 = g
```

mà `MutexGuard` Copy thì có thể:

```text
g
g2
```

cùng đại diện một lock ownership.

Do đó:

```text
MutexGuard = !Copy
```

và move.

Đây là ví dụ điển hình cho nguyên tắc:

> Resource identity được bảo vệ bằng ownership semantics, không cần GC.

# 27. Channel

Channel:

```axiom
let (tx, rx) = channel<Buffer>()

spawn(move || {
    tx.send(buffer)?
})

let buffer = rx.receive()?
```

`send` chuyển ownership:

```text
producer
   │
   MOVE
   ▼
channel
   │
   MOVE
   ▼
consumer
```

Không phải copy.

Nếu `Buffer` chứa heap allocation lớn, đây là điểm rất quan trọng về performance.

# 28. Channel + view

Không nên cho:

```axiom
tx.send(view(buffer))
```

nếu channel có thể sống lâu hơn `buffer`.

Nếu muốn gửi dữ liệu không copy, phải có abstraction với ownership/storage contract rõ ràng, ví dụ:

```text
Arc<Buffer>
Box<Buffer>
ArenaHandle
```

Chứ `view<T>` không được trở thành một cách "lách" ownership.

**ACONC-22 — Channels Transfer Ownership, Not Unbounded Borrowed Views**

# 29. Atomic + aliasing

Ví dụ:

```axiom
var counter: Atomic<i64>

counter.fetch_add(1, SeqCst)
```

Atomic mutation không giống:

```text
mut_view<i64>
```

Nó là một semantic operation trên atomic object.

Điều này cho phép:

```text
multiple threads
     │
     ├── atomic operation
     ├── atomic operation
     └── atomic operation
```

mà không vi phạm rule:

```text
WRITE + WRITE → conflict
```

vì atomic type cung cấp một synchronization capability khác.

### Quan trọng

Không được cho:

```axiom
let x: mut_view<i64> = view_atomic_as_mut(...)
```

một cách safe.

Atomic và ordinary memory access phải giữ semantics riêng.

# 30. Atomic ≠ volatile

Ta cần giữ:

```text
atomic
```

cho inter-thread synchronization.

Còn:

```text
volatile
```

cho hardware/external observable memory.

Ví dụ MMIO:

```axiom
unsafe {
    volatile_write(addr, value)
}
```

Không được coi volatile là atomic.

Và atomic cũng không tự động có nghĩa:

```text
hardware register access
```

### Invariant

**AATOM-20 — Atomicity And Volatility Are Distinct Semantics**

# 31. Unsafe pointer → view

Ví dụ:

```axiom
unsafe fn bytes(ptr: *const u8, len: usize) -> view<u8> {
    ...
}
```

Điểm quan trọng:

`unsafe` chỉ nói:

> Programmer chứng minh precondition.

Sau khi tạo thành công:

```text
view<u8>
```

thì compiler lại theo dõi nó như capability bình thường.

Không được có:

```text
unsafe
  ↓
compiler ignores everything
```

Mà là:

```text
unsafe operation
      ↓
trusted boundary
      ↓
safe capability
      ↓
normal verifier
```

# 32. Raw pointer và lifetime

```axiom
unsafe {
    let p = ...
    let x = make_view(p, 100)
}
```

Compiler không thể tự chứng minh allocation phía dưới còn sống.

Do đó API unsafe phải có contract.

Ví dụ conceptually:

```text
make_view:
    pointer valid
    region initialized
    region remains alive
    alignment valid
    no conflicting mutation
```

Compiler không cần chứng minh toàn bộ.

Programmer chịu trách nhiệm tại unsafe boundary.

# 33. FFI

Ví dụ:

```axiom
extern "C" fn strlen(ptr: *const u8) -> usize
```

Đây là raw boundary.

Không tự động:

```text
*const u8 → view<u8>
```

vì C không cung cấp length.

Wrapper an toàn:

```axiom
fn length(text: view<CStr>) -> Result<usize, Error>
```

có thể kiểm tra invariant trước khi gọi.

# 34. FFI ownership

Đây là một vấn đề cực kỳ quan trọng.

```axiom
extern "C" fn create_buffer() -> *mut Buffer
extern "C" fn destroy_buffer(p: *mut Buffer)
```

Axiom **không được đoán**:

```text
who owns p?
who frees p?
which allocator?
```

Phải có ABI contract.

Ví dụ:

```text
C allocates
C frees
```

hoặc:

```text
Axiom allocates
Axiom exports free()
```

Không được:

```text
Axiom Drop → random C free()
```

### Invariant

**AFFI-20 — FFI Allocation Ownership Must Be Explicit**

**AFFI-21 — FFI Must Not Guess Allocation Domains**

# 35. `extern "C"` + Drop

Giả sử:

```axiom
@repr(C)
struct Config {
    ptr: *const u8,
    len: usize
}
```

Nếu truyền:

```axiom
extern "C" fn process(config: Config)
```

thì C ABI chỉ thấy data layout.

Không có chuyện C ABI tự biết Axiom `Drop`.

Vì vậy:

> ABI representation và Axiom ownership semantics là hai tầng khác nhau.

Nếu C nhận ownership:

```text

```

phải có explicit contract/API wrapper.

# 36. Panic qua FFI

```axiom
extern "C" fn api(...) -> i32
```

Nếu bên trong Axiom panic:

Có thể:

# 37. Comptime + ownership

```axiom
comptime fn make_table() -> Array<u32, 256> {
    ...
```

Comptime sử dụng cùng type system.

```axiom
struct Node {
```

```text
├── value
└── next
    └── Box<Node>
```

# 40. Recursive ownership + cycle

Không cho:

```text
A owns B
B owns A
```

# 41. Handle + generation

```text
(index, generation)
```

Ví dụ:

# 42. `dyn Trait`

Ví dụ:

```axiom
trait Shape {
    fn area(self: view<Self>) -> f64
}
```

Dynamic:

```axiom
let shape: dyn Shape = ...
```

Semantic representation conceptually:

```text
data_ptr
dispatch_ptr
```

Không có object header bắt buộc.

Static:

```text
impl Shape for Circle
```

có thể được monomorphized/direct call.

Dynamic dispatch chỉ xuất hiện khi programmer chọn:

```text
dyn Shape
```

Điều này rất hợp với mục tiêu performance của Axiom.

# 43. `dyn Trait` + ownership

Một `dyn Trait` owning value phải có storage ownership rõ ràng.

Ví dụ:

```text
Box<dyn Shape>
```

là rõ:

```text
Box → owns dynamic object
```

Trong khi:

```text
view<dyn Shape>
```

là:

```text
non-owning capability
```

Không được để `dyn Trait` tự động imply heap.

# 44. Public API + private type

Ví dụ:

```axiom
struct InternalState {
    ...
}

```

Không hợp lệ nếu `InternalState` private.

```axiom
struct InternalState {
    ...
```

# 45. `impl Trait` + ownership

Ví dụ:

```axiom

    ...
}
```

Nhưng compiler vẫn phải đưa đủ semantic information vào public API fingerprint:


```text
behavior
ownership contract

trait constraints
```

nhưng không biết implementation.

# 46. Một vấn đề cần sửa: `impl Trait` không nên là "dynamic"


|---|---|
| `T` | static |
| `impl Trait` | static |
| generic `T: Trait` | static |
| `dyn Trait` | dynamic |

Không được compiler âm thầm biến `impl Trait` thành vtable.
