Tiếp tục, tôi nghĩ đã đến lúc đi sâu vào phần **ABI + Machine IR + x86-64 backend**, vì đây là chỗ quyết định Axiom có thực sự đạt mục tiêu “native, không cần compiler thứ ba” hay không.

## 48. Đóng băng ABI MIR v0.1

Một lỗi kiến trúc nên tránh là để LIR trực tiếp quyết định register.

Ta giữ:

```text
Typed MIR
   ↓
ABI Lowering
   ↓
ABI MIR
   ↓
LIR
   ↓
Target Lowering
   ↓
Machine IR
```

ABI MIR giải quyết câu hỏi:

> Giá trị semantic này được truyền/nhận như thế nào theo ABI?

Nó **chưa cần biết chính xác RDI hay RSI**.

## 49. ABI classification

Đầu tiên phân loại kiểu:

```text
ABIClass =
    Integer
    Float
    Aggregate
    Memory
    Void
```

Ví dụ:

| Axiom type | ABI class |
|---|---|
| `i8..i64` | Integer |
| `f32/f64` | Float |
| `bool` | Integer |
| pointer | Integer |
| nhỏ struct | Aggregate |
| lớn struct | Memory |
| `()` | Void |

Nhưng **không hard-code “struct 16 bytes = X” trong frontend**.

Việc đó thuộc target ABI.

# 50. Logical ABI location

ABI MIR có location trừu tượng:

```text
AbiLocation =
    IntArg(index)
    FloatArg(index)
    StackArg(offset)
    IntReturn
    FloatReturn
    SRet
```

Ví dụ:

```axiom
fn add(a: i64, b: i64) -> i64
```

ABI MIR:

```text
arg0 → IntArg(0)
arg1 → IntArg(1)
return → IntReturn
```

SysV backend:

```text
IntArg(0) → RDI
IntArg(1) → RSI
IntReturn → RAX
```

Windows x64 backend sau này:

```text
IntArg(0) → RCX
IntArg(1) → RDX
IntReturn → RAX
```

Frontend không thay đổi.

# 51. Aggregate ABI

Đây sẽ là một trong những phần khó nhất của compiler.

Ví dụ:

```axiom
struct Vec2 {
    x: f64,
    y: f64
}
```

Không nên quy định trong Axiom:

```text
Vec2 luôn truyền qua stack
```

Thay vào đó:

```text
Axiom semantic value
        ↓
Target ABI classifier
        ↓
registers / stack / memory
```

Với SysV AMD64, backend sẽ áp dụng luật ABI của SysV.

Với Windows:

```text
khác
```

Với ARM64:

```text
khác nữa
```

---

# 52. Hidden return pointer

Ví dụ một aggregate quá lớn:

```axiom
fn make_big() -> BigStruct
```

ABI có thể biến:

```text
return BigStruct
```

thành:

```text
hidden sret pointer
```

Conceptually:

```text
fn make_big(out: *mut BigStruct)
```

Nhưng **đây không phải source-level transformation**.

ABI MIR mới thấy:

```text
return_mode = SRet
```

Backend mới biến nó thành hidden argument.

Điều này rất quan trọng cho tính trong sáng của language semantics.

---

# 53. Move không phải memcpy

Ví dụ:

```axiom
fn consume(x: BigStruct) {}
```

gọi:

```axiom
consume(value);
```

MIR có:

```text
MOVE value
```

Không được tự động biến thành:

```text
memcpy(temp, value, sizeof(BigStruct))
```

ABI/backend phải xem:

- value đang ở register?
- stack?
- caller storage?
- callee có thể consume trực tiếp không?

Có thể cuối cùng:

```text
không có memcpy
```

Đây là một điểm lớn để Axiom tránh overhead kiểu “high-level abstraction”.

Block:

```text
MachineBlock {

    successors[]

```

Instruction:


# 55. Machine Operand

Tối thiểu:

```text
MachineOperand =
    VirtualReg
    PhysicalReg
    Immediate
    Memory
    StackSlot
    BlockRef
    SymbolRef
```

Memory:

```text
MemoryOperand {
    base
    index
    scale
    displacement
}
```

Đây chính là nơi x86 addressing mode xuất hiện.

Ví dụ:

```text
[rax + rcx*8 + 16]
```

Machine IR:

```text
Memory {
    base = RAX
    index = RCX
    scale = 8
    displacement = 16
}
```

LIR không cần biết `scale`.

---

# 56. Vì sao không đưa addressing mode vào LIR?

LIR:

```text
%p = PTR_ADD %base, %offset
%x = LOAD %p
```

Machine selector có thể nhận ra:

```text
PTR_ADD + LOAD
```

và biến thành:

```asm
mov rax, [rbx + rcx*8]
```

Nếu LIR đã chứa:

```text
base + index * 8
```

thì LIR bị phụ thuộc x86.

Do đó:

> **LIR mô tả semantics; Machine IR mô tả khả năng của CPU.**

# 57. Register classes

x86-64 Genesis:

```text
GPR8
GPR16
GPR32
GPR64
XMM
```

Có thể chưa cần:

```text
YMM
ZMM
MMX
mask registers
```

ở Genesis.

Register descriptor:

```text
PhysicalRegister {
    id
    class
    width
    aliases
    caller_saved
    callee_saved
    reserved
}
```

Ví dụ:

```text
RAX
 ├── EAX
 ├── AX
 ├── AL
```

Đây là alias relationship.

Register allocator phải hiểu:

```text
RAX và EAX không phải hai register độc lập.
```

# 58. Fixed-register constraints

Một số instruction/function có register bắt buộc.

Ví dụ SysV:

```text
return → RAX
```

Call:

```text
arg0 → RDI
arg1 → RSI
```

Một số x86 instruction về sau sẽ yêu cầu:

```text
RAX
RDX:RAX
CL
XMM0
```

Do đó Machine IR phải hỗ trợ:

```text
FixedUse(RAX)
FixedDef(RAX)
```

Không nên hack register allocator bằng các trường hợp đặc biệt.

---

# 59. CALL phải có clobber set

Ví dụ:

```text
CALL foo
```

không chỉ là:

```text
CALL foo
```

Machine IR phải biết:

```text
uses:
    argument registers

defs/clobbers:
    caller-saved registers

return:
    RAX
```

Conceptually:

```text
CALL foo
  uses  RDI RSI
  clobbers RAX RCX RDX R8 R9 R10 R11
  defines RAX
```

Register allocator dựa vào đó để biết value nào phải spill.

---

# 60. Prologue/epilogue không phải source semantics

Axiom source:

```axiom
fn foo() -> i64 {
    ...
}
```

không biết:

```text
push rbp
sub rsp, 32
pop rbp
```

MachineFrame quyết định.

Nếu function là leaf và không cần stack:

```text
foo:
    ...
    ret
```

Nếu không cần callee-saved registers:

```text
không save chúng
```

Đây là một optimization tự nhiên.

# 61. Stack frame

MachineFrame:

```text
MachineFrame {
    stack_size
    alignment
    locals[]
    spills[]
    outgoing_args
    saved_regs[]
}
```

Nhưng:

> **Source local không đồng nghĩa với stack slot.**

Ví dụ:

```axiom
let x = 42;
```

có thể:

```text
x → constant
```

hoặc:

```text
x → RAX
```

hoặc:

```text
x → stack
```

Compiler tự quyết định.

# 62. Register allocation

Genesis dùng **Linear Scan**.

Lý do:

- dễ implement
- compile nhanh
- đủ tốt cho Genesis
- phù hợp AI agent
- sau này có thể thay bằng graph coloring/hybrid mà không đổi frontend.

Pipeline:

```text
Machine IR virtual registers
        ↓
Liveness
        ↓
Live intervals
        ↓
Linear Scan
        ↓
Physical registers
        ↓
Spill
        ↓
Reload insertion
```

---

# 63. Live interval

Ví dụ:

```text
v1 = ...
v2 = ...
v3 = ADD v1, v2
RETURN v3
```

Có thể:

```text
v1: [1,3]
v2: [2,3]
v3: [3,4]
```

Nếu register không đủ:

```text
spill v1
```

ra stack.

---

# 64. Nhưng đừng spill quá sớm

Axiom backend nên có:

```text
SpillCost {
    use_count
    loop_depth
    rematerializable
}
```

Value nằm trong loop:

```text
while (...) {
    x = ...
}
```

đắt hơn để spill.

Genesis có thể dùng heuristic đơn giản:

```text
cost = uses × loop_weight
```

sau này nâng cấp.

---

# 65. Rematerialization

Ví dụ:

```text
v1 = CONST 42
```

Nếu spill `v1`, không nhất thiết:

```text
store [stack], 42
...
load rax, [stack]
```

Có thể:

```text
mov rax, 42
```

Đây là optimization rất rẻ mà đáng làm sớm.

---

# 66. Copy coalescing

Một vấn đề sẽ xuất hiện ngay với ABI:

```text
v0 → RDI
v1 → RSI

v2 = ADD v0, v1
```

Machine selection có thể tạo:

```text
COPY RDI, v0
COPY RSI, v1
ADD ...
```

Nhưng nếu allocator có thể:

```text
v0 = RDI
v1 = RSI
```

thì COPY biến mất.

Do đó cần:

```text
CopyCoalescer
```

trước hoặc trong register allocation.

---

# 67. Phi elimination

MIR:

```text
bb1:
    v3 = PHI(v1, v2)
```

Không tồn tại trực tiếp trong x86.

Phải hạ thành:

```text
predecessor1:
    COPY v3, v1

predecessor2:
    COPY v3, v2
```

sau đó coalescing có thể xóa COPY.

Đây là lý do cần xử lý **parallel copy**, không chỉ copy tuần tự.

---

# 68. Parallel copy

Ví dụ:

```text
v1 → RAX
v2 → RBX

PHI yêu cầu:
RAX → RBX
RBX → RAX
```

Nếu phát tuần tự:

```asm
mov rbx, rax
mov rax, rbx
```

thì sai.

Phải dùng:

```asm
xchg
```

hoặc temporary register/stack.

Do đó backend nên có:

```text
ParallelCopyResolver
```

Đây là một module nhỏ nhưng rất quan trọng.

# 69. Instruction Selection

Không dùng:

```text
switch opcode:
    ADD -> ...
    SUB -> ...
```

cho toàn bộ backend.

Nên có pattern:

```text
Pattern {
    match
    predicate
    emit
    cost
}
```

Ví dụ:

```text
LIR:
    ADD i64 x, y
```

có thể match:

```text
ADD_REG_REG
ADD_REG_IMM
LEA
```

tùy operand.

---

# 70. `ADD` và x86 destructive operands

LIR:

```text
v3 = ADD v1, v2
```

semantic:

```text
v1 unchanged
v2 unchanged
v3 new
```

x86:

```asm
add rax, rbx
```

lại sửa `rax`.

Do đó selector có thể:

```text
COPY v3, v1
ADD v3, v2
```

Sau register allocation:

```text
v3 coalesce v1
```

→

```asm
add rax, rbx
```

Không cần thêm abstraction overhead.

---

# 71. Comparison + branch

LIR:

```text
v3 = ICMP_GT v1, v2
BR v3, true, false
```

Không nhất thiết tạo bool vật lý.

Selector có thể trực tiếp:

```asm
cmp rdi, rsi
jg .true
jmp .false
```

Tức:

```text
ICMP + BR
```

được fuse.

Đây là ví dụ rất rõ tại sao:

> LIR không phải assembly.

Nó biểu diễn semantic intent, để backend chọn instruction sequence tối ưu.

---

# 72. SELECT

LIR:

```text
v3 = SELECT cond, v1, v2
```

x86 có thể:

```asm
cmp ...
cmov...
```

hoặc:

```asm
jcc ...
```

Backend chọn dựa trên cost model.

Do đó Axiom không cần source-level:

```text
if expression → CMOV
```

Compiler tự quyết.

---

# 73. Branch layout

Machine optimizer có thể đổi:

```text
if cond:
    A
else:
    B
```

thành:

```text
fallthrough → A
branch → B
```

hoặc đảo:

```text
fallthrough → B
branch → A
```

để giảm jump.

Đây là machine-level optimization, không ảnh hưởng semantics.

# 74. Encoder architecture

x86 encoder không nên nhận AST/MIR.

Chỉ:

```text

        ↓
Encoder
        ↓
Bytes + Relocations
```

Ví dụ:

```text
X86Instruction {
    opcode
    operands
}
```

Encoding pipeline:

```text
instruction
 ↓
prefix
 ↓
REX
 ↓
opcode
 ↓
ModRM
 ↓
SIB

displacement

immediate
```

# 75. Encoder không được “thông minh”

Đây là một nguyên tắc tốt:

> **Instruction selector quyết định instruction; encoder chỉ encode instruction.**

Không để encoder tự biến:

```text
ADD
```

thành instruction khác.

Nếu muốn:

```text
ADD → LEA
```

thì instruction selection/optimization làm.

Encoder chỉ cần đảm bảo:

```text
MachineInstruction
→ đúng bytes
```

# 76. Relocation

Ví dụ:

```axiom
fn main() -> i64 {
    add(20, 22)
}
```

Nếu `add` ở object khác:

```text
CALL add
```

Machine encoder chưa biết final address.

Nó tạo:

```text
.text
    E8 00 00 00 00

.rela.text
    offset
    symbol = add
    type = R_X86_64_PLT32 / PC32
```

Linker giải quyết.

Đây là lý do Object Writer phải giữ relocation metadata.
