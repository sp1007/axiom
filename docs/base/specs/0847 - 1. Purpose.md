Tiếp tục với **BOOTSTRAP-616**, xây lớp media native thống nhất cho audio, video, camera, codec, capture và streaming, đồng thời nối trực tiếp với GPU/graphics của 614–615.

## Native Media, Audio, Video, Camera, Codec, Capture, Streaming & Hardware Media Acceleration Runtime 5.0

**Status:** Architecture Specification — Complete  
**Layer:** Native Runtime / Media  
**Depends on:** BOOTSTRAP-603, 606, 607, 608, 609, 610, 611, 612, 613, 614, 615  
**Provides foundations for:** media players, recorders, video editors, screen recording, camera applications, audio applications, streaming, conferencing, game capture, media processing, AI media pipelines

---

# 1. Purpose

BOOTSTRAP-616 defines Axiom's native media runtime.

It provides one unified architecture for:

- audio input;
- audio output;
- microphone capture;
- speakers/headphones;
- audio mixing;
- audio processing;
- audio clocks;
- video capture;
- camera devices;
- image/video frames;
- video decoding;
- video encoding;
- hardware media acceleration;
- software codecs;
- media containers;
- demuxing;
- muxing;
- timestamps;
- synchronization;
- audio/video synchronization;
- frame queues;
- zero-copy GPU/media transfer;
- screen/window capture;
- media streaming;
- adaptive buffering;
- seeking;
- recording;
- transcoding;
- media pipeline graphs.

The design must support both:

```text
simple application
    ↓
MediaPlayer
    ↓
Audio + Video
```

and:

```text
professional media engine
    ↓
MediaGraph
    ├── Demuxer
    ├── Decoder
    ├── VideoProcessor
    ├── AudioProcessor
    ├── Encoder
    └── Muxer
```

without requiring every application to understand codec internals.

---

# 2. Design Goals

616 SHALL provide:

1. Native low-latency audio.
2. Native camera access.
3. Hardware video acceleration where available.
4. Software fallback where practical.
5. Explicit media formats.
6. Explicit timestamps.
7. Sample-accurate audio timing where supported.
8. Frame-accurate video timing.
9. Deterministic media pipelines.
10. Zero-copy GPU/media paths where supported.
11. Streaming support.
12. Seekable media.
13. Capture support.
14. A/V synchronization.
15. Backpressure.
16. Bounded buffering.
17. Cancellation.
18. Device-loss recovery.
19. Resource quotas.
20. Security and permission boundaries.
21. Cross-platform operation.
22. No mandatory third-party multimedia runtime dependency.

---

# 3. Non-Goals

616 does not define:

- a complete video editor;
- a DAW;
- a nonlinear editing timeline;
- a GUI;
- a subtitle editor;
- a professional color-grading application;
- a complete audio DSP library;
- a complete computer-vision framework;
- an AI model runtime;
- a game engine.

Those consume 616.

# 13. Presentation Timestamp

`PTS` represents presentation time.

```text
PTS = integer × TimeBase
```

No floating-point timestamp is required.

---

# 14. Decode Timestamp

`DTS` represents decode order.

A packet MAY have:

```text
PTS != DTS
```

for codecs with frame reordering.

---

# 15. Time Base

A media stream has:

```text
TimeBase = numerator / denominator
```

Example:

```text
1 / 90000
```

or:

```text
1 / 48000
```

All timestamp conversion uses integer/rational arithmetic where practical.

---

# 16. Media Duration

Durations are represented using:


The runtime MUST avoid accumulated floating-point drift for long media sessions.

# 50. Real-Time Safety

A real-time audio callback MUST NOT:

- allocate heap memory;
- acquire unbounded locks;
- perform synchronous disk I/O;
- perform DNS/network I/O;

# 477. Core Invariants

### Invariant 1 — Explicit timestamps

Media timing is never inferred from packet order alone.

### Invariant 2 — Explicit clock domains

Every hardware/media timestamp has an identifiable clock domain.

### Invariant 3 — Bounded buffering

No media node may allocate unbounded buffers as an implicit response to backpressure.

### Invariant 4 — Real-time audio safety

Real-time audio paths cannot perform arbitrary blocking operations.

### Invariant 5 — Explicit ownership

Media frame/buffer ownership is deterministic.

### Invariant 6 — Capability security

Camera, microphone, screen capture, protected media and native device access require explicit authority.

### Invariant 7 — Hardware acceleration is optional

Applications must remain valid when hardware acceleration is unavailable.

### Invariant 8 — No mandatory multimedia framework

The core Axiom media runtime does not depend on FFmpeg, GStreamer or another third-party multimedia framework.

### Invariant 9 — GPU interoperability

Video frames can use the 615 resource model when the platform permits.

### Invariant 10 — Device generations

Removed/recreated devices cannot be confused with their previous instances.

### Invariant 11 — No language GC dependency

Media resource lifetime is deterministic and independent of garbage collection.

### Invariant 12 — Synchronization is explicit

A/V correction policies are represented by the media synchronization subsystem rather than hidden arbitrary timing behavior.

# 494. Final Architecture Decision

BOOTSTRAP-616 establishes:

> **Axiom's media architecture is a timestamp-driven, graph-based, explicitly synchronized runtime in which audio, video, capture, codecs, containers, streaming and hardware acceleration share one resource and scheduling model.**

The most important architectural decision is that **media is not built as a collection of unrelated APIs**.

Instead:

```text
Audio
Camera
Video
Codec
Streaming
Capture
GPU
Storage
Network
```

all participate in the same:

```text
MediaGraph
     ↓
Format Negotiation
     ↓
Resource Planning
     ↓
Clock Planning
     ↓
Scheduling
     ↓
Execution
```

This permits Axiom to implement:

```text
simple media player
        │
        ├── video editor
        │
        ├── screen recorder
        │
        ├── streaming server
        │
        ├── camera application
        │
        ├── audio application
        │
        ├── game capture
        │
        └── AI media pipeline
```

without creating separate incompatible runtime architectures.
