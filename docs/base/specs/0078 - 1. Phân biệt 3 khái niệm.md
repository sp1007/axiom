Tiếp tục với **Pinning + Stable Address**. Đây là phần nên chốt ngay sau Allocation & Storage, vì nó giải quyết một câu hỏi rất thực tế:

> Nếu Axiom cho phép compiler tự do relocate object, vậy khi nào programmer được phép yêu cầu một địa chỉ không đổi?

Tôi đề xuất **không đưa `pin`/`stable address` thành một hệ thống lifetime phức tạp**. Chỉ cần một semantic contract rõ ràng.

---

# 1. Phân biệt 3 khái niệm

Axiom nên phân biệt:

```text
Value
Storage Identity
Stable Address
```

Ví dụ:

```axiom
var x = Foo(...)
```

chỉ có:

```text
Value
```

Nếu:

```axiom
var x = Box.create(Foo(...))
```

thì có:

```text
Value
   +
Storage Identity
```

Nhưng chưa nhất thiết:

```text
Stable Address
```

Nếu programmer yêu cầu:

```axiom
let p = stable_address(x)
```

thì:

```text
Value
   +
Storage Identity
   +
Stable Address
```

---

# 2. Tôi không muốn `Box` mặc định đồng nghĩa với pin

Đây là điểm quan trọng.

Một cách thiết kế dễ mắc phải là:

```text
Box<T> = heap + stable address
```

Tôi không nghĩ nên làm vậy.

`Box<T>` nên có nghĩa:

> `T` có dynamic storage ownership.

Còn stable address là một **property riêng**.

Lý do: compiler có thể muốn tối ưu:

```axiom
fn f() {
    let x = Box.create(123)
    return *x
}
```

thành:

```text
return 123
```

Nếu không có address observable.

Thậm chí:

```text
Box allocation
    ↓
escape analysis
    ↓
eliminate allocation
```

Đây là optimization rất giá trị.

---

# 3. Khi nào compiler bắt buộc giữ địa chỉ?

Chỉ khi **address trở thành observable**.

Ví dụ:

```axiom
unsafe {
    let p = address_of(x)
}
```

hoặc:

```axiom
ffi_use_pointer(x)
```

hoặc API có contract:

```axiom
stable_storage(x)
```

Khi đó compiler phải bảo đảm:

```text
address(x) = constant
```

trong phạm vi contract.

Đây là nguyên tắc:

> **Address observability creates a relocation constraint.**

---

# 4. `Vec` là ví dụ quan trọng nhất

Giả sử:

```axiom
var v = Vec<i32>()
v.push(10)
v.push(20)
```

Storage có thể:

```text
capacity = 2
address = 0x1000
```

Sau:

```axiom
v.push(30)
```

compiler/library có thể relocate:

```text
0x1000 → 0x5000
```

Điều đó hoàn toàn hợp lệ.

Nhưng:

```axiom
let x = view(v)
```

thì:

```text
x
 ↓
region(v)
```

đang tồn tại.

Nếu `push()` có khả năng relocation:

```text
x ───────────────┐
                 │
v.push() ──X─────┘
```

→ compile error.

Sau:

```axiom
use(x)
```

capability hết hạn:

```text
x → EXPIRED
```

thì:

```axiom
v.push(30)
```

được phép.

---

# 5. Stable address nên là một capability

Tôi đề xuất mô hình:

```text
Stable<T>
```

không nhất thiết là một Core type bắt buộc phải có syntax đặc biệt.

Nó là một **storage contract/capability**.

Ví dụ API library có thể là:

```axiom
let x = stable(box)
```

hoặc một abstraction tương đương.

Semantic:

```text
ordinary storage
       │
       ▼
  relocation allowed
       │
       │ stable()
       ▼
stable storage
       │
       └── relocation forbidden
```

---

# 6. Stable không có nghĩa là immortal

Cực kỳ quan trọng.

```text
stable address
```

không đồng nghĩa:

```text
permanent lifetime
```

Ví dụ:

```axiom
fn foo() {
    let x = stable(Box.create(Foo(...)))
    use(x)
}
```

Địa chỉ có thể ổn định trong lifetime của storage:

```text
┌───────────────────────┐
│ Stable Storage        │
│                       │
│ address = 0x5000      │
│                       │
│ lifetime              │
└───────────────────────┘
```

Khi owner chết:

```text
DROP
 ↓
storage released
```

Địa chỉ không còn hợp lệ.

---

# 7. Stable address và `view` vẫn là hai thứ khác nhau

Ví dụ:

```axiom
let b = stable(Box.create(Foo(...)))
let x = view(b)
```

Ta có:

```text
b
│
├── owns storage
│
└── stable address
      │
      └── x = read capability
```

`x` không trở thành owner.

Nếu:

```axiom
return x
```

compiler vẫn phải kiểm tra lifetime.

Stable address **không biến view thành static reference**.

---

# 8. Self-referential structure

Đây là nơi pinning thực sự cần thiết.

Ví dụ concept:

```text
Object A
 ├── data
 └── pointer → data
```

Nếu A relocate:

```text
0x1000 → 0x8000
```

pointer nội bộ có thể trở thành dangling/invalid.

Axiom không nên cho phép kiểu này trong safe code chỉ vì programmer tạo raw pointer.

Safe solution:

```text
Self-referential object
        │
        ▼
Stable storage required
```

Hoặc tốt hơn nữa, trong nhiều trường hợp:

```text
self-reference
```

được thay bằng:

```text
index
handle
ID
offset
```

để tránh pinning.

---

# 9. Nhưng đừng biến self-reference thành một feature Core phức tạp

Tôi đề xuất:

### Safe Core

Cho phép:

```text
value
view
mut_view
owner
stable storage contract
```

Nhưng không cần một hệ thống:

```text
Pin<'a>
Unpin
Pin<&mut T>
Pin<Box<T>>
...
```

như Rust.

Compiler chỉ cần kiểm tra:

```text
stable storage required?
```

Nếu có:

```text
storage cannot relocate
```

Thế là đủ cho semantic model v0.1.

---

# 10. Async là nơi pinning phải được xử lý đặc biệt

Ví dụ:

```axiom
async fn foo() {
    var x = BigStruct(...)
    await something()
    use(x)
}
```

Compiler biến thành state machine:

```text
FutureState {
    state
    x
}
```

Nếu future nằm ở:

```text
stack
```

và được move sang nơi khác:

```text
stack A
   ↓
move
stack B
```

thì địa chỉ của `x` cũng có thể thay đổi.

Do đó:

> **Async state không mặc định có stable address.**

---

# 11. Vì vậy view qua `await` phải rất nghiêm

Ví dụ:

```axiom
async fn foo() {
    var x = Foo(...)

    let v = view(x)

    await something()

    use(v)
}
```

Tôi vẫn đề xuất rule v0.1:

```text
mut_view across await → reject
```

và:

```text
view across await → chỉ cho phép nếu compiler chứng minh provenance/storage hợp lệ
```

Nhưng có một cách đơn giản hơn cho v0.1:

```text
Any capability borrowed from a local
cannot cross await
```

Sau này có thể nới.

Điều này làm compiler đơn giản và tránh một lượng lớn bug.

---

# 12. `move` Future cũng phải bảo toàn semantics

Ví dụ:

```axiom
let task = foo()
spawn(task)
```

Compiler có thể:

```text
Future object
    ↓
move
    ↓
executor storage
```

Nếu future có:

```text
x
```

thì compiler phải cập nhật provenance:

```text
old storage
    ↓ move
new storage
```

Một **semantic move** không làm địa chỉ ổn định.

Nếu một object bên trong cần stable address:

```text
Future
 └── Stable<T>
```

thì storage của `T` phải đáp ứng contract đó.

---

# 13. `Vec` + stable address

Đây là trường hợp dễ gây nhầm:

```axiom
var v = Vec<Foo>()
let p = stable_address(v[0])
```

Có hai khả năng.

### Cách tôi đề xuất

API này **không hợp lệ nếu Vec có thể relocate**.

Phải dùng abstraction khác:

```text
Vec<Stable<Foo>>
```

hoặc:

```text
StableVec<Foo>
```

hoặc:

```text
Pool<Foo>
```

Ví dụ:

```text
Vec
 ├── fast contiguous
 └── relocation allowed

StablePool
 ├── stable slots
 └── relocation forbidden
```

Như vậy programmer chọn đúng semantic requirement.

---

# 14. `reserve()` không nên tạo stable address

Ví dụ:

```axiom
v.reserve(1024)
```

chỉ có nghĩa:

```text
capacity >= 1024
```

Không có nghĩa:

```text
address stable forever
```

Điều này rất quan trọng.

Nếu API muốn:

```text
no relocation
```

thì phải có contract riêng.

Không được suy luận:

```text
capacity sufficient
→ address stable
```

vì sau này implementation có thể thay đổi storage strategy.

---

# 15. Memory mapping cũng phù hợp mô hình này

Ví dụ:

```text
mmap()
```

thường tạo storage có address semantics rõ ràng.

Ta có:

```text
MappedRegion
    │
    ├── storage identity
    ├── address
    ├── size
    └── external backing
```

Compiler không được biến nó thành register hay stack.

Đây chính là lúc:

```text
Storage Abstraction
```

có contract mạnh hơn value semantics.

---

# 16. DMA/GPU cũng vậy

Ví dụ GPU buffer:

```text
GpuBuffer<T>
```

không nên được compiler coi như:

```text
ordinary Vec<T>
```

vì backing storage có thể nằm ngoài CPU address space.

Semantic contract có thể là:

```text
EXTERNAL
DEVICE
ADDRESSABLE
TRANSFER
SYNC
```

Nhưng đây là library/platform layer.

Core chỉ cần hiểu các effect/capability cần thiết.

# 19. Các invariant mới nên freeze

Tôi đề xuất thêm:

**ASP-01 — Stable Address Is Explicit**

> Stable address is never implied by ordinary ownership.

**ASP-02 — Relocation Is Default**

> Storage may relocate unless a semantic contract prohibits relocation.

**ASP-03 — Address Exposure Is Observable**

> Exposing an address creates a storage constraint that optimization must preserve.

**ASP-04 — Stable Does Not Mean Permanent**

> Stable address guarantees address stability only for the lifetime of the associated storage contract.

**ASP-05 — Box Does Not Imply Pinning**

> Dynamic ownership and stable addressing are independent properties.

**ASP-06 — Reserve Does Not Guarantee Stability**

> Capacity reservation does not imply stable address.

**ASP-07 — View Does Not Imply Stability**

> A view is a capability into storage; storage stability must be established separately.

**ASP-08 — Async State Is Relocatable by Default**

> Async state machines do not inherently guarantee stable addresses.

**ASP-09 — Self-Reference Requires Stability**

> Safe self-referential storage requires a stable-address guarantee or an equivalent non-address-based representation.

**ASP-10 — Physical Storage Is Not Semantic Type**

> Stack, heap, arena, pool, slab, mapped, and device storage are storage strategies/contracts, not universal type categories.
