Tiếp tục từ `ELF-001`. Đây là bước rất quan trọng vì nó kiểm chứng rằng **x86-64 backend thực sự độc lập với platform**, chứ không phải backend Windows được viết riêng rồi sau đó copy sang Linux.

# ELF-001 — x86-64 Linux ELF64

## 1. Mục tiêu

Axiom phải có thể đi từ:

```text
Axiom Source
    ↓
Verified MIR
    ↓
Optimizer
    ↓
LIR
    ↓
x86-64 ISel
    ↓
Machine IR
    ↓
Register Allocation
    ↓
Frame Layout
    ↓
ELF64 Object
    ↓
Axiom ELF Linker
    ↓
Linux ELF Executable
```

Điểm quan trọng:

> **Toàn bộ phần từ LIR đến Machine IR phải được dùng lại từ Windows.**

Chỉ thay đổi:

```text

    COFF
    PE
    Windows startup
    Windows imports

Linux:
    SysV AMD64 ABI
    ELF64
    ELF linker
    Linux startup
    ELF dynamic/static linking
```

# 9. Red Zone

Đây là một điểm Linux/SysV có mà Windows không có.

SysV AMD64 có **128-byte red zone** phía dưới `RSP` cho leaf code trong điều kiện ABI cho phép.

Windows x64 không có cơ chế tương đương.

Vì vậy không được để:

```text
FrameLayout
```

tự động giả định:

```text
RSP - local_size
```

Mà phải có:

```text
AbiFramePolicy {
    stack_alignment
    has_red_zone
    red_zone_size
    ...
}
```

MVP tôi đề xuất:

> **Ban đầu Axiom có thể không sử dụng red zone.**

Điều này đơn giản hơn và tránh tạo dependency sớm giữa optimizer và ABI.

Sau này optimizer có thể bật:

```text
leaf + small locals + no async/signal constraints
    → red-zone optimization
```

Đây là optimization, không phải semantic requirement.

# 27. Shared x86 backend boundary

```text

 ↓
Object format
 ↓
```

# 29. Invariants mới

## AELF-20

ELF writer không phụ thuộc semantic frontend.

## AELF-21

ELF object là relocatable artifact hợp lệ độc lập với executable linker.

## AELF-22

Machine encoder không resolve ELF symbols.

## AELF-23

Relocation semantics được biểu diễn trước khi được map sang ELF relocation type.

## AELF-24

ELF section identity độc lập với source module identity.

## AELF-25

ELF section và ELF segment là hai abstraction khác nhau.

## AELF-26

Program headers được linker tạo từ final memory layout.

## AELF-27

ELF linker không cần external linker.

## AELF-28

Linux ABI không được hard-code vào x86 register allocator.

## AELF-29

SysV AMD64 argument classification thuộc ABI lowering.

## AELF-30

Stack alignment thuộc ABI/frame planning.

## AELF-31

Red-zone usage là target ABI policy, không phải x86 instruction-selection rule.

## AELF-32

Linux startup không thuộc generic x86 backend.

## AELF-33

Linux syscall semantics không thuộc Axiom Core.

## AELF-34

ET_EXEC và PIE/dynamic linking là các linker profiles khác nhau.

## AELF-35

Static executable không bắt buộc libc.

## AELF-36

Freestanding Linux binary không bắt buộc Axiom runtime.

## AELF-37

Same source + same semantic input must produce equivalent observable result across supported targets.

## AELF-38

Target-specific lowering cannot alter Axiom language semantics.

## AELF-39

ELF generation is deterministic.

## AELF-40

ELF reader/writer round-trip preserves semantic object representation.

```text
  ↓
ELF-004 — ELF64 Linker
  ↓
ELF-005 — Linux Startup
  ↓
ELF-006 — Static Executable
  ↓
ELF-007 — PIE
  ↓
ELF-008 — Linux FFI
  ↓
ELF-009 — Dynamic Linking
  ↓
ELF-010 — Linux Conformance
```

Nhưng **không nên làm PIE/dynamic linking ngay**.

Mốc quan trọng trước tiên là:

```text
Axiom
 → x86-64 Machine IR
 → SysV ABI
 → ELF relocatable
 → Axiom ELF linker
 → Linux native executable
```

Khi mốc này chạy được, Axiom đã chứng minh được một điều rất lớn:

> **Compiler backend không bị khóa vào Windows.**

Và khi Windows PE + Linux ELF cùng chạy được từ một x86-64 Machine IR, kiến trúc tiếp theo tự nhiên sẽ là **AArch64-001**. Khi đó ta mới kiểm chứng tầng thứ hai: không chỉ khác OS/ABI/object format, mà **khác hoàn toàn instruction set** nhưng vẫn dùng chung LIR → target lowering architecture.
