Được. Ta tiếp tục từ **Effect System**, nhưng tôi muốn thiết kế nó theo hướng rất “Axiom”: **compiler phải biết effect, programmer không phải gánh annotation**.

## Axiom Effect System v0.1

Mục tiêu không phải tạo một hệ thống effect kiểu học thuật phức tạp, mà là cung cấp cho compiler đủ thông tin để trả lời:

> Function này có thể làm gì, và compiler được phép tối ưu đến đâu?

### 1. Effect không phải type

Ví dụ:

```axiom
fn add(a: i64, b: i64) -> i64 {
    a + b
}
```

Type:

```text
(i64, i64) -> i64
```

Effect:

```text
PURE
```

Còn:

```axiom
fn save(file: File, data: view<u8>) -> Result<(), IOError> {
    ...
}
```

Type:

```text
(File, view<u8>) -> Result<(), IOError>
```

Effect có thể là:

```text
READ
IO
```

Effect là **property của computation**, không phải một phần trực tiếp của value type.

# 2. Bộ effect cơ bản

Tôi đề xuất v0.1 chỉ cần:

```text

SYNC

PANIC
UNSAFE
FFI
```

Nhưng chúng không nhất thiết độc lập hoàn toàn.

Có thể tổ chức thành nhóm:

```text
Memory:
    READ
    WRITE
    ALLOC
    DROP

Control:
    PANIC
    SUSPEND

Concurrency:
    ATOMIC
    SYNC
    SPAWN

External:
    IO

Safety:
    UNSAFE
```

`PURE` không phải effect thực hiện hành động; nó là trạng thái:

```text
no observable effect
```

# 3. Compiler tự suy luận effect

Ví dụ:

```axiom
fn square(x: i64) -> i64 {
    x * x
}
```

Compiler:

```text
square
effects = {}
```

Sau đó:

```axiom
fn calc(x: i64) -> i64 {
    square(x) + 10
}
```

Compiler suy ra:

```text
calc
effects = {}
```

Nếu:

```axiom
fn load(path: Text) -> Result<Data, Error> {
    ...
}
```

thì:

```text
load
effects = { IO }
```

và:

```axiom
fn process(path: Text) -> Result<i64, Error> {
    let data = load(path)?;
    calculate(data)
}
```

suy ra:

```text
process
effects = { IO }
```

Effect propagation:

```text
caller
   │
   ├── pure function
   │       └── {}
   │
   └── IO function
           └── IO
```

# 4. Effect lattice

Không nên coi effects đơn giản là một enum.

Một function có thể có:

```text
{ READ, ALLOC, IO }
```

Do đó:

```text
EffectSet = bitset
```

rất phù hợp với compiler.

Ví dụ:

```text
000000000000
```

= pure

```text
000000000001
```

= READ

```text
000000000101
```

= READ + ALLOC

Compiler có thể union rất nhanh:

```text
Effects(f)
=
OwnEffects(f)
∪
Effects(callee1)
∪
Effects(callee2)
...
```

# 5. Nhưng READ/WRITE cần gắn với region

Đây là chỗ Effect System nối với Memory Model.

Không nên chỉ nói:

```text
READ
WRITE
```

mà cần:

```text
READ(region A)
WRITE(region B)
```

Ví dụ:

```axiom
fn length(v: view<Vec>) -> usize
```

có:

```text
READ(v)
```

Trong khi:

```axiom
fn clear(v: mut_view<Vec>)
```

có:

```text
WRITE(v)
```

Compiler có thể chứng minh:

```text
READ(A)
+
WRITE(B)
```

an toàn nếu:

```text
A DISJOINT B
```

Đây chính là lý do **region model** trước đó rất quan trọng.

---

# 6. Effect không nên bắt programmer viết

Tôi **không khuyến nghị**:

```axiom
fn foo() pure
```

hay:

```axiom
fn foo() effects(IO, ALLOC)
```

làm syntax bắt buộc.

Vì nó tạo ra một lớp bureaucracy mới.

Thay vào đó:

```text
source
 ↓
type checking
 ↓
effect inference
 ↓
effect summary
```

Compiler tự biết.

Nếu programmer muốn assertion:

```axiom
@pure
fn foo() ...
```

có thể tồn tại sau này.

Khi đó:

```text
@pure
fn foo() {
    file.read()
}
```

→ compile error.

Annotation là **contract**, không phải mô tả bắt buộc.

---

# 7. Effect dùng cho optimization

Đây mới là giá trị lớn.

Nếu:

```text
f = PURE
```

compiler có thể:

- constant fold
- CSE
- inline
- eliminate unused call
- reorder
- evaluate tại compile time
- vectorize
- duplicate computation nếu rẻ

Ví dụ:

```axiom
let a = square(x);
let b = square(x);
```

có thể trở thành:

```text
let t = square(x);
let a = t;
let b = t;
```

nếu `square` pure.

Ngược lại:

```axiom
let a = random();
let b = random();
```

không được gộp thành một call nếu `random()` có observable effect.

---

# 8. Effect + concurrency

Đây là phần rất mạnh.

Hai computation:

```text
A = READ(region1)
B = WRITE(region2)
```

có thể chạy song song nếu:

```text
region1 DISJOINT region2
```

Trong khi:

```text
A = READ(region1)
B = WRITE(region1)
```

thì có dependency.

Compiler có thể dùng effect/region information để hỗ trợ:

```text
parallelization
vectorization
task scheduling
```

mà không cần programmer khóa mọi thứ bằng mutex.

Tuy nhiên tôi **không đề nghị compiler tự động biến code tuần tự thành thread** trong v0.1.

Effect system chỉ cung cấp **proof/fact**.

---

# 9. `UNSAFE` nên là effect đặc biệt

Ví dụ:

```axiom
unsafe fn read_memory(p: *const u8) -> u8 {
    ...
}
```

Compiler ghi:

```text
effects = { UNSAFE }
```

Nhưng cần phân biệt:

```text
UNSAFE
```

với:

```text
UNDEFINED
```

`unsafe` không có nghĩa compiler ngừng kiểm tra mọi thứ.

Nó nghĩa:

> Programmer đã bước qua một boundary mà compiler không thể chứng minh đầy đủ.

Ví dụ vẫn phải kiểm tra:

```text
type correctness
CFG correctness
ABI correctness
register constraints
```

nhưng memory safety của raw pointer là trách nhiệm của programmer.

---

# 10. FFI effect

FFI là một boundary đặc biệt.

Ví dụ:

```axiom
extern "C" fn printf(...) -> i32
```

Compiler mặc định nên coi unknown external function là:

```text
READ
WRITE
IO
FFI
```

thậm chí conservative hơn:

```text
UNKNOWN
```

Tôi đề xuất thêm effect:

```text
UNKNOWN
```

cho những function mà compiler chưa biết semantic behavior.

Khi đó optimizer phải bảo thủ.

Ví dụ:

```text
UNKNOWN
```

có thể:

- đọc memory
- ghi memory
- modify global
- perform IO
- panic
- synchronize

Do đó compiler không được tùy tiện reorder.

---

# 11. Nhưng FFI có thể khai báo contract

Sau này:

```axiom
extern "C"
@effects(readonly)
fn strlen(s: *const u8) -> usize
```

hoặc compiler có intrinsic knowledge.

Khi đó:

```text
strlen
effects = READ
```

thay vì:

```text
UNKNOWN
```

Điều này rất hữu ích cho hiệu năng FFI.

---

# 12. `ALLOC` và `DROP`

Ví dụ:

```axiom
fn make_buffer() -> Buffer {
    Buffer.new(1024)
}
```

effect:

```text
ALLOC
```

Nhưng compiler có thể phát hiện:

```text
Buffer
 ↓
returned
```

nên allocation thực sự cần thiết.

Ngược lại:

```axiom
fn temp() {
    let x = Box.new(42);
    println(x);
}
```

compiler có thể không cần heap allocation nếu:

- address không escape
- storage identity không observable
- ABI không yêu cầu stable address.

Khi đó semantic effect vẫn có thể là:

```text
ALLOC
```

nhưng machine implementation:

```text
no actual allocation
```

Đây là distinction rất quan trọng:

```text
semantic effect ≠ physical instruction
```

---

# 13. `DROP` cũng vậy

```axiom
let file = File.open(...)?;
```

File có:

```text
Drop
```

Compiler phải đảm bảo cleanup.

Nhưng nếu:

```axiom
let x = Point { x: 1, y: 2 };
```

Point không có Drop.

Không cần runtime cleanup.

Thậm chí một resource có Drop nhưng compiler chứng minh resource không bao giờ cần cleanup ở một path cụ thể thì có thể tối ưu **chỉ khi semantics vẫn được giữ**.

# 14. Async effect

`await` nên tạo:

```text
SUSPEND
```

Ví dụ:

```axiom
async fn download() -> Data {
    let x = await fetch();
    process(x)
}
```

Effect:

```text
SUSPEND
IO
```

Compiler phải xác định state nào sống qua suspension:

```text
before await
     ↓
SUSPEND
     ↓
state machine
     ↓
resume
```

Đây là nơi effect system + ownership verifier gặp nhau.

---

# 15. Effect và `await`

Một nguyên tắc rất mạnh:

> Mọi giá trị/capability sống qua `SUSPEND` phải được kiểm chứng riêng.

Ví dụ:

```axiom
async fn foo(v: mut_view<Data>) {
    await something();
    modify(v);
}
```

v0.1:

```text
ERROR
```

vì `mut_view` không được sống qua suspension.

Nhưng:

```axiom
async fn foo(data: Data) {
    await something();
    modify(data);
}
```

có thể hợp lệ vì ownership của `data` nằm trong async state machine.

Điều này khiến async không cần một memory model riêng.

# 16. Compile-time effect

Đây là một điểm tôi nghĩ Axiom có thể làm rất sạch.

`comptime` chỉ được gọi function nếu effect của nó nằm trong capability được phép.

Mặc định:

```text
COMPTIME_ALLOWED =
{
    PURE,
    READ_CONST,
    ALLOC_TEMP
}
```

Ví dụ:

```axiom
const TABLE = comptime make_table();
```

`make_table()`:

```text
PURE + ALLOC
```

→ OK.

Nhưng:

```axiom
const X = comptime read_file("secret.txt");
```

nếu compiler/build profile không cấp filesystem capability:

```text
ERROR
```

Như vậy compile-time execution không biến compiler thành một shell tùy ý.

# 20. Bộ invariant mới

Tôi đề nghị thêm:

### AEF-01 — Effect Soundness

Effect summary phải bao phủ mọi observable effect của function.

### AEF-02 — Effect Inference

Compiler tự suy luận effect từ body và callees.

### AEF-03 — Effect Is Not Type

Effect không làm thay đổi identity của value type.

### AEF-04 — Region-Aware Memory Effects

READ/WRITE phải có thể gắn với memory region.

### AEF-05 — Unknown Conservatism

Unknown external behavior phải khiến optimizer bảo thủ.

### AEF-06 — Pure Optimization

Compiler chỉ được reorder/eliminate/duplicate computation khi effect semantics cho phép.

### AEF-07 — Unsafe Boundary

`UNSAFE` đánh dấu boundary trách nhiệm của programmer, không vô hiệu hóa toàn bộ compiler verification.

### AEF-08 — FFI Boundary

FFI không có contract phải được xử lý conservative.

### AEF-09 — Suspend Boundary

`SUSPEND` tạo điểm kiểm tra ownership/capability riêng.

### AEF-10 — Compile-Time Capability

Compile-time execution chỉ được sử dụng effects được cấp phép.

### AEF-11 — Semantic/Physical Separation

Semantic `ALLOC`, `DROP`, `COPY`, `MOVE` không bắt buộc tương ứng với machine instruction.

### AEF-12 — Effect Erasure

Effect metadata không cần xuất hiện trong binary nếu không có runtime-observable consequence.

## Và đây là điểm tôi muốn Axiom đi xa hơn

Sau Effect System, chúng ta có thể gom toàn bộ các hệ thống trước đây thành một mô hình thống nhất:

```text
                    ┌──────────────┐
                    │    VALUE     │
                    └──────┬───────┘
                           │
                    Ownership state
                           │
              ┌────────────┴────────────┐
              │                         │
        Capability                   Storage
              │                         │
        READ / WRITE               local / heap
        provenance                 arena / static
              │                         │
              └──────────┬──────────────┘
                         │
                       Region
                         │
                         ▼
                      Effects
                         │
          ┌──────────────┼──────────────┐
          │              │              │
       Memory        Concurrency     Control
          │              │              │
       READ/WRITE     Send/Share      await
       ALLOC/DROP     Atomic          panic
                         │
                         ▼
                   Optimization
                         │
                         ▼
                    Machine Code
```

**Đây mới là “xương sống” của Axiom.**

Nếu xương sống này đúng, những thứ như `Vec`, `Arc`, `Mutex`, `async`, closure, generic, trait, allocator... chủ yếu trở thành **các abstraction xây trên cùng một semantic engine**, thay vì mỗi feature lại phát minh một hệ thống memory/concurrency riêng.

### Bước tiếp theo tôi đề xuất

Sau Effect System, ta nên đi vào **Axiom Control Flow & `Result`/`Option`/`panic` v0.1**, đặc biệt là:

```text
return
break
continue
?
defer? / cleanup?
panic
unwind vs abort
Drop trên mọi CFG path
```

Đây là phần rất dễ làm sai nếu không thiết kế trước, vì nó quyết định trực tiếp **Drop elaboration + MIR cleanup + optimizer + async state machine**.
