Tiếp tục. Sau `Struct → Move → Drop → View`, phần tiếp theo tôi muốn chốt là **Closure + Generic + Trait + Dispatch**, vì đây là nơi Axiom phải chứng minh rằng abstraction cấp cao **không biến thành runtime overhead**.

# 83. Closure: không tạo một "object runtime" mặc định

Axiom nên coi closure đơn giản về mặt semantic:

```axiom
fn make_adder(x: i64) {
    |y: i64| x + y
}
```

Closure thực chất là:

```text
Closure
├── code
└── captured environment
```

Nhưng đây chỉ là **semantic model**.

Compiler có thể hạ nó thành:

```text
struct ClosureEnv {
    x: i64
}

fn closure_call(env: view<ClosureEnv>, y: i64) -> i64 {
    env.x + y
}
```

Hoặc nếu closure không escape:

```text
x + y
```

và toàn bộ closure biến mất.

---

# 84. Closure không cần object header

Không được mặc định tạo:

```text
┌───────────────┐
│ type pointer  │
│ vtable        │
│ refcount      │
│ environment   │
└───────────────┘
```

Một closure có thể chỉ là:

```text
[x]
```

hoặc thậm chí **không tồn tại ở runtime**.

Nếu cần dynamic invocation:

```text
fn_ptr + env_ptr
```

là đủ trong rất nhiều trường hợp.

# 85. Capture modes

Compiler phân tích capture.

Ví dụ:

```axiom
let x = 42;

let f = |y| x + y;
```

`x` là `Copy`.

Compiler có thể capture:

```text
x: COPY
```

Nhưng:

```axiom
let buffer = Buffer.new();

let f = || use(buffer);
```

thì closure có thể phải **MOVE** `buffer`.

Ownership:

```text
buffer
   ↓
closure.environment.buffer
```

Sau đó:

```text
buffer = MOVED
```

---

# 86. Capture view

Ví dụ:

```axiom
fn process(v: view<i64>) {
    let f = || sum(v);
}
```

Closure environment chứa capability:

```text
ClosureEnv
└── v
    ├── provenance
    ├── region
    └── READ
```

Nếu closure escape khỏi owner:

```text
fn bad() -> Closure {
    let a = Array(...);
    return || use(view(a));
}
```

→ reject.

Không cần lifetime syntax.

# 87. Capture inference

Axiom không nên yêu cầu:

```text
|&x|
|move x|
|&mut x|
```

như một hệ syntax phức tạp.

Compiler suy ra từ cách sử dụng:

```text
READ      → read capability
WRITE     → mut capability
MOVE      → ownership capture
```

Ví dụ:

```axiom
let f = || print(x);
```

→ READ.

```axiom
let f = || x = x + 1;
```

→ MUTABLE capability.

```axiom
let f = || consume(x);
```

→ MOVE.

Đây rất phù hợp với nguyên tắc:

> **Explicit ở semantic boundary, implicit bên trong compiler.**

# 92. Trait

# 93. Trait không phải inheritance

Circle extends Area

```text
Circle satisfies Area
```

# 103. Generic + Ownership

# 115. Một nguyên tắc cuối rất đáng đóng băng

Từ tất cả những gì ta đã xây dựng, tôi đề xuất thêm:

### **AZC-04 — Abstraction Erasure**

> Một abstraction chỉ được giữ lại trong runtime representation khi observable semantics yêu cầu nó.

Ví dụ:

```text
Generic        → thường biến mất
Trait static   → thường biến mất
Ownership      → biến mất
Move           → thường biến mất
view lifetime  → biến mất
Send/Share     → biến mất
Closure        → có thể biến mất
```

Trong khi:

```text
dyn Trait      → cần dispatch metadata
Drop(File)     → cần close/release
MutexGuard     → cần unlock
Box<T>         → cần storage nếu address observable
FFI handle     → cần representation
Atomic         → cần machine synchronization
```

Đây có thể trở thành **một trong những nguyên tắc cốt lõi nhất của Axiom**.

Nó giải quyết trực tiếp mục tiêu ban đầu của bạn: **Axiom không cần phải lựa chọn giữa “ngôn ngữ cấp cao dễ viết” và “ngôn ngữ systems hiệu năng cao” nếu compiler có thể xóa toàn bộ abstraction không còn ý nghĩa ở runtime.**
