Tiếp tục. Tôi sẽ chốt **Representation + Layout + Union + Bitfield + ABI Interop v0.1**. Đây là phần rất quan trọng vì Axiom phải đủ thấp để viết kernel/driver/FFI nhưng không biến Core thành một bản sao của C.

# 1. Quyết định lớn: `union`

Tôi đề xuất:

> **Có `union`, nhưng không đưa C-style unrestricted union vào safe core.**

Axiom nên phân biệt hai thứ:

```text
enum      = type-safe sum
union     = overlapping storage
```

Ví dụ enum:

```axiom
enum Value {
    Int(i64)
    Float(f64)
    Text(Text)
}
```

Compiler luôn biết variant hiện tại.

Union:

```axiom
union Register {
    u32: u32
    f32: f32
}
```

cùng một vùng nhớ có nhiều interpretation.

Đây là machine-level concept.

---

# 2. Vì sao vẫn cần union?

Có những thứ `enum` không thay thế được:

- hardware register;
- C ABI;
- network packet;
- SIMD reinterpretation;
- operating-system structures;
- legacy APIs;
- binary formats;
- tagged/untagged protocol data;
- memory overlays.

Nếu bỏ union hoàn toàn, FFI/system programming sẽ phải dùng raw byte tricks quá nhiều.

---

# 3. Nhưng union không nên giống C hoàn toàn

C cho phép:

```c
union U {
    int i;
    float f;
};
```

rồi ghi `i`, đọc `f`.

Axiom không nên mặc định coi đây là safe semantic operation.

Đề xuất:

```text
union storage
    ↓
unsafe access / explicit bit reinterpretation
```

---

# 4. `union` chỉ có một storage region

Conceptually:

```text id="2z2q5v"
union U {
    a: u32
    b: f32
}
```

Layout:

```text
+----------------+
|                |
|  SAME STORAGE  |
|                |
+----------------+
```

Không có tag.

Không có object header.

Không có runtime metadata.

---

# 5. Union không có ownership ambiguity

Ví dụ:

```axiom
union U {
    a: Box<Foo>
    b: Box<Bar>
}
```

Đây là vấn đề rất nguy hiểm.

Nếu không có active variant tracking:

```text
U.a = Box<Foo>
U.b = Box<Bar>
```

thì compiler không biết Drop cái nào.

Vì vậy tôi đề xuất:

> **Union field phải là trivially-manageable representation trong v0.1.**

Nói đơn giản:

- primitive;
- pointer;
- `Copy` type;
- `repr`-controlled POD-like type.

Không cho arbitrary `Drop` type trong raw union v0.1.

---

# 6. Nếu cần union chứa resource?

Dùng enum:

```axiom
enum Resource {
    File(File)
    Socket(Socket)
}
```

Compiler biết active variant và Drop chính xác.

Hoặc sau này có:

```text
ManagedUnion<T...>
```

nhưng không cần Core v0.1.

---

# 7. Union và bitcast

Không nên dùng union làm “joker”:

```text
u.f = ...
read u.i
```

thay cho mọi kiểu conversion.

Axiom cần phân biệt:

```text id="cnr3xa"
value conversion
bit reinterpretation
pointer reinterpretation
storage overlay
```

---

# 8. Bit cast

Ví dụ:

```axiom
let bits: u32 = bit_cast<f32, u32>(x);
```

Semantics:

```text id="f5m2kx"
same bit pattern
different semantic type
```

Yêu cầu:

```text
size_of<T> == size_of<U>
```

và representation phải được xác định.

Đây là API/intrinsic tốt hơn việc abuse union.

---

# 9. Pointer cast

Khác hoàn toàn:

```text id="s9r5vz"
*T → *U
```

là pointer reinterpretation.

Phải unsafe vì cần đảm bảo:

- alignment;
- pointee validity;
- aliasing;
- provenance;
- object representation.

---

# 10. `union` nên là `unsafe` type?

Có hai hướng.

### Hướng A

Khai báo:

```axiom
union Register {
    value: u32
    bits: [u8; 4]
}
```

được phép, nhưng access variant khác active interpretation cần unsafe.

### Hướng B

Toàn bộ `union` chỉ được khai báo trong unsafe.

Tôi thích **A**.

Vì representation declaration tự nó không nguy hiểm; nguy hiểm là cách đọc/ghi overlapping storage.

---

# 11. Union API

Conceptually:

```axiom
union U {
    i: i32
    f: f32
}

var u = U{ i: 42 };

unsafe {
    let x = u.f;
}
```

Compiler biết:

```text
u.f
```

là potentially type-punning access.

---

# 12. Nhưng có một vấn đề: active member

Axiom có thể lưu semantic state:

```text
U
├── active = i
└── storage
```

nhưng **không nhất thiết runtime lưu tag**.

Compiler chỉ dùng state để kiểm tra.

Nếu đọc variant khác:

```text
active != requested
```

→ unsafe requirement.

Như vậy:

```text
union
```

không cần hidden tag.

---

# 13. Layout của union

Union layout:

```text id="9r5zqv"
size = max(member size, alignment padding)
alignment = max(member alignment)
```

conceptually.

Ví dụ:

```text
union U {
    a: u8
    b: u64
}
```

thường:

```text
size = 8
alignment = 8
```

Nhưng ABI-specific details vẫn do layout engine quyết định.

---

# 14. Bitfield

Tôi vẫn đề xuất:

> **Không có C-style bitfield trong Core v0.1.**

Ví dụ không có:

```axiom
struct Flags {
    a: u8: 1
    b: u8: 3
    c: u8: 4
}
```

---

# 15. Vì sao bitfield rất khó?

Không chỉ là packing.

Phải định nghĩa:

```text
bit numbering
byte order
endianness
alignment
atomic access
read-modify-write
volatile behavior
ABI layout
```

Ví dụ:

```text
bit 0
```

là LSB của byte?

Hay MSB?

Cross-platform sẽ nhanh chóng thành một đống semantic rules.

---

# 16. Thay bằng bit operations

Core đã có:

```text
&
|
^
<<
>>
```

và có thể:

```text
mask
extract
insert
```

library/intrinsics.

Ví dụ:

```axiom
let enabled = (flags & 0x01) != 0;
let mode = (flags >> 1) & 0x07;
```

Compiler có thể optimize thành vài instruction.

Không cần bitfield language feature.

---

# 17. Nhưng FFI bitfield thì sao?

Đây là trường hợp thực sự cần.

Ví dụ Linux/C ABI có struct chứa bitfields.

Tôi đề xuất:

```text
@repr(C, bitfields(...))
```

là **system/FFI representation facility**, không phải normal struct field feature.

Compiler backend/layout engine xử lý.

---

# 18. Tách representation syntax khỏi semantic type

Đây là nguyên tắc:

```text id="v4q8mc"
semantic type
    ≠
memory representation
```

Ví dụ:

```axiom
struct Flags {
    value: u32
}
```

semantic type là Flags.

Representation có thể:

```text
C
packed
aligned
bitfield
transparent
```

nếu explicit.

# 19. `repr(C)`

Đã thống nhất:

```axiom
@repr(C)
struct Point {
    x: f64
    y: f64
}
```

Compiler phải tuân thủ C-compatible layout.

Không được tự:

```text

remove padding
niche-optimize
```

---

# 20. `repr(transparent)`

Ví dụ:

```axiom
@repr(transparent)
struct UserId(u64)
```

Semantic:

```text
UserId != u64
```

nhưng representation:

```text
UserId ≡ u64
```

trong ABI contexts được phép.

Rất hữu ích để tránh primitive obsession mà vẫn FFI-friendly.

---

# 21. Transparent restrictions

Chỉ nên cho:

```text id="c8z2mx"
exactly one representation-bearing field
```

Ví dụ:

```axiom
@repr(transparent)
struct UserId {
    value: u64
}
```

OK.

Nhưng:

```axiom
struct Foo {
    id: u64
    debug: bool
}
```

không được transparent.

---

# 22. Empty/ZST type

Axiom nên hỗ trợ zero-sized type.

Ví dụ:

```axiom
struct Marker {}
```

Semantic:

```text
size = 0
```

nhưng alignment có thể >1 tùy type.

Không cần allocate actual bytes cho ZST.

---

# 23. ZST và address

Nếu:

```axiom
let x = Marker{};
```

thì không nên đảm bảo:

```text
address(x)
```

là unique.

Compiler có thể cho nhiều ZST share conceptual address hoặc eliminate hoàn toàn.

Nếu programmer cần identity:

```text
Box<Marker>
```

hoặc explicit storage abstraction.

---

# 24. Field order

Default:

```axiom
struct Foo {
    a: u8
    b: u64
    c: u8
}
```

compiler có thể reorder.

Ví dụ physical:

```text
b
a
c
padding
```

để tối ưu.

Không được programmer suy ra offset.

---

# 25. Khi nào field order ổn định?

```text id="eq3f7m"
@repr(C)
```

hoặc representation contract khác.

Đây là boundary.

---

# 26. Padding

Padding không phải semantic data.

Ví dụ:

```text id="6j3r8p"
struct X {
    a: u8
    b: u64
}
```

có thể:

```text
byte 0      a
byte 1..7   padding
byte 8..15  b
```

Padding contents không được coi là initialized semantic value.

---

# 27. Không cho raw byte equality của struct

Không nên:

```text
memcmp(&a, &b, sizeof(X)) == 0
```

để định nghĩa:

```text
a == b
```

vì padding có thể khác.

`==` là semantic equality.

---

# 28. `memcmp` vẫn tồn tại

System code vẫn có:

```text
memcmp
```

nhưng đó là byte representation comparison.

Không phải language-level equality.

---

# 29. Serialization

Không được mặc định:

```text
dump memory(Foo)
```

Muốn binary representation ổn định:

```text

```

library.

# 34. Enum layout

Ví dụ:

```axiom
enum Result {
    Ok(i64)
    Err(i32)
}
```

Semantic:

```text

```

nhưng representation không bắt buộc:

# 35. Niche optimization

Ví dụ:

```text
Option<NonNull<T>>
```

Nếu `NonNull<T>` không bao giờ null:

```text
None = null
Some(p) = p
```

không cần extra tag.

Tương tự:

```text
Option<Box<T>>
```

có thể dùng null niche.

---

# 36. Niche không phải semantic guarantee

Programmer không được viết:

```text
assume Option<Box<T>> == pointer size
```

trừ khi compiler cung cấp representation contract.

Đây là optimizer freedom.

---

# 37. Enum discriminant

# 42. Function ABI

Axiom function:

```axiom
fn add(a: i64, b: i64) -> i64
```

semantic:

```text

```

ABI lowering:

```text
SysV:
a → RDI
b → RSI
return → RAX
```

Windows:

```text
a → RCX
b → RDX
return → RAX
```

Source semantics không biết những register này.

# 57. Representation invariants

### AREP-13 — Union Is Overlapping Storage
Union không có implicit tag.

### AREP-14 — Union Does Not Own Arbitrary Resources
Raw union v0.1 không chứa unrestricted Drop values.

### AREP-15 — Bitfields Are Not Core Fields
Bitfield chỉ thuộc representation/FFI/system layer.

### AREP-16 — No Implicit Type Punning
Đọc representation khác phải explicit/unsafe.

### AREP-17 — Layout/ABI Separation
Layout không đồng nghĩa calling convention.

### AREP-18 — No Unrestricted Transmute
Không có universal reinterpretation primitive.

### AREP-19 — Valid Bit Patterns Matter
Không phải mọi byte sequence đều là valid semantic value.

### AREP-20 — ABI Must Be Explicit
Cross-language ABI phải chỉ rõ representation/calling convention.

### AREP-21 — SIMD Is Semantic, Not Register-Based
Vector type không phụ thuộc XMM/YMM/NEON.

### AREP-22 — Padding Is Nonsemantic
Padding không tham gia equality/value semantics.

## Phần tôi đề xuất làm tiếp theo

Bây giờ chúng ta đã khóa gần như toàn bộ **data/memory model**. Bước tiếp theo nên chuyển sang một vấn đề lớn hơn:

# **Execution Model: Thread + Async + Coroutine + Scheduler + Parallelism**

Không chỉ API `thread`/`async`, mà phải quyết định ở cấp semantic:

```text
function
    ↓
closure
    ↓
thread
    ↓
task
    ↓
async state machine
    ↓
suspend/resume
    ↓
scheduler
```

Đặc biệt cần trả lời một câu rất quan trọng cho Axiom:

> **Có nên coi `async/await` là một tính năng ngôn ngữ thực sự, hay chỉ coi `async` là compiler lowering thành state machine còn executor/task system hoàn toàn thuộc library?**

Tôi nghiêng khá mạnh về phương án thứ hai: **compiler hiểu suspension/state-machine để tối ưu và kiểm tra ownership, nhưng scheduler/executor/thread-pool không thuộc language runtime**. Điều này rất phù hợp với mục tiêu runtime cực nhẹ của Axiom.
