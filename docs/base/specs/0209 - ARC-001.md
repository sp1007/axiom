Tiếp tục với **ARC-001 — Shared Ownership & Reference Counting**.

Đây là chỗ cần giữ đúng triết lý Axiom: **shared ownership là một lựa chọn của programmer/library, không phải memory model mặc định**.

# ARC-001

## 1. Quyết định lớn: `Arc` không phải Core primitive

Chốt:

```text
Core:
    Ownership
    Move
    Copy
    Drop
    Send
    Share
    Atomic

std:
    Rc<T>
    Arc<T>
    Weak<T>
    AtomicShared<T> nếu cần
```

Không có:

```text
Core GC
Core RC
Core object header
Core implicit reference counting
```

`Arc<T>` chỉ là một type library được xây dựng trên các primitive Axiom đã có.

---

# 2. Hai loại shared ownership

Axiom nên có hai abstraction rõ ràng:

```text
Rc<T>
```

cho một execution domain duy nhất.

và:

```text
Arc<T>
```

cho shared ownership có thể đi qua execution domains.

Mô hình:

```text
Rc<T>
    │
    └── non-atomic refcount

Arc<T>
    │
    └── atomic refcount
```

Đây là tối ưu quan trọng.

Không nên bắt mọi shared pointer dùng atomic increment/decrement.

---

# 3. `Rc<T>`

Ví dụ:

```axiom
let a = Rc.new(data)
let b = a.clone()
```

Semantic:

```text
        ┌──────────────┐
        │ Rc control   │
        │ count = 2    │
        └──────┬───────┘
               │
               ▼
              T
```

`clone()` chỉ tăng ownership count.

Nó **không clone `T`**.

---

# 4. `Arc<T>`

```axiom
let a = Arc.new(data)
let b = a.clone()
```

Conceptually:

```text
             Arc
          ┌────┴────┐
          ↓         ↓
      strong=2    weak=...
          │
          ▼
          T
```

`Arc.clone()`:

```text
strong_count += 1
```

không:

```text
clone(T)
```

---

# 5. `Arc<T>` là owner

Khác `view<T>`:

```text
view<T>
    = non-owning capability
```

Trong khi:

```text
Arc<T>
    = owning shared handle
```

Vì vậy:

```text
Arc<T>
```

giữ resource sống.

`view<T>` thì không.

---

# 6. `Arc<T>` không được Copy

Rất quan trọng.

```text
Arc<T> : !Copy
```

Vì copy ngầm:

```axiom id="arc-copy"
let b = a
```

sẽ rất dễ gây bất ngờ về refcount.

Phải dùng:

```axiom
let b = a.clone()
```

để biểu thị rõ:

> Tôi đang tạo thêm một shared ownership.

---

# 7. `Rc<T>` cũng không Copy

Tương tự:

```text
Rc<T> : !Copy
```

và:

```text
Arc<T> : !Copy
```

---

# 8. Move vẫn miễn phí

```axiom
let a = Arc.new(x)
let b = a
```

là:

```text
Arc ownership:
a → b
```

Không tăng count.

Không atomic operation.

Không physical copy bắt buộc.

Đây là:

```text
Move
```

chứ không phải:

```text
clone()
```

---

# 9. Clone mới tăng count

```axiom
let b = a.clone()
```

với `Arc`:

```text
atomic_fetch_add(strong, 1)
```

với `Rc`:

```text
non_atomic_increment(strong)
```

---

# 10. Drop

Khi:

```axiom
drop(a)
```

thì:

```text
strong_count -= 1
```

Nếu:

```text
strong_count == 0
```

thì:

```text
drop(T)
```

Sau đó control block có thể được giải phóng nếu không còn weak owner.

---

# 11. `Weak<T>`

`Weak` không giữ `T` sống.

Ví dụ:

```axiom
let strong = Arc.new(node)
let weak = strong.downgrade()
```

Ta có:

```text
strong_count = 1
weak_count   = 1
```

Nếu:

```axiom
drop(strong)
```

thì:

```text
strong_count = 0
```

→ `T` được Drop.

Nhưng control block có thể vẫn sống vì:

```text
weak_count = 1
```

---

# 12. `Weak.upgrade()`

```axiom
match weak.upgrade() {
    Some(value) => ...
    None => ...
}
```

Nếu object còn sống:

```text
Weak
 ↓
CAS strong_count
 ↓
Arc<T>
```

Nếu đã chết:

```text
None
```

Đây là operation cần CAS để tránh race:

```text
Thread A:
    last strong owner drops

Thread B:
    weak.upgrade()
```

---

# 13. Tại sao cần Weak?

Để tránh cycle:

```text
A → B
B → A
```

Nếu cả hai là strong `Arc`:

```text
A strong = 1
B strong = 1
```

không bao giờ về zero.

Memory leak.

Dùng:

```text
A ──strong──> B
B ──weak────> A
```

cycle được phá.

---

# 14. Axiom không tự động phát hiện cycle

Compiler **không** cố giải quyết:

```text
Arc cycle
```

vì đây là semantic của shared ownership abstraction.

Programmer chọn:

```text
Arc
Weak
Handle
Arena
```

tùy graph model.

---

# 15. Đây là một điểm khác biệt quan trọng với GC

GC có thể tự nhận:

```text
A → B → A
```

là unreachable.

Axiom `Arc` không.

Nhưng đổi lại:

- deterministic destruction
- không tracing pause
- không GC runtime
- predictable ownership
- memory footprint nhỏ hơn trong nhiều trường hợp.

---

# 16. `Rc<T>` không được Send

Thông thường:

```text
Rc<T> : !Send
```

vì refcount non-atomic.

Cũng không nên:

```text
Rc<T> : Share
```

để tránh accidental cross-thread use.

---

# 17. `Arc<T>` có thể Send/Share

Nếu:

```text
T: Send
```

thì:

```text
Arc<T>
```

có thể được chuyển qua execution domain.

Nếu:

```text
T: Share
```

thì:

```text
Arc<T>
```

có thể được shared concurrent theo semantics của T.

Nhưng:

```text
Arc<T>
```

**không biến T thành thread-safe mutable object**.

---

# 18. `Arc<Mutex<T>>`

Đây mới là pattern:

```axiom
let state = Arc.new(Mutex.new(State.new()))
```

Có:

```text
Arc
 │
 └── Mutex
      │
      └── T
```

Nhiều thread có thể giữ:

```text
Arc<Mutex<T>>
```

rồi:

```axiom
let guard = state.lock().write()
```

để mutate.

---

# 19. `Arc<T>` không cho mutable view trực tiếp

Không được:

```axiom
let v = arc.view_mut()
```

vì nhiều `Arc` có thể tồn tại.

Muốn mutable shared access phải qua abstraction:

```text
Arc<Mutex<T>>
Arc<RwLock<T>>
Arc<Atomic<T>>
```

hoặc specialized concurrent structure.

Đây là một invariant rất mạnh.

---

# 20. Immutable view từ Arc

Có thể:

```axiom
let v = arc.view()
```

nếu API chứng minh owner vẫn sống.

Nhưng cần phân biệt:

```text
Arc<T>.view()
```

và:

```text
view<T>
```

`view` phụ thuộc vào lifetime của `Arc` handle.

Nếu handle bị drop trong khi view còn live:

```text
ERROR
```

trừ khi view được tạo từ một owner khác vẫn còn sống.

---

# 21. Compiler capability graph

Ví dụ:

```text
Arc<T> #1
    │
    └── strong ownership
          │
          ▼
          T
          │
          └── view<T> #7
```

Verifier biết:

```text
view #7 depends on Arc #1
```

Nếu:

```axiom
drop(arc)
```

trong khi `view` còn sống:

```text
reject
```

Tuy nhiên compiler có thể nhìn thấy một `Arc` clone khác:

```text
Arc #2
   │
   └── same control block
```

thì ownership vẫn tồn tại.

---

# 22. Physical pointer vs logical ownership

`Arc<T>` control block có thể chứa:

```text
strong_count
weak_count
T
```

Nhưng programmer không được phụ thuộc vào:

```text
control_block_address
```

trừ API unsafe/system.

Logical identity:

```text
Arc<T>
```

không phải raw address.

---

# 23. Allocation

`Arc.new(T)` thường cần storage:

```text
control block + T
```

nhưng semantic không bắt compiler phải heap allocate nếu compiler chứng minh object không escape.

Tuy nhiên trong thực tế:

```text
Arc
```

có shared identity nên allocation thường sẽ trở thành observable storage requirement.

Axiom vẫn giữ nguyên:

> allocation strategy là compiler/runtime choice trừ khi storage identity trở thành observable.

---

# 24. Single allocation

Implementation nên ưu tiên:

```text
┌──────────────────────────────┐
│ strong │ weak │ T            │
└──────────────────────────────┘
```

thay vì:

```text
control block allocation
+
T allocation
```

trừ khi specialized layout yêu cầu khác.

Điều này giảm:

- allocation count
- pointer chasing
- fragmentation.

---

# 25. `Arc<T>` với DST/slice

Sau này có thể hỗ trợ:

```text
Arc<[T]>
Arc<str>
```

nhưng không cần Core v1.

Library có thể có:

```text
ArcBuffer
ArcString
```

trước.

---

# 26. Strong/weak counter overflow

Đây là edge case cần specification.

Không được để:

```text
strong_count++
```

wrap silently.

Tôi đề xuất:

> Reference count overflow là fatal resource exhaustion / abort condition.

Không `panic` có thể được recover một cách an toàn vì object graph đã không còn representable.

Trong debug có diagnostic sớm.

---

# 27. Saturating count không phải solution

Không nên:

```text
count = MAX
```

rồi giữ object mãi.

Điều đó biến bug thành leak vĩnh viễn.

Overflow phải là violation của abstraction.

---

# 28. Memory ordering của Arc

`Arc` nên là library implementation.

Một implementation điển hình:

### Increment strong

Có thể:

```text
Relaxed
```

vì đã có một strong reference hợp lệ giữ control block sống.

### Decrement

Thường:

```text
Release
```

và khi count về zero:

```text
Acquire fence
```

trước destruction.

Nhưng đây là **implementation detail**, không nên đưa thành language semantic.

---

# 29. Weak upgrade

`Weak.upgrade()` cần atomic CAS.

Conceptually:

```text
load strong
if strong == 0:
    fail

CAS(strong, strong, strong + 1)
```

nếu CAS fail:

```text
retry
```

hoặc object đã chết.

---

# 30. `Arc::get_mut`

Có thể cung cấp:

```axiom
let v = arc.get_mut()
```

trả:

```text
Option<mut_view<T>>
```

chỉ khi compiler/runtime chứng minh:

```text
strong_count == 1
```

và không có conflicting capability.

Điều này rất hữu ích:

```text
unique Arc
   ↓
mutable access
```

không cần Mutex.

---

# 31. `make_mut`

Có thể có abstraction:

```axiom
arc.make_mut()
```

nhưng semantics là **copy-on-write**:

```text
strong_count == 1
    → mutable access

strong_count > 1
    → clone T
    → detach
    → mutable access
```

Không nên đặt tên gây hiểu nhầm.

`make_mut()` có thể rất đắt vì có thể clone toàn bộ T.

---

# 32. Arc + channels

Giờ ta có hai cách truyền:

### Ownership transfer

```axiom
tx.send(buffer)
```

→ zero-copy ownership transfer.

### Shared ownership

```axiom
tx.send(buffer_arc.clone())
```

→ message chứa shared owner.

Đây là distinction rất rõ.

---

# 33. Arc không thay thế Channel

Không nên:

```text
Arc<Queue<T>>
```

là channel mặc định.

Channel có semantics:

```text
send → ownership transfer
receive → ownership acquisition
wake
backpressure
ordering
```

Arc chỉ giải quyết:

```text
shared lifetime
```

---

# 34. `AtomicShared<T>`

Chưa nên đưa vào v1 Core.

Nhưng về sau có thể cần abstraction:

```text
AtomicShared<T>
```

để:

```text
atomic pointer swap
+
reference-counted ownership
```

Ví dụ lock-free immutable data structure.

Implementation có thể dựa trên:

```text
Atomic pointer
+
Arc control block
+
hazard/epoch strategy
```

Nhưng đây là advanced concurrent library.

---

# 35. Hazard pointers / epoch GC

Cần phân biệt:

```text
reference counting
```

với:

```text
hazard pointers
epoch reclamation
RCU
```

Axiom không cần biến chúng thành memory management primitives.

Chúng là library/runtime strategies cho lock-free structures.

---

# 36. `Arc` không đảm bảo lock-free

Một `Arc` có thể dùng:

```text
atomic increment/decrement
```

nhưng target atomic implementation có thể không lock-free.

Do đó:

```text
Arc
```

không đồng nghĩa:

```text
lock-free
```

Nếu cần guarantee:

```text
LockFreeArc
```

có thể là specialized target/library type sau.

---

# 37. Destructor ordering

Khi strong count về zero:

```text
T.Drop
```

xảy ra deterministic.

Nhưng thời điểm cụ thể phụ thuộc:

```text
last strong owner
```

Do đó programmer không được dựa vào:

```text
Arc<T>
```

để xác định thứ tự giữa nhiều shared resources nếu graph có nhiều owners.

Nếu thứ tự cleanup quan trọng:

```text
explicit close()
```

vẫn là mechanism đúng.

---

# 38. `Weak<T>` không giữ resource

Điều này cần trở thành invariant rất rõ:

```text
Weak<T>
```

không giữ:

```text
T alive
```

nó chỉ giữ:

```text
control block alive
```

---

# 39. Cycle-safe design

Pattern:

```text
struct Node {
    children: Vec<Arc<Node>>
    parent: Weak<Node>
}
```

là canonical.

Graph:

```text
        Arc
 A ───────────> B
 ↑              │
 │              │
 └──── Weak ────┘
```

Khi A/B không còn external strong references:

```text
A strong = 0
B strong = 0
```

cả hai được destroy.

# 40. Rc và Arc không nên có syntax khác

Cùng interface:

```text
Rc.new
Rc.clone
Rc.downgrade

Arc.new
Arc.clone
Arc.downgrade
```

Điều này giúp programmer chuyển:

```text
Rc<T>
```

→

```text
Arc<T>
```

khi cần concurrency mà không phải học abstraction mới.

Khác biệt chủ yếu là:

```text
Rc = local
Arc = concurrent-capable
```

# Kiến trúc memory/concurrency lúc này

Axiom đã có một tầng rất nhất quán:

```text
                         MEMORY
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
        ▼                  ▼                  ▼
    Ownership          Capability          Atomic
        │                  │                  │
   ┌────┴────┐        ┌────┴────┐       Ordering
   │         │        │         │           │
  Move     Share    view    mut_view        │
   │         │        │         │           │
   │       Arc/Rc     │      Mutex/RwLock   │
   │         │        │         │           │
   └─────────┴────────┴────────┴────────────┘
                           │
                     Concurrency
                           │
            ┌──────────────┼──────────────┐
            ▼              ▼              ▼
         Channel        Scheduler       Thread
            │              │              │
            └──────────────┼──────────────┘
                           ▼
                         Task
                           │
                         Future
```

Điểm đáng chú ý: **không có một cơ chế memory management duy nhất**.

Axiom có thể chạy:

```text
plain values
    ↓
zero allocation
```

hoặc:

```text
owned heap object
    ↓
Box
```

hoặc:

```text
shared local
    ↓
Rc
```

hoặc:

```text
shared concurrent
    ↓
Arc
```

hoặc:

```text
arena
pool
slab
handle
atomic structure
```

mà không cần thay đổi ngôn ngữ.

# Bước tiếp theo: `COLLECTION-001`

Bây giờ chúng ta đã có đủ nền tảng để thiết kế **collections/storage model**:

```text
Array
Slice/View
Vec
String
StringView
Map
Set
Deque
Queue
SmallVec
Arena
Pool
Hashing
Iterator
```

Đặc biệt cần giải quyết một vấn đề rất quan trọng trước khi đi tiếp:

> **`Vec<T>` phải có semantics thế nào khi `mut_view<T>` đang tồn tại?**

Ví dụ:

```axiom
let v = vec.view()

vec.push(x)
```

Nếu `push()` relocation xảy ra thì view có thể dangling. Đây là nơi **AMEM-24, AMEM-71, capability provenance, relocation và compiler escape analysis** phải được biến thành một API collection cực kỳ đơn giản cho programmer.

Mục tiêu là programmer chỉ cần viết:

```axiom
let x = vec[i]
```

hoặc:

```axiom
let v = vec.view()
```

nhưng compiler vẫn tự ngăn:

```text
reallocation
dangling view
iterator invalidation
use-after-relocation
```

mà **không yêu cầu lifetime annotation**.
