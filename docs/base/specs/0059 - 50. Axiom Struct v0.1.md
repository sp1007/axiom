Tiếp tục từ Genesis. Bây giờ tôi nghĩ ta nên đi vào **semantic feature đầu tiên thực sự khác biệt Axiom với C/C++**: `struct → Copy/Move → Drop → view/mut_view`.

Đây mới là nơi mô hình memory của Axiom được kiểm chứng.

# 50. Axiom Struct v0.1

Trước tiên cần chốt một nguyên tắc:

> `struct` chỉ mô tả **data layout + value semantics**. Nó không phải object/class runtime.

Ví dụ:

```axiom
struct Point {
    x: i64
    y: i64
}
```

Semantic:

```text
Point
├── x : i64
└── y : i64
```

Không có:

```text
vtable
type pointer
object header
refcount
GC metadata
hidden mutex
```

Một `Point` có thể về cơ bản chỉ là:

```text
16 bytes
```

trên target phù hợp.

# 51. Struct trong Type System

Type table:

```text
TypeId(7)
    kind = Struct
    struct_id = StructId(0)
```

Struct definition:

```text
StructId(0)

name = Point

fields:
    FieldId(0):
        name = x
        type = i64

    FieldId(1):
        name = y
        type = i64
```

Compiler tự suy ra:

```text
Point:
    Copy = true
    Drop = false
    Sized = true
```

vì:

```text
i64:
    Copy = true
    Drop = false
```

# 52. Auto Property Derivation

Đây là điểm tôi nghĩ Axiom nên làm rất mạnh.

Không bắt programmer viết:

```text
impl Copy for Point
```

nếu compiler có thể chứng minh.

Compiler suy ra:

```text
Point
├── x: Copy
└── y: Copy

=> Point: Copy
```

Tương tự:

```text
struct A {
    p: Point
}
```

suy ra:

```text
A: Copy
```

nếu tất cả thành phần Copy.

Nhưng:

```text
struct FileData {
    file: File
}
```

nếu:

```text
File: !Copy
Drop
```

thì:

```text
FileData:
    !Copy
    Drop
```

Không cần programmer khai báo.

# 53. Struct Literal

Syntax:

```axiom
let p = Point {
    x: 10,
    y: 20,
};
```

Typed HIR:

```text
Construct Point
├── x = 10 : i64
└── y = 20 : i64
```

MIR:

```text
%p = aggregate Point {
    x = 10,
    y = 20
}
```

Không có heap allocation.

Compiler có thể:

```text
register
stack
inline
SSA
```

tùy context.

# 54. Struct Field Access

```axiom
p.x
```

AST:

```text
FieldAccess(
    Name("p"),
    "x"
)
```

HIR:

```text
FieldAccess(
    Local(p),
    Field(x)

```

MIR `Place`:

```text
Place {
    base = Local(p),
    projections = [
        Field(x)
    ]
}
```

Đây là lý do `Place` cực kỳ quan trọng.

# 55. Partial Move

Đây là nơi Axiom bắt đầu khác rõ rệt với kiểu value-only đơn giản.

Ví dụ:

```axiom
struct User {
    name: String
    age: i64
}

fn take_name(name: String) {
}

fn test() {
    let user = User {
        name: Text.from("A"),
        age: 20,
    };

    take_name(user.name);

    print(user.age);
}
```

Sau:

```text
take_name(user.name)
```

ownership tree:

```text
user
├── name → MOVED
└── age  → OWNED
```

Do đó:

```text
user.age
```

vẫn hợp lệ.

Nhưng:

```axiom
print(user);
```

không hợp lệ.

Compiler:

```text
AX_MOVE_0003:
cannot use `user` as a whole value because field `name` was moved
```

Đây là một tính năng rất quan trọng.

---

# 56. MIR cho Partial Move

Ban đầu:

```text
%user
```

có logical ownership tree:

```text
user
├── name
└── age
```

Move:

```text
MOVE user.name
```

không nhất thiết tạo machine copy.

Verifier cập nhật:

```text
user.name = MOVED
user.age  = OWNED
user     = PARTIAL
```

Đây là:

> ownership state của `Place`, không phải state của SSA register.

---

# 57. Copy

Ví dụ:

```axiom
let a = Point { x: 1, y: 2 };
let b = a;
```

Vì `Point: Copy`, semantic là:

```text
a = OWNED
b = OWNED
```

Không phải:

```text
a = MOVED
```

Machine code có thể thậm chí không copy.

Ví dụ:

```axiom
let a = Point { x: 1, y: 2 };
return a.x;
```

compiler có thể biến toàn bộ thành:

```text
return 1;
```

---

# 58. Move

Nếu:

```axiom
struct Buffer {
    data: Vec<u8>
}
```

và:

```axiom
let a = Buffer.new();
let b = a;
```

thì:

```text
a → MOVED
b → OWNED
```

Không nhất thiết có:

```text
memcpy
```

Thậm chí native representation có thể là:

```text
a = ptr/len/cap
```

và move chỉ là transfer compiler ownership.

Machine code có thể:

```text
không có instruction nào
```

hoặc chỉ copy representation nếu cần.

Đây là **semantic erasure**.

---

# 59. Một nguyên tắc rất quan trọng

Không được định nghĩa:

```text
Move = machine MOV
```

Hai thứ hoàn toàn khác nhau.

```text
Axiom MOVE
    = chuyển quyền sở hữu semantic
```

Trong khi:

```text
x86 MOV
    = sao chép bit/register/memory
```

Một Axiom MOVE có thể:

```text
0 instruction
1 register move
3 memory moves
```

tùy representation.

# 60. Drop

Bây giờ đến resource.

```axiom
struct File {
    handle: RawHandle
}
```

giả sử:

```text
File:
    !Copy
    Drop
```

Khi:

```axiom
fn test() {
    let f = File.open("x");
}
```

compiler phải sinh semantic:

```text
create f
...
DROP f
```

MIR:

```text
%f = call File.open(...)

...

DROP %f
RETURN
```

Nếu compiler có thể chứng minh `f` không tồn tại ở runtime nữa thì drop vẫn phải được bảo toàn nếu có observable effect.

---

# 61. Drop không phải destructor kiểu C++

Tôi khuyên Axiom tránh mô hình:

```text
~File()
```

theo kiểu class.

Thay vào đó:

```text
Drop
```

là **semantic resource-release operation**.

Ví dụ:

```text
File
    Drop
    ↓
close OS handle
```

hoặc:

```text
MutexGuard
    Drop
    ↓
unlock
```

Không có inheritance/destructor dispatch ngầm.

---

# 62. Drop order

Ví dụ:

```axiom
fn test() {
    let a = A();
    let b = B();
    let c = C();
}
```

Mặc định:

```text
C.drop()
B.drop()
A.drop()
```

Tức reverse declaration order.

Nhưng compiler phải tính theo **ownership tree**.

Nếu:

```text
user.name
```

đã move:

```text
user
├── name MOVED
└── age OWNED
```

Drop chỉ được thực hiện cho phần còn owned.

Không được:

```text
drop(user)
```

rồi lại:

```text
drop(user.name)
```

---

# 63. Drop + Move

Ví dụ:

```axiom
let a = File.open();
let b = a;
```

Sau move:

```text
a = MOVED
b = OWNED
```

Cuối scope:

```text
drop(b)
```

Không:

```text
drop(a)
drop(b)
```

Verifier invariant:

```text
V4:
No resource may be dropped more than once.
```

---

# 64. Drop + Branch

Đây là test cực quan trọng:

```axiom
fn test(flag: bool) {
    let f = File.open();

    if flag {
        use(f);
    }

    close_scope();
}
```

Compiler phải đảm bảo mọi control-flow path đều có cleanup đúng.

Một case khó hơn:

```axiom
fn test(flag: bool) {
    let f = File.open();

    if flag {
        return;
    }

    use(f);
}
```

Path:

```text
flag = true
    ↓
return
    ↓
drop f
```

Path:

```text
flag = false
    ↓
use f
    ↓
drop f
```

Do đó cleanup là một phần của CFG semantics.

---

# 65. Cleanup Blocks

MIR có thể dùng:

```text
bb_cleanup:
    DROP %f
    RETURN
```

Ví dụ:

```text
bb0:
    %f = File.open()
    branch %flag, bb1, bb2

bb1:
    jump bb_cleanup

bb2:
    call use(%f)
    jump bb_cleanup

bb_cleanup:
    DROP %f
    return
```

Optimizer sau đó có thể eliminate/merge cleanup khi an toàn.

# 66. `Drop` và `Copy`

Tôi vẫn khuyên giữ quyết định:

> **Một type có destructive Drop không được là implicit Copy trong Core v0.1.**

Nếu không:

```text
let a = File();
let b = a;
```

sẽ tạo hai logical owners.

Điều đó phá mô hình.

Nếu thực sự muốn sao chép resource:

```axiom
let b = a.clone();
```

hoặc:

```axiom
let b = a.duplicate()?;
```

Đây là **business semantics**, không phải Copy semantics.

# 67. View

Bây giờ mới đến phần đặc biệt nhất.

Axiom không dùng Rust syntax:

```rust
&T
&mut T
```

mà:

```text
view<T>
mut_view<T>
```

Ví dụ:

```axiom
fn sum(v: view<i64>) -> i64 {
    ...
}
```

Gọi:

```axiom
let a = Array { 1, 2, 3 };

sum(a);
```

compiler có thể tạo ephemeral view:

```text
a
 │
 └── READ capability ──→ sum
```

Không tạo ownership mới.

---

# 68. `view` là capability

Không nên coi:

```text
view<T>
```

chỉ là:

```text
struct {
    ptr: *T,
    len: usize
}
```

Semantic:

```text
View {
    provenance
    region
    access = READ
}
```

Machine representation có thể là:

```text
pointer + length
```

nhưng semantic representation là capability.

Đây là một distinction cực kỳ quan trọng.

---

# 69. `mut_view`

```axiom
fn fill(v: mut_view<i64>) {
    ...
}
```

Có:

```text
WRITE capability
```

Trong khi owner vẫn tồn tại.

Rule:

```text
READ + READ       OK
READ + WRITE      ERROR
WRITE + WRITE     ERROR
OWNER + WRITE     ERROR
```

Ví dụ:

```axiom
let a = Array { 1, 2, 3 };

let x = view(a);
let y = view(a);
```

OK.

Nhưng:

```axiom
let x = view(a);
let y = mut_view(a);
```

không OK nếu overlap.

---

# 70. Explicit binding

Theo quyết định trước:

```axiom
let v = view(a);
```

là explicit.

Không cho:

```axiom
let v: view<i64> = a;
```

tự động tạo escaping capability.

Nhưng:

```axiom
sum(a);
```

được implicit owner → ephemeral `view`.

Điều này giữ syntax đơn giản mà vẫn tránh hidden lifetime.

---

# 71. Tại sao không cho tất cả implicit?

Vì:

```axiom
let v = a;
```

đã có semantic:

```text
Copy hoặc Move
```

Nếu compiler tự đoán:

```text
Copy?
Move?
View?
```

từ context thì code sẽ trở nên khó đọc và khó debug.

Axiom nên:

> implicit trong **call boundary**, explicit trong **persistent binding**.

Đây là một quy tắc rất đẹp.

---

# 72. View Lifetime

Ví dụ:

```axiom
fn test() {
    let a = Array { 1, 2, 3 };

    let v = view(a);

    use(v);

    mutate(a);
}
```

Nếu `v` đã last-used ở:

```text
use(v)
```

thì compiler có thể expire capability:

```text
v = EXPIRED
```

và:

```text
mutate(a)
```

hợp lệ.

Không cần programmer viết:

```text
drop(v)
```

hay lifetime annotation.

Đây là nơi Axiom khác Rust rất rõ.

---

# 73. Nhưng nếu View escape?

Ví dụ:

```axiom
fn bad() -> view<i64> {
    let a = Array { 1, 2, 3 };
    view(a)
}
```

Verifier:

```text
AX_VIEW_0001

returned view may outlive its owner
```

Không cần programmer hiểu lifetime parameter.

Compiler tự chứng minh:

```text
owner lifetime < returned capability lifetime
```

→ reject.

---

# 74. Return View hợp lệ

Ví dụ:

```axiom
fn first(v: view<i64>) -> view<i64> {
    v
}
```

Provenance:

```text
input v
  ↓
returned view
```

Có thể hợp lệ nếu compiler chứng minh return capability không vượt owner.

Semantic rule:

```text
return provenance ⊆ input provenance
```

Không được tạo provenance mới từ local.

---

# 75. View và Vec relocation

Đây là một test tuyệt vời:

```axiom
let v = view(vec);

vec.push(42);
```

Nếu `push` có thể relocate storage:

```text
old address
    ↓
new allocation
```

thì `v` sẽ dangling.

Do đó API `push` phải có semantic effect:

```text
MAY_RELOCATE
```

Verifier thấy:

```text
active view → vec.region
push(vec) → MAY_RELOCATE(vec.region)
```

→ reject nếu relocation có thể phá capability.

---

# 76. Nhưng không nên cấm Vec mutation quá mức

Ví dụ:

```axiom
let v = view(vec[0..10]);

vec[100] = 42;
```

Nếu region:

```text
v = [0..10]
write = [100]
```

và compiler biết chúng disjoint:

```text
DISJOINT
```

thì có thể cho phép.

Đây chính là lý do ta đã thiết kế:

```text
MemoryRegion
```

thay vì borrow checker kiểu:

```text
"đã borrow vec => cấm mọi mutation"
```

Axiom có thể chính xác hơn.

---

# 77. Region Model

Ví dụ:

```text
vec
├── region [0..10]
└── region [100..101]
```

Quan hệ:

```text
[0..10] ∩ [100..101] = ∅
```

→ DISJOINT.

Trong verifier:

```text
conflict(region_a, region_b)
```

chỉ xảy ra nếu:

```text
relation ∈ {
    SAME,
    OVERLAPS,
    CONTAINS,
    CONTAINED_BY,
    UNKNOWN
}
```

Không conflict khi:

```text
DISJOINT
```

---

# 78. Đây là nơi Axiom có thể đạt mục tiêu ban đầu

Bạn từng lo:

> borrow checker có thể làm ngôn ngữ phiền phức và giảm performance.

Thiết kế hiện tại tránh một phần lớn vấn đề đó vì:

```text
Programmer:
    không viết lifetime
    không viết borrow annotation
    không viết ownership annotation

Compiler:
    phân tích ownership
    phân tích region
    phân tích last-use
    phân tích escape
    phân tích alias
```

Và sau khi verify:

```text
ownership
views
Send
Share
```

thường **biến mất khỏi machine code**.

# 79. Pipeline mới

Sau Struct/Move/View:

```text
Source
 ↓
AST
 ↓
HIR
 ↓
Typed HIR
 ↓
MIR
 │
 ├── Ownership
 ├── Region
 ├── Capability
```

Một chương trình:

```axiom
fn length(v: view<i64>) -> usize {

}
```

có thể cuối cùng chỉ còn:

```text
pointer

```

Không có runtime borrow checker.

# 80. Tôi đề xuất một thay đổi quan trọng cho `view`

Có một nguy cơ với mô hình:

```text
view<T>
```

nếu chúng ta cho phép nó quá tự do.

Vì vậy Core v0.1 nên đặt:

### `view<T>`:

```text
Copy
Sized
!Drop
non-owning
READ only
```

### `mut_view<T>`:

```text
Copy
Sized
!Drop
non-owning
WRITE capability
```

Nhưng **Copy ở đây không có nghĩa Copy ownership**.

Copy chỉ tạo thêm capability cùng provenance nếu verifier chứng minh các READ capability hợp lệ.

`mut_view<T>` là trường hợp đặc biệt: không được dùng Copy theo nghĩa “tạo hai WRITE capability độc lập”.

Do đó tôi đề xuất sửa chính xác hơn:

```text
view<T>:
    Copy-like capability duplication allowed for READ

mut_view<T>:
    semantically non-duplicable WRITE capability
```

Tức `mut_view` không nên thực sự mang property `Copy` mặc dù representation có thể copy bit.

Điều này tránh một lỗ hổng lớn.

# 81. Một quy tắc đẹp hơn nữa

Thay vì coi:

```text
view
mut_view
```

là hai ownership types hoàn toàn độc lập, compiler có thể coi chúng là:

```text
Capability<READ>
Capability<WRITE>
```

surface syntax vẫn:

```text
view<T>
mut_view<T>
```

Nhưng verifier nội bộ:

```text
Capability {
    provenance
    region
    access
}
```

và:

```text
READ capability
WRITE capability
```

Đây là kiến trúc rất sạch.

# 82. Feature progression tiếp theo

Tôi sẽ không đi ngay vào Generic/Trait.

Sau `Struct + Move + Drop + View`, nên làm một **Memory Safety Gauntlet**:

```text
M1  basic struct
M2  Copy struct
M3  Move
M4  use-after-move
M5  partial move
M6  Drop
M7  branch Drop
M8  loop Drop
M9  early return Drop
M10 view
M11 mut_view
M12 overlapping view
M13 disjoint view
M14 dangling view
M15 return view
M16 closure capturing owner
M17 closure capturing view
M18 Vec relocation
M19 escape analysis
M20 unsafe raw pointer
```

Nếu cả 20 nhóm này chạy đúng, tôi sẽ coi **memory model v0.1 đã được chứng minh**, chứ không chỉ được thiết kế trên giấy.

Sau đó mới chuyển sang:

```text
Generic
  ↓
Trait
  ↓
Static Dispatch
  ↓
Closure
  ↓
Option / Result
```

Và khi đó chúng ta mới có đủ nền để xây một Axiom thực sự có thể thay thế vai trò của C/C++ ở tầng systems programming mà vẫn giữ syntax và memory model đơn giản hơn.
