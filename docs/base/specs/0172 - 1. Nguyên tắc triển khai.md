## XXXV — Bắt đầu triển khai Axiom: KERNEL-001 → KERNEL-007

Từ đây tôi chuyển hẳn từ **thiết kế ngôn ngữ** sang **implementation blueprint**. Không mở thêm SPEC-31; semantics đã đóng băng.

Mục tiêu của giai đoạn này là tạo được một compiler skeleton có kiến trúc đúng ngay từ đầu, nhưng chưa cần biết ownership, trait, MIR hay x86.

---

# 1. Nguyên tắc triển khai

Có một quyết định rất quan trọng:

> **Bootstrap compiler không được trở thành “compiler tạm bợ” mà sau này phải viết lại.**

Nó chỉ là implementation đầu tiên của cùng kiến trúc.

```text
ax-bootstrap
    │
    ├── compiler/kernel
    ├── source
    ├── lexer
    ├── parser
    ├── resolver
    └── ...
          ↓
    Axiom compiler
          ↓
    self-hosting
```

Vì vậy ngay từ Stage 0 phải giữ các boundary:

```text
kernel
  ↓
source
  ↓
lexer
  ↓
parser
```

và tuyệt đối không cho:

```text
kernel → x86
kernel → ELF
kernel → ownership
kernel → runtime
```

# 2. KERNEL-001: Typed IDs

Đây là nền móng đầu tiên.

Không dùng:

```text
uint32 id
```

một cách tự do.

Thay vào đó:

```text
FileId
ModuleId
SymbolId
TypeId
FunctionId
FieldId
VariantId
ImplId
LocalId
BlockId
ExprId
StmtId
PatternId
ItemId
InstrId
AllocationId
QueryId
DiagnosticId
```

Mỗi ID là một semantic type riêng.

Ví dụ về mặt implementation:

```text
FileId {
    index: u32
}

ModuleId {
    index: u32
}
```

nhưng:

```text
FileId != ModuleId
```

về type system của compiler.

Điều này ngăn lỗi kiểu:

```text
resolve_module(FileId)
```

hoặc:

```text
get_function(ModuleId)
```

ngay ở compiler implementation.

### Invariant

```text
AKERNEL-24
All compiler semantic identities use typed IDs.

AKERNEL-25
Session-local IDs are never persistent cache identities.
```

# 3. ID allocation

Mỗi arena/table có ID allocator riêng:

```text
IdTable<T, Id>
```

về concept:

```text
table.push(value) -> Id
table.get(Id) -> &T
table.get_mut(Id) -> &mut T
```

Ví dụ:

```text
files: IdTable<SourceFile, FileId>
symbols: IdTable<Symbol, SymbolId>
types: IdTable<Type, TypeId>
```

Không cho phép dùng index trực tiếp.

### Không làm

```text
files[3]
```

### Làm

```text
files.get(FileId(3))
```

Điều này cực kỳ hữu ích khi compiler lớn lên.

# 4. Span

```text

    file: FileId
    start: u32
    end: u32

```

Không lưu:


```text
LineMap
```

Ví dụ:

```text

     ↓
```

### Vì sao?

Compiler cần byte offset để:

- slicing source
- lexer
- diagnostics
- incremental compilation
- cache
- IDE
- source mapping

Line/column chỉ là presentation.

Invariant:

```text
AKERNEL-26
Source spans use byte offsets.
```


### Persistent identity

```text

```

được dùng cho cache.

Ví dụ:


# 15. Query System


# 16. Query dependency graph

Ví dụ:

```text
object(main)
    ↓

    ↓

    ↓

    ↓

    ↓

    ↓
```

Nếu sửa một comment:



Do đó function/object cache có thể được giữ tùy dependency graph.

# 26. Vertical Slice 001: `main()`

Source:

```axiom
fn main() {}
```

Typed semantics:

```text
Function main
    params = []
    return = unit
    body = {}
```

MIR concept:

```text
BB0:
    RETURN unit
```

LIR:

```text
RETURN
```

x86-64:

```text
xor eax, eax
ret
```

hoặc nếu entry bridge xử lý return semantics:

```text
return 0
```

Tuy nhiên executable đầu tiên cần có startup contract.

# 29. VS-003 — Function call

```axiom
fn add(a: i32, b: i32) -> i32 {
    a + b
}

fn main() -> i32 {
    add(20, 22)
}
```

MIR:

```text
main:
    %a = CONST 20
    %b = CONST 22
    %r = CALL add(%a, %b)
    RETURN %r
```

ABI lowering:

```text
20 → EDI
22 → ESI
CALL add
result → EAX
```

Machine:

```text
mov edi, 20
mov esi, 22
call add
ret
```

Đây là milestone cực quan trọng vì nó đồng thời test:

- resolver
- FunctionId
- type checking
- call lowering
- ABI
- relocation
- linker
