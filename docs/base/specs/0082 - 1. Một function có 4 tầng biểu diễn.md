Tiếp tục với **Function ABI + Calling Convention + Parameter Passing + Return Value**. Đây là phần rất quan trọng vì nếu thiết kế sai, dù type system và memory model đẹp đến đâu, Axiom vẫn có thể sinh code kém C/C++.

Tôi đề xuất một nguyên tắc trung tâm:

> **Source-level parameter semantics và physical calling convention phải hoàn toàn tách biệt.**

---

# 1. Một function có 4 tầng biểu diễn

Ví dụ:

```axiom
fn add(a: i64, b: i64) -> i64 {
    return a + b
}
```

Source semantics:

```text
add(i64, i64) -> i64
```

Sau type checking:

```text
Typed Function
```

Sau ABI lowering:

```text
RDI = a
RSI = b
RAX = result
```

Sau machine lowering:

```asm
add rdi, rsi
mov rax, rdi
ret
```

Do đó:

```text
Source
  ↓
Semantic Signature
  ↓
ABI Signature
  ↓
Machine Signature
```

Không nên để source syntax quyết định register/stack.

---

# 2. Axiom có 3 ABI chính

Ta đã định hướng:

```text
extern "axiom"
extern "C"
extern "system"
```

### `axiom`

ABI native của Axiom.

Compiler được tự do tối ưu mạnh nhất.

### `C`

C-compatible ABI.

Dùng cho:

```text
FFI
libraries
OS APIs
native interop
```

### `system`

Target system ABI.

Ví dụ Windows API.

---

# 3. Native Axiom ABI không cần stable giữa compiler versions

Đây là quyết định nên giữ.

```text
Axiom compiler v0.1
       ↓
Axiom ABI v0.1
```

không nhất thiết binary-compatible với:

```text
Axiom compiler v0.2
```

nếu không có explicit ABI contract.

Điều này cho compiler freedom cực lớn.

Nếu muốn stable ABI:

```axiom
extern "C"
```

hoặc một ABI versioned trong tương lai.

---

# 4. `view<T>` không phải một runtime object

Ví dụ:

```axiom
fn sum(x: view<i64>) -> i64
```

Semantic:

```text
READ capability
```

Typical ABI:

```text
ptr + length
```

tức:

```text
RDI = pointer
RSI = length
```

Nhưng đây chỉ là **ABI representation phổ biến**, không phải semantic definition.

Compiler có thể:

```text
eliminate length
```

nếu biết static size.

Hoặc truyền:

```text
pointer + metadata
```

tùy type.

---

# 5. `mut_view<T>` cũng tương tự

```axiom
fn fill(x: mut_view<i32>, value: i32)
```

có thể thành:

```text
RDI = ptr
RSI = len
RDX = value
```

Compiler biết:

```text
mut_view
```

có exclusive write capability.

Nhưng ABI chỉ cần representation.

Lifetime/provenance không cần runtime metadata.

Đây chính là zero-cost abstraction.

---

# 6. View lifetime không truyền qua ABI

Ví dụ:

```text
view<T>
```

không cần:

```text
pointer
length
lifetime_id
owner_id
borrow_id
```

runtime.

Compiler đã kiểm tra lifetime trước khi ABI lowering.

Do đó:

```text
source safety
    ↓
compile-time
    ↓
erased
    ↓
native code
```

# 7. Scalar arguments

Các primitive:

```text
i8/i16/i32/i64
u8/u16/u32/u64
f32/f64
bool
pointer
```

được ABI classifier đưa vào:

```text
integer registers
FP/vector registers
stack
```

theo target ABI.

Axiom source không cần biết register nào.

# 8. Struct nhỏ nên được truyền bằng value

Ví dụ:

```axiom
struct Vec2 {
    x: f32
    y: f32
}
```

```axiom
fn add(a: Vec2, b: Vec2) -> Vec2
```

không nên mặc định hạ thành:

```text
pointer to a
pointer to b
pointer to result
```

chỉ vì đó là struct.

ABI classifier có thể truyền trực tiếp:

```text
XMM registers
```

hoặc integer registers.

Đây là nơi Axiom có thể đạt performance tương đương C.

---

# 9. Nhưng large struct không nhất thiết truyền bằng registers

Ví dụ:

```axiom
struct Huge {
    a: ...
    ...
    z: ...
}
```

ABI có thể biến:

```text
fn f(Huge) -> Huge
```

thành:

```text
hidden pointer to argument
hidden sret pointer
```

hoặc target ABI tương ứng.

Source programmer không cần biết.

---

# 10. Return large struct

Đây là case quan trọng.

Source:

```axiom
fn create() -> BigStruct
```

không có nghĩa:

```text
copy BigStruct
```

ABI lowering có thể:

```text
caller
  │
  ├── allocate result storage
  │
  └── pass hidden result pointer
             │
             ▼
          callee
             │
        construct directly
```

Ví dụ:

```text
RDI = sret pointer
```

callee ghi trực tiếp vào caller storage.

Không cần temporary.

---

# 11. Đây rất phù hợp với ownership model

```axiom
let x = create()
```

semantic:

```text
create owns result
```

nhưng ABI:

```text
caller-provided storage
```

Không có contradiction.

**Semantic move != physical memcpy.**

---

# 12. Return optimization

Ví dụ:

```axiom
fn make() -> Big {
    var x = Big(...)
    return x
}
```

Compiler có thể:

```text
construct x
   ↓
directly construct caller result
```

Không cần:

```text
x
 ↓ memcpy
temporary
 ↓ memcpy
caller
```

Đây là NRVO/RVO-style optimization nhưng có thể được thiết kế thành **ABI lowering**, không cần compiler heuristic đơn thuần.

---

# 13. `Copy` không đồng nghĩa truyền bằng memory copy

Ví dụ:

```axiom
fn f(x: SmallCopy) -> SmallCopy
```

nếu ABI có thể truyền trong registers:

```text
RDI → RAX
```

thì physical copy chỉ là register move.

Semantic `Copy` chỉ nói:

> Có thể tạo một value độc lập.

Không nói cách machine copy.

---

# 14. `Move` thậm chí có thể không có machine instruction

Ví dụ:

```axiom
let a = create()
let b = a
use(b)
```

Compiler:

```text
a semantic ownership
    ↓ MOVE
b semantic ownership
```

nhưng machine:

```text
không instruction nào
```

nếu cùng SSA value.

Đây là abstraction erasure.

---

# 15. `Drop` có thể ảnh hưởng ABI

Một type:

```text
T: Drop
```

không có nghĩa ABI phải truyền pointer.

Ví dụ:

```text
SmallDropType
```

vẫn có thể truyền trong register.

Sau khi function return:

```text
caller
 ↓
Drop(result)
```

Compiler generate cleanup.

---

# 16. Parameter ownership modes

Tôi đề xuất ABI/source semantics có 4 mode:

```text
IN
VIEW
MUT_VIEW
OWN
```

### IN

```axiom
fn f(x: Foo)
```

value parameter.

Nếu Foo Copy:

```text
COPY
```

Nếu non-Copy:

```text
MOVE
```

### VIEW

```axiom
fn f(x: view<Foo>)
```

read capability.

### MUT_VIEW

```axiom
fn f(x: mut_view<Foo>)
```

exclusive capability.

### OWN

Nếu cần explicit ownership semantic ở API/ABI boundary.

Có thể dùng:

```axiom
fn consume(x: own Foo)
```

nếu sau này thấy syntax này cần thiết.

Nhưng tôi **chưa muốn thêm `own` syntax ngay**.

`Foo` mặc định đã mang value/move semantics.

---

# 17. Có nên có `inout` không?

Tôi nghĩ không cần trong Core.

Thay vì:

```text
inout T
```

dùng:

```axiom
mut_view<T>
```

Ví dụ:

```axiom
fn normalize(x: mut_view<Vec3>)
```

đã biểu đạt rõ:

```text
read + write exclusive capability
```

và ABI có thể là pointer.

---

# 18. Method syntax không ảnh hưởng ABI

Ta đã chọn:

```axiom
fn length(self: Vec2) -> f32
```

gọi:

```axiom
v.length()
```

semantic lowering:

```text
length(v)
```

ABI:

```text
v trở thành argument đầu tiên
```

Do đó method không có hidden object pointer kiểu C++.

Không có:

```text
this pointer
vtable
object header
```

trừ dynamic dispatch.

# 19. Trait static dispatch

Ví dụ:

```axiom
trait Shape {
    fn area(self: view<Self>) -> f64
}
```

và:

```axiom
impl Shape for Circle {
    ...
}
```

Generic:

```axiom
fn print_area<T: Shape>(x: T) {
    x.area()
}
```

Compiler specialization:

```text
print_area<Circle>
```

có thể biến thành direct call:

```text
Circle.area
```

hoặc inline.

Không có vtable.

# 20. Dynamic dispatch mới cần dispatch data

Ví dụ:

```axiom
fn render(x: dyn Shape)
```

Conceptual representation:

```text

```

`dispatch_ptr` có thể trỏ đến:

```text
method table
drop
size
alignment
...
```

Nhưng **không đặt trong object itself**.

Ví dụ:

```text
struct Circle
{
    radius
}
```

vẫn chỉ có:

```text
radius
```

không có:

```text
vtable*
```

# 21. `dyn Trait` nên là fat value

Conceptually:

```text
dyn Shape
┌─────────────┬──────────────┐
│ data_ptr    │ dispatch_ptr │
└─────────────┴──────────────┘
```

Nhưng compiler có thể pass chúng:

```text
RDI = data
RSI = dispatch
```

hoặc target ABI khác.

# 22. `dyn Trait` và `view<dyn Trait>`

Có thể có:

```axiom
view<dyn Shape>
```

conceptually:

```text
data_ptr
dispatch_ptr
```

không cần:

```text
length
```

nếu trait object không phải contiguous sequence.

Nếu:

```text

```

với T là sequence:


Hai abstraction khác nhau.

# 23. Closure ABI

Closure:

```axiom
let f = |x| x + offset
```

conceptually:

```text
closure
├── code
└── environment
```

ABI có thể là:

```text
fn_ptr
env_ptr
```

Call:

```text
call(fn_ptr, env_ptr, x)
```

Nhưng với static closure:

```text
compiler knows exact closure type
```

nó có thể biến thành:

```text
direct function
```

và inline toàn bộ.

# 24. Captureless closure

```axiom

```

không có environment.

Có thể coerce:



Nhưng capturing closure:

không tự động biến thành:

```text

```

vì cần environment.

# 25. C callback

# 37. Các invariant ABI nên freeze

### AABI-01 — Semantic/ABI Separation
Source signatures do not prescribe physical calling convention.

### AABI-02 — Explicit ABI
Calling convention is explicit at ABI boundaries.

### AABI-03 — Native ABI Freedom
Native Axiom ABI may evolve unless explicitly versioned/stabilized.

### AABI-04 — C ABI Compatibility
`extern "C"` follows target C ABI rules.

### AABI-05 — Value Passing Freedom
Values may be passed in registers, stack, or caller storage.

### AABI-06 — Return Storage Freedom
Aggregate returns may use registers or hidden caller-provided storage.

### AABI-07 — No Semantic Copy Requirement
Passing or returning a value does not require physical memory copying.

### AABI-08 — View ABI Erasure
View lifetime/provenance metadata is compile-time unless explicitly required by an external ABI.

### AABI-09 — Static Trait Dispatch
Static trait calls do not require runtime dispatch metadata.

### AABI-10 — Explicit Dynamic Dispatch
Dynamic dispatch requires explicit `dyn`/equivalent abstraction.

### AABI-11 — No Object Header
Ordinary structs do not contain implicit runtime dispatch/type headers.

### AABI-12 — Closure Environment Explicit
Capturing closures carry environment only when required.

### AABI-13 — Captureless Closure Coercion
Captureless closures may coerce to compatible function pointers.

### AABI-14 — Generic ABI After Instantiation
Generic ABI classification occurs after concrete type instantiation.

### AABI-15 — ABI Before Machine Lowering
Target-specific calling convention lowering occurs before machine instruction selection.

### AABI-16 — ABI Observable Boundaries
External ABI contracts constrain representation and optimization.

### AABI-17 — Tail Call Freedom
Compiler may perform tail-call optimization when ABI permits.

### AABI-18 — Variadic ABI Isolation
General variadic semantics are primarily an FFI/ABI concern.

# 38. Một vấn đề tôi muốn sửa nhẹ trong baseline

Trước đây ta nói:

```text
IN
VIEW
MUT_VIEW
OWN
```

Tôi nghĩ **không nên biến `OWN` thành một parameter mode riêng ở v0.1**.

Chỉ cần:

```axiom
fn f(x: T)
```

là đủ.

Nếu `T` là Copy:

```text
COPY
```

Nếu `T` là non-Copy:

```text
MOVE
```

Nếu cần borrow:

```axiom
fn f(x: view<T>)
```

Nếu cần mutable capability:

```axiom
fn f(x: mut_view<T>)
```

Như vậy source language rất sạch:

```text
T          → value
view<T>    → read capability
mut_view<T>→ write capability
```

Không cần:

```text
own T
in T
out T
inout T
```

trong core.

# 39. Tôi cũng nghĩ Axiom nên có một quy tắc cực mạnh cho function call

**Arguments được evaluate deterministic left-to-right.**

Ví dụ:

```axiom
f(a(), b(), c())
```

luôn:

```text
a()
 ↓
b()
 ↓
c()
 ↓
f(...)
```

Sau đó compiler được phép reorder machine instructions **chỉ khi observable semantics không thay đổi**.

Điều này giải quyết rất nhiều vấn đề optimizer.
