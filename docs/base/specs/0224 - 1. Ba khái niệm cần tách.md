Tiếp tục với **COMPTIME-001 — Compile-time, Reflection và Code Generation**.

Đây là phần tôi muốn thiết kế khá “cứng”, vì nếu làm sai Axiom rất dễ biến thành kiểu:

> runtime language + macro language + template language + build-script language + compiler plugin language.

Mục tiêu của Axiom nên ngược lại:

> **Chỉ có một ngôn ngữ Axiom. Comptime là Axiom chạy trước runtime.**

---

# 1. Ba khái niệm cần tách

Axiom có:

```text
const
comptime
runtime
```

### `const`

Một giá trị được biết tại compile time.

```text
const MAX = 1024
```

### `comptime`

Chạy code Axiom trong quá trình biên dịch:

```text
comptime {
    ...
}
```

### runtime

Code bình thường:

```text
fn main() {
    ...
}
```

Không có macro language riêng.

---

# 2. `const` không phải `comptime`

Ví dụ:

```text
const SIZE: usize = 1024
```

Compiler chỉ cần evaluate expression.

Trong khi:

```text
comptime {
    generate_something()
}
```

có thể thực hiện nhiều computation.

Do đó:

```text
const = compile-time value
comptime = compile-time execution
```

---

# 3. Comptime dùng chính Axiom

Ví dụ:

```text
fn factorial(n: usize) -> usize {
    if n <= 1 {
        1
    } else {
        n * factorial(n - 1)
    }
}

const N = comptime factorial(10)
```

Không cần:

```text
constexpr
consteval
template
macro
```

cùng lúc.

---

# 4. Comptime phải dùng cùng type system

Nếu runtime có:

```text
struct User {
    id: u64
    name: String
}
```

thì comptime cũng hiểu `User`.

Không tạo:

```text
CompileTimeUser
```

hay AST-specific fake types.

Điều này rất quan trọng.

---

# 5. Ownership vẫn tồn tại ở comptime

Ví dụ:

```text
comptime {
    let data = load_schema()
    process(data)
}
```

Compiler vẫn chạy:

```text
MOVE
COPY
DROP
```

theo semantic model bình thường.

Không có một memory model hoàn toàn khác.

---

# 6. Nhưng comptime resource không được escape runtime

Ví dụ:

```text
comptime {
    let buffer = ...
}
```

buffer này tồn tại trong compile-time world.

Không được:

```text
fn get_buffer() -> ??? {
    return compile_time_buffer
}
```

Nếu cần dữ liệu runtime:

```text
const DATA = comptime generate_data()
```

thì compiler **materialize value** vào executable.

# 9. Vì sao cần capability?

Nếu:

```text

    network_request()
}
```

thì build có thể phụ thuộc internet.

Kết quả:

```text
build A hôm nay != build A ngày mai
```

Do đó external effects phải explicit.

# 10. Determinism

Comptime phải deterministic theo declared inputs.

Nếu:

```text
const X = comptime calculate()
```

thì compiler có thể cache.

Cache key phải bao gồm:

```text
source
compiler version
target
comptime inputs
capabilities
environment inputs
```

# 11. External input phải trở thành dependency

Ví dụ:

```text
comptime read_file("schema.json")
```

Compiler phải biết:

```text
schema.json
```

là dependency.

Nếu file thay đổi:

```text
recompile
```

Nếu không thay đổi:

```text
cache comptime result
```

# 12. Environment variable

Không cho:

```text
comptime getenv("HOME")
```

```text

```

và compiler đưa:

```text

```

# 13. Time/randomness

Đây là vấn đề quan trọng.

Không nên cho:

```text
comptime now()

```

Nếu cần:

```text
comptime build_timestamp()
```

Random seed cũng vậy.

# 15. Unsafe trong comptime

```text
    unsafe {
        ...
    }

```

nhưng không đồng nghĩa được phép phá sandbox.

# 16. Reflection

Axiom nên có **compile-time reflection**, không phải runtime reflection mặc định.

Ví dụ:

```text
comptime {
    let info = reflect(User)
}
```

Compiler có thể cung cấp:

```text
type.name
type.fields
field.name
field.type
enum.variants
trait.methods
```

---

# 17. Reflection không nên là object runtime

Không:

```text
TypeInfo object
```

được nhúng vào executable mặc định.

Ví dụ:

```text
let fields = reflect(User).fields
```

chỉ là compile-time information.

Compiler sau đó erase toàn bộ metadata.

---

# 18. Runtime reflection chỉ khi explicit

Nếu ứng dụng thực sự cần:

```text
runtime_type_info(User)
```

thì library/compiler có thể generate metadata.

Ví dụ:

```text
@reflect
struct User { ... }
```

lúc đó metadata mới được emit.

# 19. Derive

Axiom cần một cách generate implementation.

Ví dụ:

```text
@derive(Debug, Clone, Eq)
struct User {
    id: u64
    name: String
}
```

Compiler sinh:

```text
impl Debug for User ...
impl Clone for User ...
impl Eq for User ...
```

Nhưng `derive` không phải macro language.

Đây là **compiler-known comptime transformation**.

# 20. User-defined derive

Đây là vấn đề khó.

Tôi đề xuất:

### v1.0

Chỉ compiler/std derive:

```text
@derive(Debug)
@derive(Clone)
@derive(Eq)
@derive(Hash)
@derive(Default)
```

Không cho arbitrary user-defined procedural macros.

Lý do:

- deterministic;
- compiler đơn giản;
- diagnostics tốt;
- không có compiler plugin ABI;
- không có code generation tùy tiện phá parser.

# 21. Nhưng Axiom vẫn cần code generation mạnh

Nếu không có macro thì làm sao generate code?

Comptime có thể tạo **typed declarations** thông qua compiler API sau này.

Ví dụ conceptually:

```text
comptime fn generate_accessors(T: Type) -> Generated {
    ...
}
```

Nhưng đây phải là **typed compiler IR**, không phải tạo source string rồi parse lại.

# 25. Comptime function

Ví dụ:

```text
comptime fn make_name(T: Type) -> String {
    T.name
}
```

Có thể gọi:

```text
const NAME = make_name(User)
```

`comptime fn` chỉ được gọi ở compile time.

Nếu gọi runtime:

```text
let name = make_name(User)
```

→ compile error.

# 26. `comptime` block

```text

    register_schema(User)

```

```text
register_schema(User)
```

# 27. Có nên cho `comptime if`?

Không cần keyword mới.

Có thể:

```text
comptime if target.arch == "x86_64" {
    ...
}
```

Nhưng tôi thích:

```text
if comptime(target.arch == "x86_64") {
    ...
}
```

hay attribute:

```text
@cfg(target_arch = "x86_64")
```

Tốt nhất:

> **Configuration dùng `@cfg`; computation dùng `comptime`.**

Không tạo `comptime if`.

# 41. Comptime errors

Comptime failure phải là **compiler diagnostic**, không phải runtime panic.

Ví dụ:

```text
comptime fn parse_schema(...) {
    ...
}
```

Nếu schema sai:

```text
AXC4xxx: compile-time evaluation failed
```

Compiler hiển thị source location của invocation.

---

# 42. Comptime panic

`panic()` trong comptime:

```text
comptime {
    if invalid {
        panic("invalid configuration")
    }
}
```

không crash compiler process.

Nó phải trở thành:

```text
compile error
```

Compiler implementation vẫn có internal panic/ICE riêng.

---

# 43. User panic ≠ compiler ICE

Phân biệt:

```text
User comptime panic
    ↓
normal diagnostic
```

và:

```text
Compiler internal invariant failure
    ↓
ICE
```

Đây là lý do trước đây ta đã định nghĩa structured compiler errors.

# 44. Comptime resource lifetime

Ví dụ:


Không thể giữ:

```text
file
```

sang runtime.

Điều này tận dụng chính Drop system.

# 45. Comptime parallelism

Không nên cho user tự tạo thread compiler tùy ý trong v1.

Compiler có thể parallelize comptime evaluation nếu semantic engine chứng minh:

```text
no dependency
```

Ví dụ:

```text
comptime A()
comptime B()
comptime C()
```

có thể chạy song song.

Đây là **compiler optimization**, không phải programmer-visible concurrency.

Phần **rất quan trọng còn thiếu ở tầng semantic** là:

# **EFFECT/CONTROL/EXECUTION-001**

Không phải một Effect System tổng quát, mà là chốt chính xác **compiler theo dõi những loại “tác động” nào**:

```text
pure / impure?
unsafe?
allocation?
blocking?
async suspension?
panic?
IO?
atomic?
GPU?
foreign call?
```

Đây là điểm cần đặc biệt cẩn thận. Nếu đánh dấu mọi thứ thành effect:

```text
fn foo() throws allocates blocks async unsafe io ...
```

Axiom sẽ nhanh chóng trở thành một ngôn ngữ có signature cực kỳ phiền phức.

Tôi nghiêng mạnh về hướng:

> **Chỉ những thuộc tính có ảnh hưởng đến correctness/optimization/codegen mới trở thành compiler facts; phần còn lại là library/tooling metadata.**

Sau đó ta có thể chốt **EXECUTION/CONTROL-001**, rồi chuyển sang phần cực kỳ quan trọng tiếp theo: **GENERIC/TRAIT SOLVER + MONOMORPHIZATION + SPECIALIZATION**, tức cách compiler biến abstraction của Axiom thành machine code mà không tạo runtime overhead.
