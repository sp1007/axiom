Tiếp tục **MACHINE-IR-006 — Machine Optimization & Peephole Optimization**.

Đây là tầng cuối cùng trước encoder. Tôi đề xuất không biến nó thành một optimizer khổng lồ; chia thành các pass nhỏ, mỗi pass có invariant rõ ràng.

# 1. Mục tiêu

Input:

```text id="0sl9qt"
Machine IR
+ physical registers
+ stack slots
+ target instructions
+ ABI information
```

Output:

```text id="m6t4qf"
Machine IR tối ưu hơn
```

nhưng:

> **Không được thay đổi semantics.**

Pipeline:

```text id="o8h7y2"
Machine IR
    │
    ├── Target-independent cleanup
    │
    ├── Target peephole
    │
    ├── Copy propagation
    │
    ├── Dead instruction elimination
    │
    ├── Branch optimization
    │
    ├── Load/store optimization
    │
    ├── Register-aware optimization
    │
    ├── Frame-aware optimization
    │
    └── Final scheduling
            │
            ▼
       Machine Verify
```

# 2. Tại sao phải có post-RA optimizer?

Ví dụ trước RA:

```text id="7r6x9j"
v1 = ...
v2 = ...
v3 = COPY v1
```

Sau RA:

```text id="k0e2d1"
RAX = ...
RBX = ...
RBX = RAX
```

Sau khi thấy physical register thật, compiler có thể phát hiện:

```text id="8p9z3k"
RAX và RBX
```

không cần khác nhau ở một đoạn nào đó.

Hoặc:

```text id="2v2r4m"
COPY RAX,RAX
```

→ xóa ngay.

# 4. Dead Machine Instruction Elimination

Ví dụ:

```text id="8ksb1z"
MOV RAX, 10
MOV RBX, 20
ADD RAX, RBX
MOV RCX, 42
RET RAX
```

Nếu `RCX` không được dùng:

```text id="3g7f9y"
MOV RCX,42
```

→ dead.

Cũng không xóa:


# 7. Copy propagation

```text id="t0d4b7"
MOV RAX,RBX
ADD RCX,RAX
```

Nếu không có write nào vào RAX:

```text id="6m9v6a"
ADD RCX,RBX
```

→ xóa MOV.

---

# 8. Copy folding

Ví dụ:

```text id="v2dd8x"
MOV RAX,RBX
MOV RCX,RAX
```

→

```text id="xjz9qa"
MOV RCX,RBX
```

nếu semantics cho phép.

---

# 9. Identity operations

```text id="sv8f9m"
ADD RAX,0
SUB RAX,0
XOR RAX,0
OR  RAX,0
```

có thể xóa.

Nhưng phải cẩn thận với flags.

Ví dụ:

```text id="6xw7kf"
ADD RAX,0
```

không chỉ thay đổi RAX; nó có thể thay đổi flags.

Nếu flags live:

→ không được xóa.

---

# 10. Flags là machine resource

Đây là lý do ta đã quyết định từ MACHINE-IR-002:

> Flags không phải “vô hình”.

Ví dụ:

```text id="2o7x5q"
ADD RAX,RBX
JZ label
```

ADD tạo ZF.

Không thể thay ADD bằng operation không tạo ZF nếu JZ vẫn dùng ZF.

---

# 11. Dead flags

Ngược lại:

```text id="9b6m4j"
ADD RAX,RBX
MOV RCX,RAX
RET RCX
```

Nếu không instruction nào đọc flags:

```text id="p3y0h5"
flag production
```

không cần ảnh hưởng optimizer.

Nhưng không nhất thiết đổi ADD thành một instruction khác nếu semantics register vẫn giống.

---

# 12. Redundant extension

Ví dụ:

```text id="1x8h2j"
MOVZX RAX,EAX
MOV EAX,5
```

Nếu `MOV EAX,5` đã zero-extend RAX:

```text id="8r1b6a"
MOVZX
```

→ redundant.

---

# 13. Sign extension

Ví dụ:

```text id="5vcz1d"
MOVSX RAX,EAX
MOVSXD RAX,EAX
```

có thể có sequence redundancy.

Optimizer phải biết chính xác instruction semantics.

Không được dựa vào tên opcode.

---

# 14. Constant folding ở Machine IR

Ví dụ:

```text id="yqu0kl"
MOV RAX,10
ADD RAX,20
```

→

```text id="n1wq0r"
MOV RAX,30
```

Nhưng nếu flags được sử dụng:

```text id="g4v9dz"
ADD RAX,20
JZ ...
```

thì cần tạo flags tương ứng hoặc không được fold đơn giản.

condition chắc chắn true.

Có thể:


# 17. Peephole optimizer

Một peephole nhìn:

```text id="j8xw4m"
N instructions
```

ví dụ N = 2–8.

Ví dụ:

```text id="m4x1qf"
MOV RAX,RBX
MOV RBX,RAX
```

có thể tối ưu tùy liveness.

```text id="q2v7n0"
    instructions[0..N]
    live_in
    live_out
    flags_live
    memory_state
}
```

Pattern:

# 19. Peephole pattern không được phá memory

Ví dụ:

```text id="j2d4ps"
STORE [A],X
STORE [A],Y
```

Không thể luôn xóa store đầu tiên nếu:

- volatile
- atomic
- memory observable
- aliasing unknown
- trap possibility

Nếu là ordinary nonvolatile memory và compiler chứng minh first store dead:

→ có thể xóa.

---

# 20. Load/store forwarding

Ví dụ:

```text id="6k8e4x"
STORE [A],RAX
LOAD RBX,[A]
```

Nếu compiler chứng minh không có intervening write/observable memory effect:

```text id="1a5m2h"
MOV RBX,RAX
```

Có thể bỏ memory round-trip.

---

# 21. Store-to-load forwarding không phải lúc nào cũng legal

Ví dụ:

```text id="2j3x7k"
STORE [A],RAX
CALL foo
LOAD RBX,[A]
```

`foo` có thể modify A.

→ không forward.

Nếu:

```text id="6s0k5c"
A = stack private slot
```

và noalias/provenance proof cho phép:

→ có thể.

---

# 22. Load elimination

```text id="w1cx8z"
LOAD RAX,[A]
...
LOAD RBX,[A]
```

Nếu giữa hai load:

```text id="8q9j5c"
no write to A
```

→ second load có thể dùng RAX.

# 23. Nhưng alias analysis đã giảm mạnh trước đó

Axiom safe memory model cho compiler thông tin rất mạnh:

```text id="m9h1dw"
view
mut_view
ownership
capability
```

Sau khi lowering, các facts quan trọng có thể được chuyển thành:

```text id="y2j3w7"
NoAlias
ReadOnly
NonEscaping
```

Machine optimizer có thể sử dụng **compiler-proven facts**, không tự đoán.

# 24. Branch optimization

Ví dụ:

```text id="v0w9hx"
CMP RAX,0
JE L1
JMP L2

L1:
...
```

có thể đổi:

```text id="0qk2cm"
CMP RAX,0
JNE L2
```

và fall-through L1.

---

# 25. Branch inversion

Nếu:

```text id="e6yq7m"
JE cold
JMP hot
```

thì:

```text id="2d2s0e"
JNE hot
```

để hot path fall-through.

---

# 26. Branch threading

```text id="i3q7ze"
L1:
    JMP L2

L2:
    JMP L3
```

→

```text id="0hr3b8"
L1:
    JMP L3
```

---

# 27. Empty block elimination

```text id="8b7f0y"
L1:
    JMP L2
```

Nếu L1 không có label-observable semantics khác:

→ remove L1.

---

# 28. Basic block merging

```text id="7xq2v5"
L1:
    ...
    JMP L2

L2:
    ...
```

Nếu L2 chỉ có predecessor L1:

→ merge.

---

# 29. Fall-through optimization

Thay:

```text id="p8a2s4"
JMP next_block
```

bằng:

```text id="c0w4k1"
nothing
```

nếu layout đã đặt `next_block` ngay sau.

---

# 30. Block layout

Machine optimizer có thể reorder blocks:

```text id="6p1v9r"
hot
cold
hot2
```

để:

```text id="r2b7u0"
fallthrough → hot
conditional branch → cold
```

Mục tiêu:

- giảm taken branch
- tăng I-cache locality
- giữ hot path contiguous

# 31. Cold blocks

Compiler facts từ MIR có thể đánh dấu:

```text id="h6k3u2"

error
unlikely
trap
```

cold.

Nhưng đây chỉ là optimization hint.

Không ảnh hưởng semantics.

# 36. Register-aware optimization

Ví dụ:

```text id="j9n0q2"
MOV RAX,RBX
MOV RBX,RCX
```

có thể reorder/rename nếu dependencies cho phép.

Nhưng sau RA, physical register constraints rất thật.

Optimizer cần MachineVerifier kiểm tra sau mỗi transformation quan trọng.

---

# 37. Two-address cleanup

Ví dụ:

```text id="q7w3p9"
MOV RAX,RBX
ADD RAX,RCX
```

Nếu RBX chết sau đó:

```text id="7e2c4a"
```

không thể chỉ bỏ MOV, vì cần preserve RBX nếu còn dùng.

Nhưng nếu allocator đã coalesced:

```text id="r8y1p3"
RAX == RBX
```

thì MOV có thể biến mất.

---

# 38. Stack reload optimization

Ví dụ:

```text id="q4z8o1"
LOAD RAX,[spill0]
ADD RAX,RCX
STORE [spill0],RAX
LOAD RAX,[spill0]
```

Nếu giữa store/load không có tác động:

```text id="0j9s4x"
LOAD RAX,[spill0]
```

cuối cùng có thể dùng giá trị đang còn trong RAX.

---

# 39. Spill/reload folding

Một target có thể cho phép:

```text id="t1x6v8"
ADD RAX,[spill]
```

thay vì:

```text id="n5w3p1"
LOAD RCX,[spill]
ADD RAX,RCX
```

Nếu instruction addressing mode hỗ trợ.

Đây là optimization rất target-specific.

---

# 40. x86 memory operands

Ví dụ:

```text id="9c8p1k"
ADD RAX, [RBX+8]
```

có thể thay:

```text id="a4v6s2"
MOV RCX,[RBX+8]
ADD RAX,RCX
```

Nhưng:

- memory latency
- register pressure
- microarchitecture

có thể khiến lựa chọn thứ hai tốt hơn.

Cost model quyết định.

Không được bê nguyên x86 peephole rules sang AArch64.

Pattern database target-specific.

Ví dụ large immediate:

```text id="3k1h8d"

ADDI
```

hoặc:

```text id="v5q4s7"

...
```

Optimizer cần nhận diện sequence.

# 43. Constant materialization

Ví dụ:

```text id="2v7x1m"
MOV RAX, 0x123456789ABCDEF0
```

x86 có thể dùng immediate 64-bit trực tiếp trong một số instruction.

AArch64 thường cần:

```text id="z4q8h2"
MOVZ
MOVK
MOVK
MOVK
```

RISC-V:

```text id="7b1m4v"
LUI
ADDI
...
```

Đây là target-specific lowering.

---

# 44. Constant folding sau materialization

Nếu:

```text id="r2k8q5"
MOVZ/MOVK/MOVK...
```

sau đó constant được dùng một lần, optimizer có thể tìm sequence ngắn hơn.

Do đó constant materialization không nên coi là immutable ngay sau selection.

---

# 45. Instruction fusion

Một số CPU có macro-fusion:

```text id="v3f9k2"
CMP
JCC
```

x86 có thể fuse ở CPU frontend.

Machine optimizer không nhất thiết biến thành một instruction mới.

Nó chỉ cần **không phá pattern** nếu có lợi.

Đây là distinction quan trọng:

> CPU microarchitectural optimization không nhất thiết là Machine IR instruction.

---

# 46. Scheduling

Sau register allocation, có thể reorder independent instructions.

Ví dụ:

```text id="9n2b6m"
LOAD A
ADD B,C
LOAD D
```

có thể reorder:

```text id="r4j8t1"
LOAD A
LOAD D
ADD B,C
```

để hide latency.

---

# 47. Nhưng scheduling có thể ảnh hưởng register pressure

Ví dụ:

```text id="2f6h8q"
LOAD A → v1
LOAD B → v2
LOAD C → v3
```

Nếu delay uses:

→ ba registers sống cùng lúc.

Có thể spill.

Vì vậy scheduler phải có:

```text id="q0w8e1"
latency cost
register pressure cost
```

Và đây là một điểm rất đáng chú ý đối với mục tiêu Axiom:

> **Không có LLVM, libc, assembler hay linker bên thứ ba nào nằm trong đường đi bắt buộc của compiler cuối cùng.**

LLVM có thể dùng trong **bootstrap/differential testing**, nhưng kiến trúc chính của Axiom đã có:

## Bước tiếp theo

Giờ không nên tiếp tục đào sâu Machine IR mãi. **Encoder/Object Writer là bước kế tiếp**, cụ thể:

### `OBJECT-001 — Machine Encoder & Binary Encoding`

Ta sẽ thiết kế:

```text
Machine IR
   ↓
Instruction Encoding
   ↓
Machine Bytes
   ↓
Relocations
   ↓
Sections
   ↓
Symbols
   ↓
Object File
```

và triển khai kiến trúc cho:

- x86-64 instruction encoding
- AArch64 fixed 32-bit encoding
- RISC-V encoding
- WASM binary encoding
- immediates
- ModRM/SIB của x86
- prefixes/REX/VEX/EVEX
- relocation
- symbol references
- `.text/.rodata/.data/.bss`
- alignment
- COMDAT/weak/visibility
- TLS relocations
- debug/unwind sections

Đây sẽ là bước chuyển từ **“compiler đã biết phải chạy instruction nào”** sang **“compiler tự viết ra chính xác byte machine code/object file”**.
