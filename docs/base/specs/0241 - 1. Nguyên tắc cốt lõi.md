Tiếp tục **TARGET-001 — Target Description & ABI Registry**.

Đây là tầng rất quan trọng: nếu thiết kế tốt, Axiom có thể mở rộng từ x86-64 sang ARM64/RISC-V/WASM mà **không phải rải `if target == ...` khắp compiler**.

---

# 1. Nguyên tắc cốt lõi

Axiom cần phân biệt rõ:

```text
Target
ABI
CPU
ISA
Object Format
OS
Link Policy
```

Chúng liên quan nhưng **không phải một thứ**.

Ví dụ:

```text
x86_64-linux-gnu
```

không nên được coi là một chuỗi magic string mà compiler tự parse khắp nơi.

# 3. Target identity

Target identity phải canonical.

Ví dụ:

```text

aarch64-apple-ios
```

Nhưng đây chỉ là **tên định danh**.

Compiler làm việc với cấu trúc `TargetDescription`.

# 13. Struct layout

Target không nên trực tiếp quyết định toàn bộ struct layout.

```text

        ↑

```

Ví dụ:

```text

```

→ C ABI layout.

Còn:

```text
struct Foo { ... }
```

→ compiler-controlled layout.

# 19. Return-value ABI

Target ABI phải trả lời:

```text
T return bằng register?
T return bằng nhiều register?
T cần sret?
T caller-allocated?
```

Đây chính là input cho:

```text
ABI MIR → LIR
```

# 27. Không dùng libcall mặc định

Ví dụ target không có hardware:

```text
128-bit division
```

có thể lower thành:

```text
software sequence
```

hoặc optional compiler runtime.

Nhưng **không mặc định phụ thuộc libgcc**.

Đây là điểm quan trọng với mục tiêu self-contained của Axiom.

# 28. Compiler runtime nhỏ

Nếu cần helper:

```text

```

Axiom có thể tự cung cấp implementation.

Sau đó linker chỉ link helper nếu thực sự cần.

---

# 29. Runtime helper ≠ mandatory runtime

Đây là distinction quan trọng.

Binary:

```text

```

không cần runtime.

Binary dùng:

```text

```

có thể kéo một helper.

# 42. WASM


```text

```

# 61. Sau TARGET-001, kiến trúc Axiom đã có một "xương sống" khá hoàn chỉnh

```text
             ┌──────────────────────┐
             │      Axiom Source    │
             └──────────┬───────────┘
                        ↓
                 Semantic Compiler
                        ↓
                    Verified MIR
                        ↓
                       LIR
                        ↓
              ┌─────────┴─────────┐
              ↓                   ↓
         CPU Backend          WASM Backend
              ↓                   ↓
        Machine IR             WASM
              ↓                   ↓
          Encoder              Binary
              ↓                   ↓
             Object
              ↓
          Axiom Linker
              ↓
        Native Executable
```

Trong đó `TargetDescription` chạy xuyên suốt:

```text
             TargetDescription
              ↓ ↓ ↓ ↓ ↓ ↓ ↓
Type → ABI → LIR → Machine → Object → Linker
```

# 62. Bước tiếp theo nên chuyển sang **BOOTSTRAP-001**

Từ đây không nên tiếp tục thêm vô hạn feature vào spec trước khi thử xây compiler.

Ta đã có đủ kiến trúc để bắt đầu bootstrap.

Tôi đề xuất bootstrap theo **3 stage**:

```text
Stage 0
Existing host compiler
        ↓
Stage 1
Axiom compiler written in C
        ↓
Stage 2
Axiom compiler rewritten in Axiom
        ↓
Stage 3
Self-hosted Axiom compiler
```

Nhưng có một điểm tôi muốn thay đổi so với cách bootstrap thông thường:

**Không viết một compiler C khổng lồ rồi port nguyên xi sang Axiom.**

Nên xây một **Axiom Bootstrap Kernel** cực nhỏ:

```text
Lexer
Parser
AST
Type basics
HIR
MIR
x86-64 backend
Object writer
Linker
Driver
```

sau đó để chính Axiom dần thay thế từng subsystem.

Điều này sẽ kiểm chứng sớm nhất những thứ quan trọng nhất của dự án:

> **Axiom có thực sự đủ mạnh để tự xây compiler của chính nó hay không.**

Và sau BOOTSTRAP-001, bước kế tiếp sẽ là **COMPILER-001 — Lexer/Parser + ngữ pháp Axiom v0.1**, tức lúc chúng ta bắt đầu đóng băng syntax thực tế thay vì chỉ thiết kế backend.
