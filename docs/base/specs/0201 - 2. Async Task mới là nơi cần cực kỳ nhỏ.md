Đúng, nhưng cần phân biệt **OS thread** và **async task/future**. Con số ~32 bytes mà bạn nhớ về Rust **không phải kích thước của một OS thread**; nó thường liên quan đến kích thước/overhead của một số future/task representation hoặc handle, tùy runtime.

Với Axiom, tôi đề xuất **không đóng đinh một con số kiểu “task = 32 bytes”**, mà thiết kế sao cho task cực nhỏ khi có thể.

### 1. OS Thread

Axiom không nên tự cấp phát một “struct thread” lớn cho mỗi thread.

```text
Thread handle
    ├── ThreadId
    ├── state
    └── platform handle
```

Phần lớn bộ nhớ thực tế nằm ở:

```text
OS Thread
├── OS/kernel metadata
├── stack                ← lớn nhất
├── TLS
├── register/context
└── Axiom Thread object ← rất nhỏ
```

Ví dụ một API:

```axiom
let t = spawn(worker)
t.join()
```

`Thread` chỉ là **handle**, không phải toàn bộ thread state.

Axiom nên cho phép:

```text
@stack_size(64 * 1024)
spawn(worker)
```

và:

```text
spawn(worker)             // OS/default
spawn_local(worker)       // không tạo OS thread
```

Không nên bắt buộc mỗi thread có một runtime object lớn.

# 2. Async Task mới là nơi cần cực kỳ nhỏ

Đây mới là phần tôi nghĩ Axiom có thể làm rất tốt.

Ví dụ:

```axiom
async fn download() -> Result<Data, Error> {
    ...
}
```

Compiler biến nó thành state machine:

```text
Future<download>
┌──────────────────────────┐
│ state                    │
│ locals surviving await   │
│ child futures            │
│ captured values          │
└──────────────────────────┘
```

**Không cần stack riêng cho task.**

Nếu future chỉ có:

```axiom
async fn foo() -> i32 {
    42
}
```

thì compiler hoàn toàn có thể tạo representation gần như:

```text
enum FooFuture {
    Ready
}
```

thậm chí **0 bytes / được tối ưu biến mất** nếu context cho phép.

---

# 3. Task thực sự nên gồm 2 phần

Tôi đề xuất Axiom tách:

```text
Task Handle
    ↓
Task Control Block
    ↓
Future State Machine
```

Ví dụ:

```text
TaskHandle
    ├── TaskId
    └── pointer/index → TaskControlBlock
```

và:

```text
TaskControlBlock
├── state
├── waker/scheduler metadata
├── cancellation state
├── join state
└── pointer → Future
```

Future:

```text
FutureState
├── state machine state
├── values surviving await
└── child futures
```

Điểm quan trọng:

> **Task không nhất thiết phải chứa scheduler metadata + future + stack + allocator metadata trong một object.**

---

# 4. Axiom nên hướng tới task cực nhỏ

Tôi đề xuất mục tiêu kiến trúc:

| Loại | Stack riêng | Heap bắt buộc | Mục tiêu |
|---|---:|---:|---:|
| OS Thread | Có | Không | OS-dependent |
| Fiber | Có | Không | configurable |
| Async Future | Không | Không | compiler-dependent |
| Async Task | Không | Không bắt buộc | ~tens of bytes nếu state nhỏ |
| Task Handle | Không | Không | 1–2 machine words |

Không nên ghi trong spec:

> `Task = 32 bytes`

mà ghi:

> **Task representation has no mandated size. The compiler/runtime shall minimize persistent task state to the state required for scheduling, synchronization, cancellation, and values live across suspension.**

Như vậy compiler có quyền biến:

```text
Task = 24 bytes
```

hoặc:

```text
Task = 48 bytes
```

hoặc thậm chí inline task:

```text
Task = 0 additional bytes
```

nếu optimization cho phép.

---

# 5. Quan trọng hơn: không cấp phát heap cho mọi task

Ví dụ:

```axiom
for item in items {
    spawn(process(item))
}
```

Một runtime kiểu truyền thống có thể làm:

```text
malloc(Task)
malloc(Future)
malloc(...)
```

cho từng task.

Axiom **không nên bắt buộc như vậy**.

Scheduler có thể dùng:

```text
TaskPool
├── TaskSlot
├── TaskSlot
├── TaskSlot
└── ...
```

hoặc intrusive queue:

```text
Task
 ├── state
 ├── next
 └── future state
```

hoặc arena:

```text
Arena
 ├── Task A
 ├── Task B
 ├── Task C
 └── Task D
```

Compiler/runtime được phép chọn chiến lược.

---

# 6. Một điểm rất hợp với memory model của Axiom

Điều này khớp hoàn toàn với nguyên tắc chúng ta đã chốt:

> **Storage strategy is not part of ordinary value semantics.**

Do đó:

```axiom
async fn foo() ...
```

chỉ định **semantic Future**, không chỉ định:

- heap
- stack
- arena
- pool
- pinned memory
- task allocation

Compiler/runtime quyết định.

Nếu future không escape:

```axiom
await foo()
```

compiler có thể **inline hoàn toàn state machine**.

Nếu:

```axiom
spawn(foo())
```

future phải tồn tại đủ lâu cho task, nhưng nó có thể nằm trong:

```text
scheduler arena
task pool
caller-provided storage
heap
inline task storage
```

---

# 7. `await` không nên tạo allocation

Đây là invariant tôi đề xuất thêm cho Axiom:

**AASYNC-51 — Suspension Does Not Imply Allocation**

> Suspending an async computation shall not inherently require heap allocation, task allocation, or stack allocation.

Và:

**AASYNC-52 — Future Size Is Determined By Live State**

> The persistent representation of a Future contains only state semantically required across suspension, subject to ABI and optimization constraints.

**AASYNC-53 — Task Storage Is Runtime-Selectable**

> Task scheduling storage may use stack, inline storage, pool, arena, heap, or other implementation-defined storage without changing async semantics.

**AASYNC-54 — Non-Escaping Futures May Be Stack/Register Resident**

> A future that does not escape may be represented entirely in local/register storage or eliminated.

**AASYNC-55 — Spawn Requires Persistent State**

> `spawn` requires the spawned computation's required state to outlive the spawning call, but does not mandate a particular allocation strategy.

## 8. Và tôi muốn sửa một điểm quan trọng trong thiết kế trước đây

Ta từng nói:

```text
spawn(fn)
```

yêu cầu `Send`.

Đúng, nhưng **đừng để `Send` kéo theo heap allocation**.

Ví dụ:

```axiom
spawn(worker(x))
```

Compiler có thể tạo:

```text
Scheduler
    │
    ▼
┌──────────────────────┐
│ Task slot            │
│ state = 2            │
│ x                    │
│ worker state         │
└──────────────────────┘
```

Toàn bộ task có thể nằm trong **một allocation duy nhất**, hoặc thậm chí trong một pool slot.

Không:

```text
Task
 ↓ malloc
Future
 ↓ malloc
Captured x
 ↓ malloc
Waker
 ↓ malloc
```

Đó sẽ là thiết kế tệ cho Axiom.

---

# 9. OS thread và async task phải là hai tầng hoàn toàn khác nhau

Tôi muốn đóng kiến trúc thành:

```text
                 Axiom Concurrency
                       │
          ┌────────────┴────────────┐
          ↓                         ↓
      OS Thread                 Async Task
          │                         │
      OS stack                 Future state
      TLS                       Scheduler
      registers                 Waker
      kernel state              cancellation
```

Và:

```text
Thread ≠ Task
Task ≠ Future
Future ≠ Stack
```

Đây là một distinction rất quan trọng.

Một OS thread có thể chạy:

```text
100,000 async tasks
```

miễn là scheduler và task state đủ nhỏ.

Ngược lại:

```text
100,000 OS threads
```

thì bộ nhớ chủ yếu sẽ bị giới hạn bởi **stack + OS resources**, chứ không phải bởi Axiom `Thread` struct.

## 10. Mục tiêu tôi đề xuất cho Axiom

Thay vì quảng bá:

> “Axiom task luôn 32 bytes”

hãy đặt mục tiêu mạnh hơn:

> **Axiom async task has no fixed minimum representation size; for a task whose live state fits in N bytes, the persistent task state should approach N bytes plus minimal scheduler/control metadata. No heap allocation is semantically required by `async` or `await`.**

Đây là hướng tốt hơn Rust-style “32 bytes”, vì nó cho phép compiler tối ưu rất sâu.

Và đặc biệt nó phù hợp với mục tiêu của Axiom: **không biến compiler/runtime sophistication thành bureaucracy cho programmer**.

**Task tiếp theo hợp lý trong chuỗi này là thiết kế cụ thể `Task/Future/Scheduler` của Axiom** — gồm layout tối thiểu, intrusive task, task pool, work-stealing, cancellation, `JoinHandle`, `spawn`, `spawn_local`, và cách compiler sinh state machine mà không cần `Pin` hay heap bắt buộc.
