# 90. `if` là expression

Axiom đã xác định:

```axiom
let result = if condition {
    10
} else {
    20
}
```

Hai nhánh phải có type tương thích.

```text
condition
   │
 ┌─┴────┐
10     20
 │       │
 └───┬───┘
     ▼
    i32
```

Nếu:

```axiom
let result = if condition {
    10
} else {
    "hello"
}
```

→ compile error.

Không có implicit `Any`.

---

# 91. `if` không có `else`

Vẫn cho phép:

```axiom
if ready {
    start()
}
```

Semantic type của expression này là:

```text
unit
```

Tức:

```axiom
let x = if ready {
    start()
}
```

thì:

```text
x: ()
```

Nếu một branch trả `i32`:

```axiom
if ready {
    42
}
```

thì phải có quy tắc rõ.

Tôi đề xuất:

> Block dùng ở statement position có thể discard value; trong value position, `if` không có `else` có type `unit`.

Ví dụ:

```axiom
let x = if ready {
    42
}
```

→ `x: ()`, không phải `i32`.

Điều này tránh việc compiler phải đoán programmer muốn gì.

---

# 92. Block cũng là expression

```axiom
let x = {
    let a = 10
    let b = 20
    a + b
}
```

→ `x: i32`.

Nhưng:

```axiom
let x = {
    let a = 10
}
```

→ `x: ()`.

Do đó:

```text
expression
   │
   └── block
          │
          ├── statements
          └── final expression
```

Nếu không có final expression:

```text
unit
```

# 93. `return` trong nested block

Ví dụ:

```axiom
fn test(x: i32) -> i32 {
    let y = {
        if x < 0 {
            return 0
        }

        x * 2
    }

    y + 1
}
```

`return` thoát khỏi **function**, không chỉ block.

Compiler MIR:

```text
block
 ├── condition
 │    └── RETURN 0
 └── continue
```

Drop cần chạy trước return.

Ví dụ:

```axiom
fn test() -> Result<i32, Error> {
    let file = open()?

    let x = {
        if something() {
            return Ok(10)
        }

        20
    }

    Ok(x)
}
```

`return` phải Drop `file`.

### Invariant

**ACFLOW-20 — Return Performs Required Cleanup**

# 94. `break` và `continue`

`continue`:

```axiom
while condition {
    let file = open()?

    if skip {
        continue
    }

    process(file)
}
```

Trước `continue`, compiler phải drop những local có scope kết thúc tại iteration hiện tại.

Không được để resource sống xuyên iteration nếu source scope không cho phép.

# 95. `break` có trả value không?

Nhiều ngôn ngữ cho:

```text
break value
```

nhưng tôi **không khuyến nghị đưa vào v0.1**.

Hiện tại:

```axiom
break
```

chỉ thoát loop và có type `unit`.

Nếu muốn loop tạo value:

```axiom
var result = ...
while ... {
    ...
}
```

hoặc dùng iterator/combinator.

Lý do: `break value` kéo theo khá nhiều interaction với:

```text
loop expression
type inference
Drop
defer-like semantics
labeled loops
```

không đem lại giá trị đủ lớn ở v0.1.

### Quyết định

**ASURF-41 — `break` Has No Value in v0.1**

có type:

```text
()
```

`for` cũng:

# 97. Có cần `defer` không?

Đây là một feature đáng cân nhắc vì systems programming thường dùng:

```text
defer cleanup()
```

Nhưng Axiom đã có deterministic Drop.

Ví dụ C-style:

```text
open
defer close
```

Axiom:

```axiom
let file = File.open(...)?
```

scope exit tự động:

```text
DROP file
```

Do đó `defer` không cần thiết cho resource cleanup.

Nếu cần cleanup logic:

```axiom
{
    let guard = ...
    ...
}
```

có thể tạo scope rõ ràng.

### Quyết định

**`defer` không thuộc Core v0.1.**

Nếu sau này cần, nó phải là control-flow sugar được lower thành cleanup action, không phải một runtime mechanism.

# 99. Có cần unchecked indexing?

Có, nhưng không nên đưa vào safe syntax bình thường.

Ví dụ:

```axiom
unsafe {
    array.get_unchecked(i)
}
```

Compiler có thể optimize:

```axiom
for i in 0..array.len() {
    sum += array[i]
}
```

để loại bounds checks nếu chứng minh được.

Do đó programmer không cần dùng unsafe chỉ để đạt performance.

# 100. Range semantics

Ta có:

```axiom
0..10
```

là:

```text
0 <= x < 10
```

và:

```axiom
0..=10
```

là:

```text
0 <= x <= 10
```

Các range phải có semantics rõ về type.

Tôi đề xuất:

```text
Range<T>
RangeInclusive<T>
```

library/core-known abstraction.

Compiler có thể optimize chúng thành loop counters.

# 101. Operator overloading

Đây là feature nên có vì Axiom cần:

```axiom
a + b
```

cho user-defined numeric/vector types.

Nhưng không được biến operator resolution thành C++ template nightmare.

Ví dụ:

```axiom
trait Add<Rhs = Self> {
    type Output
    fn add(self, rhs: Rhs) -> Self.Output
}
```

Compiler desugar:

```text
a + b
```

→ `Add.add(a, b)`.

Nhưng primitive types có intrinsic implementation.

---

# 102. Operator semantics phải deterministic

Nếu:

```axiom
a + b
```

có nhiều impl:

```text
Add<A>
Add<B>
```

thì ambiguity compile error.

Không có implicit conversion chain dài để tìm candidate.

Tôi đề xuất operator resolution chỉ cho phép:

```text
exact match
+
limited compiler-defined numeric compatibility
```

Không có conversion graph tùy ý.

---

# 103. Có nên cho implicit numeric promotion?

Tôi tiếp tục giữ:

> **Không.**

Ví dụ:

```axiom
let x: i64 = i32_value
```

phải explicit:

```axiom
let x = i32_value as i64
```

Lý do:

```text
i32 + i64
```

không được compiler tự quyết định:

```text
→ i64
```

hay:

```text
→ i32
```

hay:

```text
→ common type
```

Numeric code càng thấp-level càng cần predictable.

# 104. Arithmetic overflow

Đã có:

```text
+
+%
+|
```

Tôi đề xuất semantics:

| Operator | Semantics |
|---|---|
| `+` | checked |
| `+%` | wrapping |
| `+|` | saturating |

Tương tự:

```text
-
*
```

Trong debug/release:

**không thay đổi semantics**.

Đây là điểm rất quan trọng.

Release optimization không được biến:

```text
checked +
```

thành wrapping chỉ vì nhanh hơn.

# 105. Floating point

`f32/f64` cần tách khỏi integer overflow semantics.

Ví dụ:

```text
NaN
+∞
-∞
```

theo IEEE-style target semantics trong phạm vi target hỗ trợ.

Không nên hứa mọi CPU có bit-perfect behavior trong mọi floating operation.

Compiler được phép dùng target floating instructions theo một **floating-point mode** xác định.

V0.1 nên có profile:

```text
strict
fast
```

nhưng tôi **không muốn đưa `fast-math` vào surface syntax**.

Đây nên là compiler/profile policy.

# 106. `==`

Equality nên là trait/operator semantics:

```text
Eq
```

nhưng compiler có intrinsic implementations cho primitive.

Không cho:

```axiom
ptr1 == ptr2
```

trong safe code nếu đây là raw pointers; raw pointer operations thuộc unsafe.

Logical value equality và address equality phải phân biệt.

# 107. Hashing

Library:

```text
trait Hash
trait Eq
```

Map yêu cầu:

```text
K: Eq + Hash
```

Compiler chỉ cần biết generic constraints.

# 108. `never`

Axiom có:

```text
never
```

cho:

```axiom
fn abort() -> never
```

và:

```axiom
let x = if condition {
    42
} else {
    unreachable()
}
```

`never` có thể coerce vào mọi expected type:


Đây là một trong rất ít implicit coercions tôi cho rằng đáng giữ.

# 110. Type inference

Axiom nên có inference, nhưng không nên có "magic".

Ví dụ:

```axiom
let x = 10
```

→ mặc định `i32` nếu context không xác định.

```axiom
let x: i64 = 10
```

→ literal được kiểm tra theo expected type.

```axiom
let x = Vec.new()
```

nếu không có context xác định `T`:

```text
cannot infer type parameter
```

Không đoán từ runtime.

# 111. Integer literal

```axiom
let x = 10
```

không nên lập tức parse thành `i32` rồi mới cast.

Compiler nên giữ:

```text
IntegerLiteral(10)
```

ở HIR/type inference.

Sau expected type:

```text
10 : i64
```

hoặc default:

```text
10 : i32
```

Điều này giúp:

```axiom
let x: u8 = 255
```

hợp lệ mà không cần:

```text
255 as u8
```

vì literal chưa có concrete type trước inference.

Nhưng:

```axiom
let n = 300
let x: u8 = n
```

vẫn phải explicit conversion.

# 112. `const` vs `comptime` vs `static`

Đây là chỗ rất cần phân biệt.

## `const`

```axiom
const MAX: usize = 1024
```

Là:

> compile-time value.

Không có storage identity runtime bắt buộc.

Có thể inline.

---

## `comptime`

```axiom
comptime fn make_table(...) -> ...
```

Là:

> execute code trong compile-time execution domain.

Có thể thực hiện tính toán phức tạp.

---

## `static`

```axiom
static VERSION: Text = "1.0"
```

Là:

> runtime storage identity với program lifetime.

Không được inline nếu address/identity observable.

---

# 113. `static` mutable

```axiom
static var COUNTER: Atomic<u64> = ...
```

cho phép.

Nhưng:

```axiom
static var COUNTER: u64
```

nếu có mutation từ nhiều threads → data race.

Compiler phải reject safe code nếu truy cập không có synchronization.

Có thể dùng:

```axiom
static COUNTER: Atomic<u64>
```

hoặc lock.

---

# 114. Global mutable state

Tôi không nghĩ cần cấm.

Systems language cần:

```text
MMIO
kernel state
runtime state
global caches
```

Nhưng safe global mutation phải tuân concurrency model.

Do đó:

```text
static
+
ordinary mutable access
```

chịu cùng alias/concurrency rules như local storage.

Không có “global variable được miễn ownership”.

---

# 115. Static initialization

Không cho:

```text
global constructor magic
```

Ví dụ:

```axiom
static TABLE = make_runtime_table()
```

không được tự động tạo hidden startup function nếu `make_runtime_table()` là runtime computation.

`static` initializer phải:

1. compile-time constant, hoặc
2. explicit initialization API.

Điều này tránh `.init_array`/constructor-order surprises.

### Invariant

**ASTATIC-20 — Static Initialization Has No Hidden Runtime Constructors**

# 116. `static` + Drop

Đây là một câu hỏi khó.

Ví dụ:

```axiom
static RESOURCE: File = ...
```

Nếu File có Drop, khi process kết thúc có nên Drop?

Tôi đề xuất:

> **Static values không có implicit Drop-at-process-exit trong Core v0.1.**

Lý do:

- shutdown order khó xác định;
- OS tự reclaim process memory;
- resource cleanup cần explicit lifecycle;
- tránh hidden runtime.

Nếu cần cleanup:

```axiom
shutdown()
```

explicit.

Điều này đặc biệt phù hợp với mục tiêu runtime tối thiểu.

# 117. Thread-local static

Cho phép:

```text
static thread_local CACHE: ...
```

Semantic:

```text
one storage instance / thread
```

Lifetime:

```text
thread lifetime
```

Không phải process-wide.

Cleanup tương tự static:

> Không mặc định tạo hidden destructor chain.

Nếu cần explicit teardown, library/thread runtime quản lý.

# 120. `@repr` tổng kết

Ta hiện có:

```text
@repr(C)
@repr(transparent)
@repr(packed)
@align(N)
```

Quy tắc:

- `@repr(C)` → ABI/layout contract.
- `@repr(transparent)` → wrapper có representation của field duy nhất phù hợp.
- `@repr(packed)` → giảm alignment, có thể tạo unaligned access; unsafe/system-level.
- `@align(N)` → yêu cầu alignment tối thiểu.

Không có:

```text
@repr(Rust)
```

cần thiết; default Axiom representation đã là compiler-controlled.

# 123. Bức tranh semantics bây giờ khá hoàn chỉnh

Có thể viết ngắn gọn semantics Axiom thành:

```text
                    SOURCE
                       │
                       ▼
                    VALUES
                       │
              ┌────────┴────────┐
              │                 │
            OWNED             CAPABILITY
              │                 │
          Copy / Move      view / mut_view
              │                 │
              └────────┬────────┘
                       │
                    RESOURCE
                       │
                      Drop
                       │
               ┌───────┴───────┐
               │               │
             LOCAL           SHARED
               │               │
             Send            Share
               │               │
               └───────┬───────┘
                       │
                 EXECUTION DOMAIN
                       │
          ┌────────────┼────────────┐
          │            │            │
         CPU          GPU          FFI
          │            │            │
          └────────────┼────────────┘
                       │
                    STORAGE
                       │
     ┌────────┬────────┼────────┬────────┐
     │        │        │        │        │
   stack    heap     arena    static   external
```

Điều tôi thích ở model này là **không một tầng nào ép tầng khác phải có implementation cụ thể**.

Ví dụ:

```text
Box<T>
```

không đồng nghĩa:

```text
malloc()
```

`async` không đồng nghĩa:

```text
heap
```

`trait` không đồng nghĩa:

```text
vtable
```

`view` không đồng nghĩa:

```text
reference object
```

`Drop` không đồng nghĩa:

```text
free()
```

`Send` không đồng nghĩa:

```text
thread
```

Đây chính là điều giúp Axiom có cơ hội đạt mục tiêu **high-level nhưng vẫn gần machine-level**.

# 124. Còn một vấn đề lớn trước Semantic Freeze

Sau vòng này, phần semantics cơ bản gần như đủ.

Nhưng trước khi đóng `v0.1`, tôi muốn thực hiện **End-to-End Consistency Test** thay vì tiếp tục thêm luật nhỏ.

Ta sẽ lấy khoảng 10 chương trình đại diện:

```text
01 hello
02 struct + methods
03 generic + trait
04 Vec + views
05 partial move + Drop
06 Result + ?
07 async + Future
08 threads + channel + atomic
09 unsafe + FFI
10 GPU kernel
11 recursive graph
12 public package API
```

Với mỗi chương trình, chúng ta sẽ viết:

```text
SOURCE
  ↓
AST
  ↓
HIR
  ↓
TYPE CHECK
  ↓
OWNERSHIP/CAPABILITY
  ↓
DROP
  ↓
VERIFIED MIR
  ↓
LIR
```

và quan trọng nhất:

> **Không được phép có bước nào phải "đoán ý programmer".**

Sau End-to-End Test đó, tôi sẽ tạo một bảng:

```text
Language Rule
Compiler Rule
Optimization Rule
ABI Rule
Library Rule
```

để tách hẳn những gì thuộc **ngôn ngữ** khỏi những gì chỉ là **implementation strategy**.

Đây sẽ là bước cuối trước khi chúng ta có thể gọi bộ semantics này là **AXIOM LANGUAGE SPECIFICATION v0.1 — Semantic Freeze Candidate**.
