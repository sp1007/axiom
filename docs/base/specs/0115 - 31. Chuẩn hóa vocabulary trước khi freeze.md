# 31. Chuẩn hóa vocabulary trước khi freeze

Hiện Axiom đang có nhiều từ gần nghĩa:

```text
ownership
lifetime
view
reference
capability
storage
identity
provenance
region
allocation
resource
```

Nếu không định nghĩa thật chặt, compiler sau này sẽ rất dễ có semantics mâu thuẫn.

Tôi đề xuất bộ định nghĩa chính thức sau.

---

## 31.1 Value

**Value** là dữ liệu có type và semantic identity theo value semantics.

Ví dụ:

```axiom
let a = 42
let b = a
```

với `i32`:

```text
a = 42
b = 42
```

Hai value độc lập.

---

# 31.2 Storage

**Storage** là nơi physical representation của value/resource tồn tại.

Có thể là:

```text
register
stack
inline aggregate
heap
arena
pool
static
TLS
device memory
external memory
```

Storage **không phải** value.

Ví dụ:

```axiom
let x = Box.new(...)
```

`Box<T>` có semantic ownership của storage, nhưng compiler có thể eliminate heap allocation nếu stable address không observable.

---

# 31.3 Ownership

**Ownership** là quyền chịu trách nhiệm đối với một resource/value instance.

Ví dụ:

```text
x owns Buffer
```

Khi:

```axiom
let y = x
```

với non-Copy:

```text
x → MOVED
y → OWNS
```

Ownership không đồng nghĩa với physical address.

---

# 31.4 Capability

Đây là abstraction quan trọng nhất.

**Capability** là quyền truy cập có giới hạn vào một vùng dữ liệu/resource.

Ví dụ:

```text
view<T>      = READ capability
mut_view<T>  = WRITE capability
```

Capability có:

```text
owner/provenance
region
access mode
validity
```

nhưng không nhất thiết chứa metadata runtime.

---

# 31.5 Region

**Region** là tập các locations mà capability có thể truy cập.

Ví dụ:

```text
array[0..10]
```

là region.

Struct:

```text
User.name
```

cũng là region.

Do đó:

```text
Region(A)
Region(B)
```

có thể:

```text
DISJOINT
SAME
CONTAINS
CONTAINED_BY
OVERLAPS
UNKNOWN
```

Đây là **compiler semantic relation**, không phải runtime object.

---

# 31.6 Provenance

**Provenance** trả lời:

> Capability này được tạo từ storage/resource nào và bằng chuỗi phép biến đổi nào?

Ví dụ:

```text
user
 ↓
user.profile
 ↓
user.profile.name
```

Compiler vẫn biết:

```text
name capability ← user
```

dù machine representation cuối cùng chỉ còn pointer.

---

# 31.7 Lifetime

Đây là chỗ tôi muốn thay đổi cách diễn đạt trước đây.

Không nên nói:

> “Axiom không có lifetime.”

Điều đó không đúng.

Axiom **có lifetime semantics**, nhưng:

> programmer không phải viết lifetime annotations.

Ta có:

```text
Storage lifetime
Ownership lifetime
Capability lifetime
Resource lifetime
```

đây là những khái niệm khác nhau.

---

# 31.8 Resource lifetime

Ví dụ:

```axiom
let file = File.open(path)?
```

`file` có resource lifetime.

Nhưng memory backing resource có thể do OS quản lý.

Vì vậy:

```text
resource lifetime ≠ memory lifetime
```

Điểm này đã có `AMEM-43`.

# 32. Chuẩn hóa thành một mô hình 4 lifetime

Ta nên chính thức hóa:

```text
              VALUE
                │
        ┌───────┴────────┐
        │                │
    STORAGE           RESOURCE
        │                │
 storage lifetime   resource lifetime
        │
        └──────┐
               │
          CAPABILITY
               │
       capability lifetime
```

Không có một "universal lifetime".

Đây là điểm rất quan trọng cho Axiom.

---

# 33. Ownership không phải capability

Ví dụ:

```axiom
let buffer = Buffer(...)
let v = view(buffer)
```

Ta có:

```text
buffer
  ownership ───────────────► storage

v
  capability ──────────────► region(buffer)
```

`v` **không own** buffer.

Nếu:

```axiom
drop(buffer)
```

trong khi `v` còn sống:

```text
ERROR
```

Không phải vì `v` là owner.

Mà vì:

```text
capability lifetime > owner validity
```

---

# 34. Đây là invariant nền tảng

**ACAP-23 — A Capability Does Not Transfer Ownership**

**ACAP-24 — A Valid Capability Requires Valid Provenance**

**ACAP-25 — An Owner Cannot Be Destroyed While Dependent Capabilities Remain Live**

---

# 35. Nhưng có một vấn đề: `view` có thể được copy không?

Có.

Ví dụ:

```axiom
let a = view(buffer)
let b = a
```

Hai READ capabilities:

```text
a → READ
b → READ
```

được phép.

Nhưng:

```axiom
let a = mut_view(buffer)
let b = a
```

không được tạo hai active mutable capabilities.

Do đó:

```text
view<T>      ≈ Copy capability
mut_view<T>  ≈ Move-only capability
```

Đây không nhất thiết phải là source-level `Copy` trait implementation.

Nó là một **intrinsic capability rule**.

---

# 36. `mut_view` và Copy

Điều này cũng giải quyết một vấn đề trước đây.

Nếu:

```text
mut_view<T>
```

về mặt physical representation chỉ là:

```text
pointer + extent
```

thì machine-level có thể copy nó.

Nhưng language semantics không cho phép programmer tạo alias bằng copy.

Do đó:

> **Bitwise-copyable ≠ semantically Copy.**

Đây là distinction cực kỳ quan trọng.

### Invariant

**ACAP-26 — Representation Copyability Does Not Imply Semantic Copyability**

---

# 37. Move cũng không phải memcpy

Tương tự:

```axiom
let b = a
```

với non-Copy type.

Semantics:

```text
a → MOVED
b → OWNED
```

Không nói:

```text
memcpy(a, b)
```

Compiler có thể:

```text
register rename
pointer transfer
SSA rename
physical move
zero move
```

### Invariant

**AOWN-20 — Move Is An Ownership-State Transition, Not A Required Physical Copy**

---

# 38. Copy cũng không nhất thiết memcpy

Ví dụ:

```axiom
struct Vec {
    x: f32
    y: f32
}
```

Copy có thể trở thành:

```text
two register values
```

hoặc compiler eliminate hoàn toàn.

### Invariant

**AOWN-21 — Copy Is A Semantic Value Duplication, Not A Required Memory Copy**

---

# 39. Drop cũng không phải `free`

Đây là điểm cần đóng băng rất rõ.

```axiom
drop(x)
```

semantic:

> resource/value cleanup obligation đã hoàn thành.

Nó có thể:

```text
free memory
close file
release lock
decrement explicit Arc count
return object to pool
release GPU resource
do nothing
```

Vì vậy:

```text
Drop ≠ deallocation
```

đã có `AMEM-44`.

Tôi đề nghị nâng nó thành nguyên tắc cấp cao:

**ADROP-20 — Drop Completes Ownership Cleanup, Not Necessarily Memory Deallocation**

---

# 40. Storage lifetime và ownership lifetime

Ví dụ `Box<T>`:

```axiom
let x = Box.new(value)
```

Ownership:

```text
x owns Box
```

Storage:

```text
heap storage
```

Nếu compiler scalar-replace:

```text
x
 ↓
stack/register
```

thì semantic ownership vẫn không đổi.

Do đó:

```text
ownership semantics
        ↓
storage strategy
```

chứ không ngược lại.

# 41. Stable address là ngoại lệ

Nếu:

```axiom
let p = address_of(x)
```

hoặc:

```axiom
extern_call(&x)
```

thì physical address trở thành observable.

Compiler không còn tự do relocate.

Đây là:

```text
Stable Address Contract
```

Do đó:

```text
observable address
        ↓
storage constraint
```

Đây là một trong số ít trường hợp implementation strategy trở thành semantic requirement.

---

# 42. `Vec` relocation

Ví dụ:

```axiom
var v = Vec(...)
let x = view(v)

v.push(...)
```

Nếu `push` có khả năng relocate:

```text
x
```

đang active.

Compiler phải reject hoặc yêu cầu capability kết thúc trước mutation.

Ví dụ:

```axiom
use(x)

v.push(...)
```

→ hợp lệ.

Không phải `reserve()` là đủ.

Đã có:

**AMEM-23 — Reserve Does Not Imply Stable Address**

Điểm này nên giữ tuyệt đối.

---

# 43. Handle không phải view

Đây là distinction rất quan trọng cho graph/ECS.

```text
view<T>
```

là:

```text
temporary access capability
```

trong khi:

```text
Handle<T>
```

là:

```text
logical identity
```

Handle có thể sống lâu hơn object storage hiện tại.

Ví dụ:

```text
Handle<Node>
```

có:

```text
index
generation
```

Không giữ raw pointer.

Do đó:

```text
view ≠ reference identity
handle ≠ memory capability
```

---

# 44. Raw pointer là gì?

Raw pointer:

```text
*const T
*mut T
```

không phải owner.

Không phải safe capability.

Nó là:

> machine-address-level value với semantics được giới hạn bởi `unsafe`.

Sau khi validate raw pointer và tạo:

```text
view<T>
```

thì compiler quay lại capability model.

Đây là một bridge rất đẹp:

```text
SAFE
  ↓
view<T>
  │
  │ unsafe conversion
  ▼
*const T
  │
  │ validation
  ▼
view<T>
```

---

# 45. Unsafe không phải "tắt compiler"

Đóng băng:

```text
unsafe {
    ...
}
```

cho phép programmer tạo các state mà compiler không thể tự chứng minh.

Nhưng compiler vẫn kiểm tra:

```text
syntax
types
ABI
machine legality
basic ownership consistency
```

và quan trọng:

> Sau khi unsafe code tạo ra một safe capability, capability đó lại chịu toàn bộ safe verifier.

### Invariant

**AUNSAFE-20 — Unsafe Suppresses Specific Proof Obligations, Not Compiler Correctness Checks**

# 46. Đây là điểm rất mạnh cho Axiom

Ví dụ:

```axiom
unsafe {
    let p = ...
    let buffer = view_from_raw(p, len)
    process(buffer)
}
```

`process` không cần biết `buffer` đến từ unsafe.

Nó nhận:

```text
view<Bytes>
```

và có thể hoạt động hoàn toàn safe.

Điều này cho phép viết low-level library một lần, sau đó expose safe API.

# 47. Trait và capability

Trait method:

```axiom
trait Reader {
    fn read(self: view<Self>) -> Result<...>
}
```

không có nghĩa object phải có reference counter/vtable.

Static dispatch:

```text
Reader<T>
```

có thể compile thành direct function.

Dynamic:

```axiom
dyn Reader
```

mới cần runtime dispatch representation.

# 48. `dyn Trait` cần được xem là storage abstraction hay capability?

Nó là **dynamic value representation**, không phải capability.

Conceptually:

```text
dyn Trait
 ├── data pointer
 └── dispatch metadata
```

Nó có thể own hoặc borrow tùy surrounding type/context.

Ví dụ:

```text
Box<dyn Reader>
```

→ owned dynamic object.

Trong khi:

```text
view<dyn Reader>
```

→ borrowed/read capability.

Như vậy:

```text
dynamic dispatch
```

và:

```text
ownership
```

là hai orthogonal axes.

Đây là kiến trúc đúng.

# 49. Generic cũng orthogonal với ownership

```axiom
fn consume<T>(x: T) { ... }
```

`T` có thể:

```text
Copy
Move
Drop
Send
Share
```

tùy constraints.

Compiler không nên mặc định:

```text
T = Copy
```

hoặc:

```text
T = Move-only
```

Mọi generic operation phải chứng minh requirement.

Ví dụ:

```axiom
fn duplicate<T>(x: T) -> (T, T)
```

→ yêu cầu:

```text
T: Copy
```

Trong khi:

```axiom
fn consume<T>(x: T)
```

không yêu cầu Copy.

# 50. Generic + Drop

Compiler monomorphization có thể biết:

```text
T: Drop
```

và generate cleanup.

Nếu specialization:

```text
T = i32
```

thì Drop có thể disappear.

Đây là:

```text
semantic Drop requirement
```

được erase sau optimization.

Không cần runtime type information.

---

# 51. Trait object + Drop

`dyn Trait` nếu owned phải có đủ metadata để thực hiện destruction đúng concrete type.

Ví dụ:

```text
Box<dyn Service>
```

conceptually:

```text
data_ptr
dispatch_ptr
drop_fn
method_table
```

Nhưng đây là ABI/implementation detail của dynamic representation.

Không phải mọi trait đều cần object header.

# 52. Error semantics cũng cần vocabulary alignment

`Result<T,E>`:

```text
value
```

`panic`:

```text
control-flow termination
```

`abort`:

```text
process termination
```

Không gọi cả ba là "error".

Nên terminology:

```text
Result = recoverable outcome
panic  = unrecoverable execution failure
abort  = process termination
```

Điều này giúp tránh việc sau này ai đó đề xuất:

```text
try/catch
```

chỉ vì gọi panic là exception.

# 53. `Drop` trong `Result`

Ví dụ:

```axiom
let file = File.open(path)?
let result = file.read()?
```

Nếu `read` trả `Err`:

```text
file must Drop
```

Nếu `File.open` trả `Err`:

```text
file chưa tồn tại
```

không có Drop.

Do đó `?` là một control-flow edge trong MIR.

```text
CALL
  │
  ├── Ok → continue
  │
  └── Err → cleanup → return
```

Không cần exception table.

# 54. Async + Drop + Result

Đây là chỗ cần kiểm tra sâu.

```axiom
async fn f() -> Result<(), E> {
    let file = open()?

    await work()?

    Ok(())
}
```

State machine:

```text
State0
  file
  ↓
await
  ↓
State1
  file
```

Nếu Future bị dropped khi suspended:

```text
DROP file
DROP future state
```

Nếu await trả Err:

```text
DROP file
RETURN Err
```

Nếu thành công:

```text
DROP file
RETURN Ok
```

Ba đường đều có deterministic cleanup.

# 58. Comptime

Comptime phải sử dụng cùng type semantics nhưng **không được có arbitrary runtime effects** mặc định.

Ví dụ:


Nhưng:

```text
comptime
 ├── arbitrary network
 ├── arbitrary process execution
 └── mutate user's system
```

không được mặc định.

Capability sandbox:

```text
ReadSource
WriteGenerated
ExecuteTool
Network
Environment
Filesystem
```

được cấp explicit.

Điều này giữ compiler deterministic.

# 59. Comptime ownership

Một object tạo trong comptime:

```text
comptime value
```

không được "escape" thành runtime resource nếu semantics không định nghĩa được representation.

Ví dụ compile-time file handle:

```text
comptime File
```

không thể đơn giản trở thành runtime `File`.

Comptime resource lifetime phải kết thúc trong compile-time execution domain.

Chỉ **result value** được materialize sang runtime.

### Invariant

**ACOMP-20 — Compile-Time Resources Cannot Implicitly Escape Into Runtime**

**ACOMP-21 — Comptime Produces Runtime Values, Not Hidden Runtime Resources**
