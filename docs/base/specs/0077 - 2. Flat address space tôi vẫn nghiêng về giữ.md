Tiếp tục theo đúng baseline hiện tại, phần đáng chốt tiếp theo là **Allocation & Storage Model**. Đây là phần rất quan trọng vì nó quyết định Axiom có thật sự đạt được mục tiêu “nhẹ như C nhưng tiện hơn C” hay không.

## 1. Tôi đề xuất Axiom không có “stack model” và “heap model” ở cấp ngôn ngữ

Thay vì:

```text
stack<T>
heap<T>
arena<T>
pool<T>
...
```

làm thành các loại bộ nhớ cứng trong type system, Axiom nên có:

```text
Semantic Value
      │
      ▼
Storage Requirement
      │
      ├── register
      ├── inline
      ├── stack
      ├── heap
      ├── arena
      ├── pool/slab
      ├── static
      ├── TLS
      └── external/device
```

**Type không quyết định nơi lưu trữ.**

Ví dụ:

```axiom
fn square(x: i64) -> i64 {
    return x * x
}
```

`x` có thể hoàn toàn không tồn tại trong RAM:

```text
RDI → multiply → RAX
```

Compiler không cần “allocate stack slot” chỉ vì source có biến.

Tương tự:

```axiom
var x = BigStruct(...)
```

có thể được:

```text
register
    ↓
stack
    ↓
heap
```

tùy escape analysis, ABI và optimization.

Đây nên là **nguyên tắc bất biến**.

---

# 2. Flat address space: tôi vẫn nghiêng về giữ

Ý tưởng trước đây của bạn về **bộ nhớ phẳng** là hợp lý, nhưng cần phân biệt:

> **Flat address space ≠ một allocator duy nhất.**

Ở semantic level:

```text
                 Axiom Address Space
┌─────────────────────────────────────────────┐
│                                             │
│  static     heap      mmap      device      │
│     │         │          │          │       │
│     └─────────┴──────────┴──────────┘       │
│                  address                    │
│                                             │
└─────────────────────────────────────────────┘
```

Nhưng compiler/library có thể sử dụng:

```text
General Heap
Arena
Pool
Slab
Stack
TLS
Shared Memory
Memory Mapping
DMA
GPU Memory
```

mà **không biến chúng thành những type hệ thống khác nhau một cách bắt buộc**.

Điều này cho Axiom hai ưu điểm:

- lập trình viên không phải học một hệ thống pointer/reference/storage phức tạp;
- compiler vẫn có đủ tự do để tối ưu storage.

---

# 3. Nhưng cần thêm một khái niệm: Storage Identity

Đây là điểm tôi nghĩ Axiom cần chốt.

Không phải mọi value đều có **identity**.

Ví dụ:

```axiom
let x = 10
let y = x
```

`x` và `y` là hai value.

Không cần có:

```text
address(x)
address(y)
```

Nhưng:

```axiom
let b = Box.create(...)
```

thì `b` đại diện cho một storage object có identity.

Ta có thể phân biệt:

```text
VALUE
STORAGE
ADDRESS
POINTER
VIEW
```

chính xác hơn:

```text
Value
  │
  ├── no storage identity
  │
  └── storage-backed
          │
          ├── stable identity
          │
          └── relocatable identity
                    │
                    └── address
```

Đây giải quyết rất nhiều vấn đề.

---

# 4. “Addressable” phải là một property, không phải mặc định

Ví dụ:

```axiom
let x = 123
```

Compiler có quyền:

```text
x = RAX
```

Không có địa chỉ.

Nhưng:

```axiom
let b = Box.create(123)
```

thì storage identity tồn tại.

Nếu chương trình làm:

```axiom
let p = unsafe_address_of(b)
```

thì lúc này địa chỉ trở thành **observable**.

Compiler không còn được tùy tiện relocate nữa nếu contract yêu cầu stable address.

Đây chính là:

> **Address exposure creates a storage constraint.**

Rất quan trọng cho optimizer.

---

# 5. Tôi đề xuất 3 mức storage semantic

Không cần hàng chục loại pointer.

### Level 0 — Value

```axiom
let x = MyStruct(...)
```

Không đảm bảo address.

Compiler tự do:

```text
register
stack
inline
eliminate
```

---

### Level 1 — Storage Identity

Một object/storage tồn tại độc lập với value representation.

Ví dụ:

```axiom
Box<T>
Arena<T>
Vec<T>
```

Có identity:

```text
Storage #42
```

nhưng **chưa nhất thiết stable address**.

Ví dụ `Vec`:

```text
storage #42
capacity = 1024
```

có thể relocate từ:

```text
0x1000
```

sang:

```text
0x8000
```

nếu không có capability đang phụ thuộc vào vùng đó.

---

### Level 2 — Stable Address

Chỉ khi programmer/library yêu cầu:

```text
stable storage
```

thì relocation bị cấm.

Ví dụ concept:

```axiom
Box<T>
Pinned<T>
Stable<T>
```

Không nhất thiết cả ba phải tồn tại trong Core.

Có thể chỉ cần library abstraction.

---

# 6. Đây giúp Vec cực kỳ đơn giản

Ta có:

```axiom
var v = Vec<i32>()
v.push(10)

let x = view(v)
```

Compiler biết:

```text
x → capability → storage(v)
```

Nếu:

```axiom
v.push(20)
```

có khả năng realloc:

```text
ERROR
```

nếu `x` vẫn còn sống.

Nhưng:

```axiom
use(x)

v.push(20)
```

thì capability đã hết lifetime:

```text
x
│
├── READ
│
└── EXPIRED

v.push()
    ↓
may relocate
```

Không cần programmer viết:

```text
'a
'b
```

Không cần borrow annotation.

Đây chính là nơi compiler làm phần việc khó.

---

# 7. Arena cũng không cần trở thành một memory model mới

Ví dụ:

```axiom
var arena = Arena.create()

let a = arena.alloc(Foo(...))
let b = arena.alloc(Bar(...))
```

Semantic:

```text
Arena
 ├── Storage A
 ├── Storage B
 └── owns both
```

Khi arena chết:

```text
Arena.drop()
    ↓
all storage released
```

Compiler vẫn kiểm tra:

```axiom
return view(a)
```

nếu `a` thuộc arena local:

```text
ERROR: view escapes arena lifetime
```

Nhưng người dùng không phải quản lý lifetime.

---

# 8. Pool/Slab tương tự

Pool chỉ là một allocation strategy:

```text
Pool<T>
 ├── slot 0
 ├── slot 1
 ├── slot 2
 └── ...
```

Semantic type:

```axiom
Pool<T>
```

không phải:

```text
PoolMemoryPointer<T>
PoolLifetime<'a>
PoolReference<'b>
```

Điều này phù hợp với triết lý:

> **Storage strategy belongs to library/implementation, not the fundamental type system.**

---

# 9. Stack cũng nên được compiler quản lý hoàn toàn

Không nên có:

```axiom
stack_alloc<T>()
```

trong Core thông thường.

Compiler tự quyết:

```text
local
 ↓
escape analysis
 ↓
┌───────────────┐
│ register      │
│ stack         │
│ inline        │
│ heap          │
└───────────────┘
```

Chỉ system programming mới cần primitive đặc biệt.

Ví dụ:

```axiom
unsafe {
    let p = stack_address(...)
}
```

thì mới phá abstraction.

---

# 10. Một điểm rất quan trọng: `move` không có nghĩa là copy memory

Ví dụ:

```axiom
var a = BigStruct(...)
var b = a
```

Nếu `BigStruct` là Move:

```text
semantic:

a ──MOVE──> b
```

Không nhất thiết:

```text
memcpy(a, b)
```

Compiler có thể biến thành:

```text
same registers
```

hoặc:

```text
same stack slot
```

hoặc thậm chí:

```text
no physical object at all
```

Đây là một trong những lợi ích lớn nhất của việc tách:

```text
semantic ownership
```

khỏi:

```text
physical memory movement
```

---

# 11. Cache locality nên là optimization, không phải semantic property

Không nên đưa:

```text
Cache<T>
Hot<T>
Cold<T>
NUMA<T>
HugePage<T>
```

vào Core type system.

Compiler/backend/library có thể hỗ trợ:

```text
@align
@cacheline
@cold
@hot
prefetch()
```

khi cần.

Nhưng chương trình bình thường không cần biết CPU cache hoạt động thế nào.

---

# 12. NUMA cũng không nên phá flat memory model

Semantic:

```text
Address Space
```

Implementation:

```text
NUMA node 0
NUMA node 1
NUMA node 2
...
```

Nếu programmer cần kiểm soát:

```axiom
numa.allocate(...)
```

thì đây là **system library**.

Không cần:

```text
NUMA pointer
Remote pointer
Local pointer
```

trong type system trừ khi một platform-specific API thực sự cần.

---

# 13. Device/GPU memory là ngoại lệ đáng chú ý

Ở đây tôi không muốn ép mọi thứ thành một loại memory duy nhất.

Ví dụ:

```text
CPU RAM
GPU VRAM
MMIO
DMA buffer
Shared memory
Mapped file
```

có semantics khác nhau.

Nhưng thay vì đưa tất cả vào Core, ta có thể có:

```axiom
trait Storage {
    ...
}
```

hoặc các system/library abstractions:

```axiom
CpuBuffer<T>
GpuBuffer<T>
Mapped<T>
DmaBuffer<T>
```

Compiler chỉ cần hiểu một số capability cơ bản:

```text
READ
WRITE
ADDRESSABLE
VOLATILE
ATOMIC
EXTERNAL
```

Như vậy Core vẫn sạch.

# 14. Memory model hoàn chỉnh sẽ trở thành

Tôi đề xuất Axiom chốt mô hình theo tầng này:

```text
                 AXIOM MEMORY MODEL
                         │
              ┌──────────┴──────────┐
              │                     │
          VALUE SEMANTICS      STORAGE SEMANTICS
              │                     │
        Copy / Move             Identity
              │                     │
              │               Lifetime
              │                     │
              │             Relocation
              │                     │
              └──────────┬──────────┘
                         │
                  ACCESS CAPABILITY
                         │
              ┌──────────┼──────────┐
              │          │          │
             READ       WRITE      MOVE
              │          │
              └────┬─────┘
                   │
               PROVENANCE
                   │
          ┌────────┴────────┐
          │                 │
        SAFE              UNSAFE
          │                 │
        view             pointer
        mut_view         address
```

Phần dưới:

```text
                 STORAGE STRATEGY
                       │
       ┌───────┬───────┼───────┬────────┐
       │       │       │       │        │
    register stack   heap    arena    external
                       │
                    pool/slab
                       │
                    mmap/TLS
                       │
                  device/GPU
```

**Storage strategy không làm thay đổi semantic type.**

# 15. Và đây là nguyên tắc tôi muốn thêm vào Axiom

### ASM-13 — Value/Storage Separation

> A semantic value does not inherently imply a particular physical storage location.

### ASM-14 — Identity Is Explicit

> Storage identity exists only when required by the semantic abstraction.

### ASM-15 — Addressability Is Not Default

> A value is not addressable unless its storage/addressability is semantically required or explicitly exposed.

### ASM-16 — Relocation Is Permitted by Default

> Storage may relocate unless a stable-address contract or observable address dependency prohibits relocation.

### ASM-17 — Physical Movement Is Not Semantic Move

> A language-level move transfers ownership semantics; it does not require physical memory copying.

### ASM-18 — Allocation Strategy Independence

> Program semantics do not depend on whether storage is implemented using stack, heap, arena, pool, slab, register, or another strategy, unless explicitly exposed.

### ASM-19 — Flat Address Space

> Axiom presents a unified address/provenance model while allowing multiple physical allocation/storage strategies.

### ASM-20 — Storage Constraints Propagate

> Once address, external storage, stable identity, volatile access, DMA, or equivalent physical constraints become observable, optimization must preserve those constraints.

## 16. Điểm tôi nghĩ Axiom đang rất khác C/C++

C:

```c
int x;
int *p = &x;
```

Ngay từ đầu programmer thường phải nghĩ:

> x nằm ở đâu? stack? heap? static?

Axiom:

```axiom
var x = 10
```

chỉ có nghĩa:

> Có một value `10`.

Compiler có thể biến nó thành:

```asm
mov eax, 10
```

Nếu programmer thực sự cần storage:

```axiom
Box(...)
```

hoặc một storage abstraction phù hợp.

Nếu thực sự cần địa chỉ:

```axiom
unsafe ...
```

Như vậy **pointer không còn là trung tâm của lập trình Axiom**, nhưng Axiom vẫn có đủ khả năng làm kernel, driver, compiler, game engine, database engine, networking stack...

Đây theo tôi là hướng rất đáng giữ.

---

### Tiếp theo nên chốt

Sau Allocation & Storage, còn **4 vấn đề nền tảng** tôi cho là quan trọng hơn cả syntax:

1. **Pinning + stable address** — khi nào object được phép relocate.
2. **Memory ordering + atomics** — mô hình memory concurrency chính thức.
3. **Object lifetime + initialization** — đặc biệt partial initialization và `Drop`.
4. **Optimization contract** — compiler được phép “ma thuật” đến mức nào mà vẫn đảm bảo semantics.

Trong đó tôi đề xuất đi tiếp **Pinning + Stable Address**, vì nó nối trực tiếp `Vec / Box / Arena / view / async / FFI / self-referential data` thành một mô hình thống nhất.
