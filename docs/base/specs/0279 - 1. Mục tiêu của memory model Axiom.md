## BOOTSTRAP-021 — Axiom Memory Model + Data-Race Semantics

Đây là phần rất quan trọng vì từ đây **ownership/capability, atomic, mutex, channel, thread, async, optimizer và codegen** phải cùng dựa trên một semantic model duy nhất.

Tôi đề xuất Axiom **không bê nguyên memory model của C++**. C++ memory model rất mạnh nhưng phức tạp, đặc biệt ở các góc như `consume`, release sequence, out-of-thin-air, compiler reordering. Axiom có thể đạt hiệu năng tương đương mà vẫn có model dễ hiểu hơn.

---

# 1. Mục tiêu của memory model Axiom

Axiom cần đồng thời đạt:

1. **Safe code không có data race.**
2. Atomic có semantics chuẩn, đủ cho lock-free programming.
3. Mutex/channel/thread join tự tạo synchronization.
4. Compiler được phép reorder/optimize mạnh.
5. Programmer không phải học một hệ thống memory-order quá phức tạp.
6. Unsafe vẫn cho phép lập trình machine-level.
7. Không bắt compiler phải giữ nguyên thứ tự source code nếu observable semantics không yêu cầu.
8. GPU có thể mở rộng model nhưng không làm CPU Core phức tạp.

Mô hình nền:

```text
              Axiom Memory Model
                     │
        ┌────────────┼────────────┐
        │            │            │
   Ordinary      Atomic       External
    Memory       Memory        Memory
        │            │            │
 ownership/      ordering      FFI/MMIO/
 capability      semantics      device
        │            │
        └────── synchronization ──────┐
                                      │
                              happens-before
```

---

# 2. Ba khái niệm phải tách biệt

Axiom không nên gom tất cả thành "memory ordering".

### 2.1 Sequenced-before

Trong **một execution context**, các operation có quan hệ:

```text
A
↓
B
↓
C
```

gọi là:

```text
A sequenced-before B
B sequenced-before C
```

Ví dụ:

```axiom
var x = 0
var y = 0

x = 10
y = 20
```

Về semantic model:

```text
x = 10
   ↓
y = 20
```

Nhưng compiler vẫn có thể đổi instruction order nếu không làm thay đổi observable semantics.

**Source order ≠ machine instruction order.**

---

# 3. Happens-before

Đây mới là quan hệ quan trọng giữa các execution domain.

Axiom định nghĩa:

```text
happens-before =
    sequenced-before
  + synchronizes-with
  + transitive closure
```

Ví dụ:

```text
Thread A:

data = 42
flag.store(1, Release)
```

Thread B:

```text
if flag.load(Acquire) == 1 {
    print(data)
}
```

Nếu Acquire load quan sát publication tương ứng của Release:

```text
data = 42
    ↓
flag.store(1, Release)
    ↓
flag.load(Acquire)
    ↓
print(data)
```

Do đó `data == 42` được bảo đảm.

Đây là **publication pattern** cơ bản.

---

# 4. Synchronizes-with

Axiom nên định nghĩa một tập nhỏ các synchronization edges rõ ràng.

### Atomic

```text
Release store
      ↓
Acquire load
```

khi Acquire quan sát giá trị/publication tương ứng.

### Mutex

```text
unlock()
   ↓
lock()
```

khi lock acquisition tương ứng với release của mutex.

### Channel

```text
send(value)
      ↓
recv()
```

Message nhận được nhìn thấy trạng thái đã được publish trước send.

### Thread

```text
parent
   │
   └── spawn ──→ child
```

Các thao tác trước khi child bắt đầu được publish cho child.

Ngược lại:

```text
child work
    ↓
thread completion
    ↓
join()
    ↓
parent continues
```

Child writes xảy ra-before code sau `join`.

### Task/Future

Scheduler cũng phải tạo synchronization khi task được migrate giữa execution domains.

# 5. Scheduler wake không tự động là memory barrier

Điểm này rất quan trọng.

Không được định nghĩa:

```text
wake()
```

tự động có nghĩa:

```text
Acquire + Release + full barrier
```

Nếu không, runtime sẽ bị ép thành một memory-ordering primitive khổng lồ.

Thay vào đó:

```text
Task state publication
       +
scheduler synchronization
       +
wake notification
```

mới tạo ra semantic cần thiết.

`wake()` chủ yếu là:

> "có thể poll lại task này."

Không phải:

> "mọi memory trước đó đã được publish."

Điều này giữ scheduler nhẹ.

# 6. Atomic modification order

Mỗi atomic object có một **modification order** riêng.

Ví dụ:

```axiom
a.store(1, Relaxed)
a.store(2, Relaxed)
a.store(3, Relaxed)
```

Một atomic object:

```text
a
```

có thứ tự modification:

```text
M1 → M2 → M3
```

Các thread không được quan sát một atomic object theo cách phá vỡ modification order của nó.

Nhưng:

> Relaxed atomic không tạo happens-before với các memory access khác.

Đây là distinction cực kỳ quan trọng.

---

# 7. Năm memory orders

Giữ đúng bộ hiện tại:

```text
Relaxed
Acquire
Release
AcqRel
SeqCst
```

Không đưa `Consume` vào Axiom.

### Relaxed

Đảm bảo:

- atomicity
- modification order

Không đảm bảo publication của ordinary memory.

```axiom
counter.fetch_add(1, Relaxed)
```

phù hợp cho:

- counters
- statistics
- reference counters trong một số thiết kế
- unique ID generation

---

### Acquire

Acquire tạo ordering cho các operation **sau nó**.

Ví dụ:

```axiom
if ready.load(Acquire) {
    use(data)
}
```

Nếu `ready` được Release publish:

```text
writer:
    data = X
    ready.store(1, Release)

reader:
    ready.load(Acquire)
    use(data)
```

`data = X` được publish.

---

### Release

Release ordering áp dụng cho operations **trước nó**.

```axiom
data = X
ready.store(1, Release)
```

Có nghĩa:

```text
data write
    ↓
Release publication
```

---

### AcqRel

Cho operation vừa đọc vừa ghi:

```axiom
counter.compare_exchange(..., AcqRel, Acquire)
```

Phần load:

```text
Acquire
```

Phần store thành công:

```text
Release
```

---

### SeqCst

Sequential consistency.

Ngoài Acquire/Release semantics, các SeqCst atomic operations tham gia một **single total order** nhất quán với happens-before.

Ví dụ:

```axiom
x.store(1, SeqCst)
y.store(1, SeqCst)
```

và thread khác:

```axiom
x.load(SeqCst)
y.load(SeqCst)
```

Compiler/backend không được tạo ra quan sát vi phạm total SeqCst order.

# 8. Không có `memory_order_consume`

Tôi khuyến nghị **cấm hoàn toàn** trong Axiom v1.

Không cần:

```text
Consume
```

vì:

- khó reasoning
- khó compiler
- ít giá trị thực tế
- dễ tạo khác biệt giữa compiler
- không phù hợp triết lý "một semantic question → một mechanism"

Nếu programmer cần dependency ordering:

```text
Acquire
```

là lựa chọn rõ ràng.

---

# 9. Data race

Định nghĩa Axiom:

> Data race xảy ra khi hai execution có thể truy cập cùng một memory location, ít nhất một access là write, các access không được atomic và không có synchronization bảo vệ phù hợp.

Ví dụ:

```axiom
var x = 0

thread {
    x = 1
}

thread {
    x = 2
}
```

Đây là conflict:

```text
WRITE x
   ×
WRITE x
```

Safe Axiom phải reject.

---

# 10. Safe code không được chứa data race

Điểm này nên trở thành invariant mạnh:

```text
Safe Axiom program
        ↓
No undefined data race
```

Nhưng cần phân biệt:

> "compiler có thể chứng minh an toàn"

với

> "mọi dynamic data race đều có thể được compiler chứng minh."

Axiom không nên tuyên bố compiler có omniscient static race detector.

Thay vào đó:

### Safe abstractions

```text
Mutex
RwLock
Atomic
Channel
Arc<Mutex<T>>
structured concurrency
```

cung cấp synchronization contracts mà verifier hiểu.

### Unsafe/raw memory

Programmer chịu trách nhiệm:

```axiom
unsafe {
    *ptr = value
}
```

Nếu phá invariant, behavior không còn thuộc safe memory guarantees.

# 11. `view<T>` và `mut_view<T>` trong memory model

Đây là chỗ BOOTSTRAP-021 phải nối trực tiếp với BOOTSTRAP-012.

### `view<T>`

```text
READ capability
```

Nhiều reader được phép.

Nhưng nếu một thread khác đang:

```text
WRITE T
```

thì phải có synchronization.

`view<T>` **không tự tạo synchronization**.

---

### `mut_view<T>`

```text
exclusive WRITE capability
```

Không thể có:

```text
mut_view<T>
+
another read/write access
```

đồng thời nếu region có thể overlap.

---

# 12. Atomic không biến thành `mut_view<T>`

Rất quan trọng:

```axiom
Atomic<u32>
```

không được phép làm:

```axiom
mut_view<u32>
```

bằng cách thông thường.

Vì:

```text
Atomic<u32>
```

có semantic:

```text
atomic access
```

trong khi:

```text
mut_view<u32>
```

là:

```text
ordinary exclusive memory access
```

Nếu cho phép:

```axiom
var a: Atomic<u32>

let p = mut_view(a)
```

thì programmer có thể bypass atomic semantics.

=> **reject trong safe code.**

---

# 13. Nhưng `view<Atomic<T>>` có thể Share

Ví dụ:

```axiom
let a: Atomic<u64> = Atomic(0)

spawn {
    a.fetch_add(1, Relaxed)
}

spawn {
    a.fetch_add(1, Relaxed)
}
```

Đây là hợp lệ vì:

```text
Atomic<T> : Share
```

không có nghĩa:

```text
T : Share
```

Atomic là một synchronization-safe access abstraction.

---

# 14. Mutex publication

Ví dụ:

```axiom
var data = 0
var mutex = Mutex(data)
```

Thread A:

```axiom
var g = mutex.write()
g.value = 42
```

Thread B:

```axiom
var g = mutex.read()
print(g.value)
```

Semantic chain:

```text
write data
   ↓
unlock
   ↓
lock/read-lock
   ↓
read data
```

Không cần programmer viết:

```text
Acquire
Release
```

bởi vì **Mutex abstraction đã encapsulate memory ordering**.

Đây là một nguyên tắc quan trọng:

> Low-level primitive exposes memory order; high-level synchronization API hides it when the abstraction is sufficient.

# 15. Channel publication

Ví dụ:

```axiom
var x = create_large_object()

sender.send(x)
```

Receiver:

```axiom
var x = receiver.recv()?
```

Axiom semantic:

```text
producer writes object
       ↓
send
       ↓
channel synchronization
       ↓
receive
       ↓
consumer reads object
```

Không cần:

```text
Arc
mutex
atomic flag
```

cho payload.

Đây chính là lý do channel ownership-transfer rất mạnh.

# 16. Move qua channel không phải Copy

Ví dụ:

```axiom
var buffer = Buffer(...)

sender.send(buffer)

// buffer không còn usable ở đây
```

Semantic:

```text
Owner A
  │
  │ Move
  ↓
Channel
  │
  │ Move
  ↓
Owner B
```

Không cần copy payload.

Memory model và ownership model khớp nhau ở đây.

# 17. Thread spawn

Axiom nên định nghĩa một synchronization edge rõ ràng:

```text
parent before spawn
        ↓
child execution
```

Ví dụ:

```axiom
var config = Config(...)

spawn {
    use(config)
}
```

Nếu `config` được Move sang child:

```text
ownership transfer
+
execution publication
```

được thiết lập bởi spawn primitive.

Nếu programmer muốn shared access:

```axiom
Arc<Config>
```

và `Config: Share`.

---

# 18. Thread join

Ví dụ:

```axiom
var result = 0

let t = spawn {
    result = calculate()
}

t.join()
print(result)
```

Nếu API/ownership abstraction cho phép result được trả về, cách tự nhiên hơn là:

```axiom
let t = spawn {
    calculate()
}

let result = t.join()?
```

Semantic:

```text
child writes
    ↓
child completion
    ↓
join
    ↓
parent reads result
```

`join` là synchronization boundary.

---

# 19. Fiber

Fiber switching **không tự tạo memory barrier**.

Nếu cùng execution thread:

```text
Fiber A
   ↓ yield
Fiber B
   ↓ yield
Fiber A
```

thì semantic vẫn là execution của cùng domain nếu không có migration.

Compiler không được coi:

```text
yield()
```

là một atomic fence.

Nếu fiber migration xảy ra qua scheduler:

```text
Worker A
   ↓
scheduler synchronization
   ↓
Worker B
```

thì runtime phải đảm bảo migration contract.

---

# 20. Async/Await

Tương tự:

```axiom
await future
```

không mặc định có nghĩa:

```text
full memory barrier
```

Một future state machine vẫn phải obey ownership/capability rules.

Khi task chuyển worker:

```text
Worker A
   ↓
Future suspended
   ↓
scheduler
   ↓
Worker B
   ↓
Future resumed
```

runtime phải bảo đảm state machine không bị concurrent access trái phép.

# 21. `Atomic.wait/notify`

Đừng định nghĩa:

```axiom
notify()
```

là synchronization publication độc lập.

Pattern:

```axiom
state.store(READY, Release)
state.notify()
```

receiver:

```axiom
while state.load(Acquire) != READY {
    state.wait(...)
}
```

Synchronization đến từ:

```text
Release store
        ↓
Acquire load
```

`notify` chỉ giúp scheduler/OS đánh thức waiter.

Điều này cho phép implementation:

```text
spin
futex
park
kernel wait
platform primitive
```

mà không thay đổi semantics.

# 22. Volatile hoàn toàn khác Atomic

Đây phải là invariant rất mạnh.

### Atomic

Dùng cho:

```text
concurrent synchronization
```

### Volatile

Dùng cho:

```text
observable external memory access
```

Ví dụ:

```text
MMIO
device register
hardware status register
memory-mapped peripheral
```

Volatile:

- không được loại bỏ
- không được merge tùy tiện
- không được biến thành ordinary load/store
- không tạo happens-before
- không tạo synchronization
- không thay thế Atomic

Ví dụ:

```axiom
volatile_store(register, value)
```

không có nghĩa:

```text
Release
```

# 23. Compiler reorder

Đây là nơi cần bảo vệ hiệu năng.

Axiom không yêu cầu:

```text
source order == machine order
```

Compiler được phép:

```text
reorder
inline
vectorize
eliminate
hoist
sink
merge
split
scalarize
```

miễn là kết quả không vi phạm memory model.

Ví dụ:

```axiom
var a = expensive()
var b = cheap()
```

compiler có thể thực hiện:

```text
cheap()
expensive()
```

nếu không có observable semantic khác biệt.

Nhưng:

```axiom
atomic
volatile
FFI
syscall
lock
channel
```

là các semantic barriers tương ứng với contract của chúng.

# 24. Ordinary memory không có "global visibility"

Không nên có khái niệm:

> "Thread A viết memory rồi thread B eventually sẽ thấy."

Đó là cách reasoning không đủ chặt.

Axiom chỉ đảm bảo visibility khi có semantic relation:

```text
happens-before
```

hoặc contract tương ứng.

# 25. Publication pattern là pattern chuẩn

Đây nên là một trong những ví dụ nền tảng của tài liệu Axiom:

```axiom
var message: Message
```

```axiom

    use(message)

```

Semantic:

```text
message initialization
       ↓

       ↓

       ↓
```

# 26. Store Buffering

Axiom phải xác định rõ behavior của các litmus test.

```axiom
x = 0
y = 0
```

Thread A:

```axiom
x.store(1, Relaxed)
r1 = y.load(Relaxed)
```

Thread B:

```axiom
y.store(1, Relaxed)
r2 = x.load(Relaxed)
```

Axiom **không được giả định SeqCst** cho Relaxed.

Vì vậy:

```text
r1 = 0
r2 = 0
```

có thể xảy ra trên kiến trúc/compiler phù hợp.

Đây là điều cần thiết để không giết performance trên ARM/RISC-V.

# 28. FFI và foreign memory

Đây là một vấn đề lớn.

Ví dụ C function:

```c
void external_write(int *p);
```

Axiom gọi:

```axiom
extern fn external_write(p: mut_view<i32>)
```

Compiler **không được tự suy luận** rằng external function không giữ pointer, trừ khi ABI contract nói vậy.

Đặc biệt:

```text
foreign code
   ↓
may mutate memory
   ↓
Axiom optimizer
```

phải được conservative.

# 29. FFI synchronization

Một `extern fn` **không mặc nhiên là synchronization primitive**.

Ví dụ:

```axiom
extern fn foo()
```

không có nghĩa:

```text
full memory fence
```

Nếu API tương tác với thread synchronization của C/OS, binding phải khai báo semantic contract phù hợp ở system layer.

Như vậy:

```text
FFI ABI
≠
memory synchronization
```

# 34. "Undefined behavior" trong Axiom

Tôi khuyến nghị Axiom tránh biến mọi lỗi concurrency thành kiểu UB mơ hồ của C.

Phân biệt:

### Safe violation

Compiler reject:

```text
conflicting mut_view
invalid ownership
invalid capability
illegal Send
illegal Share
```

### Unsafe contract violation

Programmer đã dùng:

```text
unsafe
```

và phá machine-level invariant.

Behavior lúc đó:

```text
not guaranteed by Axiom safe semantics
```

nhưng compiler vẫn có quyền tối ưu dựa trên những assumptions của semantic model.

Không nên hứa:

> unsafe code luôn chạy theo đúng machine instruction tưởng tượng của programmer.

# 35. Một thay đổi rất đáng giá: không expose "memory fence" thường xuyên

Axiom vẫn cần low-level:

```axiom
fence(Acquire)
fence(Release)
fence(SeqCst)
```

nhưng chỉ system/atomic layer.

Programmer bình thường nên dùng:

```text
Atomic
Mutex
Channel
Semaphore
```

thay vì tự ráp:

```text
fence + volatile + raw pointer
```

Điều này làm language đơn giản hơn mà không giảm khả năng viết kernel/runtime.

# 36. Compiler semantic model

Trong compiler, mỗi memory operation nên mang semantic metadata:

```text
MemoryAccess {
    kind:
        Read
        Write
        Move
        Atomic
        Volatile

    region
    provenance
    storage_domain
    execution_domain

    ordering:
        None
        Relaxed
        Acquire
        Release
        AcqRel
        SeqCst

    synchronization:
        none / explicit edge
}
```

Không nhất thiết tất cả tồn tại đến Machine IR.

Sau verifier:

```text
Semantic MIR
      ↓
verified
      ↓
optimization
      ↓
lowered atomic/volatile operations
```

# 37. Optimizer rule

Optimizer được phép loại bỏ ordinary load/store nếu:

```text
không observable
+
không ảnh hưởng synchronization
+
không ảnh hưởng FFI
+
không ảnh hưởng volatile
+
không ảnh hưởng atomic semantics
```

Nhưng không được làm:

```text
atomic → ordinary
```

hoặc:

```text
volatile → ordinary
```

hoặc làm yếu:

```text
Acquire → Relaxed
```

trừ khi compiler chứng minh transformation vẫn giữ nguyên semantic ordering.

Trong v1 tôi khuyến nghị **không cho phép memory-order weakening ở semantic optimizer**. Backend có thể chọn instruction tương đương yếu hơn nếu target semantics vẫn chính xác.

# 40. Kết luận kiến trúc

Sau BOOTSTRAP-021, Axiom đã có một chuỗi semantic khá sạch:

```text
Ownership
    ↓
Capability
    ↓
Execution Domain
    ↓
Synchronization
    ↓
Memory Model
    ↓
Atomic / Mutex / Channel
    ↓
Optimizer
    ↓
Machine Code
```

Điểm tôi đặc biệt muốn **giữ nguyên** là:

> **Axiom không bắt programmer quản lý memory ordering bằng tay trong code thông thường.**

Programmer chỉ cần biết:

```text
ordinary data
Atomic<T>
Mutex<T>
Channel<T>
```

Còn khi xuống system-level mới cần:

```text
Relaxed
Acquire
Release
AcqRel
SeqCst
fence
volatile
raw pointer
```

Như vậy Axiom vẫn có toàn bộ sức mạnh cần cho:

- kernel
- runtime
- lock-free structures
- game engine
- database
- networking
- GPU
- embedded
- OS
- compiler

nhưng **không biến memory model thành gánh nặng thường trực**.

### Bước tiếp theo hợp lý

Sau khi memory model đã khóa, phần còn thiếu để nối concurrency với compiler backend là:

**BOOTSTRAP-022 — Memory Allocation + Reclamation + Object Lifetime Runtime**

Phần đó sẽ giải quyết sâu hơn vấn đề mà bạn từng quan tâm: **flat address space, fragmentation, arena/pool/slab, heap, allocator, object lifetime, relocation, stable address, lock-free reclamation và làm thế nào để Axiom đạt performance gần C/C++ mà không bắt programmer dùng GC/borrow checker.**
