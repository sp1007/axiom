- **AXS-GRM-011 conformance.** `expect_term` (C `parse.c`, port `parse.ax`) behaves as follows:
  - `;` is consumed for a statement. For an item it is left as an empty item.
  - A line break counts only when `mode_on` (port `line_break_before` = `mode_on && token_follows_newline`).
  - `}` and EOF are accepted without being consumed.
  - Anything else reports `AX_PARSE_EXPECTED_TERMINATOR` at the next token.
  The rule is applied after every statement and after every item. Trait, impl and extern members go
  through `parse_item`. The code is registered in `diag/codes/PARSE.def:6` and `compiler/diag/code.ax`
  (24). Probes with the snapshot axiom0 all gave exactly 1 error at the right token, for example:
  - the task's own repro `fn f(c: bool) -> i32 { if c { return 5; } return 6; }`: col 43, `return`;
  - `let a = 1 let b = 2`;
  - `while {..} x`, `match {..} x`, `loop { break } return 1`;
  - `x = 1 x = 2`, `return 1 2`;
  - `use a.b use c.d`, `const .. const ..`, `struct S {..} struct T {..}`, `module a.b fn ..`;
  - trait/impl/extern members on one line;
  - `fn main() {..} fn g() {}`;
  - a block in a call argument.
  Accepted forms (`;;`, line comment, block comment containing a LF, `[ ]` and `( )` continuation lines)
  compile.
- **Parity axiom0 vs. port (ADR-0034 §2).** I built a stage-1 `axiomc` from the snapshot

- **No silent token discard.** The only remaining skips are `sync_to_term`/`skip_to_terminator` after a

- **`{` inside `(`/`[` (AXS-GRM-010).** `parse_block` and the `match` body now push mode ON and restore

### Notes (not FAIL)
1. Recovery deviation, documented in the report: when a statement already has an error, the rest of
   its line is skipped. This includes a following independent statement. For example,
   `if true { let a = 1 let b = 2 } let c = 3` reports only the inner error, and `let c = 3` is
   skipped. It is always after a diagnostic, so it is never a silent miscompile. Acceptable, but the
   architect may want SPEC-02 §recovery to state it.
2. Pre-existing, not caused by T146 (HEAD axiom0 behaves the same), proposed as follow-ups for the
   architect:
   - `fn main() -> i32 { let x = 1;; let y = 2; x + y }` makes axiom0 ICE: "Unhandled HIR expr kind in
     MIR builder: 0" (builder.c:2777). axiomc accepts the same program, so this is a divergence too.
   - axiomc rejects derived `impl Hash` for two types with `AX_LINK_DUPLICATE_SYMBOL: hash`. This is
     the same gap as the registered `tests/run/trait2/test_derive.ax`. For that reason my derive test
     lives in `tests/conformance/adversarial/`, outside the e2e corpus. When it sat under `tests/run`,
     `axiomc_e2e` reported it as a REGRESSION.
3. The engineer's note stands: `tests/std/fs/qa_binary_file_buf.ax` uses a fixed file name across
   parallel modes, so it can race. It did not reproduce in this run.
