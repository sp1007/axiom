### Findings
No FAIL findings.

Notes (not blocking):
- N1 (spec deviation, judged acceptable): AXS-GRM-056 follower set widened for value position (`;` `,` `)` `]` `}` EOF, or a line break after exactly one argument). This is exactly the "Wider follower set for generic arguments (function values such as `id<i32>`)" row deferred in SPEC-02 section 12 ("decide before E23.2") and required by acceptance repro 2. Safety argument holds: `>` followed by a terminator can never be a comparison. Architect should amend GRM-056 (follower list; `.name<...>` after a dot commits only before `(`, a stricter subset of the spec text, identical to HEAD behaviour for method calls) and the section-12 row.
- N2: the line-break follower changes the diagnostic for the (invalid) chained comparison `a < b >` + newline + `c`: it is now parsed as the value `a<b>` followed by a new statement (no `AX_PARSE_CHAINED_COMPARISON`), consistent with the language's newline termination; inside `( )`/`[ ]` (newline mode OFF, SPEC-02 line 95) the line-break follower still applies. Only invalid programs are affected (probed: `let g = a < b >` / `c;`). Architect may want the line-break follower limited to newline mode ON.

### Follow-ups (architect)
- Pre-existing, not caused by T422a (identical at HEAD): calling a function-pointer field through parentheses `(h.f)()` is rejected with `AX_TYPE_UNKNOWN_FIELD` (typeck); workaround `let f = h.f; f()`.
- Pre-existing: array types in expression generic arguments (`f<[u8; 4]>(x)`, `v.get<[u8; 4]>(0)`) do not parse (same at HEAD, with more diagnostics there); method values `x.f<T>` unsupported (documented by the engineer).
- Generic-fn value forms must not be used in compiler sources until stage 0 parses them (engineer's note 5; unchanged).
