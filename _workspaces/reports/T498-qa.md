### Follow-ups (for the architect; all reproduce identically with the HEAD compiler, not caused by T498)
- FU-T498-FNPTR-INDEX confirmed and broader than the report says: any two Copy field reads through an index of a non-Copy array,
  e.g. `let a = m[0].v; let b = m[1].v;` with `m: [2]NC` and `v: i32`, report `AX_MOVE_USE_AFTER_MOVE` (own/init index handling).
  My first version of `qa_generic_closure.ax` hit it and was rewritten to read a single indexed field.
- Tuple expressions that contain a local name, `let (x, y) = (a, a);`, report `AX_NAME_UNRESOLVED` at the first element,
  and `fn dup(a: [2]u8) -> ([2]u8, [2]u8) { (a, a) }` compiles silently and the program exits 127 without output (HEAD and new).
  Needs a triage task (tuple expression lowering); it blocked probing "array in a tuple".
- FU-T498-AGG-WIDEN (engineer's follow-up 3, native 3/6/7-byte aggregate store widened over the next field): I could NOT reproduce it
  with four variants (`Rec { tag: u8, vals: [3]u16 }` constructed, copied by binding, by call, by assignment, via a view; native
  printed the right tag each time). The architect should ask for the exact failing program before filing a high-priority task.
- FU-T498-INTERP-ARG256 not re-verified (large by-value arguments); `large_and_edge.ax` already avoids it with views.
