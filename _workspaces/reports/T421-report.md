# T421 report

E11.5 -- single-thread `LocalExecutor`, multi-thread work-stealing `Executor`, `TaskHandle`/`LocalTaskHandle`,
atomic `Waker` state machine, `AsyncMutex`, `AsyncSemaphore`, async channels (module `std.asyn`, because
`async` is a keyword).

## Summary

A previous attempt had already written `std/async/*.ax` and four test bundles; this round inspected it,
found it only half-working, and finished it.

State found: 4 of 5 bundles passed; `work_stealing_executor` crashed (interp UB + native access violation).
The AsyncMutex/channel tests passed only because they never exercised the waiter paths.

Work done this round:

1. **Work-stealing executor fixed** (`std/async/executor.ax`). Root cause was a compiler bug (FU-1): a struct
   field typed `*mut T` where `T` is declared later in the file reads through the pointer with wrong field
   offsets. `WorkerData.executor: *mut ExecutorInner` (forward reference) made every worker see a zeroed
   `ExecutorInner`. Fixed by storing the field as `*mut u8` and casting at use. The previous author had worked
   around the symptom with hard-coded byte offsets and `usize` pointer arithmetic; all of that was replaced by
   ordinary typed field access (`(*inner).global_lock`, `(*w).queue[i]`, `workers + i`).
2. **Real work stealing**: wakes issued from a worker thread now push to that worker's local Chase-Lev deque
   (`current_worker` looks the caller up by OS thread id); other threads and a full deque use the global
   injection queue. Previously every task went through the global queue, so the local deques/stealing were dead
   code. Added `Executor.steal_count()` (diagnostics), `SeqCst` on the pop fence, and `@derive(Copy)` on
   `Executor` (a handle, so tasks can spawn children).
3. **Wait-queue wakers rewritten** (`waker.ax`, `sync.ax`, `channel.ax`, `task.ax`). The contested path of
   AsyncMutex / AsyncSemaphore / channels / `TaskHandle` join had never run and was broken:
   - a `Waker`/`RawWaker` stored as a struct field inside a `std.*` module reads back as 0 or shifted fields
     (FU-3), so nodes now keep `waker_data` + `waker_vt` pointer pairs that own one reference, managed with
     `waker_leak` / `raw_waker_wake` / `raw_waker_wake_by_ref` / `raw_waker_drop`;
   - channel waiter nodes were freed by the waking peer while the waiting future still pointed at them
     (use after free / double free on `Drop`). Nodes are now owned by their future; wakers only unlink and
     wake by reference; a woken-but-unsatisfied future re-queues its node;
   - mutex/semaphore re-poll now re-checks `granted` under the queue lock before replacing the waker;
     cancelling a waiting future releases its stored waker;
   - `TaskSlot<T>` fields reordered (`output` last) because the join-waker fields were reached through
     `TaskSlot<u8>` casts and sat at different offsets for different `T`.
4. **Tests**: new `work_stealing_spawn_tree` (parents spawn children from worker threads, 4 workers, stealing
   verified manually to occur), new `async_semaphore_limits` (max 2 concurrent holders across an await),
   `async_mutex_across_await` rewritten so the guard really is held across an `.await` with 3 contending
   waiters (asserts zero mutual-exclusion violations and `waited > 0`), `check_async_bundles.test` and
   `compile_live_async.test` (bundle freshness / live compile, as `tests/std/sync`).

## Design decisions (for the architect)

- API keeps the explicit `poll_fn` argument on `spawn`/`spawn_local` (the previous attempt's choice; a generic
  `tcb_poll_fn<F,T>` function pointer cannot yet be formed inside the generic method). Spec SPEC-34 shows
  `spawn(fut)`; this is a deviation to revisit when generic fn-pointer instantiation works.
- `TaskHandle<T>` is a `Future` only for `T = i64` (no generic `impl Future for TaskHandle<T>` yet);
  `join()` is a blocking spin/yield join, not `async fn`.
- `Executor` is `Copy` (raw-pointer handle). `shutdown()` joins workers but does not free `ExecutorInner`
  (handles remain valid for `worker_count()` afterwards).
- Idle workers `thread_yield` rather than parking on the futex (the park word is bumped and woken but not
  waited on) -- adequate for the oracle and tests; parking can come with `T424` benchmarks.
- No `ResourceGovernor`, `spawn_blocking`, `TaskGroup`, `CancellationToken` (T422 / out of scope).

## Follow-ups (compiler bugs found; repros are in the notes, not in the tree because only `paths` may be edited)

- **FU-1 forward-referenced pointee layout.** A struct field `*mut B` where `struct B` is declared *after* the
  struct holding the field gives wrong field offsets when dereferenced (interp reads 0, native reads the
  first word for every field). Repro: `struct W { id: usize, inner: *mut Inner }` then
  `struct Inner { count: usize, ptr: *mut u8 }`, set fields through `heap_alloc`ed memory, read
  `(*(*w).inner).ptr`. Swapping the declaration order fixes it. Owner: semantics (layout/type resolution).
- **FU-2 calling a function-pointer field expression** `((*vt).wake)(data)` links as undefined symbol
  `__ax_fn_0` in native mode (interp fine). Binding to a local first works. Owner: backend/MIR lowering.
- **FU-3 `Waker`/`RawWaker` struct fields inside `std.*` modules.** `(*n).waker = w; (*n).waker.raw.data`
  reads 0 (interp) / shifted words (native) when the node struct lives in a module whose path starts with
  `std`; the identical struct in module `zz.yy` works, and so does a user-declared nested struct in
  `std.asyn.zz`. Looks like special handling of the `@lang("waker")` types. Owner: semantics.
- **FU-4 moving out of a field then re-assigning it drops the moved value.** `match self.guard { Option.Some(g)
  => { ... self.guard = Option.Some(g2) } }` (field of a `mut_view`) runs `Drop` on the old, already moved-out
  value (released a mutex guard early). Owner: semantics (move/drop elaboration for partial moves out of
  `mut_view` fields).
- **FU-5 type inference** `let h = self.exec.spawn(Child {..}, poll_child)` inside a `Future::poll` reports
  `AX_TYPE_UNKNOWN`; annotating `let h: TaskHandle<i64>` fixes it (same call in `main` infers fine).
- **FU-6** `cx.waker()` on a `mut_view<Context>` parameter is treated as a move of `cx` (second use gives
  `AX_MOVE_USE_AFTER_MOVE`); `mut_view(*cx).waker()` is used where `cx` is needed again.
- `std/async/executor.ax` had CRLF line endings from the previous attempt; normalised to LF.
