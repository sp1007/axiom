### Findings

**F1 (FAIL) — an explicit `std.` path trait bound no longer finds the trait's methods.**
`compiler/traits/solver.ax` `find_trait_item` (new domain logic, ~l.700-790). Repro (`qa_std_path_bound.ax`, 10 lines):
`fn s<T: std.core.cmp.Ord>(a: view<T>, b: view<T>) -> i64 { match a.cmp(b) { … } }` called on u32.
Expected `-1 1 0` (HEAD axiomc2 prints it in interp/native/native-O1); actual with T164:
`error[AX_TYPE_UNKNOWN_FIELD]: struct has no such field` at `a.cmp(b)`. It fails the same way with a user module
`m` (with `Ord`, with `Ordx`, with `use m`, without `use`). `use std.core.cmp.Ord` + `T: Ord` (the form in
`many_symbols.ax`) still works, so the `std.`-spelled site path is the broken case. Note `site_path_is_std` reads
the span text of the bound; check that the `site` passed down the method-lookup route is the bound `HirType`
and that the std candidate passes `dom_ok`.

**F2 (FAIL) — a qualified user path to a trait whose name the prelude exports resolves to the std trait.**
Repro (`qa_user_future_full_path.ax`): user `pub trait Future { fn ready_val(…) -> i32 { 11 } }` in module `m`,
`impl m.Future for P {}`, then `p.ready_val()`. HEAD prints `11 12`; T164 rejects `p.ready_val()` and
`x.ready_val()` with `AX_TYPE_UNKNOWN_FIELD`. Cause: for `m.Future` with no `use` binding the name,
`site_use_domain` returns 0, so `prelude_ok = true`, and the prelude candidate (std `Future` in
`std.core.prelude`) is returned ahead of the user trait. A path with more than one segment can never be a prelude
binding; it names its module explicitly (its prefix segments give the defining module exactly).

**F3 (FAIL) — std trait re-exported through a user module (the report's "known residual difference").**
Repro (`qa_reexport_std_trait.ax`): `module facade` / `pub use std.core.cmp.Ord`, `use facade.Ord`,
and another module `mytraits` with its own `Ord`; `T: Ord` + `a.cmp(b)`. HEAD prints `std -1 1 0` / `user 4`;
T164 rejects `a.cmp(b)`. It is not acceptable as a follow-up: the program is valid, it compiles at HEAD,
and this task turns it into a compile error. The domain of a `use` must follow the binding to the item it
names, not the first segment of the `use` path. Re-exports (`pub use`) are a normal std/user idiom.

All three come from the same design: the solver guesses the resolver's binding from lexical HIR data. The report's
Follow-up 1 is the exact fix: pass the resolver's per-symbol module path / std flag, which the naming table already
holds for the trait's collection id C, to the solver. Another exact fix is Follow-up 3: keep the trait item's
collection id on the HIR item so `sym` matches directly. The architect should decide whether that plumbing
(`typeck.ax`/`hir.ax`/`lower.ax`, outside `paths:`) joins this task or T164 lands first with a solver fix that
passes the 5 QA tests above. A heuristic that still fails any of the five is not acceptable.

### Required fix (owner: T164-impl)
Make the solver's std/user decision exact instead of lexical. The only correct source is the resolver's binding.
Recommended plumbing, port only: axiom0 has no id-range test left, and its typeck needs no change.
1. `compiler/hir/hir.ax`: add a field to the HIR path, e.g. `HirPath.def_std: bool`, or `def_module` holding the
   defining module path. The field records the domain of the item `path.symbol` names.
2. `compiler/hir/lower.ax` (today only a lock of this task, so add it to `paths:`): in `lower_path_into`, fill the
   field from the resolver's naming table (`rmap.naming_ctx`, the module path per collection id). That table
   already holds the module path of the trait's collection id C, which every trait reference carries. Re-exports
   are handled for free, because the table names the defining module.
3. `compiler/traits/solver.ax`: `find_trait_item` takes the domain from the site path's new field and compares it
   with `hir_item_is_std(it)`. Remove `site_use_domain`, `site_path_is_std`, the prelude/same-module ranking and the
   span-text test. A qualified path then also gets the module exactly: match `HirItem.module_path` to the stored
   module, which fixes F2 even for two user modules with same-named traits.
4. Templates under `tests/selfhost/**/*.ax.in` that build `HirPath`/HIR literals must name the new field. Bundles
   are regenerated by `taskctl snapshot`; do not list them.
Alternative (Follow-up 3, larger): keep the collection id C on the HIR trait item and give `Self` its own id, so
`sym` matches the item directly. This touches `compiler/resolve/resolver.ax` and axiom0 `resolve.c` in lockstep,
changes body-pass ids in every id-printing golden again, and changes the axiom0 C side. Use it only if the architect
prefers it.
No change to `compiler/types/typeck.ax` (T444's file) is needed for option 1.

Acceptance for round 1: the 5 QA tests in `tests/run/symbol_id_space/` and `many_symbols.ax` PASS in interp, native
and native-O1; the stage-2/stage-3 fixed point holds; ids-only check of every regenerated golden/template again.
