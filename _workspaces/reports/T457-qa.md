### Findings

**F1 (FAIL, lexer, `compiler/lex/scanner.ax` `scan_number`, lines ~862-880).** A float literal whose exponent has a sign and no fractional part is split into three tokens: `1e-5` lexes as `Float(1e)` `Minus` `Int(5)`, `2E+10` as `Float(2E)` `Plus` `Int(10)`, `1_0e-3f64` as `Float` `Minus` `Int(3 f64)`. When the number is entered through `e`/`E` the code does `cur.pos = cur.pos + 1` and the loop then meets `+`/`-` and breaks; the sign is only consumed in the branch that entered through `.`. Because T457 is what makes float literals reachable (before it they were rejected), the compiler now silently computes the wrong value: `let a = 1e-5` is MIR `const f64#3ff0000000000000 - const 5` (= -4.0), `2E+10` is `2 + 10`. `1e5` (no sign) and every form with a fraction (`1.0e-5`) are correct, which is why the engineer's tests and my random fuzz (which used `d.dde<exp>`) did not hit it. SPEC-01 AXS-LEX-055/056 and SPEC-41 AXS-FLT-003 rule 1 list `1e-5`, `2E+10` as single float literals. The frozen axiom0 C lexer has the same bug (`axiom0 inspect --emit=tokens` shows the same split), but the axiom0 lexer is not under change here; the Axiom lexer is within T457's `paths:` and the fix is two lines (after skipping `e`/`E` in the `is_float` entry, also skip one `+`/`-`). Repro and regression test: `tests/mir/float_mixed/qa_exp_sign.test` (currently FAILS, 5 mismatches; expected bit patterns computed with Python `struct.pack`). Expected: `const f64#3ee4f8b588e368f1`, `const f64#4212a05f20000000`, `const f32#3a83126f`, `const f32#00000001`, `const f64#3f847ae147ae147b`.

**F2 (note / follow-up, REQ-OWNER-007 deviation, owner requirement; not a FAIL on its own).** Pattern B: `((mask >> sh) & 0x3F) + delta * step` with `u32` + `isize` infers `i64`, not the `isize` that SPEC-41 AXS-FLT-036 step 3/4 prescribes (`delta` cast to `isize`, `_t6: isize`). MIR for Pattern B casts `delta`, `step` and the `u32` side to type#9 (i64), not type#10 (isize). The value is identical (both 64-bit) and the engineer reported it as decision 3. It is an inherited T451/T455 `join_int` order dependence, and it is order dependent and visible to users: `let t = mask + step` has type `isize` (assignable to `isize`), whereas `let t = mask + delta * step` and `let t = ((mask >> sh) & 0x3F) + delta * step - 5` have type `i64` (`let q: isize = t` gives `AX_TYPE_MISMATCH`). With an `isize` expected type, `let t: isize = (mask & 0x3F) + delta * step` is accepted. I do not FAIL T457 for it because the pure-integer lattice is T455/T499/T462 territory and the result type name is the only difference; the architect must decide (fix `join_int` so `u32 + isize` gives isize in every nesting, or amend AXS-FLT-036), and T462 conformance must pin it. No test of T457 asserts the isize-vs-i64 choice.

**F3 (follow-up for the architect, hazard, out of T457 scope).** Float programs now pass typeck and MIR build, but `build` has no float backend yet: `axiomc2 build` of `let x: f64 = 1.5; let y = x * 2; if y > 2.0 { return 7 }; return 3` produced an exe without diagnostic that exits 3 (expected 7: wrong code), and `run --interp` exits 3 (ICE) with no message. Until T458/T459 land, the interpreter and LIR lowering should reject a float MIR instruction with a clear diagnostic or ICE message instead of mis-compiling. Suggest the architect puts a guard in T458/T459 or a tiny priority task.

**F4 (note).** `!x` on a float gives `AX_TYPE_MISMATCH`, while SPEC-41 AXS-FLT-070 lists `!x` under `AX_TYPE_OPERATOR`. `!i` on an integer gives the same `AX_TYPE_MISMATCH` today, so this is the existing logical-not rule; the spec table and the implementation disagree, still an error. Architect: align the table or the code. `~x`, `&`, `|`, `^`, `<<`, `>>` correctly give `AX_TYPE_OPERATOR`.

- Pattern B isize vs i64: see F2.
- `AX_TYPE_LITERAL_OUT_OF_RANGE` keeps the integer-literal message text for float literals: note only.
- Float `const` items not enabled: allowed (T458 owns constant evaluation).
