**F1 — MS-P1 manifest lists two test paths that will never exist**
- **Where:** `spec/SPEC-00-bootstrap.md:365`.
- **Expected:** the entries match the paths the tasks actually own. T005 has
  `paths: [tools/axtest.py, tools/tests/axtest, …]` and its self-tests run as

  - either an `exec` manifest under `tests/` that runs the self-test scripts,

    vocabulary of AXS-BOOT-050.
- **Repro:** `python scratchpad/qa-T003/check_manifests.py build-snap-T003`, then grep
  `_workspaces/tasks/*/T00[56]-*.md` for `tests/axtest`. The only hits are `tools/tests/axtest`.

**F2 — Native behaviour of checked arithmetic between T028 and T037 is unspecified (silent semantic choice at the interp/native seam)**
- **Where:**
  - `spec/SPEC-00-bootstrap.md:122`: F-ARITH, native "T028 (no trap), T037 (overflow checks)";
  - `spec/SPEC-03-core-semantics.md` AXS-SEM-001 (l.~45), AXS-SEM-030, AXS-SEM-071;
  - FP-03 at `SPEC-00:196-204`.
- **The problem:** FP-03 says that `return 40 + 2` builds MIR with a checked `Add` plus an overflow
  assert to the panic path. That program is in the VS1 set, which T028 must run natively, while
  T025/T028 explicitly do "arithmetic without traps" and no branches, and `jo` checks arrive only
  in T037. Nothing says what native code does with the MIR overflow assert in MS-P4. The two
  possible readings are:
  - (a) emit the check anyway: a conditional jump to an abort stub with exit 101. This is branch
    lowering, scheduled for T033/T037.
  - (b) drop the check. Then for an accepted program such as `x + 1` with `x = i32::MAX`, native
    wraps while the oracle panics. That contradicts AXS-SEM-001 ("native code at every
    optimisation level must produce the same observable behaviour … for every program accepted")
    and AXS-SEM-030 ("no build mode … in which these operators wrap").
- **Expected:** SPEC-00 and/or SPEC-03 state the MS-P4 contract explicitly. One option is (b) as a
  documented `BOOTSTRAP-SHORTCUT` retired by T037: AXS-SEM-001 then gets a stated, time-limited
  exception covering only programs whose tests carry `native-after: T037`, and T037's removal of
  that marker becomes the proof. Another option is that T025/T028 must lower the MIR assert
  terminator to a shared abort path, or that axiom0 refuses with a NOT_YET_SUPPORTED code.
- **Actual:** the only text is "no trap", which a T025/T028 engineer will read as "drop the check".
  The differential leg of T029 cannot catch the divergence, because overflow tests are skipped in
  native mode. Fixing this is a one- or two-sentence edit inside T003's paths.

### Findings

**F3 — The normative panic-stub machine code misaligns the stack at `call [ExitProcess]`, and the two spec texts disagree on it**
- **Where:**
  - `spec/SPEC-00-bootstrap.md:89-91` (AXS-BOOT-007) prescribes the stub
    `sub rsp, 40; mov ecx, 101; call [ExitProcess]`;
  - ADR-0012 §9 prescribes `mov ecx, 101; call [ExitProcess]`, without the `sub`.
- **The problem:** the stub is reached by `jo` (a jump, so no return address is pushed) from inside
  a function body. Windows x64 bodies keep `rsp` ≡ 0 (mod 16), and T025b's machine-IR verifier
  enforces 16-byte alignment at every call site (ADR-0003 B2). On arrival `rsp` ≡ 0 (mod 16), so
  `sub rsp, 40` leaves it at ≡ 8 (mod 16) at the `call`. That violates the Win64 ABI.
- **Effect:** ntdll/kernel32 code reached from ExitProcess may execute aligned SSE stores, so the
  process can die with 0xC0000005 instead of exit 101. The ADR variant has no shadow space at all.
- **Where the copied sequence comes from:** `sub rsp,40` is correct only at a function entry
  reached by `call`, as for `axiom_start` in T027.
- **Expected:** one alignment-independent sequence, stated identically in both documents. For
  example `and rsp, -16; sub rsp, 32; mov ecx, 101; call [ExitProcess]`, which is also correct if a
  frameless leaf jumps there. T027's fixture test should run the stub from a body with `rsp` ≡ 0
  (mod 16) and also from one with ≡ 8 (mod 16).

**F4 — `AX_DRIVER_UNSUPPORTED_IN_BOOTSTRAP` is in the wrong diagnostic family of the T002 taxonomy**
- **Where:**
  - `spec/SPEC-00-bootstrap.md:74-79` (AXS-BOOT-006, which cites AXD-013);
  - SPEC-03 AXS-SEM-001;
  - ADR-0012 §9.
- **What the registry defines** (main tree, reference only):
  - AXD-013 (`spec/diagnostics.md:60-68`) reserves the suffix `_UNSUPPORTED_IN_BOOTSTRAP` for valid
    Axiom outside the self-host subset. That condition is permanent in axiom0, and
    `data.epic` names the delivering epic.
  - AXD-014 (`:69-73`) covers exactly this new case: "a stage that meets a construct it cannot handle
    yet". Its codes are `AX_<AREA>_NOT_YET_SUPPORTED` (seeded `AX_DRIVER_STAGE_NOT_AVAILABLE`). They
    are transient: "once the delivering task is done, no test of the self-host subset may expect
    them".
- **The problem:** the native refusal disappears when T033/T037/… are done, so it is an AXD-014
  code. SPEC-00 also puts a task id into `data.epic` (an AXD-013 field). Using the AXD-013 family
  loses the AXD-014 guarantee that gatecheck/QA can use, namely that no test expects the code after
  its native task. T002 would also be asked to register a code that contradicts its own AXD-013
  text.
- **Expected:** a name in the AXD-014 family, for example `AX_DRIVER_NOT_YET_SUPPORTED`, with data
  `construct` plus a task field. The new name goes in all three documents and in the board-edit
  list. Alternatively, record an explicit agreed amendment of AXD-013/014 with T002.
- **Scope of this finding:** that the code is not yet registered stays a follow-up, as instructed.
  The finding is only about which family it belongs to.
