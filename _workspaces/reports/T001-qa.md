### Findings

**F1 — ADR-0010 §2 misstates three sources on operator precedence.**
`spec/decisions/ADR-0010-grammar-forms-v0-1.md:35-38` and the source tag of AXS-GRM-050,
`spec/SPEC-02-grammar.md:395`.
- Claimed: "Rust-like order with bitwise tighter than comparison in 0243 §35, 0155 §35, 0173 §30".
- Actual: all three give the C order — `|`, `^`, `&` looser than `== !=` and `< <= > >=`, and two
  comparison levels (0243 §35 priorities 4–8; 0155 §35 lines 4–8; 0173 §30 list). tasks/0324 §28 and
  tasks/0476 §136 give the C order too.
- The order actually decided (bitwise tighter, one comparison level, `as` near unary) is the one of
  **0109 §92**, which the ADR does not cite.
- Expected: Context of §2 lists 0243 §35, 0155 §35, 0173 §30, tasks/0324 §28, tasks/0476 §136 as the C
  order and 0109 §92 as the source of the chosen order; the AXS-GRM-050 tag is corrected the same way. The
  decision itself stays; only its record is wrong (a reader now believes three documents support it).
- Repro: `sec.py docs/base 30 0243:35 0155:35`; `sed -n '1107,1130p'` of 0173; `sed -n '1695,1718p'` of 0109.

**F2 — Label after `break` / `continue` across a line break is not determined.**
`spec/SPEC-02-grammar.md:105-107` (AXS-GRM-015), `:116-129` (AXS-GRM-017), `:399` (`JumpExpr`).
- AXS-GRM-015 gives the same-line rule for the *operand* only ("after its optional label"). AXS-GRM-017
  says the flag is consulted nowhere else and justifies it by "none of the listed tokens can begin a new
  statement" — but a `LABEL` can begin a statement (`'a: loop { }`).
- Repro (inside a loop body): `break` ↵ `'a: loop { }` and `continue` ↵ `'a: loop { }`.
  Reading the text literally (QA parser) the label belongs to the jump and `:` then gives
  `AX_PARSE_EXPECTED_TERMINATOR`; the implementer's reference parser gives two statements and no
  diagnostic. `return` ↵ `'a: loop { }` is two statements in both. Two parsers from one spec disagree,
  against ADR-0008 "one rule for all implementations" and ASYNTAX-22.
- Expected: one explicit rule (most consistent with AXS-GRM-015: the label of `break` / `continue` is
  taken only without `NL_BEFORE` in mode ON), listed in AXS-GRM-017 and ADR-0008 §6, plus one row in the
  continuation matrix.

**F3 — Skill and two summaries state the leading-operator rule more strongly than the spec.**
`.claude/skills/axiom-syntax/SKILL.md:100-101`, `spec/SPEC-02-grammar.md:11`,
`spec/decisions/ADR-0008-statement-termination-newline.md:12`.
- Stated: "Any other operator at the start of a line is an error (`AX_PARSE_LEADING_OPERATOR`)" /
  "mọi toán tử khác ở đầu dòng là lỗi".
- Actual rule (AXS-GRM-019, matrix N03, ADR-0008 §5): a line that starts with `-`, `*`, `!`, `~`, `|`,
  `||`, `(`, `[`, `{` is a **new statement with no diagnostic** — `let d = a` ↵ `- b` silently becomes two
  statements. An agent writing Axiom from the skill is told the opposite for the one case that changes
  meaning silently. Acceptance 3 (consistency with the skill) is not met on this line.
- Expected: the three texts say "an operator that can only be binary/postfix at line start is an error;
  `-`, `*`, `!`, `~`, `|`, `||`, `(`, `[`, `{` start a new statement".

**F4 — Lexer: number of diagnostics for malformed numbers and a trailing backslash is not determined.**
`spec/SPEC-01-lexical.md:181-185` (AXS-LEX-051), `:192-193` (AXS-LEX-053), `:455-457` (AXS-LEX-101),
`:267-272` (AXS-LEX-061) with `:312-315` (AXS-LEX-068).
- `0x_`: AXS-LEX-051 gives `AX_LEX_BAD_DIGIT_SEPARATOR` (and lists `0x_ff` as its example); AXS-LEX-053
  says a prefix with no digit "also before a separator" gives `AX_LEX_MISSING_DIGITS`; AXS-LEX-101 says
  "one per literal for digit/suffix errors". QA lexer: two codes; implementer's lexer: one code.
  `0b12_` gives two codes in both, which contradicts the AXS-LEX-101 wording under its other reading.
- `"abc\` followed by a line break or end of file: AXS-LEX-061 ("any other character after `\`") and
  AXS-LEX-068 do not say whether `AX_LEX_INVALID_ESCAPE` is reported in addition to
  `AX_LEX_UNTERMINATED_STRING`. QA lexer: both; implementer's lexer: one.
- T010 must write ui tests with exact diagnostics for these inputs. Expected: AXS-LEX-101 states the
  count rule unambiguously (for example "one diagnostic per code per literal"), `0x_` and `0x_ff` get
  stated results, and the backslash-before-line-end case gets one stated result; add the rows to §10.
- Repro: `lexprobe.py` (inputs `'0x_'`, `'0b12_'`, `'"\\'`, `'"abc\\'`).
