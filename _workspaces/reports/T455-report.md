# T455 report - E12.1 integer model completion and Pattern D mixed-width conformance suite

## Summary

Test-only task (no compiler or std source touched).  Everything runs in the MIR interpreter and in native -O0 / -O1 (the
default `run` modes); every native leg pins an observable result (exact `stdout:` `OK <name>` or `exit: 101` +
`stderr-contains`), never "exit 0 only".  All expected values are exact Python integers computed by the two generators;
neither the compiler nor the library produces an expectation.  A `generated_current.test` in each directory fails when a
checked-in file is stale.

- `index_types.ax`: `a[i]`, `a[i + 1]`, `a[i - 1]` for all 12 index types, and 11 mixed-width composite index expressions
  (`a[i + o]`, `a[(i + o * 2) - 1]`); `index_trap_*` (6): `i64`/`u64` `2^32 + k` (no 32-bit aliasing), negative `i32`/`i8`/`i128`, `u8` 255.

- `mir_homogeneous.test` + `mir_check.py` + `mir_shapes.ax`: `inspect --emit=mir` of Pattern D shows a promotion cast (IntToInt) from each of u8, i8, u16, i32 to

- `ui_*.ax` (6): `u128 + i64`, `u128 < i8`, `i64 * u64` standalone, wide tree into narrow target, `-u8` inside a tree, bare variable argument (`AX_TYPE_MISMATCH`).

## Design decisions

1. **Generated suites.**  Thousands of boundary cases are produced by two Python generators with exact-integer oracles, as in T140/T454; the generated files
   are checked in and guarded by `--check` tests.  Case numbers are returned by chunk functions, so a failure points at one line.
2. **Tree model.**  Each tree is evaluated entirely in its declared context type (SPEC-40 AXS-INT-052); a shift is a leaf of its left operand's own type with the
   shifted-out bits lost (AXS-INT-052.1 does not list shifts as tree nodes; this matches the compiler).  Trees containing `~` over an operand with an unsigned
   leaf are not generated (follow-up 4); `-` on an unsigned leaf is covered by a `ui` test instead.
3. **The mixed-pair matrix excludes undefined joins** and the three pointer-width pairs whose result type depends on the context (AXS-INT-051.2).
4. **Expected-type contexts other than `let r: T = ...`** (return expression, call argument, assignment) are not pinned: SPEC-40 is silent on whether a tree
   there is promoted (it only says a bare variable is not).  `ui_argument_after_tree.ax` pins the one thing the spec does say.
5. **Arrays are passed as `view<[N]T>`** in the index tests because a by-value array argument is moved (follow-up 3).

## Follow-ups (real defects / spec gaps; none is silently weakened - each has a repro and its test is excluded, not loosened)

1. **FU-T455-IDX128: 128-bit index aliasing.**  `a[i]` with `i: u128 = 2^64 + 1` reads element 1 instead of trapping `index out of bounds`
   (interp, native -O0, native -O1: exit 0, prints 20).  SPEC-40 AXS-INT-053/054 lower the index as `Cast(IntToInt, i, usize)` followed by `idx_usize < len`,
   which truncates 128-bit values.  Needs an architect decision (check the 128-bit value against `len` before the cast) and a fix task in `compiler/mir/builder.ax`.
   Repro: `tests/run/numeric/mixed_int_matrix/repro_u128_index_alias.ax` (`// test: helper`).  The matching `index_trap_u128_alias.ax` was generated, failed, and was removed
   from the generator rather than marked xfail (no ADR/open task exists yet); the architect should add it back (or an xfail) with the fix task.  `i64`/`u64` aliasing at `2^32 + k` is correct, `i128 -1` traps.
2. **FU-T455-IDXCODE: `AX_TYPE_INDEX_NOT_INT` (2014) is not defined.**  SPEC-40 AXS-INT-053/060 require it for a non-integer index; `compiler/diag/code.ax`
   has no such code and `a[true]` is reported as `AX_TYPE_MISMATCH` (`a[1.0f32]` hits `AX_TYPE_UNSUPPORTED_IN_BOOTSTRAP`).  Repro: `repro_index_not_int_code.ax`.
3. **Arrays are move-only.**  `fn take(a: [2]u8) -> u8` called twice with the same array is `AX_VERIFY_USE_AFTER_MOVE`; SPEC-51 treats `[N]T` of
   primitives as `Copy`.  This makes `T.from_le_bytes(arr)` consume the array.  Decide whether `[N]T` with a `Copy` element is `Copy`.
4. **Spec ambiguity: unary `~` on a narrow unsigned operand inside a wider tree.**  `let t: i64 = ~b8 + s64` with `b8: u8 = 255`, `s64 = 1000` gives 1000 (`~b8` is computed in u8 = 0
   and then widened) whereas unary `-` and every binary operator promote first (`~b8` in i64 would be -256 and the sum 744).  AXS-INT-052.1 lists `~` as a tree node, which favours
   promote-first; the compiler (`check_unary_in_arith`) does not.  Not pinned by any test.
5. Known gaps from the brief that were avoided and are not hit: native `print_int` of `u64 >= 2^63` (large values are compared in-program), `x.into()` / `x.try_into()` for integers,
   tuple expressions that name variables.
6. The `AX_CONST_*` diagnostics of AXS-INT-005 fire for `const` items (and array lengths), not for literal arithmetic in a `let` initialiser, which traps at run time.  The spec wording ("compile-time constant evaluation") is consistent; tested as is.
