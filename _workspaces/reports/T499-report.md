# T499 report — unary `~` inside a widening integer tree promotes its operand first

## Summary
`~x` of a narrower concrete integer leaf inside a widening arithmetic tree of context type `C` is now evaluated in
`C` (ADR-0044 §2, SPEC-40 AXS-INT-052 rule 4): `let t: i64 = ~b8 + s64` with `b8 = 255u8`, `s64 = 1000` gives `744`
in interp, native and native-O1. A `~x` outside a widening tree keeps `x`'s type (`let r: u8 = ~b8` is `0`;
`let f: i32 = ~x` is still `AX_TYPE_MISMATCH`), and `-b8` in a tree is still `AX_TYPE_NEG_UNSIGNED`.

## Design
- `compiler/types/typeck.ax` `check_unary_in_arith`, `~` branch: after typing the operand, when the operand's concrete
  integer type `L` differs from the tree context `C` and `can_widen_int_to(L, C)` holds, typeck inserts an **implicit
  promotion cast** node between `~` and its operand: a `HIR_EXPR_CAST` whose `cast_ty` is null and whose THIR type is
  `C`. The `~` node is typed `C`. The MIR builder's existing `HIR_EXPR_CAST` lowering turns it into
  `_t = copy _leaf as C` (`MIR_CAST_INT_TO_INT`, zero-extension for unsigned / sign-extension for signed), and the
  `~` then reads `_t` in `C` (homogeneous, INV-INT-003). MIR for `~b8 + s64`:
  `_5 = copy _1 as type#9; _4 = ~move _5; ... _3 = move _4 + copy _2;`.
- Why a typeck-inserted cast and not a builder change: the builder only inserts the operand promotion cast for unary
  `-` (`inner_ty != e_ty`), and `compiler/mir/builder.ax` is locked by T496 and outside T499's paths. The explicit
  cast node keeps the decision in typeck (where the tree context is known), works unchanged for every consumer that
  already understands `HIR_EXPR_CAST` (MIR builder, typeck const evaluator `eval_const_expr_u128`, backend/interp_opt
  const folders, ownership/unsafe walkers, THIR dump), and needs no new MIR construct.
- Robustness of the synthesized node (helper `tc_is_promote_cast`: a cast with a null `cast_ty`):
  - a re-check of the same `~` node strips the cast inserted by the previous check and decides again (no double wrap);
  - `check_expr` on such a cast checks its operand and returns the recorded context type (it never calls
    `hir_type_to_typeid(null)`);
  - `peek_expr_type_nonmut` returns the recorded type, so a later peek of the tree still sees an integer leaf.
  All readers of `cast_ty` outside typeck (`hd_type`, `td_type`, `walk_hir_type_fixup_array_len`) already accept null.
- Literals (`~0 + s64`) keep the old path (IntVar unified with `C`); `-` is unchanged; shifts are unchanged (a shift
  is a leaf of its left operand type).
- Compile-time evaluation: `const K1: i64 = ~255u8 + 1000;` is a tree typed in `i64`; the const evaluator goes
  through the cast node (normalised to `i64`) and yields `744`, equal to the run-time value (test
  `const_and_standalone.ax`).

## Notes / decisions
- Decision (no question left open): the promotion is materialised in typeck as an implicit `HIR_EXPR_CAST`
  (null `cast_ty`) rather than in the MIR builder, because the builder is outside this task's paths and locked by
  T496; the resulting MIR is exactly the shape the task asks for (`Cast(IntToInt, b8, i64)` then `Not` in `i64`).
  If a later task wants the builder to own all unary promotions, it can extend line `uop == UNOP_NEG && ...` in
  `mir_build_expr` (`compiler/mir/builder.ax`) to `UNOP_BITNOT` and drop the typeck cast; the tests here pin the behaviour either way.
- No new diagnostic codes; `bootstrap/axiom0`, `spec/`, `docs/` untouched.
