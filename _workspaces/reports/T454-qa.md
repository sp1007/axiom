### Findings

**F1 (FAIL, soundness): a shipped public std API silently returns wrong values for 128-bit sources.**
`std/core/convert.ax:671-887` (`Dst.try_from<S: IntValue>`) and the `LosslessTo*` helpers: because
`prim_kind_matches_name` (compiler/traits/solver.ax) has no `i128`/`u128` branch, the bound `S: IntValue` with a 128-bit `S`
runs the first impl (the `i8` one) and reads one byte.
Repro (both `run --interp` and native, same output), scratch package with `std/core/num.ax` + `convert.ax`:
`u64.try_from(100000000000000000000u128)` prints `Ok 0` (must be `Err`); the same for any value whose low byte fits
(2^64 u128 -> `Ok 0`). `u64.try_from(5u128)` and `u64.try_from(u128.MAX)` happen to be right, so the bug is easy to
miss. The report acknowledges it (Design decision 5) and ships it with `convert128.test` as xfail. The task acceptance
says "`From`/`TryFrom` ... for all 12 integer widths"; the 128-bit source widths do not work, and the failure mode is a
wrong value, not a compile error or panic. An xfail only documents it; the public API is still reachable and nothing guards
it. Required: before T454 is accepted either (a) the solver fix (about 10 lines, verified by the engineer in a scratch
compiler: add `TY_I128`/`TY_U128` branches to `prim_kind_matches_name`) lands first as its own task (owner semantics, with
`convert128.test`, `int128_dispatch_xfail.ax` and my `qa_try_from_128_source.test` turning XPASS and losing their `xfail:`
lines), with T454 depending on it; or (b) `try_from`/`from` get a guard that makes a 128-bit source impossible to use silently
(for example a `size_of<S>() == 16` check that panics, or a compile error), with the guard covered by a test. Option (a) is
the proper fix.

**F2 (note, not a FAIL by itself): documented spec deviations.** `From`/`TryFrom` are inherent generic methods rather than
trait impls; integer `into()`/`try_into()` are absent; `TryFromIntError` has no Debug/Display. They are forced by the six
compiler bugs, each with a minimal xfail repro (`static_dispatch_xfail.ax`, `trait_dispatch_xfail.ax`,
`tuple_names_xfail.ax`, `empty_copy_xfail.ax`, `into_xfail.test`, `int128_dispatch_xfail.ax`). `trait_dispatch_xfail.ax`
describes a silent miscompile (prints `7 7` instead of `7 5007`) in user code, not in the shipped std, so it is a compiler
issue for the architect. Follow-ups below.

No other finding: no warnings, no layer violations, no flakiness seen (the gate and my reruns agree), spec rule IDs and
generated banners are in place.
