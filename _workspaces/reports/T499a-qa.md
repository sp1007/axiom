### Regression check (separate, not a T499a finding)
Question: do `ui/slice/iter_move.ax` and `ui/slice/qa_slice_iter_move.ax` fail on HEAD without T499a, and which commit broke them?
- Method: temporary git worktree `build-base-T499a` (removed afterwards), fresh stage-0 + `build_axiomc.py --stage 1` (axiomc1), `axtest --no-cache` on the two ids, at three commits:
  - 37a299d8 (parent of T498): `TOTAL 2 PASS 2`.
  - 9f31ed56 (T498 itself): both FAIL, `missing diagnostics: ERROR AX_CAP_OUTLIVES_OWNER at line 11` / `at line 10`.
  - ce6d6714 (HEAD, no T499a): both FAIL, identical message.
- Culprit: **T498, commit 9f31ed56** (`compiler/mir/builder.ax`: `mb_operand_from_place` now treats `[N]T` of a Copy element as Copy, emitting COPY instead of MOVE; ADR-0044 section 3 / AXS-OWN-003). The tests do `let arr: [3]u8 = [..]; let it = Iter { s: view(arr), .. }; consume(arr)` and expect `AX_CAP_OUTLIVES_OWNER` because `consume(arr)` moved the array out from under the view.
- Assessment: **stale expectation, not a real regression.** With `[3]u8` Copy, `consume(arr)` copies the array and `arr` (the owner the view points into) stays alive, so there is no dangling view and no diagnostic is correct. The cap check is driven by the MIR MOVE, which no longer exists for this case. T498's gate missed it because the `ui/slice` group was neither in its affected set nor its smoke pick.
- Not in `_workspaces/baseline-failures.txt` (grep `iter_move`: no hit). Suggested architect action: a small test-fix task (owner of `tests/ui/slice`) that changes both tests to move a non-Copy array (e.g. an array of a struct without Copy / a droppable element) so the owner really is moved while the view lives, plus adding the two ids to the baseline until it lands. T499a is unaffected.
