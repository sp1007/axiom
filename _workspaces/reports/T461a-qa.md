### 3. Root cause, verified independently

- HEAD reproduction: compiler from the cache `_workspaces/artifacts/compiler-cache/axiomc2_O1_645ebaec5b06a5c8.exe`,
  whose `inputs.json` has the HEAD hashes of coff.ax, writer.ax and linker.ax (36 cached builds match HEAD, so
  the bug is in all of them). `run_large.py ... 66` passes; `run_large.py ... 330` fails:
  `native -O0 rc=3221225477 (0xC0000005)`, 0 of 33000 lines, exactly the T461-qa N4 symptom.
- Old code: `coff_buf_put_u16(..., rlen as u16)` in writer.ax. Truncation is real, and the linker had the only
  reader (`linker_load_coff_object_ex` and `_v2`; `grep number_of_relocations compiler` shows no other reader
  of the field, and `pe.ax` only writes the linker's own PE section headers with 0).
- Encoding check against the PE/COFF spec and `spec/SPEC-91-windows-arm64.md:117`:
  `IMAGE_SCN_LNK_NRELOC_OVFL = 0x01000000` correct; header `NumberOfRelocations = 0xFFFF` correct; the first
  10-byte entry's `VirtualAddress` holds the real count INCLUDING the placeholder entry itself (PE spec wording),
  which is what `coff_reloc_entries` (+1) and the reader (`total - 1`, start `ptr + 10`) implement. The switch at
  `rlen >= 0xFFFF` matches SPEC-91 (">= 65535 relocations") and LLVM. Reader rejects count 0 and tables
  past EOF as `AX_LINK_BAD_OBJECT` (existing code, registered). Byte offsets are summed in u64 and refused above 4 GiB.
- GNU acceptance (my test `qa_reloc_boundary`, section 6): `objdump -r` lists exactly the header's relocation
  count, and `ld -r` re-reads and re-writes objects with 0xFFFE, 0xFFFF and 0x10000 relocations without error.
  The engineer's `--obj` leg additionally checks objdump on the 330 and 500 chunk objects.

### 4. Writer refusal path (judgement)

`coff_write_to_buf` returns false for `sections_len > 65279` (PE/COFF limit 0xFEFF, correct) and for a total file
offset above 0xFFFFFFFF. All callers in `driver/pipeline.ax` map false to `AX_EXIT_DIAG` without pushing a
diagnostic, so the user gets a failed build with no message. That departs from diagnostics-as-data and from scope
item 2 ("emit a diagnostic instead of a broken image"), but: no broken image is ever produced (the intent of the
rule holds), the false path pre-existed as the writer's failure channel, and both limits are unreachable
in practice (a section count above 65,279 is not generated by the compiler; a 4 GiB object is ~800x the
330-chunk program and cannot be tested here). Judged a NOTE, not a FAIL; follow-up F2 below.
