### Findings

**F1 (FAIL) — constant block/aggregate initialisers still report `AX_CONST_OVERFLOW` for an out-of-range shift.**
- Scope bullet 2 of the task ("compiler/interp const path ... emits it instead of AX_CONST_OVERFLOW for shifts, all
  widths") and SPEC-60 line 110 / 215 (the comptime evaluator emits `AX_CONST_SHIFT_RANGE`).
- Repro (`build-snap-T483/build/axiomc2.exe check f.ax`):
  `const BLK: u32 = { 1u32 << 32u32 };`, `const ARR: [2]u8 = [1u8 << 8u8, 0u8];`,
  `const TUP: (u32, u32) = (1u32 >> 40u32, 0u32);`, `const NEG: [1]i64 = [1i64 << -1i32];`
  -> `error[AX_CONST_OVERFLOW]` on each (expected `AX_CONST_SHIFT_RANGE`). In-range forms such as `[1u8 << 3u8, 0u8]` evaluate
  fine, and the scalar form `const A: u8 = 1u8 << 8u8;` correctly gives 168 (typeck evaluator).
- Cause (read from the code): the MIR builder guards every shift with
  `assert(count >= 0 / count < BITS, "shift amount out of range")` (`compiler/mir/builder.ax:5803, 5896`; visible in
  `axiomc2 inspect --emit=mir`). In the interpreter a failing `MIR_TERM_ASSERT` calls `interp_panic_sv(msg)`
  (`compiler/interp/interp.ax:4078, 4588, 5683`), which in comptime mode maps to `AX_CONST_DIV_ZERO` or else
  `AX_CONST_OVERFLOW` (`compiler/interp/value.ax:866-876`). The engineer's mapping sits only in `interp_panic(..,
  INTERP_MSG_PANIC_SHIFT_RANGE)` (`value.ax:884-890`, reached only by the BinaryOp overflow route), which a guarded shift
  never reaches. Fix: classify the assert message "shift amount out of range" in `interp_panic_sv`'s comptime branch (as is
  done for the division-by-zero message), then regenerate the interp_opt test expectations if needed.
- Regression test (added by QA, currently FAIL): `tests/ui/const_shift_range/qa_const_block_and_aggregate_shift.ax`.
  Note the T483 selfhost case `qa_shift_ovf_err.ax` (`const SHIFT_OVF: i32 = 1 << 32;`) passes only because it is a scalar
  expression; it does not cover this route.
