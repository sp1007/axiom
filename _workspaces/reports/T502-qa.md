### Findings

**F1 (FAIL). False positive: padding bytes of an aggregate are reported as an uninitialized read.**
- Where: `compiler/interp/interp.ax` `exec_assign_use` (`interp_check_init_read(..., src, d_size)` with `d_size` = whole struct size) and `eval_operand_u64`/`u128` (`interp_check_init_read` over the whole loaded type); `compiler/interp/value.ax` `interp_check_init_read`.
- Expected: SPEC-50 AXS-UNS-014 (init rule, line 196: "every non-padding byte of `T`") and the UB-04 row ("other than padding bytes during aggregate copy") make a typed load or copy of a struct with uninitialised padding defined behaviour. The T502 acceptance text itself says false positives are not acceptable.
- Actual: both `let s: P = *src;` and `*dst = *src;` report `AX_UNSAFE_INTERP_UB: read of uninitialized memory` for `@repr(C) struct P { a: u8, b: u64 }` in a heap block where only offsets 0 and 8 were written (bytes 1..7 are padding).
- Repro (snapshot): `build-snap-T502/build/axiomc2.exe run --interp --std-root std tests/run/unsafe/oracle_ub/qa_ok_padding_load.ax` and `.../qa_ok_padding_store.ax`; both exit 125 where 0 and stdout `7 9` are expected. `qa_ok_padding_ptr_copy.ax` (byte copy) passes.
- Fix direction: when the loaded/copied type is an aggregate, check only the non-padding byte ranges (or skip the check for aggregates with padding; a false negative is acceptable, a false positive is not). The two new tests then pass without change; they are also valid in native, where the padded load is defined.

### Follow-ups (not findings)
- The detector under-reports partially written aggregates (field stores mark the whole pointee range). Acceptable per the task, worth a note in SPEC-50 conformance work (T505).
- `std` and compiler code were only exercised through the affected set and smoke; the periodic full run is the next place a further latent uninitialised read (not padding) could surface.
