# T499a — `(x, y)` with variables

## Goal
Only tuple expressions of literals work (`_workspaces/reports/T454-report.md` follow-up 4, `_workspaces/reports/T499-qa.md` F1):
- `let total = 4i64; let t = (total, true);` reports `AX_NAME_UNRESOLVED` at `total` (reproduced with `build/axiomc2.exe`).
- `fn f(s64: i64) -> i64 { let t: (i64, i32) = (s64, 3i32); t.0 }` makes `axiomc2` die with a stack overflow (exit 0xC00000FD,
  no diagnostic), at `check` and `inspect --emit=thir`.
`std/core/num.ax` works around it with `pair_T` helpers. A compiler crash on valid input and a false name error are both blockers
for ordinary code.

## Scope
- Find why names inside a tuple expression do not resolve (the resolver's expression walk, or the parser producing a different node
  for `(ident, ...)`, e.g. a pattern/parenthesised path) and why the parameter form recurses without end (typeck/THIR of a tuple with an
  expected tuple type); fix both in the owning modules. Any remaining recursion on malformed input must end in a diagnostic, not a crash.
- Remove the `xfail` line of `tests/std/num/tuple_names_xfail.ax` (it must pass in interp and native).
- Tests `tests/run/tuple_expr_names/*.ax` (interp/native/native-O1, exact `// stdout:`): locals, parameters, fields, calls, nested
  tuples, `(x,)` one-tuple, mixed literal/variable, with and without an annotated type, as a return value, as a call argument,
  in a `match` scrutinee, destructured by `let (a, b) = (x, y)`. `tests/ui/tuple_expr_names/*.ax`: an unknown name inside a tuple still
  reports `AX_NAME_UNRESOLVED` with the exact span; a type mismatch of one element reports `AX_TYPE_MISMATCH` (no crash).
- Keep the stage-2/stage-3 fixed point; selfhost bundles are regenerated by `taskctl snapshot`/`accept` (do not edit or list them).
