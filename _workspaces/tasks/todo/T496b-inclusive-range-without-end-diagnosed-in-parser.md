# T496b — `..=` without end is a parse error; `str` inclusive sub-ranges tested

## Goal
ADR-0045 / SPEC-02 AXS-GRM-070: `a..=` (no end bound) is a syntax error. T496a reports it from `compiler/hir/lower.ax`
(`emit_inclusive_range_without_end`, outside its paths at the time), so `check --emit=ast`/parse-only tools, the formatter and
the LSP accept it (`_workspaces/reports/T496a-report.md`, `T496a-qa.md` follow-ups). `str[a..=b]` shares the code path
(`mb_range_base_is_checked`) but has no test.

## Scope
- `compiler/syntax/parse.ax` (`parse_binary_suffix` or the range-operand parser): after `..=`, an end operand is required;
  otherwise report `AX_PARSE_EXPECTED_EXPR` with the same message and span as today ("inclusive range needs an end bound
  after ..="), in every expression context (index brackets, `for` ranges, `let r = a..=`).
- Remove the lowering-side check and its message constant from `compiler/hir/lower.ax` once the parser reports it (keep one
  source of the diagnostic).
- Tests: keep `tests/ui/slice_inclusive/inclusive_without_end.ax` passing (same code/line:col); add parse-level cases under
  `tests/parse/range_inclusive/` (format used by that group) for the non-index contexts; `tests/run/slice_inclusive_str/`
  (three modes, exact `stdout:`) for `s[a..=b]`, `s[..=b]` on `str` with ASCII and multi-byte UTF-8 text ("Xin chào thế
  giới"), plus traps `b == len` and a non-char-boundary end if `str` slicing checks boundaries (assert the current behaviour
  from SPEC-03; if `str` sub-ranges are not supported, report it and test the diagnostic instead).
- Keep the stage-2/stage-3 fixed point; selfhost bundles are regenerated by `taskctl snapshot`/`accept` (do not edit or list them).
