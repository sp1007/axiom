# T498b — Copy reads through an index do not move the array

## Goal
`let a = hs[0].f; let b = hs[1].f;` with `hs: [2]H`, `H` not Copy and `f: fn(i32) -> i32` (or any Copy field type) reports
`AX_MOVE_USE_AFTER_MOVE` on the second read. The MIR is correct (`_5 = copy ((_4)[_6]).1`); the own checker is wrong
(FU-T498-FNPTR-INDEX in `_workspaces/reports/T498-report.md` follow-up 1; `_workspaces/reports/T422b-qa.md` notes).

Root cause (architect, from the report): `own_bits_resolve` in `compiler/own/init.ax` skips `MIR_PROJ_INDEX` and keeps resolving the
following `FIELD` projection against the array node, so `hs[i].1` is treated as `hs.1`/`hs`; `own_bits_visit_operand` handles a
`COPY` operand like a `MOVE`, so the non-Copy array node is marked moved.

## Scope
- `own_bits_resolve`: stop at the first `MIR_PROJ_INDEX` (element-level tracking is post-v1, REQ-OWN-049) and return the array node
  with a flag that the place went through an index.
- `own_bits_visit_operand`: a `COPY` operand reads (checks initialised/not moved) and never moves. A `MOVE` out of an indexed
  non-Copy element (`let x = hs[0];`, `let g = hs[0].name;` with a non-Copy field) is still rejected with the existing diagnostic.
- Tests `tests/run/own_index_copy/*.ax` (interp/native/native-O1, exact `// stdout:`): two and more reads of a Copy field
  (`i32`, `fn` pointer, `[2]u8`, `view<...>`) through `hs[i]`, nested `hs[i].inner.f`, `hs[i][j]` on an array of arrays, in a loop,
  then a later move of the whole `hs`. `tests/ui/own_index_copy/*.ax`: moving out of an indexed non-Copy element and moving a non-Copy
  field through an index still report `AX_MOVE_USE_AFTER_MOVE` (or the existing move-out-of-index code) with the exact span.
- Keep the stage-2/stage-3 fixed point; selfhost bundles are regenerated by `taskctl snapshot`/`accept` (do not edit or list them).
